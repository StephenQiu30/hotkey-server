# 可观测性、SLO 与事件响应

## 适用环境与前置检查

适用于开发基线、验收、灰度和生产事件响应。执行前确认代码/配置版本、目标环境、值班责任人、时间窗、候选 SLO 口径、关联 ID、只读观测入口、相关 Runbook 与最近可用恢复点；指标或日志尚未验收时必须标记“不可观测”，不得据此宣称健康。

## 候选 SLO

| 场景 | 候选目标 | 校准要求 |
|---|---:|---|
| 核心 API 月可用性 | 99.5% | 明确统计端点、维护窗口和错误预算 |
| 普通 API P95 | 300 ms | 固定并发、数据量、硬件、缓存冷热 |
| 热点列表 P95 | 500 ms | 固定筛选、排序和分页条件 |
| 全文检索 P95 | 800 ms | 固定语料量、查询集和权限过滤 |
| 新通知页面可见 | 2 秒 | 从已提交事实到前端可见的端到端时延 |
| 手动扫描入队 | 1 秒 | 不包含上游采集时间 |
| 运行状态更新 P95 | 5 秒 | 从持久任务状态提交到 API/页面可见，固定轮询/WebSocket 条件 |
| Obsidian 发布 | 审批后 30 秒 | 固定 Vault 大小和磁盘条件 |
| PostgreSQL/Vault 检索投影可见 | 10 秒 | 从可搜索事实提交到权限内检索可见，不包含人工审批时间 |
| RPO / RTO | 15 分钟 / 2 小时 | 必须由隔离恢复演练证明 |

在容量基线和验收环境未固定前，这些数字是候选指标，不是无条件生产承诺。

## 信号

- API：请求量、业务错误码、HTTP 状态、延迟、并发和鉴权失败；
- Worker：任务排队、领取、成功、失败、重试、超时、死信/终止与运行时长；
- 来源：每来源请求、条目、401/403/429、解析失败、延迟和预算；
- Codex：任务量、并发、超时、输出/Schema/Evidence 失败和降级积压；
- 数据：数据库连接、慢查询、锁、存储、MinIO 失败和证据哈希错误；
- 业务：Monitor 扫描、部分成功、事件生成、通知 Read Receipt、Delivery Claim 抢占/`unknown` Attempt、报告、Vault 冲突和检索投影延迟。

日志和 Trace 使用固定字段名白名单，至少覆盖 `request_id`、`job_id`、`attempt_id`、`collection_run_id`、`monitor_id`、`document_id`、`event_id`、`agent_run_id`、`notification_id`、`report_id`、`knowledge_id`、`retention_run_id`、`recovery_run_id` 和 `workspace_id`。这些安全 ID 可作为有界普通字段用于串联，但不得成为 Metric 标签；只有批准的安全 ID 与稳定错误码进入日志检索维度。邮件、完整 URL/查询、正文、Prompt、Payload、任意用户输入和动态字段名不得进入标签或索引维度，超长值按批准策略拒绝、截断或稳定摘要。任何字段均不得记录密码、Cookie、Bearer Token、AI/来源凭据、完整 DSN 或未经授权的原始正文。

## P0 告警目录

阈值在基线前均为候选；激活前必须补齐持续时间、Owner、Runbook 和测试证据。

| 告警 ID | 信号 | 候选触发语义 | Runbook | 激活状态 |
|---|---|---|---|---|
| `ALERT-DB-UNAVAILABLE` | PostgreSQL readiness/连接错误 | 连续不可用或写入失败超过批准窗口 | [部署回滚](001-部署升级与回滚.md) / [恢复](002-备份恢复与重建.md) | candidate |
| `ALERT-RIVER-NO-WORKER` | 可执行 Job、最老 queue age、Worker heartbeat | 有可执行任务但无健康 Worker，或 queue age 超阈值 | [部署回滚](001-部署升级与回滚.md) | candidate |
| `ALERT-SOURCE-AUTH` | 每连接连续 401/403 | 连续认证/权利失败且非人工停用 | [来源处置](003-来源授权预算与故障处置.md) | candidate |
| `ALERT-MINIO-WRITE` | Evidence 对象写入/Hash 失败 | 连续失败或证据链中断 | [恢复](002-备份恢复与重建.md) | candidate |
| `ALERT-CODEX-FAILURE` | Agent 连续失败率、待补算积压 | 超时/认证/Schema 失败持续超阈值 | 本手册降级矩阵；后续激活时绑定 003 操作步骤 | candidate |
| `ALERT-VAULT-CONFLICT` | 冲突数、最老冲突年龄 | 持续增长或超过处理时限 | [恢复](002-备份恢复与重建.md) | candidate |
| `ALERT-BACKUP-FAILED` | 备份结果、最近成功年龄 | 失败或恢复点超过候选 RPO | [恢复](002-备份恢复与重建.md) | candidate |
| `ALERT-SEARCH-BACKLOG` | 投影 queue age、撤权同步延迟 | 积压或撤权延迟超过批准阈值 | [保留与撤权](005-保留删除与撤权处置.md) | candidate |
| `ALERT-DELIVERY-UNKNOWN` | 外部 Delivery `unknown` 数量、最老年龄、Provider 回执积压 | Provider 可能已接收但本地无法确认，或超过批准对账窗口 | 本手册降级矩阵；按 004 的 Provider Capability/回执契约处置 | candidate |

## 降级矩阵

| 故障 | 允许继续 | 必须停止/切换 |
|---|---|---|
| PostgreSQL | 无新的业务写；只保留不依赖数据库的诊断 | readiness 失败，停止接流量和任务领取 |
| Redis | 已有数据库事实按安全边界读取 | 验证码、短期票据、缓存/限流相关入口明确失败 |
| MinIO | 已提交事实只读查询 | 停止要求新 Evidence 的派生和审批 |
| Worker | API 只读/提交受策略控制 | 保留 River Job，恢复后幂等重领 |
| Codex | 采集、Evidence、精确去重、确定性 Heat、人工治理 | 新智能决定进入待分析/待补算，不做无标记 Provider 回退 |
| 单来源 | 其他来源和已提交事实 | 停用故障连接，派生 `partial_success` 视图 |
| WebSocket/邮件 | PostgreSQL 通知列表、Read Receipt 与通知事实 | 关闭故障通道，用 REST 补拉；外部 `unknown` 暂停该派发键自动重发并转回执对账/批准处置，不回滚通知事实 |
| Vault | 报告/事实继续，保存待发布状态 | 暂停 Writer，不覆盖人工区域 |
| 检索投影 | 基础详情/列表查询 | 退回数据库基础查询，修复后重建可丢弃投影 |

### 001/S03 可复测故障矩阵

下表是执行状态而非验收结论。`verified` 表示已有可定位自动化证据，`partial` 表示只证明了局部边界，`pending` 表示目标实现尚未进入代码。只有后续 Acceptance 可以将本矩阵转为 `AC-001-007` 通过证据。

| Fixture ID | 故障注入 | 事实继续 | 必须停止 | 重试/恢复 | 人工介入 | 自动化证据 | 状态 |
|---|---|---|---|---|---|---|---|
| `DEG-001-CODEX-UNAVAILABLE` | Codex 未安装、未认证、超时或暂时不可达 | 采集、Evidence、精确去重、确定性 Heat 与历史查询继续 | 不产生新智能最终决定，显式进入待分析/待补算 | 恢复后按稳定复用键补算，不无标记回退旧 Provider | 允许授权人工治理，不伪造 AI 结果 | `PENDING-003-S01/S02` | `pending` |
| `DEG-001-CODEX-UNAUTHORIZED-SUGGESTION` | Codex 返回可解析但越权的建议，包括伪造 Evidence/权限/最终状态 | 既有业务事实不变 | 在 Application/Domain 校验和任何业务写入前拒绝 | 修复必须形成新 Attempt，错误结果不得进入可复用结果 | 只有授权主体可提交独立治理命令 | `PENDING-003-S01/S02` | `pending` |
| `DEG-001-SINGLE-SOURCE` | 三来源中一个返回可重试错误 | 其他来源从采集到摘要的已提交事实继续 | 失败来源不产生伪造采集事实 | River Job 保持 `available` 供后续重试 | 连续失败后停用该连接并保留其他来源 | `TestRSSHNPipelineRecovery` | `verified` |
| `DEG-001-REDIS-TRANSIENT` | Redis 连接短暂不可用 | PostgreSQL 中已提交事实不受影响 | 验证码与短期票据入口返回稳定 `unavailable`，不伪造成功 | 客户端或调用方稍后重试；尚需真实断开/恢复往返测试 | 长时不可用时由运维恢复 Redis，不从 Redis 恢复业务事实 | `TestVerificationStoreReportsUnavailableForClosedRedisClientOnEveryOperation` | `partial` |
| `DEG-001-MINIO-WRITE` | 已授权原始 Evidence 对象写入失败 | 故障前已提交事实保留 | 采集 Run 标记可重试失败，不在 Evidence 对象之前提交条目事实 | 对象存储恢复后以原幂等身份重试 | 连续失败触发对象存储处置和 Evidence 对账 | `TestCollectionServiceFailsRetryablyWhenAuthorizedRawArchiveStorageFails` | `verified` |
| `DEG-001-VAULT-UNWRITABLE` | Vault 根目录不可写 | PostgreSQL 文档与已有 Artifact 事实保留 | 投影标记 `vault_publish_failed`，不误标内容冲突/隔离，不覆盖人工区域 | 修复目录后复用同一 Artifact 身份完成投影 | 不可自动清空 Vault；冲突需人工审阅 | `TestDerivedArtifactSagaMarksRealVaultFailureWithoutQuarantine` | `verified` |

当 Codex 两项、Redis 恢复往返与真实对象存储故障注入全部闭合后，再在 001 Acceptance 中引用原始命令、Git revision 和事实计数；在此之前 `CHK-001-G4-001` 必须保持未勾选。

## 事件分级

- P0：业务事实损坏、跨 Workspace 泄漏、核心数据库不可用、无法恢复的证据丢失；
- P1：大面积 API/任务不可用、通知/报告持续失败、来源认证整体失效；
- P2：单来源降级、积压增长、性能持续超 SLO、Vault 冲突增加；
- P3：局部错误、容量预警或不影响用户的投影延迟。

## 响应流程

1. 确认影响、时间窗、用户/Workspace、数据完整性和是否仍在扩大；
2. 优先停止造成破坏的写入或任务领取，保留证据和审计；
3. 选择降级：暂停 AI、暂停单来源、关闭通知通道或退回数据库基础查询；
4. 按关联 ID 定位 API、Worker、来源、数据与前端链路；
5. 恢复后执行对账、补偿或回填，验证业务事实不重复；外部交付只按 Provider 幂等/回执证据确认，无法确认时保持 `unknown`，不以再次发送证明恢复；
6. 记录根因、检测缺口、时间线、影响、恢复和预防措施。

## 成功、停止与回滚边界

成功要求影响停止扩大、权限与事实完整性通过对账、关键队列和交付恢复、告警回归正常且没有未解释差异；外部 `unknown` 必须有 Provider 回执、经批准人工结论或仍处于明确隔离状态，不能静默标成失败/成功。发现跨 Workspace 泄漏、事实/证据损坏、补偿重复副作用、日志泄密或无法确定恢复点时立即停止自动补偿与扩流，隔离相关写入并升级 P0/P1。降级和应用回滚只能切换代码、来源、Codex、通知或查询路径，不删除 PostgreSQL 事实、River 历史、MinIO 对象、Vault 人工区域或持久卷；数据损坏转入备份恢复手册。

## 审计证据

- 事件编号、版本、时间线、影响范围、分级与责任人；
- 触发告警、关联 ID 查询、脱敏日志/Trace 和关键指标窗口；
- 停止、降级、回滚、补偿、对账及用户沟通决定；
- 恢复判据、残余风险、复发预防、Owner 和完成期限。

## 容量与演练

- 每个发布里程碑记录活跃 Monitor、每日候选/正文、任务并发、证据存储和成本；
- 压测同时覆盖正常、部分来源失败、Codex 不可用和存储退化；
- 告警必须包含 Runbook、阈值持续时间、责任人和静默规则；
- 每季度至少演练一次 Worker 中断、单来源限流、Codex 失败和备份恢复。

### 001 容量基线命令

当前可执行基线先固化 `contents` 的 `(published_at DESC, id DESC) LIMIT 50` Keyset 查询；它验证采样、并发、预热、nearest-rank P50/P95/P99 和不可覆盖 JSON 原始样本格式，不代表普通 API、热点列表或全文检索已达标。后续 002/004 必须用同格式增加对应的端到端 workload。

```bash
cd backend
export HOTKEY_TEST_DSN='<isolated-postgresql-dsn>'
export HOTKEY_TEST_REDIS_URL='<isolated-redis-url>'
export HOTKEY_CAPACITY_ROWS='100000'
make capacity-fixture

export HOTKEY_CAPACITY_OUTPUT='<new-evidence-directory>/contents-keyset.json'
export HOTKEY_CAPACITY_ENVIRONMENT='isolated-capacity-runner-identifier'
export HOTKEY_CAPACITY_HARDWARE='cpu/memory/disk/network exact description'
export HOTKEY_CAPACITY_GIT_REVISION='<40-character-lowercase-commit-sha>'
export HOTKEY_CAPACITY_CACHE_STATE='warm'
export HOTKEY_CAPACITY_CONCURRENCY='20'
export HOTKEY_CAPACITY_WARMUPS='20'
export HOTKEY_CAPACITY_SAMPLES='1000'
make capacity-baseline
```

每个冷/热缓存、并发和数据规模组合必须使用新输出文件；工具拒绝覆盖既有证据。报告保留所有成功样本微秒值、错误数、排除项、Go 运行时和操作员提供的硬件描述，且不写入 DSN。未实际运行并审批前，本手册的所有时延仍是候选值。

### 002 采集容量基线命令

`TASK-002-S04-T02` 使用独立的可缩放夹具和端到端测量器，不复用 001 的单查询结论。默认夹具建立 50 个启用 Monitor、100 个启用 RSS 连接、50,000 条 `collection_run_items` 候选事实和 20 个 `collect_source` River Job；夹具只能在隔离数据库执行，改变规模时应使用新数据库。测量器会重置自身命名空间内的 20 个 Job，使用 `FOR UPDATE SKIP LOCKED` 并发领取，提交带 Target、Item 和 TargetItem 的采集事务，并通过内存 HTTP Server 执行真实 Gin、Bearer 鉴权、Application、PostgreSQL Repository、DTO 和 JSON 链路。它不触发外部来源、不会读取或输出凭据，也不会把 DSN 写入报告。

```bash
cd backend
export HOTKEY_TEST_DSN='<fresh-isolated-postgresql-dsn>'
export HOTKEY_TEST_REDIS_URL='<isolated-redis-url>'
export HOTKEY_COLLECTION_CAPACITY_MONITORS='50'
export HOTKEY_COLLECTION_CAPACITY_SOURCES='100'
export HOTKEY_COLLECTION_CAPACITY_CANDIDATES='50000'
export HOTKEY_COLLECTION_CAPACITY_JOBS='20'
make collection-capacity-fixture

export HOTKEY_COLLECTION_CAPACITY_OUTPUT='<new-evidence-directory>/collection-capacity.json'
export HOTKEY_COLLECTION_CAPACITY_ENVIRONMENT='isolated-capacity-runner-identifier'
export HOTKEY_COLLECTION_CAPACITY_HARDWARE='cpu/memory/disk/network exact description'
export HOTKEY_COLLECTION_CAPACITY_GIT_REVISION='<40-character-lowercase-commit-sha>'
export HOTKEY_COLLECTION_CAPACITY_CACHE_STATE='warm'
export HOTKEY_COLLECTION_CAPACITY_WRITE_ROWS='500'
export HOTKEY_COLLECTION_CAPACITY_WRITE_SAMPLES='20'
export HOTKEY_COLLECTION_CAPACITY_API_SAMPLES='200'
export HOTKEY_COLLECTION_CAPACITY_API_CONCURRENCY='20'
make collection-capacity-baseline
```

报告版本固定为 `hotkey-collection-capacity-v1`，使用 nearest-rank ceiling 记录全部成功样本，并分别保留 queue wait、collection persistence commit duration、write throughput 和 `/api/v1/collection-runs?limit=50` API latency 的 P50/P95/P99 与错误数。每次执行必须写入新文件，工具以 `O_EXCL` 拒绝覆盖旧证据。报告明确排除外部 Connector 网络时延、Provider 限流、公网 TLS 和生产身份查询，因此它只证明本地采集控制面与持久化候选容量；真实来源授权冒烟、冷缓存和生产同构硬件结果仍须独立执行并审批，未审批前不得把本节样本升级为 SLO。
