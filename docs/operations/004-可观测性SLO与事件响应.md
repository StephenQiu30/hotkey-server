# 可观测性、SLO 与事件响应

## 适用环境与前置检查

适用于开发基线、验收、灰度和生产事件响应。执行前确认代码/配置版本、目标环境、值班责任人、时间窗、候选 SLO 口径、关联 ID、只读观测入口、相关 Runbook 与最近可用恢复点；指标或日志尚未验收时必须标记“不可观测”，不得据此宣称健康。

隔离告警演练参数必须包含完整 Git revision、以 `_test` 结尾的可丢弃 PostgreSQL 数据库、Redis DB `1`–`15`、生产出口禁用声明、操作者、复核人和证据目录。使用本机已安装的 Go 环境连接已运行的隔离测试依赖，不启动或重启正式 Compose 项目：

```bash
cd backend
HOTKEY_TEST_DSN='<isolated-postgresql-dsn-ending-in-_test>' \
HOTKEY_TEST_REDIS_URL='<isolated-redis-url-using-db-1-through-15>' \
make observability-alert-acceptance
```

预期输出为全部固定告警触发、净化关联、恢复清除测试通过且退出码为 `0`。测试环境身份不合法、告警缺失、恢复后未清除、出现高基数或敏感字段时立即停止；丢弃本次测试目标而不是修改正式事实，修复后创建新的隔离目标复演，并记录 revision、测试数据库身份摘要、测试名、稳定失败码、操作者和复核人。

## 候选 SLO

| 场景 | 候选目标 | 校准要求 |
|---|---:|---|
| 核心 API 月可用性 | 99.5% | 明确统计端点、维护窗口和错误预算 |
| 普通 API P95 | 300 ms | 固定并发、数据量、硬件、缓存冷热 |
| 热点列表 P95 | 500 ms | 固定筛选、排序和分页条件 |
| 全文检索 P95 | 800 ms | 固定语料量、查询集和权限过滤 |
| 新通知页面可见 | 2 秒 | 从已提交事实到前端可见的端到端时延 |
| 手动扫描入队 | 1 秒 | 不包含上游采集时间 |
| 运行状态更新 P95 | 5 秒 | 从持久任务状态提交到 API/页面可见，固定轮询/WebSocket 条件 |
| Obsidian 发布 | 审批后 30 秒 | 固定 Vault 大小和磁盘条件 |
| PostgreSQL/Vault 检索投影可见 | 10 秒 | 从可搜索事实提交到权限内检索可见，不包含人工审批时间 |
| RPO / RTO | 15 分钟 / 2 小时 | 必须由隔离恢复演练证明 |

在容量基线和验收环境未固定前，这些数字是候选指标，不是无条件生产承诺。

## 信号

- API：请求量、业务错误码、HTTP 状态、延迟、并发和鉴权失败；
- Worker：任务排队、领取、成功、失败、重试、超时、死信/终止与运行时长；
- 来源：每来源请求、条目、401/403/429、解析失败、延迟和预算；
- Codex：任务量、并发、超时、输出/Schema/Evidence 失败和降级积压；
- 数据：数据库连接、慢查询、锁、存储、MinIO 失败和证据哈希错误；
- 业务：Monitor 扫描、部分成功、事件生成、通知 Read Receipt、Delivery Claim 抢占/`unknown` Attempt、报告、Vault 冲突和检索投影延迟。

日志和 Trace 使用固定字段名白名单，至少覆盖 `request_id`、`job_id`、`attempt_id`、`collection_run_id`、`monitor_id`、`document_id`、`event_id`、`agent_run_id`、`notification_id`、`report_id`、`knowledge_id`、`retention_run_id`、`recovery_run_id` 和 `workspace_id`。这些安全 ID 可作为有界普通字段用于串联，但不得成为 Metric 标签；只有批准的安全 ID 与稳定错误码进入日志检索维度。邮件、完整 URL/查询、正文、Prompt、Payload、任意用户输入和动态字段名不得进入标签或索引维度，超长值按批准策略拒绝、截断或稳定摘要。任何字段均不得记录密码、Cookie、Bearer Token、AI/来源凭据、完整 DSN 或未经授权的原始正文。

## 降级矩阵

| 故障 | 允许继续 | 必须停止/切换 |
|---|---|---|
| PostgreSQL | 无新的业务写；只保留不依赖数据库的诊断 | readiness 失败，停止接流量和任务领取 |
| Redis | 已有数据库事实按安全边界读取 | 验证码、短期票据、缓存/限流相关入口明确失败 |
| MinIO | 已提交事实只读查询 | 停止要求新 Evidence 的派生和审批 |
| Worker | API 只读/提交受策略控制 | 保留 River Job，恢复后幂等重领 |
| Codex | 采集、Evidence、精确去重、确定性 Heat、人工治理 | 新智能决定进入待分析/待补算，不做无标记 Provider 回退 |
| 单来源 | 其他来源和已提交事实 | 停用故障连接，派生 `partial_success` 视图 |
| WebSocket/邮件 | PostgreSQL 通知列表、Read Receipt 与通知事实 | 关闭故障通道，用 REST 补拉；外部 `unknown` 暂停该派发键自动重发并转回执对账/批准处置，不回滚通知事实 |
| Vault | 报告/事实继续，保存待发布状态 | 暂停 Writer，不覆盖人工区域 |
| 检索投影 | 基础详情/列表查询 | 退回数据库基础查询，修复后重建可丢弃投影 |

## 事件分级

- P0：业务事实损坏、跨 Workspace 泄漏、核心数据库不可用、无法恢复的证据丢失；
- P1：大面积 API/任务不可用、通知/报告持续失败、来源认证整体失效；
- P2：单来源降级、积压增长、性能持续超 SLO、Vault 冲突增加；
- P3：局部错误、容量预警或不影响用户的投影延迟。

## 响应流程

1. 确认影响、时间窗、用户/Workspace、数据完整性和是否仍在扩大；
2. 优先停止造成破坏的写入或任务领取，保留证据和审计；
3. 选择降级：暂停 AI、暂停单来源、关闭通知通道或退回数据库基础查询；
4. 按关联 ID 定位 API、Worker、来源、数据与前端链路；
5. 恢复后执行对账、补偿或回填，验证业务事实不重复；外部交付只按 Provider 幂等/回执证据确认，无法确认时保持 `unknown`，不以再次发送证明恢复；
6. 记录根因、检测缺口、时间线、影响、恢复和预防措施。

## 成功、停止与回滚边界

成功要求影响停止扩大、权限与事实完整性通过对账、关键队列和交付恢复、告警回归正常且没有未解释差异；外部 `unknown` 必须有 Provider 回执、经批准人工结论或仍处于明确隔离状态，不能静默标成失败/成功。发现跨 Workspace 泄漏、事实/证据损坏、补偿重复副作用、日志泄密或无法确定恢复点时立即停止自动补偿与扩流，隔离相关写入并升级 P0/P1。降级和应用回滚只能切换代码、来源、Codex、通知或查询路径，不删除 PostgreSQL 事实、River 历史、MinIO 对象、Vault 人工区域或持久卷；数据损坏转入备份恢复手册。

### Database readiness alert response

`ALERT-DB-UNAVAILABLE` 不依赖数据库内的 Operations Overview 自我报告。API 的每次 `/readyz` 都执行真实 PostgreSQL Ping：首次失败即把 `hotkey_dependency_health{dependency="database"}` 置为 `0`，连续三次失败后把固定 `hotkey_operational_alert{alert_id="ALERT-DB-UNAVAILABLE",policy_version="p0-operational-alerts-v1",severity="p0",owner="hotkey-oncall",silence_key="ALERT-DB-UNAVAILABLE"}` 置为 `1`。错误正文、DSN、主机、用户和密码不进入 HTTP 或 Metric；Compose 每 10 秒执行一次 readiness，因此默认三次连续探测约覆盖 30 秒，但批准阈值的权威语义是三次连续失败而非时间 SLO。

1. **触发**：在隔离进程中让真实数据库 Ping 连续失败三次，或运行 `cd backend && make observability-alert-acceptance` 的固定 Pinger Fixture；三次 `/readyz` 均返回 `503/90001`，前两次告警 Metric 为 `0`，第三次变为 `1`，响应和 `/metrics` 均不得包含合成连接秘密。
2. **定位**：以 `/readyz` 的 `X-Request-ID`、实例/容器身份和固定 `database` 依赖标签串联净化日志；在受控环境单独运行 `pg_isready` 与 `hotkey db verify` 区分网络/认证/容量和 Schema 兼容问题，不把 DSN、SQL 或数据库原始错误复制到普通日志或工单。
3. **处置**：readiness 失败的实例停止接收流量，暂停 Worker 领取和所有新业务写；先恢复数据库网络、认证、容量或批准配置。若存在数据完整性疑问，保持隔离并按 [备份恢复与重建](002-备份恢复与重建.md) 处理，不把任务降级到内存队列。
4. **验证**：同一实例的真实 Ping 和 `/readyz` 恢复 `200/0`，`hotkey_dependency_health` 回到 `1` 且 `hotkey_operational_alert` 回到 `0`；随后执行 Schema 验证、关键只读查询和 River 租约/积压对账，确认没有重复事实或未解释差异后再接流量。
5. **回滚**：若故障由新应用/数据库配置引入，按 [部署升级与回滚](001-部署升级与回滚.md) 回滚应用或配置并保留卷；若数据库事实或恢复点不可信则停止应用回滚扩大写入，转入隔离恢复。不得删除 PostgreSQL 数据卷、River 历史或审计事实来清除告警。

### River alert response

`ALERT-RIVER-JOB-FAILED` 和 `ALERT-RIVER-NO-WORKER` 由 Admin 运行中心直接读取 River 持久事实并生成最多每规则一条的有界告警。结构只包含固定告警码、稳定原因码、影响数、Runbook URL 和批准的 Job/Event/Trace ID；River Args、Prompt、Payload 及上游原始错误不得返回。

1. **触发**：在隔离测试库中使 Job 进入 `discarded`，或使到期 `available` Job 持续 300 秒；运行 `cd backend && make observability-alert-acceptance`，两类告警均必须出现。
2. **定位**：在“运行中心 → 运行告警”读取 `job_id`；对已批准的 Event 语义 Job 继续用 `event_id` 和 32 位小写十六进制 `trace_id` 查询同一链路。缺失关联 ID 时不得从 Args 人工复制未审批内容。
3. **处置**：先确认事实完整性与 Worker 健康；终态失败只在原因已消除后使用运行中心的有界“重试”，队列积压先恢复 Worker，不删除 Job 历史。
4. **验证**：重新读取 `/api/v1/operations/overview`；重试 Job 进入新的 `available/running/completed` 状态后终态失败告警消失，到期队列清空后积压告警消失，业务事实计数不得因处置而重复。
5. **回滚**：如新告警投影造成运行中心不可用，只回滚应用版本；不删除、改写 River Job/尝试历史或业务事实。回滚后通过原有 Job 列表、Metric 和脱敏日志继续定位。

上述小节只演练两条 River 告警；数据库 readiness、Delivery unknown 与其他持久事实告警由各自小节独立演练。该小节本身不替代下方各规则的独立恢复往返和最终证据登记。

### River 全断点恢复复演

G5 的统一恢复复演使用本机已安装 Go 工具链与可丢弃 PostgreSQL/Redis 测试连接，不重启正式 Docker Compose 服务：

```bash
cd backend
HOTKEY_TEST_POSTGRES_DSN='<isolated-test-dsn>' \
HOTKEY_TEST_REDIS_ADDR='<isolated-test-redis>' \
HOTKEY_RIVER_FAULT_REPORT_PATH='<private-output-path>' \
make river-fault-rehearsal-acceptance
```

测试以真实子进程退出覆盖领取前、领取后、业务事务中、业务事实提交后/完成标记前，以及 Provider 已接收但本地 Attempt 未提交的 lost-ack 边界；同时覆盖可重试失败、取消和永久失败重放。成功的 River 路径最终只能有一个业务事实，事务内未提交事实必须回滚，已提交幂等事实重放不得重复；租约回收后 stale Claim Token 必须拒绝。

Provider 能力分支必须分别记录发送数与回执查询数：支持回执时复用稳定派发身份并收敛到单一 `succeeded` Attempt；不支持回执且无法确认时保存单一 `unknown` Attempt、停止再次领取与盲重发。报告必须是私有、净化、排他创建的 `hotkey-river-fault-rehearsal-v1`，绑定完整 Git revision、固定 Fixture Hash、各断点退出码、Attempt/副作用计数、受保护事实前后 Hash、`differences=[]` 和 `exactly_once_claimed=false`；任一差异、重复发送、重复事实、受保护事实变化或敏感值命中均失败停止。

该命令只使用隔离数据库和无生产出口的回环 Fake Provider，验证的是 `bounded_at_least_once_with_fencing_idempotency_and_explicit_unknown` 恢复语义；它不是生产 Provider 的投递或回执能力批准，也不允许把本地唯一约束表述为外部 exactly-once。

### Delivery unknown alert response

`ALERT-DELIVERY-UNKNOWN` 从 Notification 模块的追加式 `notification_delivery_attempts` 事实中生成，每次只返回最早一条 `unknown` Attempt 和全部未确认交付数量。Operations 只接收 Attempt、Notification、资源类型/ID、数量和时间；收件人、标题、摘要、Provider Message ID、Dispatch Key、Fencing Token、错误详情和正文不会进入告警 DTO。

1. **触发**：在隔离测试库中通过 lost-ack Fixture 形成至少两条 `unknown` Delivery Attempt，运行 `cd backend && make observability-alert-acceptance`；运行中心必须只出现一条 `ALERT-DELIVERY-UNKNOWN`，`affected_count` 等于全部未确认交付数并指向最早 Attempt。
2. **定位**：在“运行中心 → 运行告警”读取 `notification_id`、`attempt_id` 与资源类型/ID；只在 Notification 拥有模块或批准的 Provider 管理面查询相同身份。不得从告警、日志或数据库导出 Dispatch Key、收件人、内容及 Provider 原始响应。
3. **处置**：立即保持该派发键停止自动重发。Provider 支持回执查询时按既有 Capability 契约查证；支持幂等键时只能复用稳定键执行受控对账；两者都不支持时保持 `unknown` 隔离并取得经批准人工结论，不把无法确认改写为普通失败。
4. **验证**：重复读取 `/api/v1/operations/overview` 并运行专项验收；`unknown` Attempt 必须保持追加事实，`ClaimNextEmailDelivery` 不得再次领取该通知。没有 Provider 回执或批准人工结论时，告警继续可见是正确行为，不以清空告警冒充恢复。
5. **回滚**：如新投影导致运行中心异常，只回滚应用版本；不更新或删除 Delivery Attempt、Notification Outbox、User Notification、Read Receipt、Delivery Claim 历史及业务资源。回滚后继续依赖原有 `unknown` 停止语义隔离外部派发。

### Source auth alert response

`ALERT-SOURCE-AUTH` 只读取启用连接、启用 Monitor Source、Checkpoint 连续失败数和最新 Collection Target 稳定错误码；每个连接至多投影一条告警，不返回端点、查询、凭据引用或 Provider 原始错误。

1. **触发**：在隔离测试库为启用 Monitor Source 写入 `consecutive_failures=3`，并使其最新 Target 以 `authentication` 失败；运行 `cd backend && make observability-alert-acceptance`，告警必须关联 `source_connection` 安全 ID。
2. **定位**：使用运行中心的 Source Connection ID 查询当前 Rights、凭据元数据状态和最新 Collection Run/Target；不得读取、复制或导出明文凭据、完整查询和原始响应。
3. **处置**：先停用故障连接或保持其不再调度，按 [来源授权预算与故障处置](003-来源授权预算与故障处置.md) 修复授权/凭据；其他来源及已提交事实继续服务，不伪造该来源成功。
4. **验证**：在同一连接完成一次授权预检与成功采集后把 Checkpoint 连续失败归零；重新读取 Overview，告警消失，其他来源结果、游标和预算账本不重复。
5. **回滚**：如告警投影异常，只回滚应用版本；连接保持停用或原降级状态，不删除 Collection Run/Target、Checkpoint、Rights 决策和审计事实。

### Evidence object alert response

`ALERT-MINIO-WRITE` 由最新一次已结束的 `pg-minio/all` Evidence Lineage 对账事实触发；告警只返回对账 Run ID、异常数和固定策略，不返回对象键、路径、正文、Hash 明文或存储凭据。

1. **触发**：在隔离测试库完成一次 PG/MinIO 对账并写入 Evidence/Raw Object 的 `missing` 或 `digest_mismatch` Item；专项验收必须出现一条关联 `evidence_reconciliation` Run ID 的告警。
2. **定位**：以 Run ID 在受控运维面读取该次对账统计和稳定 Reason Code；对象键只能在获批恢复环境中按摘要解析，不进入 API、日志或截图。
3. **处置**：停止依赖新 Evidence 的派生与审批，隔离损坏范围；按 [备份恢复与重建](002-备份恢复与重建.md) 从批准副本恢复对象或重新执行可证明幂等的写入，禁止用空对象/错误 Hash 继续链路。
4. **验证**：重新执行全范围对账，最新 Run 必须 `completed`、零异常且数据库 Evidence Hash 与对象内容一致；Overview 告警随新的权威对账事实清除。
5. **回滚**：如恢复扩大差异立即停止写入并回到恢复前隔离快照；不得删除旧对账 Run/Item、Evidence 事实、原始对象或审计记录。

### Agent Codex alert response

`ALERT-CODEX-FAILURE` 在全局最近三次终态 AI Run 均以批准的 Provider、模型、认证、Schema 或输出类稳定错误码失败时触发；只返回最早 Run ID、失败数和固定策略，不返回 Prompt、输入、输出、模型原始错误或凭据。

1. **触发**：在隔离测试库连续形成三次符合范围的失败 AI Run；专项验收必须出现一条 `affected_count=3` 且关联 `ai_run` 的告警。
2. **定位**：使用 Run ID 和批准的 `agent_run_id` 日志字段核对 Runtime/模型配置版本与稳定错误码；不得检索或导出 Prompt、正文、结构化结果和 Provider 响应。
3. **处置**：进入 Codex 降级，保留采集、Evidence、确定性计算和人工治理，把新智能决定保持为待分析；修复 Agent 认证/Schema/运行时后，只通过既有幂等补算入口重激活拥有该 Run 的业务 Job。
4. **验证**：完成一次使用当前配置的成功 AI Run，并验证失败 Run 不被复用、业务事实不重复；最近终态窗口不再满足三连败后 Overview 告警清除。
5. **回滚**：如恢复版本产生无效建议，切回上一批准版本并停止新智能决定；保留全部 AI Run 和待补算 Job，不以无标记旧 Provider 回退冒充恢复。

### Vault conflict alert response

`ALERT-VAULT-CONFLICT` 从最新一次已结束 Vault Sync 的冲突计数触发；只返回 Sync Run ID 和冲突数，不返回 Vault 路径、正文、宿主根、差异内容或人工区域。

1. **触发**：在隔离 Vault 形成至少一个人工区冲突并结束同步；专项验收必须出现关联 `vault_sync_run` 的有界告警。
2. **定位**：使用 Sync Run ID 在受控工具中查看冲突摘要和受影响 Artifact 安全 ID；禁止把实际路径或文档正文复制到告警和普通日志。
3. **处置**：暂停对应 Writer，不覆盖人工区域；由获批人员逐项选择保留人工版本、采用派生版本或形成新 Revision，再重新运行投影。
4. **验证**：最新同步 Run 必须结束且 `conflict_count=0`，人工区域和 PostgreSQL Revision 对账无差异；Overview 告警随最新权威同步事实清除。
5. **回滚**：发生新冲突时恢复到处置前 Revision/受保护快照并继续暂停 Writer；不删除旧 Sync Run、Proposal、Revision、Annotation 或人工文件。

### Backup alert response

`ALERT-BACKUP-FAILED` 只读取最新一条追加式 `backup_runs` 事实：运行失败立即触发，运行成功但 `recovery_point_at` 距当前超过候选 900 秒同样触发。成功事实必须来自 `hotkey-backup-run-v1` 严格清单，且同时覆盖 PostgreSQL、MinIO、Vault 全量/人工区域与 River Job/Attempt 五类资产；未知字段、缺件、重复资产、无效 Hash、任意失败详情或不完整时间线在写入前拒绝。Overview 只返回 Backup Run ID、固定策略、影响数与时间，不返回清单正文、对象键、路径、失败详情、连接串或凭据。

1. **触发**：在隔离数据库通过 `hotkey maintenance record-backup --manifest '<failed-manifest>'` 追加一个带批准稳定失败码的失败运行；专项验收必须出现关联 `backup_run` 的告警。再追加五类资产齐全但恢复点早于当前 900 秒的成功运行，告警仍保持并切换到最新 Run ID。
2. **定位**：以 Backup Run ID 在受控备份目录核对不可变清单摘要、Git revision、五类资产计数/Hash、执行时间与稳定失败码；普通 API、日志、工单和截图不得复制清单原文、对象键、Vault/宿主路径或命令错误正文。
3. **处置**：停止把当前恢复点用于发布与清理，修复对应 PostgreSQL/MinIO/Vault/任务事实备份步骤；按 [备份、恢复与重建](002-备份恢复与重建.md) 在同一时间围栏重新取得五类资产，并在独立目标验证 Hash 与恢复可读性。数据库本身不可用时同时按 `ALERT-DB-UNAVAILABLE` 处理，不能用内存状态代替运行事实。
4. **验证**：追加一条清单完整、五类资产齐全、`recovery_point_at` 未超过 900 秒的成功运行；Overview 中 `ALERT-BACKUP-FAILED` 必须清除，随后仍要在隔离目标执行恢复与零差异对账。该告警清除只证明最新备份事实新鲜完整，不会把候选 15 分钟 RPO 自动批准为 SLA。
5. **回滚**：备份运行事实禁止更新或删除；若新清单或解析器有误，只回滚应用/备份执行器并追加新的失败或成功事实，不改写历史。任何资产不一致继续保持发布阻断，并保留原清单和恢复环境调查。

### Search backlog alert response

`ALERT-SEARCH-BACKLOG` 只统计到期超过 300 秒的四类检索投影 River Job，并返回最老 Job ID 和总积压数；Job Args、搜索正文、对象键及用户输入不会进入告警。

1. **触发**：在隔离测试库使任一批准的检索投影 Job 到期积压 300 秒；专项验收必须返回最老 Job ID、影响数和固定阈值。
2. **定位**：以 Job ID 检查 Worker 健康、稳定失败码和 PostgreSQL 权威资源 ID；不得从 River Args 复制索引正文或用户输入。
3. **处置**：先退回数据库基础查询并恢复投影 Worker；原因消除后让原 Job 幂等执行，必要时按 [保留删除与撤权处置](005-保留删除与撤权处置.md) 重建可丢弃投影，不改写权威事实。
4. **验证**：四类到期投影 Job 均离开积压状态，撤权后的 Search/CanDisplay 保持不可见，重建前后权威事实计数一致；Overview 告警清除。
5. **回滚**：如新投影出现越权或差异，立即停止投影 Worker、清理可丢弃索引并回退数据库查询；保留 River 历史、PostgreSQL 事实、撤权和审计记录。
