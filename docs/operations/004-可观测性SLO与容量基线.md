# 可观测性、SLO 与容量基线

## 健康与指标入口

- `/healthz` 只表示进程存活。
- `/readyz` 验证当前角色所需依赖，只有它成功才接收流量。
- `/metrics` 暴露 Prometheus 文本；应仅允许监控网络访问。
- Admin 的“治理 → 运行状态”展示安全任务投影；不展示 River `args` 或上游原始错误。

关键业务指标：

| 指标 | 用途 | 允许标签 |
| --- | --- | --- |
| `hotkey_source_collection_runs_total`、`hotkey_source_collection_duration_seconds` | 来源结果和耗时 | 固定 `source_type`、`status` |
| `hotkey_source_collection_retries_total` | 来源重试 | 固定 `source_type` |
| `hotkey_job_runs_total`、`hotkey_job_duration_seconds` | 任务状态、结果和耗时 | 固定 `kind`、`state`/`outcome` |
| `hotkey_job_retries_total`、`hotkey_job_queue_lag_seconds` | 重试与最老到期任务滞后 | 固定 `kind` 或无标签 |
| `hotkey_usage_current`、`hotkey_quota_limit` | 当前用量和限制 | 固定 `dimension`、`mode` |
| `hotkey_ai_cost_usd` | 已结算 AI 成本 | 固定 `provider`、`model`、`status` |
| `hotkey_runtime_metrics_collection_success` | 数据库指标投影自身是否成功 | 无标签 |

任何标签不得包含用户内容、查询、URL、账号、凭据、资源 ID、任务 ID或上游错误。数据库指标投影失败只把自身成功值置为 0，不影响健康端点，也不输出数据库错误文本。

## MVP 告警阈值

阈值以连续窗口触发，恢复也需连续两个评估窗口正常，避免抖动。

| 信号 | warning | critical | 首要动作 |
| --- | --- | --- | --- |
| readiness | 2 分钟内失败 2 次 | 连续 5 分钟失败 | 检查 PostgreSQL、Redis、MinIO 和角色配置；停止切流 |
| 指标投影成功值 | 一次为 0 | 连续 5 分钟为 0 | 查数据库连通性与查询超时；健康正常时不重启全栈 |
| 队列滞后 | 超过 5 分钟 | 超过 15 分钟 | 检查 Worker、失败类型与资源；暂停新任务生产者 |
| 来源失败率 | 15 分钟超过 20% 且至少 5 次 | 15 分钟超过 50% | 按来源类型停用，不影响其他来源 |
| discarded 任务 | 任一新增 | 5 分钟持续新增 | 通过安全投影定位 kind/ID；只重试明确单任务 |
| hard 配额/预算 | 使用达到 80% | 达到 95% | 降频、停用低优先级来源/AI，不绕过硬限制 |

## 排障顺序

1. 确认告警时间窗、部署版本与 `/readyz`。
2. 读取低基数指标确定来源类型或任务类型，不先搜索内容和原始参数。
3. 在治理界面用任务状态筛选，记录任务 ID、安全资源 ID、尝试次数与稳定失败码。
4. 用请求 ID/trace ID 关联结构化日志与审计；日志也不得包含凭据或上游正文。
5. 按 [来源故障手册](003-来源授权与故障处置.md) 停用最小范围能力；修复后观察两个调度周期。

## 容量基线

容量结论只来自与生产同版本、同角色拆分和同类基础设施的实测，不把开发机结果当生产上限。每次发布或基础设施规格变化后记录：

- API p50/p95/p99、错误率与最大稳定并发
- 每种任务的吞吐、p95 时长、重试和最老队列滞后
- 每种来源的调用量、成功率、配额占用
- PostgreSQL 连接、CPU、内存、磁盘和增长；MinIO 容量与对象数
- Worker 数量、任务堆积恢复时间、AI Token/成本和通知投递量

最小复核流程：先运行仓库完整门禁和 Schema 的千行任务夹具，再在隔离环境按 1×、2×、4× 当前峰值逐级压测；每级至少覆盖两个调度周期。达到任一停止条件即结束：错误率超过 1%、p95 超过产品目标、队列连续增长、hard 配额达到 80%，或任一依赖资源超过组织安全水位。

扩容优先保持单一事实源：API 与 Worker 可按现有 `HOTKEY_ROLE=api|worker` 分离，任务仍由 PostgreSQL 持久队列协调；不得为了吞吐复制业务表或引入第二套队列。容量记录必须包含 Git 提交、镜像 ID、数据规模、持续时间、机器规格、结果与下一复核日期。

### 语义监控与通知的可重复基线

以下是开发/CI 环境的有界正确性门禁，不是生产容量承诺。发布前仍须按上节在生产等价环境执行 1×、2×、4× 峰值压测。

| 能力 | 固定负载与门槛 | 自动化证据 |
| --- | --- | --- |
| Web Push fan-out | 100 条 `UserNotification` × 4 个独立设备，8 个并发领取者；400 个目标必须全部成功、无重复事实、无残留租约，15 秒内完成，`notification_delivery_attempts` 增长 1–16 KiB/目标 | `TestNotificationDeliveryCapacityBaseline` |
| 设备隔离 | 同一用户多设备分别形成 `push_subscription:{id}` 目标；404/410 只使目标设备过期，其他设备可继续投递 | `TestWebPushDeliveryRepositorySeparatesDevicesAndExpiresOnlyGoneTarget` |
| 领取一致性 | PostgreSQL `SKIP LOCKED` 候选领取后以新快照复核终态、尝试次数和退避窗口；旧快照等待者不得获得已完成目标的有效租约 | 容量测试的 8 路并发及唯一目标断言 |
| SSE | `HOTKEY_NOTIFICATION_SSE_MAX_CONNECTIONS` 只允许 1–10000；达到上限返回 503，前端切换为带 `after_id` 的持久轮询，不丢失 Last-Event-ID 之后的安全通知 | Notification Transport/Application 的连接上限、回放、撤权和轮询测试 |
| PWA 离线边界 | Service Worker 只缓存公开离线壳与图标，不拦截 `/api`、Authorization 响应、正文或通知数据；Push payload 只含标题、事件 ID、同源深链和优先级 | `pwa-contract.test.ts`、`webPush.test.ts` |
| 正文与检索 | 正文只进入 MinIO raw/Vault immutable artifact；PostgreSQL 仅保存受 Rights/retention 约束的 FTS、trigram、结构键和 1024 维向量投影 | Source/Ingestion 的真实 PostgreSQL、MinIO、Vault、撤权和重复投影测试 |

本机 2026-08-10 基线使用 PostgreSQL 16/pgvector、Redis 7 和当前工作树，在上述 100×4/8-worker 场景连续三次通过；该记录只证明有界并发下的完整性和开发机时延。正式容量记录必须另外填写 Git commit、镜像 ID、CPU/内存/磁盘、连接池、Worker 数、持续时间、p95/p99、数据库和对象存储增长，并在规格或索引变化后重新测量。

复核命令：

```bash
cd backend
HOTKEY_TEST_DSN='<isolated-postgresql-dsn>' \
HOTKEY_TEST_REDIS_URL='<isolated-redis-url>' \
go run ./test/runner test -tags=integration \
  ./internal/modules/notification/infrastructure/postgres \
  -run TestNotificationDeliveryCapacityBaseline -count=3
```
