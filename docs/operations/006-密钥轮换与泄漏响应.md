# 密钥轮换与泄漏响应

## 适用边界

覆盖 JWT 签名、认证 HMAC、来源凭据主密钥、数据库、MinIO、SMTP 和 Codex 认证。只使用合成 Secret 和隔离环境演练；真实 Secret、密文、DSN、认证文件和恢复材料不得写入本文、日志或 Acceptance。

当前手册仍为 `planned`。提交 `7b13a1cc` 的 GitHub Actions `33264824771` 已登记远端合成隔离矩阵和同轮敏感面扫描并关闭 `CHK-005-G4-010`；在 G5 Runbook dry-run、G6 发布演练与真实目标供应商接口复核完成前不改为 `active`。真实部署仍必须使用目标供应商的正式创建/撤销接口，不得把合成凭据或自动化 Fixture 当作生产凭据。

## 已实现参数

| 用途 | 当前值 | 兼容窗口（可选） |
|---|---|---|
| JWT | `HOTKEY_JWT_KEY_ID` + `HOTKEY_JWT_SECRET` | `HOTKEY_JWT_PREVIOUS_KEY_ID` + `HOTKEY_JWT_PREVIOUS_SECRET` |
| 验证码 HMAC | `HOTKEY_VERIFICATION_HMAC_SECRET` | `HOTKEY_VERIFICATION_HMAC_PREVIOUS_SECRET` |
| 来源凭据 | `HOTKEY_SOURCE_CREDENTIAL_MASTER_KEY_VERSION` + `HOTKEY_SOURCE_CREDENTIAL_MASTER_KEY` | `HOTKEY_SOURCE_CREDENTIAL_PREVIOUS_MASTER_KEY_VERSION` + `HOTKEY_SOURCE_CREDENTIAL_PREVIOUS_MASTER_KEY` |
| Python Agent | `HOTKEY_AGENT_AUTH_TOKEN` | `HOTKEY_AGENT_PREVIOUS_AUTH_TOKENS`（逗号分隔） |
| Codex 只读基线 | `HOTKEY_CODEX_AUTH_FILE`（绝对路径、私有常规 JSON） | 无双读；候选文件预检后滚动进程 |

兼容窗口期间，服务只用当前值签发或加密，旧值只用于验证或解密。不得在命令行、文档、工单或验收附件中填写明文；生产值只能通过未跟踪的 `.env.prod` 或等价 Secret 注入。

## 来源凭据重加密

项目必须保持由根目录 Docker Compose 运行。日常开发使用固定非生产值且数据可丢弃，不执行真实凭据轮换；生产编排统一使用 `.env.prod` 或等价 Secret 注入当前值和兼容窗口值。滚动更新 API/Worker 后再执行：

```bash
docker compose -f docker-compose.yml exec hotkey-server \
  /usr/local/bin/hotkey maintenance rotate-source-credentials \
  --actor-user-id "$HOTKEY_ROTATION_ACTOR_ID" --batch-size 100 --dry-run
```

预检通过后，按有界批次重复执行：

```bash
docker compose -f docker-compose.yml exec hotkey-server \
  /usr/local/bin/hotkey maintenance rotate-source-credentials \
  --actor-user-id "$HOTKEY_ROTATION_ACTOR_ID" --batch-size 100 --apply
```

只有输出持续为 `remaining=0`、来源连接冒烟通过且审计仅含版本/计数时，才能删除上一版本参数并再次滚动服务。任一批失败会整批回滚；旧密钥撤销前可回退到上一配置，撤销后不得重新启用。

## 数据库、MinIO、SMTP 与 Codex 隔离演练

- 数据库：只在 `HOTKEY_TEST_DSN` 创建的可丢弃数据库和临时 Login Role 中运行；新 Role 先执行最小读取预检，错误候选不改变旧连接，切换连接池后以 `NOLOGIN` 撤销旧 Role，并再读同一持久行。
- MinIO：在已运行的隔离 MinIO 上创建一个临时 Bucket、一条仅允许该 Bucket 读写的 Policy 和新旧两个合成 User；新 User 预检、数据对读和切换后禁用旧 User，演练结束删除临时 User/Policy/Bucket，不重启项目 MinIO。
- SMTP：使用进程内 TLS 1.2+ SMTP Fixture 分别执行 Identity 验证码和 Delivery 邮件的 AUTH、DATA 与撤销负向测试；失败候选和已撤销凭据的接收计数必须为零，错误只返回稳定的不可用/认证失败分类。
- Codex：`HOTKEY_CODEX_AUTH_FILE` 只允许绝对路径、非符号链接、不允许 group/world 读取、有界且非空的 JSON。Adapter 每个任务重新读取，以 `0600` 独占复制到临时 `CODEX_HOME/auth.json`；仍不继承 Worker 的 `CODEX_HOME`、Provider Key 或任何业务凭据。容器演练由运维把候选文件显式只读挂载到配置路径，不在 Compose 或文档写入文件内容。

合成演练的管理密钥、凭据内容和端点只通过本地未跟踪环境注入；它们不作为命令参数、不输出到测试日志，也不写入矩阵报告。

本机验收使用已安装的 Go/Python 环境和已运行的测试依赖，不重复启停项目：

```bash
cd backend
make secret-rotation-acceptance
```

执行前必须在当前 Shell 中提供可丢弃的 `HOTKEY_TEST_DSN`、`HOTKEY_TEST_REDIS_URL`、MinIO 测试端点/管理端点/专用 Docker Network 与管理凭据。开发机可向已运行 Compose 依赖添加临时 TCP 代理，但不重启 API、Worker、Agent、Web、PostgreSQL、Redis 或 MinIO。

## 轮换契约

| 类型 | 兼容窗口 | 撤销后必须验证 |
|---|---|---|
| JWT 签名 Key | 新 Token 只用新 Key；验证按 Key ID 在批准窗口接受新旧 Key | 旧 Key 不能签发/验证窗口外 Token，会话策略符合批准结论 |
| 认证 HMAC | 依实现选择双验证或受控重新派生，不得静默失效全部账号 | 旧 Key 不再接受，登录/重置/验证码负向测试通过 |
| 来源凭据主密钥 | 新写只用新 Key；旧密文在有界批次重加密或兼容解密 | 全量密文可解、旧 Key 撤销后无旧版本残留且来源冒烟通过 |
| 数据库/MinIO/SMTP/Codex 凭据 | 先创建/预检新凭据，再滚动服务，最后撤销旧凭据 | 新凭据健康，旧凭据明确拒绝，任务/交付无双写或数据丢失 |

## 计划轮换流程

1. 登记 Secret 类型、环境、Key ID/版本、Owner、维护窗、依赖、会话/密文影响和回退截止；
2. 创建新凭据并在不暴露明文的独立探针中预检权限、作用域和到期时间；
3. 取得轮换前备份/配置指纹，确认恢复材料与数据备份分开保存；
4. 启用适用的兼容窗口：只用新 Key 签名/加密，新旧 Key 仅按批准范围验证/解密；
5. 分批滚动 API/Worker/前端服务端配置，观察认证失败、任务、来源、MinIO、邮件和 Codex 指标；
6. 完成会话处理或密文重加密对账，确认没有未知 Key ID/旧版本残留；
7. 撤销旧凭据并执行旧凭据负向测试；任何继续可用都视为失败；
8. 关闭兼容窗口，保存不含明文的版本、时间线、计数、指标、审计和回退结果。

## 停止与回退

新凭据权限不符、认证失败超阈值、密文不可解、来源/对象/任务异常、旧凭据无法撤销或日志出现 Secret 时立即停止。旧凭据尚未撤销时，可在维护窗内回退到最后已验证配置并停止新写；一旦旧凭据因泄漏被撤销，不得为恢复服务重新启用，应修复新路径或从批准恢复材料重新发行。

回退不能删除新密文、会话、任务或审计；双版本密文必须以 Key ID 区分并在恢复后重新对账。

## 泄漏响应

1. 隔离泄漏入口，停止相关发布、日志出口和新任务；
2. 确认 Secret 类型、环境、首次/最后暴露时间、可能访问者和可执行权限；
3. 优先创建最小权限新凭据并撤销受影响旧凭据；不能等待常规兼容窗口；
4. 按类型撤销 Session/Token、轮换来源/数据库/MinIO/SMTP/Codex 凭据并检查审计；
5. 扫描仓库、构建物、日志、Trace、Metric、前端 Bundle、OpenAPI、备份和工单附件；
6. 对暴露窗口内的访问、数据变更、对象下载和外部副作用做调查与用户/合规沟通决定；
7. 只有旧凭据失效、受影响面闭合、服务使用新凭据且再扫描为零泄漏后才解除事件。

## 成功判据与演练证据

- 新凭据预检、滚动、兼容窗口、会话/密文处理、旧凭据撤销和失败回退均有结果；
- 旧凭据负向测试稳定失败，新凭据只具备批准的最小权限；
- 日志、Trace、Metric、River、前端、OpenAPI、文档和 Acceptance 均无新旧明文；
- 证据只保存 Secret 类型、Key ID/版本、时间、计数、稳定错误码、审批和审计摘要；
- 每类 Secret 上线前演练一次，此后至少每半年或供应商/权限变化后复演；泄漏响应每年至少桌面演练一次。
