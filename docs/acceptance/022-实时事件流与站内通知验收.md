# 实时事件流与站内通知验收

## 验收结论

022 于 2026-08-08 通过验收。事件更新、热点告警、报告终态和采集终态在原业务事务内投影为 PostgreSQL append-only 通知事件；认证用户通过同一角色过滤的 JSON 补拉与 Bearer SSE 获得可恢复通知。前端支持 Toast、铃铛未读状态、进入通知页自动已读、断线续传与明确的轮询降级，原报告订阅区域保持可用。

## 浏览器验收

按用户指定的 `$agent-browser` 连接真实 Next.js、Go、PostgreSQL 与 Redis，并使用隔离数据库和合成业务事实验收：

- 匿名访问通知页跳转到带安全 redirect 的登录页，直接访问 list/stream 均返回 401；Viewer 初始显示通知空态和实时连接状态。
- 插入真实 Event 与 EventUpdate 后，Viewer 无刷新收到 Toast、铃铛未读徽标与通知卡片；离线期间写入第二条 EventUpdate，恢复后自动补齐且没有重复。
- 真实 CollectionRun 进入 failed 后，Viewer 页面不可见，Admin 页面可见“采集任务失败”，验证 audience 层级未由客户端扩大。
- 主动拦截 stream 请求后，三次失败进入“轮询中”；随后真实 EventUpdate 由 JSON 补拉出现，解除拦截并重载后恢复“实时”。
- 在其他页面收到新通知时铃铛显示“1 条未读”；进入通知页后自动推进 read-through 游标，铃铛恢复无未读状态。
- 1440×900 与 390×844 均无横向溢出；桌面和移动的 axe-core 4.12.0 WCAG 2 A/AA 均为 0 violations、0 incomplete，稳定页无应用 JavaScript 错误。

## 安全与产品边界

- JWT 不进入 URL；SSE 由生成 Client 通过 Bearer Header 调用，Header 游标优先于 query，通知 payload 不保存正文、原始证据、凭据或内部错误文本。
- PostgreSQL 是唯一恢复事实源；未引入 Redis Pub/Sub、WebSocket、Socket.io、Kafka 或进程内广播。
- 客户端只持久化按用户隔离的 last event ID 与 read-through ID，不持久化通知正文、Token 或跨用户数据。

## 回滚

先停止前端实时控制器和通知入口，再停用四个投影触发器与通知路由；保留 append-only 通知事实供审计和恢复。旧业务表、告警、报告、采集与订阅 API 不依赖通知表，可独立继续运行。
