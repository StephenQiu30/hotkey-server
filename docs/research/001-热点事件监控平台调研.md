# 热点事件监控平台调研：鱼皮项目功能对照

调研日期：2026-09-17。对象为鱼皮公开仓库 [liyupi/yupi-hot-monitor][Y01]。核查提交为 cd48b0885bfa8ae9c8043cf78ef6cfd045530bdb，提交日期 2026-04-16，该次提交只修改项目介绍视频链接。

本轮通过 GitHub 读取 README、需求文档、数据库模型、调度、来源服务、AI、排序、路由、前端和技能报告脚本；通过 Firecrawl 查找项目一手入口并读取 X 数据供应商计费页。未部署此项目、未填写 API Key、未实采社交数据、未发送通知或执行其技能。

本文区分：**源码可确认的路径、项目文档声明、未发现实现的能力、对 HotKey 的建议**。源码存在不证明当前平台接口在真实环境可用。

## 1. 产品定位与结论

鱼皮项目主要服务于“输入关注词，定期发现有价值信息并收到通知”的个人信息发现需求。它的主要流程可以参考：

    激活关键词
      → 识别可能的 B站账号、获取内容
      → 多来源检索
      → URL 去重与新鲜度过滤
      → 文本预匹配、AI 相关性与重要性判断
      → 保存热点条目
      → 页面更新、通知记录与高重要性邮件

它具有可研究的完整发现与通知流程，但本次核查未发现将多个作品归并为事件、保存评论正文/回复树、持续指标快照、完整独立关注账号管理等实现。**可以借鉴产品流程，不能直接认为它已经覆盖 HotKey 的事件与讨论研究需求。**

当前不直接采用整个仓库：X 来源为收费第三方服务，默认 AI 为外部模型服务，仓库整体许可范围也需进一步明确。技术栈与本项目不同不是否定依据，需求覆盖、费用和可持续维护才是重点。

## 2. 已实现路径与具体边界

| 能力 | 源码/文档核查 | 对 HotKey 的启示 |
|---|---|---|
| 关键词管理 | 有新增、编辑、删除、分类及启停；Keyword.text 唯一。[Y02][Y03] | 保留低门槛主题设置；增加别名、排除词、平台范围和规则版本 |
| 定时检查 | node-cron 每 30 分钟执行；另有手动检查端点，HTTP 等待 runHotspotCheck 完成。[Y04] | 设置频率不代表数据实时；采集应有独立任务状态，提交与完成分开 |
| 多来源发现 | 定时主流程明确调用 Twitter、Bing、HackerNews、搜狗、B站、微博六个入口；还包含账号结果。[Y05] | 入口数不能直接解释为同等能力的社交平台数量 |
| X 热门与最新 | 使用 twitterapi.io；Top 最多两页、Latest 一页；合并去重后再做互动阈值过滤。[Y06] | 热门/最新分工值得保留；不能将其接入方案称为免费 X 采集 |
| 微博“搜索” | 实际取 hotSearch 热榜，并在热搜词上做关键词过滤；没有在此函数执行微博全文关键词搜索。[Y07] | “热榜线索”和“关键词主动搜索”必须分别声明 |
| B站账号内容 | 依据关键词搜索 B站用户，精确名字或首个高粉匹配后获取最新视频。[Y07] | 有账号识别与作品获取雏形，但要补用户显式选择、稳定 ID 和长期跟踪配置 |
| X 用户作品函数 | twitter.ts 定义 getUserTweets；当前定时主流程未调用它；schema 未见独立关注账号实体。[Y02][Y05][Y06] | “有函数”不等于“已有关注账号产品”；端到端入口与持久状态必须核实 |
| 查询扩展 | expandKeyword 生成变体并缓存；主流程仍将原始 keyword.text 传给上游搜索，变体用于返回内容的本地预匹配。[Y05][Y08] | 不把本地扩词匹配说成扩大了上游检索召回；两种功能分别设计 |
| AI 相关性和摘要 | 输出相关性、理由、是否提及关键词、重要性和短摘要；主流程按分数与 isReal 过滤入库。[Y05][Y08] | 相关性说明有价值；模型判断不能替代事实核验或成为唯一保存门槛 |
| 筛选与排序 | 列表支持来源、重要性、关键词、时间范围，以及时间/相关性/热度排序；时间范围查询主要使用 createdAt。[Y09][Y10] | 原始发布时间、发生时间、采集时间和排序口径要明确 |
| 手动“全网搜索” | 当前 Web POST /api/hotspots/search 只处理 Twitter/Bing，最多对前 10 条进行 AI 分析并返回；不同于定时六来源流程。[Y09][Y11] | 手动查询、定时任务、技能三个入口分别发布能力范围 |
| 通知 | 入库后创建通知，发送 Socket.io 事件；high/urgent 才调用邮件；SMTP 或收件人缺失时邮件不发送。[Y05][Y12] | 值得借鉴提醒分级；前台实时消息、离线通知、发送成功不是同一件事 |
| 历史资料 | Hotspot 持久化；以 url+source 唯一去重；已有条目在检查中跳过，不持续刷新指标。[Y02][Y05] | 保存历史条目不等于记录指标趋势；需新增快照与增量刷新 |
| 报告与技能 | skills 目录有搜索脚本、使用说明和 JSON 转 Markdown 报告脚本；后者按来源组织原始结果。[Y13] | 报告能力不是完全缺失，但技能脚本报告不等于 Web 端事件评论分析报告 |
| 评论与回复 | Hotspot 有 replyCount/commentCount/danmakuCount 等数量字段；当前 schema 和 Web 路由未发现评论正文、父子关系与评论采集流程。[Y02][Y09] | 必须把“评论数量”与“评论内容/上下文”当作不同需求 |

以上是检查到的代码路径，不含真实网络可用性或数据完整性保证。

## 3. 需要纠正的几个直觉

### 3.1 “8+ 信息源”不代表“8+ 社交平台原生搜索”

README 宣称 8+ 信息源，源码还存在 Google、DuckDuckGo 等搜索函数；但定时主流程仅明确调用六个来源入口，当前国际聚合函数仅使用 Bing 与 HackerNews。网页搜索、平台搜索、热搜过滤和作者作品都是不同能力，不能合成一个无边界的“全网搜索”。[Y01][Y05][Y14]

**产品要求：**FR-001-002/003 按入口和平台声明实际能力；FR-001-019 将热榜作为补充发现。未接通、受限和仅热榜三种状态不能都标成“支持关键词监控”。

### 3.2 “AI 真假识别”不等于事实核查

AI 服务根据输入文字生成 isReal 等结果，本次未看到独立原始事实检索、反证比对和人工核验流程。源码缺少 Key 时可回退，并默认 isReal=true；AI 调用失败时也有默认值。因此，“真实”标签可能只是默认值，不应作为事实结论。[Y08]

**产品要求：**FR-001-013/014 与 NFR-001-015 应区分相关性、内容质量提示、事实核验状态与模型不确定性。未知不自动变真；也不能只因模型分低就永久丢失所有可复核线索。

### 3.3 有排序公式，但没有经过验证的事件热度模型

检查到至少三个不同层级的公式：

- X 获取后的预排序：likes×2 + retweets×3 + views/100，再对认证标识加分。[Y06]
- 通用列表排序：likes×10 + retweets×5 + 2×log10(max(views,1))。[Y10]
- 前端热度条：另一组包含评论、回复、引用的加权值，经对数压缩至 0–100。[Y11]

这说明项目做了互动指标排序，但展示分数、排序和来源预过滤口径不同。数据库没有持续快照，已有作品又会跳过更新，因此不能据此声称已有“正在升温”或跨平台事件传播分析。

**产品要求：**FR-001-011 统一说明用于排序的分数和页面展示的分数；确需不同指标时分别命名、解释并记录版本。增长必须基于实际时间间隔的快照。认证标识不作为内容真实性或自然传播价值的默认加分理由。

### 3.4 过滤器也可能丢掉“正在发生”的事情

X 来源设置最低点赞、转发、播放、粉丝阈值，并排除回复；刚发布、互动尚低的事件可能无法进入候选集。监控任务另有来源优先级与最多保存 Twitter 15 条、其他来源合计 10 条的限制。[Y05][Y06]

后者是在成功保存后递增的数量限制，不能视为严格的网络请求或模型调用预算；大量被过滤内容仍可能消耗调用。

**产品要求：**热门与最新分别采样，保留低互动新事件的发现机会；来源预算与内容保存上限分开。平台拒绝、预算截断和模型过滤必须可观察。

### 3.5 去重与持续更新必须同时成立

当前同 URL+source 已存在则跳过，可降低重复通知，但也跳过指标更新；一个热点只有一个 keywordId，多个主题命中的来源解释不完整。[Y02][Y05]

**产品要求：**FR-001-005/008 分离作品实体、发现关系和指标快照；一次内容可以关联多个主题，后续互动/评论能更新，而不会重复发送相同变化提醒。

## 4. 对照我们的必要功能

| 我们需要的能力 | 鱼皮项目当前证据 | HotKey 决策 / 需求 |
|---|---|---|
| 关键词设置与启停 | 有 | 保留并扩展，FR-001-001 |
| 主动关键词发现与热门/最新 | 部分来源有；不同入口覆盖不同 | 逐来源声明能力，FR-001-002/003 |
| 明确关注某个用户 | 有 B站关键词识别作者及获取视频；X 有未接入定时主链路的函数 | 独立账号管理与稳定 ID，FR-001-004 |
| 作品正文与基本互动值 | 有，部分来源仅摘要 | 标记内容完整度与语义，FR-001-005 |
| 评论正文、回复树、采样说明 | 未在核查 schema/路由中发现 | 必须补齐，FR-001-006 |
| 任务可见、恢复、延期、预算 | 有 cron 与日志；未见持久任务状态模型 | 必须补齐，FR-001-007/008 |
| 事件归并、拆分、发展时间线 | 未在核查模型和路由中发现独立事件能力 | 必须补齐，FR-001-009/010/017 |
| 热门、升温与可解释排名 | 有静态互动排序；未见持续快照 | 保留可解释信号，补增长与版本，FR-001-011 |
| 评论焦点、诉求、立场与证据 | 有条目相关性/摘要；不能证明评论分析 | 独立分析验收，FR-001-013/014 |
| 通知与已读记录 | 有 WebSocket、通知表、邮件路径 | 保留，补阈值、冷却、发送结果，FR-001-015/022 |
| 基础报告与导出 | 技能中有 Markdown 报告脚本 | 作为输出形式参考，补 Web 内按事件/样本导出，FR-001-016 |
| Agent 调用入口 | 有技能包 | 后续价值验证，不作为当前核心监控首版前提 |

不因“参考项目没有做”把它认定为无价值，也不因“参考项目做了”就将它列为我们的必做。需求优先级仍由用户任务、免费约束与可核查价值决定。

## 5. 非功能需求的研究结论

| 观察 | 转化的非功能要求 |
|---|---|
| 某些来源捕获异常后直接返回空数组 | NFR-001-001/013：成功空结果、失败、部分完成必须分开记录 |
| 主调度是进程内 cron，手动执行等待完成；未见持久采集任务表 | NFR-001-003/004/005：异步受理、状态可追踪、重试幂等、重启恢复，不因日志打印结束就判全部成功 |
| 热度条与列表排序不同，已有条目不刷新 | NFR-001-002/015：指标版本一致性、可复现快照与单独的排序效果评估 |
| 数值写入用 item.likeCount 等值的“或 null”表达式 | NFR-001-001：合法的 0 与缺失 null 必须保留区别 |
| 多来源合并、部分来源失败后继续处理 | NFR-001-007：值得保留故障隔离，同时展示失败来源，不能只显示聚合成功 |
| 需求文档写页面 <3 秒、API <1 秒、100 个关键词、7×24 运行 | NFR-001-003/004/016：此类目标需硬件、数据量、并发与观测窗口；不直接复制为已证明能力 |
| 分析结果依赖外部服务与回退规则 | NFR-001-011/015：免费基础流程可独立运行，回退不伪装为完整 AI 结果 |
| 当前模型未见独立用户/会话所有权与任务审计实体 | NFR-001-008/009/013：HotKey 需自己的凭据、访问与审计边界；本轮不把该项目当作已完成安全审计 |

这部分用于提炼 HotKey 质量要求，不是对参考项目进行完整安全或性能评估。

## 6. 费用、许可与可复用范围

### 6.1 不能直接沿用的服务依赖

- **X：**源码连接 api.twitterapi.io 并读取 TWITTER_API_KEY。供应商当前页面提供充值按量计费，也提供订阅优惠；“不用订阅”仍不等于“免费”。不作为 HotKey 免费生产链路。[Y06][Y15]
- **AI：**默认走 OpenRouter 的 deepseek/deepseek-v3.2，需相应 Key。README 将 Key 列为前置条件，而源码有无 Key/调用失败回退；应准确说“完整 AI 路径依赖外部服务”，不能说无 Key 完全不能启动，也不能据此认定完整分析零成本。[Y01][Y08]
- **邮件：**使用配置的 SMTP，是否有免费可用账户、发送额度与投递质量取决于部署条件；未在本轮进行投递验证。[Y12]

### 6.2 许可证的准确表述

本次 GitHub 仓库元数据 license=null，完整文件树未找到统一 LICENSE 文件；但 **server/package.json 明确声明 license=ISC**，client/package.json 未声明对应许可证。[Y16]

因此不能笼统说“完全没有任何许可证声明”，也不能将后端包的字段直接推定覆盖整个前端、技能、图片与教程资产。当前可以研究公开源码与产品交互；复制或再发布具体代码/素材前，需要明确相应范围的许可依据。项目公开可见、可克隆，不自动等于整个项目具有统一的开源复用许可。

### 6.3 值得复用的产品思路

1. 关键词启停、手动检索和定时监控形成简单入口。
2. 热门与最新组合，列表提供来源、时间和相关性筛选。
3. 显示“为什么相关”的简短解释，减少用户阅读成本。
4. 新内容通知、重要性分级与历史记录。
5. 结构化结果生成带来源链接的报告。

优先吸收这些能力定义；采集器、指标体系、评论模型和任务管理按 HotKey 的免费约束与必要需求独立选择。

## 7. 本轮对需求的具体补充

本轮不增加重复需求条目，在 [001 PRD](../prd/001-热点舆情监控平台需求.md) 的已有 24 FR / 16 NFR / 40 AC 中补充精度：

- FR-001-001/003：别名匹配与真正扩展上游搜索分开；扩展检索词不能静默增加来源和预算。
- FR-001-002：手动、定时、技能入口的来源范围一致或明确说明差异。
- FR-001-004：用户显式选择关注对象，不能仅根据高粉同名候选自动认定身份。
- FR-001-011：列表排序与展示分数一致，或者分别命名解释，避免同名热度口径不同。
- FR-001-013/014：不把模型 isReal 或缺省值作为事实核查结论，分析失败也保留可复核资料。
- NFR-001-011：入库数量上限不等于请求与模型调用预算，预算必须覆盖被过滤内容。

尚未发生的工作：候选项目部署、真实来源验收、UI 实测、模型效果测评、持续运行与完整许可审查。本研究没有采购或调用其收费数据服务。
