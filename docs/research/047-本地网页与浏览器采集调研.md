# 本地网页与浏览器采集调研

调研日期：2026-09-22；S03-T00 同样本复核：2026-09-23；四平台官方访问路径复核：2026-09-24。用户明确要求 B站、小红书、抖音、微博的评论采集都需要，并要求按 GitHub star 评估 Scrapling。本次通过 **GitHub 插件**读取仓库、许可证、固定提交源码、Issue/PR、提交历史和发布 CI，通过 **Firecrawl 插件**的 Developer Index 发现实现线索，再以 `maxAge=0` 抓取官方自托管文档、项目 API 文档核对。仅在临时虚拟环境安装 Scrapling，执行第 6.4/6.6 节的本机受控实验；没有向 HotKey 加入候选依赖、调用公开演示接口、登录社交平台或抓取真实评论。2026-09-24 只查阅四个平台的官方公开准入资料，未安装/运行官方 CLI、申请应用权限或发起平台请求。文档、源码与受控实验不计作平台可用证明。

承接 [047 Design](../design/047-本地网页与浏览器采集设计.md)、[008 评论 Design](../design/008-评论与回复采集设计.md) 和 [047 Plan](../plans/047-本地网页与浏览器采集计划.md)。X 仍按 002 独立推进；四个国内平台不能仅选一个后将本需求记为完成。

## 1. 结论与采用方式

可以在本地建设这项能力，但需要三个分工：Firecrawl 提取公开网页正文；独立浏览器运行时执行必要的页面交互；平台适配器解析作品身份、一级评论、楼中楼与分页。采集的业务任务、权限、预算、持久化和增量水位仍由 HotKey 管理。

本地部署减少对外部采集供应商的依赖，但平台页面、登录状态和站内响应结构仍会变化。浏览器也可能读取页面自身发出的结构化响应；不把“使用 Playwright”描述为完全摆脱接口或长期免维护。

| 目标 | 建议实现 | 当前结论 |
|---|---|---|
| 普通网页、官方公告、新闻正文 | 复用本机自托管 Firecrawl | S01/S02 已完成服务恢复、受控探针与网页业务链；不代表四平台评论可用 |
| Python 浏览器与解析公共能力 | Playwright 1.63.0 原生 WS；不采用 Scrapling 0.4.15 | 同样本比较见第 6.6 节；当前只有本机机制证据，Linux/远程服务待验 |
| B站视频评论 | HotKey 有界浏览器适配器；参考 opencli 的读取语义与置顶场景 | 候选代码只获取单页，不能直接当作完整采集器 |
| 小红书视频/图文笔记评论 | 评估 xiaohongshu-mcp 的只读详情接口；无法满足会话隔离/分页证据时用 HotKey 浏览器适配器 | 源码有展开评论能力，也有默认跳过回复与文档不一致问题 |
| 抖音视频评论 | 评估 Douyin_TikTok_Download_API 的评论/回复分页接口 | 接口较完整；独立任务、身份池、归档需受控接入，不能原样成为第二个业务系统 |
| 微博含视频博文评论 | HotKey 有界适配器；参考 WeiboSpider 的字段和二级评论路径 | 需补楼中楼继续分页、根博文关联与结构化停止原因 |
| 多平台对照实验 | MediaCrawler | 四平台覆盖较全；许可证限制、运行控制及真实效果尚不能当作产品依赖已确定 |

这是候选排序，不是依赖采购/安装清单。先用同一组评论契约和验收样本比较，再为每个平台固定一个实现及提交版本；不同时部署所有爬虫。免费软件不代表零硬件/维护成本，代码许可证也不代表平台数据访问权限。

## 3. 源码核对中的关键差异

### 3.1 Firecrawl 与 Playwright

官方自托管指南说明：默认栈包含 fetch 与 Playwright 渲染，但两者不支持 page actions / screenshots，这些功能需要额外 Fire-engine；Agent/Browser 等云端能力不能假定随本地安装得到。[S01]

因此 Firecrawl 的 Markdown 可作为网页资料，但不能把登录页/视频页的一段摘要当成评论集合。B站的“展开回复”、小红书评论区滚动等交互由独立平台执行路径处理。Firecrawl 插件本次成功读文档，只证明调研工具可用，不证明用户本机 Firecrawl 已启动。

### 3.2 MediaCrawler：覆盖广，但不要沿用旧缺陷结论

README 列出四平台的指定内容及二级评论能力。许可证明确限定非商业学习研究，不能默认作为 HotKey 产品运行依赖。[S03]

Developer Index 找到 B站置顶评论漏采 Issue #956。GitHub 时间线证实它已由 PR #957 于 **2026-08-11 合并修复**；本次 HEAD 的 client 会合并 `top` / `top_replies` 和普通评论，并有去重及楼中楼调用测试。因此这是必须保留的回归场景，不是当前仍未修复的断言。[S04][S05]

仍需注意：当前代码在 cursor 缺字段/类型不符合时可能按结束处理。HotKey 应映射为协议异常或部分结果，不能照搬成成功结束。第三方测试存在也不等于我们运行过测试或验证过真实网页。

### 3.3 B站：现成读取命令不是可恢复采集服务

opencli 的 `comments` 命令支持视频 BV ID、`--parent` 获取楼中楼和 `--top` 获取置顶，默认 20、最大 50 条；当前实现楼中楼固定 `pn=1`，一级评论也没有继续翻页，结果没有可恢复分页信息。普通模式不合并置顶，展示字段还会压平正文换行。[S16]

适合作为只读功能/字段参考，不直接作为 HotKey 评论服务。自行适配需保留 BV 与实际评论对象身份映射、原始文本、所有 ID 字符串、置顶合并与去重、每个根评论独立分页及停止状态。该项目称其调用为 API，不表示这是获授权的开放平台 API。Nemo2011/bilibili-api 已关停，排除作为新实现的默认依赖。[S17]

### 3.4 小红书：配置默认值会影响样本构成

源码 `feed_detail.go` 使用 Go/Rod 浏览器，不是可直接挂到 Playwright Server 的客户端。详情读取默认 `ClickMoreReplies=false`、根评论加载目标 20、回复展开阈值 10；大于阈值的“更多回复”按钮会被跳过。`load_all_comments=true` 也不证明所有评论已获取。[S07]

**文档与源码冲突：**通过 Firecrawl 读取的 API 文档说 `max_comment_items=0` 为全量、`max_replies_threshold=0` 为不跳过；固定源码的 `normalize()` 却将这两个 `<=0` 值恢复到 20/10。实施以固定源码为准，显式发送有界配置，并验证实际输出；不得把 0 当作全量开关。[S07][S08]

HTTP 参数需放在嵌套的 `comment_config`，MCP 参数名不能原样透传。源码详情页面超时可达 10 分钟，并打印含 `xsec_token` 的详情 URL；接入前需缩短/落实取消上限、去掉敏感 URL 日志。`THE END` 表示根评论区域到底，不证明被跳过的楼中楼完整。令牌只作短期受控访问材料，稳定身份使用 note ID。

如果使用独立服务，只允许登录维护与只读详情所需内部端点，不向 HotKey 暴露发布、评论、点赞等写操作；连接/所有者隔离与撤销必须实测。首次验证可使用一个专用连接实例；未证明隔离前不共用服务 Cookie 文件。

### 3.5 抖音：有评论分页，集成负担也真实存在

v5 源码分别提供视频一级评论和评论回复接口，包含 cursor/count；回复请求同时绑定 comment ID 和作品 URL/aweme ID。解析器保留评论 ID、父 ID、时间、点赞、回复数及置顶信息，并检查 `has_more=true` 却缺少有效 cursor 的异常。一级评论中夹带的 reply previews 仍需独立回复分页。[S10]

项目官方文档确认当前面向 Douyin/TikTok，不包含另三个目标平台。它已有身份池、后台任务、PostgreSQL 归档与控制台：不能只看到名字里的 Download API 就当作无状态 HTTP 库。[S11]

具体适配要求：读取异步任务时，即使 HTTP 200 且外层 success=true，内层任务也可能 failed；`?wait=` 到期仍会返回 202，不能因等待超时重复提交。持久保存上游 task ID，恢复时先查原任务；限定轮询和后台任务寿命，核对固定身份选择与禁用隐式身份轮换/回退的效果。原始归档、缓存及过期清理必须跟随 HotKey 删除要求；如果固定版本不能满足这些边界，就改用受控平台适配器，不以部署整个 v5 系统代替验收。[S11]

### 3.6 微博：一级翻页和楼中楼翻页是两项能力

WeiboSpider 的 `comment.py` 会请求二级评论，但继续翻页分支明确排除 URL 中的 `fetch_level=1`，因此楼中楼只请求一页。输出保留部分 `reply_comment` 信息，却未统一附上根博文和遍历中的根评论身份。[S13]

需要补每个根评论自己的 max_id、父链、终止状态和恢复点。视频是博文的媒体附件，评论应归属于博文 mid，而不是媒体播放 ID；转发、原博文与回复关系分开记录。该文件上次修改远早于 README 更新，不能用仓库“最近更新”认定评论实现持续有效。[S14]

## 4. 对准确性的具体要求

动态获取主要改善新鲜度和可核查性，不自动保证评论内容真实、样本有代表性或覆盖完整。第一版把三类质量分别报告：

| 维度 | 核对方式 | 禁止的推断 |
|---|---|---|
| 内容与关系准确性 | 同一会话/排序/时间窗口下，人工逐条核对冻结的评论 ID、文本、根作品、父/回复对象 | 不用模型猜父节点、补原文或把用户观点当已证实事实 |
| 新鲜度 | 分开保存原站发布时间、本次观察时间、缓存命中/新请求与内容版本时间 | 不用采集时间冒充评论发布时间，不用缓存重读冒充更新 |
| 样本覆盖 | 分别记录根评论和每条回复分支的已见数量、分页终点、跳过/预算/异常原因 | 不以“实采/页面总数”算全站完整率，不以一级结束推断楼中楼结束 |

同 ID 跨轮出现更新只追加观察/版本，不重复建评论。第一轮未再次看到某评论不能推断删除。API 与页面冲突保留各自时间/来源，不自动以最后写入者消解。只保留内容溯源所需公开作者标识；候选输出中的 IP 归属地、完整个人资料、点赞/收藏的个人状态不默认入库。

## 5. 实验与实施出口

先冻结 008 评论契约和四平台样本矩阵；公开网页与会话基础可分别准备。评论第一条纵向链为“提交已知作品 URL → 校验/补作品身份 → 一级评论 → 独立楼中楼分页 → 原子入库 → 用户查看覆盖 → 第二次获取旧帖新回复”。它不依赖先建完全站关键词搜索。

每个平台都需要普通、零评论、至少两页根评论、至少两页楼中楼、置顶/热评重叠、缺父节点、访问失效/异常、二次采集八类样本；真实样本缺失时用受控样本验证机制，但保留相应真实平台出口未完成。验收采用 008 既有六项 AC 与 047 的平台子矩阵，不新增产品需求分母。

第一轮建议平台并发 1，条数/页数/时间/请求有硬上限；具体数值以 037 冻结预算为准。记录 p50/p95 完成耗时、峰值内存、登录状态寿命、平台/解析失败率、人工核对差异、根/回复分页缺口；本轮没有测量值，不预估“稳定支持”或“分钟级全量”。

### 6.3 它具体如何实现采集

| 层 | 固定源码中的机制 | 对 HotKey 的意义 |
|---|---|---|
| 普通 HTTP | `Fetcher` / `AsyncFetcher` 经 `curl_cffi` 请求，可处理浏览器请求特征、Cookie、代理与重试 | 适合静态页面/结构化响应；不是执行 JavaScript 的浏览器，也不是 HTTPX 的同名封装 [S22] |
| 动态浏览器 | `DynamicFetcher` / `AsyncDynamicSession` 使用 Playwright；`page_setup` 在导航前设置监听，`page_action` 在导航后点击/滚动；支持等待元素和匹配 XHR 响应 | 可实现展开评论、获取页面自己加载的数据；动作与平台解析仍要自己编写 [S23] |
| 特殊浏览器处理 | `StealthyFetcher` 使用 Patchright，提供浏览器特征调整等选项 | 属于可选执行方式；项目声明不构成任何目标站可访问证明，本轮未运行该路径 [S23] |
| HTML 解析 | `Selector` 基于 lxml，支持 CSS/XPath、文本和属性提取 | 可复用解析器，保留原生 ID 字符串，再由来源适配器校验业务字段 [S24] |
| 自适应定位 | 首次 `auto_save` 保存命中元素特征到 SQLite；原选择器无结果时，对 DOM 候选的标签、属性、文本和结构计算相似度，默认门槛 40%，取最高匹配 | 可以应对 class/结构变化；不是语义识别。相似节点可能属于别的评论，不能替代身份校验；默认关闭身份字段的自适应替换 [S24] |
| 爬虫调度 | Spider 产生 Request，Scheduler 做优先级与请求指纹去重，Engine 控制全局/域名并发，SessionManager 按 sid 分发；parse 产出 item 或下一条 Request；Checkpoint 保存待抓请求/已见指纹 | 它提供采集框架，但没有 HotKey 的 owner、连接版本、页级事务或评论增量业务；不接管现有 Kafka/PG 执行与恢复 [S25] |

典型链路是 `Request → Session / Fetcher → Response / Selector → 平台 parse → 评论 DTO / 下一页`。浏览器模式已经包含 Playwright，不需要为了采用 Scrapling 再叠加一个功能重复的通用爬虫服务；首选在现有来源适配器内部复用需要的组件，MCP 不是后端集成的必需入口。

浏览器会话可复用标签页和 Cookie；一次性的 `DynamicFetcher.fetch()` 则自行创建/关闭 session。固定实现的 `cdp_url` 调用的是 **`connect_over_cdp()`**，并创建新 context；它不等于 Playwright Server 的 `connect()` WebSocket，也不自动继承浏览器已有默认 context 的登录状态。当前 047 的远程 Playwright 服务方案不能直接把地址填入 `cdp_url` 就宣称兼容。[S23]

平台适配仍须分别处理 B站作品/评论对象、笔记 ID、aweme ID、微博 mid、一级/楼中楼游标、排序与置顶、原生父链、登录失效和终止条件。本次核对的发布源码没有可直接替代这些适配器的四平台评论连接器；“支持动态网站”不等于“已支持四平台评论全量”。

### 6.4 本机受控实验结果

临时 `uv venv --python 3.12`，仅安装 `scrapling[fetchers]==0.4.15`；实际环境为 macOS、Python 3.12.13、Playwright 1.63.0、Patchright 1.63.0、curl-cffi 0.16.3、lxml 6.1.3、Chrome 153.0.8010.53。浏览器使用两个临时独立 profile，目标仅为进程内启动的 loopback HTML/JSON fixture；未连接个人浏览器。异步实验整体截止 45 秒、请求重试 1 次；没有运行平台请求、反检测实验或性能基准。

| 受控场景 | 真实观测 | 工程结论 |
|---|---|---|
| 普通 GET | 返回 200，保留 ID `9007199254740993`；延迟 JS 标记不存在 | 静态请求/解析可用，ID 可保留字符串 |
| 动态页面点击展开 | JS 标记存在，读取到两个回复 ID `9007199254740994` / `9007199254740995` | 浏览器执行与自定义动作机制可用 |
| `page_action` 主动抛异常 | SDK 记录 error，但调用没有抛出，仍返回 200、0 条回复 | 适配器必须记录动作完成/失败并在返回后检查；HTTP 成功不能认定评论成功 |
| 等待不存在元素，350ms 超时 | SDK 记录 timeout，但调用没有抛出，仍返回 200 | 超时需映射失败/partial；同时识别平台明确空状态，不能把无元素统一当零评论 |
| 相同节点改变 class | 自适应找回 `root-1` | 可降低部分 DOM 改版维护成本 |
| 原节点被另一 ID 的相似节点替换 | 自适应返回 `other-comment`，未识别业务身份变化 | 自适应选择器需要稳定 ID、作品及父链后验校验 |
| Cookie 复用与分离 | 同 session 下一请求带 fixture Cookie；新 profile 不带 | 基本会话行为可用；不等于多租户、连接撤销或远程 context 隔离已验收 |
| checkpoint 保存/读取及损坏 | 正常恢复 1 请求/1 指纹；写入损坏 fixture 后 `load()` 返回 None 并记录 starting fresh | 本地文件恢复不提供数据库页级提交保证；不能用它替换业务 checkpoint |
| `robots.txt` 返回 503 | 两次 `can_fetch` 均为 true，仅请求 1 次 robots | 复现发布版问题；采用完整 Spider 前需确认正式修复和我们自己的失败策略 |

实验脚本首次运行在结果 JSON 序列化处失败（将 Selector 对象直接写为 JSON）；改用 `.getall()` 后整段脚本退出 0。表中为修正后的观察，负向场景复现不代表产品验收通过。脚本及原始结果留在本机临时目录 `hotkey-scrapling-review-tfjumrxv`，本节保留关键数值，不能把临时文件当作长期验收产物。

另有两个接入差异：SDK 默认日志会输出完整请求 URL，须接入脱敏；本次依赖解析得到 Playwright/Patchright 1.63.0，而发布 CI 固定 1.62.0/1.62.1，说明只固定 Scrapling 版本不足以复现整套运行环境，正式实施须锁定依赖和浏览器镜像。[S20][S21]

### 6.5 对 HotKey 的采用建议

以下为 2026-09-22 比较前建议；S03-T00 最终结论以第 6.6 节为准。

1. **列为 S03 的优先候选组件**：先对比 `Selector + AsyncDynamicSession` 与直接 Playwright，以同一组 DOM 变化、动作失败、取消和会话样本判断维护成本；暂不加入 HotKey 依赖。既有 HTTPX 普通请求路径不变；若确需 curl_cffi，先作为明确来源 SDK 例外更新 PROJECT/Design，再实施。
2. **Firecrawl 继续负责网页正文，Scrapling 候选负责平台交互/解析。** 二者输出汇入既有 sources 契约，不新建爬虫控制台、第二套队列或任务库。
3. **结果校验成为采用条件**：记录动作是否完成、目标作品是否正确、原生 ID/父链、分页是否推进、是否登录/挑战页；异常不能只写日志后当成功，未知空结果不得推进水位。默认不启用自适应身份匹配、开发响应缓存、账号/代理轮换或挑战求解。
4. **保留 HotKey 的恢复与数据所有权**：Spider 的 pickle checkpoint 与开发模式响应缓存不参与业务持久化。Selector SQLite 保存页面特征，启用时需明确隔离、保留与删除；不把它当无状态功能。平台评论 DTO → content 页级事务 → jobs checkpoint 的既有链路保持唯一。
5. **生产选型出口仍待验证**：固定 Linux 镜像及浏览器依赖；明确 Playwright 原生连接或 CDP 的运行拓扑；证明总截止、取消、连接换版、日志与缓存处理，再完成四平台真实作品、两级分页、合法空/异常及二次采集。当前只完成候选研究与受控机制验证，008/047 AC 均不因此增加。

### 6.6 S03-T00 同样本复核与选型（2026-09-23）

在隔离的 Python 3.12 环境固定 `scrapling[fetchers]==0.4.15`、`playwright==1.63.0`，安装匹配的本机 Chromium，仅访问进程内 loopback HTML fixture。临时 fixture 和 SQLite 在测试结束时清理；没有调用真实平台、启动第二套依赖服务或改动 Firecrawl。以下是本机机制证据，不是 Linux 容器或远程连接验收。

| 场景 | 直接 Playwright | Scrapling 0.4.15 | 选型影响 |
|---|---|---|---|
| 展开及原生大整数 ID | 点击后得到字符串 `9007199254740993` | `AsyncDynamicSession` 得到相同 ID | 两者均可用；平台身份仍须后验校验 |
| 动作异常、缺元素超时 | 异常/截止可由调用方直接处理 | 动作异常和 350ms 等待超时均记录错误但返回 200、空回复 | 不引入会混淆成功与失败的包装层 |
| 总截止/取消 | `asyncio.wait_for` 可取消等待；context 显式关闭 | 200ms 取消可传播，随后同 session 再取页面成功 | 取消可行，但仍需检查 SDK 内部页池和任务资源生命周期 |
| DOM 类名变化及相似节点 | 按 `data-id=root-1` 定位在类名变化前后均命中 1，换为其他 ID 后命中 0 | `Selector` 自适应把 `root-1` 匹配为 `other-comment`，且生成 SQLite 文件 | 身份、父链字段禁用自适应；MVP 不引入特征库 |
| URL 日志、缓存 | 调用方只记来源码/动作阶段，不记 URL/query；同会话重访 `Cache-Control: no-store` fixture 得到新版本 `1→2` | 默认 INFO 输出完整带 query 的请求 URL；同会话重访得到新版本 `3→5`，自适应特征另落 SQLite | 不引入 SDK 默认日志/持久特征或开发响应缓存；`no-store` 样本可刷新，不推断所有缓存策略 |

结论：S03 采用 **Playwright Python 1.63.0 原生 `BrowserType.connect()` WebSocket**，对应固定候选镜像 `mcr.microsoft.com/playwright:v1.63.0-noble`，仅运行一个 Chromium Server。Scrapling 的浏览器层需 CDP `connect_over_cdp()`，不能接原生 Playwright Server WS；`Selector` 的 CSS/XPath 能力不足以抵消新依赖、隐含 SQLite 和错误身份风险，本期均不加入生产依赖。既有 BeautifulSoup/HTTPX 用于普通网页，平台结构化响应和 DOM 解析由各自适配器显式实现。Python 包和镜像构建随 S03-T01 的真实调用者加入，并固定相同版本；不提前引入闲置依赖。T01 必须验证 Linux/worker 远程连接、非 root/sandbox、出站隔离与无公共 WS；T02 再验证任务 context、动作和会话生命周期。`no-store` 四次页面访问中 fixture 总共收到六个 HTTP 请求，不能把一次页面导航当一次出站请求或据此推断平台缓存行为。[Playwright 官方 Docker/远程连接](https://playwright.dev/python/docs/docker)、[BrowserType 协议说明](https://playwright.dev/python/docs/api/class-browsertype)、[Scrapling 固定版本控制器](https://github.com/D4Vinci/Scrapling/blob/333fa22b7a5821194ce66b59b11f4b16a6484f02/scrapling/engines/_browsers/_controllers.py)。
