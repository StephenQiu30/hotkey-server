# Plan 055：证据保留、删除与谱系回归

## 交付边界

承接 NFR-001-101/107 的共享技术回归 `TECH-001-055`，不关闭任何产品 AC。现有 `evidence_retention_policies`、`evidence_resources`、`evidence_deletions`、`evidence_cleanup_targets`、`provenance_manifests`、`provenance_manifest_inputs` 与 MinIO 适配器已有代码；本卡核对保留期、删除状态、引用谱系和 `lifecycle cleanup-once` 的真实依赖行为。051负责备份恢复，055负责对象生命周期与可追溯性；同桶副本不能宣称WORM/独立灾备。无新领域或新服务。

## 文件与 SPEC

| SPEC | 变更与断言 |
|---|---|
| SPEC-055-DATA-001 | 修改 `backend/app/evidence/services.py`、`models.py`、`schemas.py` 和必要时唯一 `backend/database/schema.sql`；保留策略/对象/删除目标/谱系均带owner及版本，已被结果引用的证据不得在清理前丢失可核对身份。旧版本关系不被新结果覆盖，缺对象显式不可用。 |
| SPEC-055-OPS-001 | 修改 `backend/app/cli/commands.py` 的 `lifecycle cleanup-once` 装配和 `evidence/adapters/minio.py`（仅在实际故障需改时）；清理先确定合法到期与引用保护，再持久记录目标、尝试和结果，失败/未知重跑不跳过也不误删，删除后仍保留最小审计与谱系缺口。 |
| SPEC-055-OBS-001 | 用 `backend/tests/integration/test_data_lifecycle.py`、`test_provenance_replay.py`、`backend/tests/unit/test_data_lifecycle.py` 覆盖到期/未到期、引用仍活跃、MinIO失败、重复cleanup、跨owner、重放、源对象缺失和恢复后的对账；日志不含正文/凭据。 |

无新增前端组件/API/生成客户端；如回归发现契约变化，先更新Design与本卡，再从运行OpenAPI生成。保留库Schema变更先消费051同版本恢复证据；跨领域写入保持同一Session，删除对象结果与数据库状态需可重试对账。

## Checklist 与验收

- [ ] CHK-055-001 → DATA-001：先保存引用仍活跃却被删、旧谱系被新版本覆盖、跨owner读取的失败测试。
- [ ] CHK-055-002 → OPS-001：真实隔离PostgreSQL/MinIO执行一次cleanup、故障注入再执行一次，核对删除目标/结果/残余对象和审计。
- [ ] CHK-055-003 → OBS-001：恢复后读取谱系清单、输入哈希和缺失状态；空清单或HTTP成功不等于追溯有效。
- [ ] CHK-055-G0-001：核对046 S03、051恢复版本、现有六表/适配器/CLI及历史受控测试。
- [ ] CHK-055-G1-001：冻结DATA/OPS/OBS的事务、对象删除先后、引用保护和保留期。
- [ ] CHK-055-G2-001：保存CHK-055-001及MinIO失败/重跑的失败摘要。
- [ ] CHK-055-G3-001：仅修复受控失败；保证cleanup幂等、谱系与删除审计可读。
- [ ] CHK-055-G4-001：运行B及上述真实PostgreSQL/MinIO测试，DDL变化重新核对051。
- [ ] CHK-055-G5-001：在隔离真实依赖执行cleanup与谱系回放，不把受控对象当平台采集。
- [ ] CHK-055-G6-001：在共享Acceptance判断TECH-001-055并记录库/桶/对象版本与未验产品范围。

失败时暂停清理入口，保留对象、删除目标和审计，修正后重跑；不得人工清空失败记录冒充完成。
