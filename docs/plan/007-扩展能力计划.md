# 扩展能力计划

状态说明：本轮仅完成文档拆分；本计划为 `planned`，实现暂停、待用户确认恢复。计划状态表示文档/任务准备进度，不表示产品 AC 通过。执行方统一为 Codex 实现与自检、Claude 规划审查/代码审查/真实库全量测试和真实运行验证、用户负责本人账号与决策；Claude 仅在用户授权后提交推送。

## 1. 范围、目标与实施门禁

依据 [PRD 007](../prd/007-扩展能力需求.md)、[总需求 PRD 001](../prd/001-热点舆情监控平台需求.md)、[里程碑 Design 007](../design/007-扩展能力设计.md) 和 [总计划 Plan 001](001-热点舆情监控平台总计划.md)。范围：导出、告警、指定账号和后续来源逐能力独立准入；X 只经官方 API。退出目标：四条 AC 分别以真实输入、权限、渠道/来源准入和对应产品证据通过。

046 S03 门禁已满足：旧 Acceptance 046 全局异常与响应契约验收（已删除，见 Git 历史） 为 `status: passed`，其中 `AC-046-006` 含真实本地上游验证；继续沿用 PROJECT.md 与 AGENTS.md 中的统一错误、响应及请求 ID 契约；旧 Design 046 全局异常与响应契约已删除，见 Git 历史。此项是已完成的公共前置证据，不再作为每张卡待满足依赖。每卡实施前在卡下补精确新增/修改/移动/生成文件、事务所有者、接口/任务状态与失败测试。默认先验证行为失败，再改代码；API 变更遵守运行 OpenAPI → 生成客户端，数据库 DDL 只用 schema.sql 新库原子执行。此处路径为预计范围，不提前创建空模块。

证据等级：代码/受控测试、真实运行、产品验收分别记录；以下“所需证据”是完成卡的要求，“现有证据”不推定 AC 通过。统一证据登记位置为 `docs/acceptance/007-扩展能力验收.md`（通过阶段验收后建立），每卡对应 `EV-007-NNN` 段及原始命令、库、时间窗、查询/截图链接。`CHK-007-G0-001`：开工时引用已通过的 046 验收证据，登记文件/职责、其余依赖和失败用例；`CHK-007-G4-001`：API/OpenAPI/客户端与真实依赖核对；`CHK-007-G6-001`：逐 AC 由 Claude 核对真实运行与产品结论。缺项保留未通过状态。

### 1.1 建议执行顺序与并行约束

`TASK-007-S01-T01` 告警在 M3 事件与 M5 渠道通过后执行；`TASK-007-S04-T01` 导出在 M4 报告存档和权限就绪后执行。二者业务模块不同，可并行准备/实现，但 API 改动和 `frontend/src/api/` 生成须按各自契约串行提交差异。`TASK-007-S02-T01` 指定账号与 `TASK-007-S03-T01` 后续来源都改 `connections/`、`sources/adapters/`、`content/`、Worker，先按来源完成准入/授权契约，再逐来源串行实现与验收；不同来源仅在适配器文件和运行预算隔离后并行取证。X 凭据与月度上限未确认前，仅做设计/受控准备，不发真实请求。

- **实施与验证要点**：只使用已验收事件/内容和已启用 M5 渠道；持久冷却键与幂等，阈值/时间窗/发送结果可查；告警单独核对，不冒充报告推送。
- **执行方**：Codex 实现/自检；Claude 真实告警核对。
- **依赖**：M3 事件；M5 已启用渠道。

- **旧卡**：M6-01、P4-1。

### TASK-007-S02-T01 指定账号追踪

## 4. 退出条件、风险与回退

退出：四条 AC 分别以真实输入、权限、渠道/来源准入和对应产品证据通过。 每个 AC 的受控、真实、产品证据须按 PRD 原文逐项记结果；只有对应证据齐全时才写 Acceptance `passed`。Ruff、mypy、pytest、OpenAPI 漂移、前端类型/构建、真实 PostgreSQL/Redis/Kafka 与浏览器等门禁按实际变更执行并留命令结果，不以静态通过代替真实来源结果。

风险与回退：扩展来源许可、预算或凭据未决，误把热榜/模拟数据当成平台接入；保持来源停用，逐来源评估，X 凭据与月上限未定前无真实请求。
