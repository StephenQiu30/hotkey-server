# Plan 016：事件热度与升温复算

## 范围与需求

依赖 Plan 014/015。[PRD 004](../prd/004-事件与热度需求.md) `FR-004-002` 要求程序综合互动量、帖子数与来源权重计算热度，记录公式版本并标新出现、快速升温；本卡结束 `AC-004-001` 的升温部分。B 站仅 M2 通过后纳入。预计修改 `events/` 计算和持久模型、读取 API/页面及 tests；事务与版本归事件领域。

## SPEC

| ID | 规格 |
|---|---|
| `SPEC-016-DATA-001` | 每次热度计算保存事件成员版本、输入时间窗、平台、互动观察、帖子数、来源权重、公式版本、结果和计算时间。 |
| `SPEC-016-JOB-001` | 人工合并拆分后按新成员版本重算；重复计算幂等，旧口径与旧结果留存并可从输入复算。 |
| `SPEC-016-OBS-001` | 新出现和快速升温分别有可检查阈值、时间窗与计算理由；热榜条目本身不能直接触发事件升温结论。 |

## 验收与 Checklist

Given：真实三平台同事件及前后两窗口互动观察，存在人工修订。When：计算、修订、重算并复查旧版本。Then：热度和升温随版本可复算，旧结论可审计，不因热榜单条命中误触发。

- [ ] `CHK-016-G0-001`：核对 PRD/Design、046 S03、Plan 014/015 和三平台样本。
- [ ] `CHK-016-G1-001`：冻结三项 SPEC 的公式、时间窗、输入缺失、阈值和版本契约。
- [ ] `CHK-016-G2-001`：保存重复计算、缺失互动、跨时区和人工修订后的失败先行测试。
- [ ] `CHK-016-G3-001`：实现版本化计算、重算和审计输出。
- [ ] `CHK-016-G4-001`：运行 Ruff/mypy/pytest、真实 PostgreSQL/Kafka 与 API/前端适用门禁。
- [ ] `CHK-016-G5-001`：用真实三平台事件核对输入、公式与升温结果。
- [ ] `CHK-016-G6-001`：联合 Plan 014/015 对 `AC-004-001` 写完整产品结论。

计算失败只保留未完成状态并可重试，旧结果与原输入不删除；公式变更必须换版本且同步 Design。
