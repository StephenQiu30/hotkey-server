# Plan 001：监控主题与关键词规则

## 1. 问题、范围与依赖

[PRD 002](../prd/002-信息获取主链路需求.md) 的 `FR-002-001` 要求配置任一、全部、排除关键词和来源选择，默认 30 分钟、最短 10 分钟。旧里程碑 Plan 002 没有独立 TASK 承接，主题接口已有代码但主题规则到真实来源的闭环尚未按本需求验收。本卡负责主题的配置、预览、版本与来源选择的受控和真实核对；来源节奏及预算执行见 Plan 002，四来源 72 小时结果见 Plan 009。报告时间、通知对象在现有 DTO 中存在，但报告和推送不属于本卡退出条件。

需求：`BR-002-001/005`、`FR-002-001`；共享 `NFR-001-102/106/107/111`。关联父级 `AC-002-002/004/005` 的主题设置与命中规则部分；父级来源和连续窗口由后续 Plan 关闭。先行条件：四关键词来源预设和 owner 登录可用；046 S03 契约真实通过证据仍有效。未满足来源准入时只做受控预览，不以列表中出现来源证明可采。

修改 `backend/app/monitors/schemas.py`、`services.py`、`models.py` 和 `backend/app/api/routers/monitor_topics.py`；前端修改 `frontend/src/components/monitors/topic-settings-fields.tsx`、`topic-rule-preview.tsx`、`frontend/src/app/monitors/new/components/topic-form.tsx` 与 `[topicId]/components/topic-editor.tsx`。生成 `frontend/src/api/`。主题服务拥有配置和版本事务；来源预设由002、实际运行入口由031交付。

## 2. SPEC

| ID | 规格与可核对结果 |
|---|---|
| `SPEC-001-API-001` | 复核现有 `/api/topics` 创建、读取、预览、更新、暂停/恢复入口；仅 owner 可读写，写入遵守版本冲突、严格输入、类型化成功和稳定 ErrorView；运行 OpenAPI 与生成客户端一致。 |
| `SPEC-001-DATA-001` | `match_any`、`match_all`、`exclude` 与来源选择随主题版本保存；重复更新、归档和克隆不得改变旧 Job 已固定的主题/连接事实；时间存 UTC、页面按 Asia/Shanghai 呈现。 |
| `SPEC-001-JOB-001` | 新主题保持暂停；恢复前核对所选来源支持搜索、已准入且预算可用；主题频率默认 1800 秒、下限 600 秒，实际调度与来源预设取更保守值。 |
| `SPEC-001-UI-001` | 主题设置与规则预览显示可用来源、暂停/待就绪状态和规则命中；加载、空列表、校验失败、权限不足及版本冲突可辨，预览不发起外部请求。 |
| `SPEC-001-SEC-001` | 不把凭据或原始敏感请求写入前端、日志和验收记录；未获准来源不可因选择主题而自动启用。 |

## 3. 本卡验收与 CHECKLIST

Given：owner 已登录，四来源预设状态可读，有包含、排除及边界词样本。When：创建、预览、更新并恢复主题，再观察首个有效来源周期。Then：规则预览与实际命中一致，版本冲突和未准入来源得到明确响应；真实命中内容可追到主题版本与原帖，空或失败仍显示状态和缺口。本卡只证明配置链路，`AC-002-002/004/005` 的 72 小时和逐来源结论仍待后续 Plan。

- [ ] `CHK-001-G0-001` → `FR-002-001`：核对 PRD/Design、046 S03、现有路由与来源预设；记录实际文件清单、接口现状和差距。
- [ ] `CHK-001-G1-001` → `SPEC-001-API-001`、`SPEC-001-DATA-001`、`SPEC-001-JOB-001`、`SPEC-001-UI-001`、`SPEC-001-SEC-001`：冻结主题版本、关键词边界、来源就绪、权限和错误规格；记录接口/DTO/事务所有者。
- [ ] `CHK-001-G2-001` → `AC-002-002/004/005`：先保存包含/排除、空规则、版本冲突、未准入来源、预览无网络与重复恢复的失败或基线用例。
- [ ] `CHK-001-G3-001` → `SPEC-001-API-001`、`SPEC-001-DATA-001`、`SPEC-001-JOB-001`、`SPEC-001-UI-001`、`SPEC-001-SEC-001`：逐规格实现或修复；API 变化后核对运行 OpenAPI 并生成客户端，不手改输出。
- [ ] `CHK-001-G4-001` → `AC-002-002/004/005`：运行适用的 Ruff、mypy、pytest、前端 lint/test/typecheck/build、OpenAPI 漂移与浏览器状态检查；保存命令和版本。
- [ ] `CHK-001-G5-001` → `AC-002-002/004/005`：本卡受控技术交付核对配置保存、刷新、规则预览和版本冲突；真实获准来源的首周期、原帖与空/失败联验由007/035—037提供输入并在009汇合，不作为001交给031前的完成条件。
- [ ] `CHK-001-G6-001` → `AC-002-002/004/005`：人工核对本卡 Given-When-Then；记录局部结论和剩余父级 AC 条件，不以本卡通过关闭父级 AC。

后端在 `backend/` 使用 `uv run ruff check .`、`uv run mypy`、`uv run pytest`；前端在 `frontend/` 使用 `pnpm lint`、`pnpm test`、`pnpm typecheck`、`pnpm build`；API 变化时启动后端后运行 `pnpm openapi:check`。真实运行另记录环境、库、来源、时间窗、预算与原始证据。失败时暂停主题并保留 Job、旧版本和缺口；Schema 如需变化只改唯一 `schema.sql`，在新库原子应用和验证恢复。

完成定义：本卡受控技术交付的SPEC、CHK及配置/规则浏览器路径有证据，形成031可消费的版本化配置；真实首周期在007/035—037/009联验，父级AC另判。

## 具体实现顺序与用例

1. 扩展 `backend/tests/unit/test_monitor_topics.py`：任一OR、全部AND、排除优先；大小写/空白规范化、同组去重、空规则拒绝、中文子串、ASCII整词（AI不能命中daily）。预览与实际采集调用同一 `evaluate_monitor_rules`。
2. 扩展 `backend/tests/integration/test_monitor_topics.py`：POST `/api/topics` 新建暂停主题；PATCH `/{id}` 携带现有version，重复旧version返回409且无部分写；来源必须在已应用search能力集合。设置report_time/notification_targets不应成为采集配置就绪的必填前提。克隆创建新身份与暂停状态，归档后不可恢复受理。
3. 前端新建/修改只用生成DTO；来源不可用解释原因，预览不能联网；追加组件测试覆盖422字段提示、409保留用户输入、401与重复提交。运行B/C/F门禁。
4. 局部退出核对配置保存→刷新一致→规则预览→版本变化。首个真实来源周期必须在031和对应来源Plan通过后联验，不形成001等待031的实现依赖环；该联验由009汇合。
