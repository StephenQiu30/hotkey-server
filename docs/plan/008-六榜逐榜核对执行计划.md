# Plan 008：六榜逐榜核对

## 范围与需求

六榜已有局部代码和开发库快照，但没有逐榜连续 72 小时结论。本卡依据 [PRD 002](../prd/002-信息获取主链路需求.md) `FR-002-006`、`NFR-001-101/102/111`，对 `AC-002-005/008` 的真实路由、快照、排名和命中分析逐项取证；最终桶达标率由 Plan 009 关闭。先行 Plan 003 空榜桶、004 覆盖、005 标注和 006 时效。验证优先，故障出现再明确 `rsshub_hotlist.py`、`hotlist*.py`、API/Web 与 tests 的修复文件。

## SPEC

| ID | 规格 |
|---|---|
| `SPEC-008-DATA-001` | 微博、百度、知乎、B 站热门、36Kr、澎湃六路由各保存来源键、观察时间、快照与实际排名；同来源前后比较 `new/up/down/same`，重扫幂等。 |
| `SPEC-008-DATA-002` | 标题/摘要匹配主题规则；命中条目按 URL 入内容库交 Codex 判相关并留理由，不命中只留快照，不直接创建事件。 |
| `SPEC-008-OBS-001` | 每榜独立核对成功、明确空榜、失败及未确认缺口；来源名称相似或其他榜成功不能替代本榜证据。 |

## 验收与 Checklist

Given：六路由可用且主题/预算已配置。When：逐榜取前后快照、重扫并核对真实命中。Then：每榜的观察、排名、空/失败和分析结果可追溯；无真实快照的榜保持未验收。

- [ ] `CHK-008-G0-001`：核对 PRD/Design、046 S03、六个确切路由和 Plan 003—006 口径。
- [ ] `CHK-008-G1-001`：确定三项 SPEC 的快照键、排序比较、命中与空/失败状态。
- [ ] `CHK-008-G2-001`：受控验证重复快照、空榜、失败、ASCII 词边界及命中/未命中。
- [ ] `CHK-008-G3-001`：只修真实失败路径，记录文件、事务与数据变化；不把诊断快照当产品数据。
- [ ] `CHK-008-G4-001`：运行适用后端、OpenAPI、前端和真实 PostgreSQL/Redis/Kafka 门禁。
- [ ] `CHK-008-G5-001`：六路由逐一保存真实快照、观察时间、排名、原帖及 Codex 标注证据。
- [ ] `CHK-008-G6-001`：按榜记录 `AC-002-005/008` 局部结论；72 小时桶率和时效待 Plan 009。

原始证据记录版本、路由、快照 ID、时间窗和来源失败原因。故障时关闭单榜并保留此前快照与失败桶，不将单榜停用扩散到其他榜。
