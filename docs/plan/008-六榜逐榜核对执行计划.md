# Plan 008：六榜逐榜核对

## 采集实现与验证范围

本卡同时负责修复六榜采集→排名→主题命中→内容发现的缺口，不能只做截图核对。修改 `backend/app/sources/adapters/rsshub_hotlist.py`、`content/hotlist.py`、`hotlist_execution.py`、`connections/presets.py`。六条固定路由逐个核对：weibo/search/hot、baidu/top、zhihu/hot、bilibili/popular/all、36kr/hot-list、thepaper/featured，均经本机RSSHub，来源键不合并。

`SPEC-008-DATA-001` 的完整执行规则：保留最多前100条实际顺序与observed_at；可空published_at不拿观察时间伪填；以同来源前一快照按规范URL比较，rank_delta=旧rank−新rank，正数up、负数down、0same，无旧条目new。标题/摘要复用001规则；只对命中主题的条目按URL身份建内容与发现关系，保留快照/条目反向关联，同文多主题不重复内容。分析由040扫描，未命中不得建分析Job。快照、命中内容、发现、检查点同一业务事务或有显式可重放关联，不允许成功快照永久丢命中内容。

- [ ] CHK-008-101 → DATA/JOB：扩展 `backend/tests/unit/test_hotlist.py`、`test_feed_adapters.py`，覆盖100/101条、排名缺失/重复链接、AI/daily、一个条目多主题、空摘要、同URL不同榜。
- [ ] CHK-008-102 → NFR-001-104：`backend/tests/integration/test_hotlist_persistence.py` 验证重放、事务中断、跨桶重试、命中内容唯一性和未命中只留快照。
- [ ] CHK-008-103 → AC-002-005：六路由分别保存真实两次快照、前后rank、命中/未命中样本、内容ID；040可引用这些ID，十来源分析联验由009/Acceptance汇合。

运行B门禁；039负责历史API和页面；009汇合逐榜≥90%与共同72小时。真实路由失败独立记录，其他五榜成功不能替代；证据归M1 Acceptance Plan008。

六榜调度间隔默认1800秒、允许配置。本卡逐榜核对运行配置、来源版本和快照时间；009开启72小时窗口时记录并冻结实际生效间隔，按该间隔计算每榜应到期桶数。窗口内变更则该窗口作废重开，不将不同间隔快照拼为一个产品分母。

## 范围与需求

六榜已有局部代码和开发库快照，但没有逐榜连续 72 小时结论。本卡依据 [PRD 002](../prd/002-信息获取主链路需求.md) `FR-002-006`、`NFR-001-101/102/111`，对 `AC-002-005` 的真实路由、快照、排名和主题命中内容身份逐项取证；Codex分析由040实施并在009汇合，最终桶达标率由009关闭。先行技术产物为003空榜桶和031/033调度与计量。故障修复仅限本卡来源/热榜文件。

Given：六路由可用且主题/预算已配置。When：逐榜取前后快照、重扫并核对真实命中。Then：每榜的观察、排名、空/失败和分析结果可追溯；无真实快照的榜保持未验收。

- [ ] `CHK-008-G0-001`：核对 PRD/Design、046 S03、六个确切路由和 Plan 003—006 口径。
- [ ] `CHK-008-G1-001`：确定三项 SPEC 的快照键、排序比较、命中与空/失败状态。
- [ ] `CHK-008-G2-001`：受控验证重复快照、空榜、失败、ASCII 词边界及命中/未命中。
- [ ] `CHK-008-G3-001`：只修真实失败路径，记录文件、事务与数据变化；不把诊断快照当产品数据。
- [ ] `CHK-008-G4-001`：运行适用后端、OpenAPI、前端和真实 PostgreSQL/Redis/Kafka 门禁。
- [ ] `CHK-008-G5-001`：六路由逐一保存真实快照、观察时间、排名及命中内容ID；Codex标注由040/009取证。
- [ ] `CHK-008-G6-001`：按榜记录 `AC-002-005` 的快照与命中身份部分；72小时桶率和分析时效待009。
