# Plan 002：来源节奏与预算安全重试

## 1. 问题、范围与依赖

[PRD 002](../prd/002-信息获取主链路需求.md) 的 `FR-002-002` 要求定时/手动采集、暂停与有限重试；连接版本与来源节奏在 Job 领取时固定。旧 `TASK-002-S04-T01` 涉及的 P2-2b/A7b 变更部分仅在 stash，未合入也未计测试通过。本卡先审候选差异和现行代码，再修复调度、重试与预算时钟。主题配置由 Plan 001 承接；空榜桶和覆盖显示分别由 Plan 003/004 承接。

需求：`BR-002-003`、`FR-002-002`、`NFR-001-104/106/112`，关联 `AC-002-002/007` 的节奏、重试与预算部分。先行条件：来源预设、预算账本和 Job/尝试事实可读；046 S03 通过。预计复核 `backend/app/connections/{presets,services}.py`、`backend/app/worker/{scheduler,app}.py`、`backend/app/jobs/{services,execution}.py`、`backend/app/content/discovery_execution.py`、`backend/app/core/config.py` 与相关 tests；只有持久状态确需变化时修改 `backend/database/schema.sql` 及本领域 ORM。M2 的节奏和风控停用使用本卡固定的执行边界。

## 2. SPEC

| ID | 规格与可核对结果 |
|---|---|
| `SPEC-002-DATA-001` | Job 保留首次 `started_at`，每次尝试另记执行时间和采集预算起点；连接版本固定到已领取 Job，后续设置变更只影响新 Job。 |
| `SPEC-002-JOB-001` | 主题频率、来源最短间隔、静默、开关、互斥及预算取更保守有效值；调度不能因重复扫描建立重复业务 Job。 |
| `SPEC-002-JOB-002` | 首次失败两分钟后手动重试在下次真实领取时可开启新采集周期；自动重试、限流重排、租约重放只消耗原周期剩余额度；重复点击幂等。 |
| `SPEC-002-OBS-001` | 分别可核对排队等待、单次尝试和整单历时，以及每日/全局上限、预留和实耗；重试后历史耗时与剩余预算不倒退。 |
| `SPEC-002-SEC-001` | 未启用或风控停用来源不再受理新任务；限流/预算耗尽有明确停止原因，不通过换连接版本重置额度。 |

## 3. 本卡验收与 CHECKLIST

Given：有首次失败、自动重试、限流重排和重复点击的受控 Job，来源与全局预算可核对。When：失败两分钟后人工重试，并执行自动重试、重排及消息重放。Then：人工重试仍可真实采集，其他路径只用剩余额度；旧 Job 的版本与首次时间不变，重复操作不新增额度或重复结果。真实来源运行记录请求数、预算和三个耗时口径。`AC-002-002` 的连续 72 小时由 Plan 009 关闭。

- [ ] `CHK-002-G0-001` → `AC-002-007`：只读审候选 stash 与当前代码；保存差异、依赖、精确文件职责和失败现象，不将 stash 当已实现。
- [ ] `CHK-002-G1-001` → `SPEC-002-DATA-001`、`SPEC-002-JOB-001/002`：确定 Job/attempt/预算周期状态、事务所有者及与 M2 的共享契约。
- [ ] `CHK-002-G2-001` → `AC-002-007`：保存手动、自动、限流、重复点击、租约重放及预算边界的失败先行测试。
- [ ] `CHK-002-G3-001` → `SPEC-002-DATA-001`、`SPEC-002-JOB-001/002`、`SPEC-002-OBS-001`、`SPEC-002-SEC-001`：逐项实现并对账 Job、attempt 和账本；旧连接版本的 Job 不被新预设覆盖。
- [ ] `CHK-002-G4-001` → `AC-002-007`：运行 Ruff、mypy、pytest；在真实 PostgreSQL/Redis/Kafka 下核对调度和消息重放，保存命令与结果。
- [ ] `CHK-002-G5-001` → `AC-002-007`：用真实来源验证首次失败后的手动重试、实际请求/页、入库、预算和停止状态。
- [ ] `CHK-002-G6-001` → `AC-002-002/007`：复算三个耗时与余额，记录本卡产品结论；连续 72 小时留待 Plan 009。

后端在 `backend/` 运行 `uv run ruff check .`、`uv run ruff format --check .`、`uv run mypy`、`uv run pytest`；契约变化再验证运行 OpenAPI 与生成客户端。发布前核对来源开关、静默和每日/全局预算，失败时停用受影响调度，保留 Job、attempt、账本和原窗口；如涉及 DDL，仅在新库原子应用并先验证备份/恢复。证据按受控、真实运行、产品核对分层登记到 M1 验收记录。

完成定义：五项 SPEC 可从持久 Job、attempt、预算和真实来源结果复核，G0—G6 留有证据；任一预算或重试路径不满足时保持未完成。
