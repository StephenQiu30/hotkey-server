## 审核结论

1. 原 6 份里程碑 Plan 各放 3—8 张 TASK，错误地把 Design/Epic 的范围放进 Plan。独立实施、验证和关闭时需要一张 Issue 对应一份 Plan，Epic 范围仍由 Design 承担。
2. 任务卡多为目标、路径范围和一段验证要点；具体 API、数据、任务、界面、安全与运维 SPEC 未逐项写明。`CHK-*-G0/G4/G6-001` 是里程碑共用检查，无法证明单一 Issue 已完成。
3. AC→TASK→EV 已有初步映射，但缺少逐 Issue 的 FR/NFR→SPEC→CHK→证据链。父级 AC 常跨多张卡和连续窗口；任一局部卡通过不能直接关闭父级 AC。
4. `FR-002-001` 的主题配置与规则没有独立 TASK；M4 的 Obsidian 日报、事件/精选帖、周报/主题笔记合在一张卡，依赖和验收时点不同；M6 后续来源的许可、授权和真实准入必须逐来源再拆。
5. 当前实现状态与计划完成状态需分开。已有代码、离线回放、开发库约 4 小时运行均不能代替 M1/M2 的连续 72 小时或产品 AC。

## 单份 Plan 的完成门槛

每份 Plan 须有独立的 `SPEC` 和 `CHK` ID。G0 记录需求、设计、依赖和文件职责；G1 确定 API/数据/任务/界面/安全与运维规格；G2 保存正常、空、边界、失败及权限场景的失败先行证据；G3 实施并逐 SPEC 验证；G4 运行适用的静态、单元、集成、契约及浏览器门禁；G5 在真实依赖或来源取证；G6 对本 Issue 给出产品结论。里程碑 AC 还须核对所有关联 Issue、真实样本和连续窗口，不能由单卡结论推定。

编号和追踪规则见[文档模板](../TEMPLATE.md)与[文档台账](../README.md)。旧 Plan 文件已由逐 Issue Plan 替代，旧原文与提交证据从 Git 历史恢复；旧 TASK 到新 Plan 的逐项对应见上表。未来新增来源或能力应先在对应 Design/Epic 明确边界，再单独建立 Issue Plan。
