# Plan 024：投递身份与未知状态

## 状态机与事务合同

本卡只实现跨渠道可靠投递，不执行真实发送。修改 `backend/app/notifications/models.py`、`schemas.py`、`services.py`、`executor.py`、`worker/app.py`、`worker/scheduler.py` 和schema。复用notification_deliveries唯一(report_id,report_version,target_id)，新增target配置快照/recipient身份与delivery_attempts（开始、调用阶段、响应类别、结束、脱敏error_code）及delivery_resolutions人工处置审计。更改目标收件人须创建新目标身份或显式新版身份，不能把旧投递记录重释为发给新地址。

状态pending→sending须在外部调用前提交；succeeded只在协议明确接受时记录，实际到达用户由025/026验。请求发送前确定失败→failed，最多3次可控尝试；已发送或无法证明未发送→unknown，Worker崩溃/硬截止/消息重放不得自动再次调用渠道。`sending`失去执行租约转unknown并保留尝试阶段。单次外部发送在DB事务外，回写检查当前租约与状态。

人工确认由服务 `resolve_delivery` 承担：仅unknown允许 `confirmed_received`→succeeded或 `confirmed_not_received`→failed，要求证据说明、actor/时间/预期状态并审计；未确认仍unknown。确认未收到后的重新发送是新的显式受理操作，保留原尝试与幂等身份，不能由轮询自动触发。API/UI在044，不在此复制接口。

- [ ] CHK-024-102 → OBS/SEC：扩展 `backend/tests/unit/test_notifications.py` 覆盖明确拒绝、超时不确定、3次上限、人工确认并发/越权/重复操作；unknown路径外部发送计数仍为1。
- [ ] CHK-024-103 → FR-006-002：受控真实PostgreSQL/Kafka执行并检查state/attempt/resolution时间线；不需要真实渠道凭据关闭技术交付。

运行B/C（只在契约被修改时），证据归M5 Acceptance Plan024；父级真实AC等待025/026。原blocked改planned只开放实施计划，飞书暂缓和真实发送授权不变。

## 范围与需求

按 [PRD 006](../prd/006-推送需求.md) FR-006-002、NFR-001-101/104和AC-006-001，本卡交付跨渠道状态机、投递身份与人工确认服务；044承担API/页面，025/026各自承担适配器和真实送达。技术用受控final报告，真实发送需获准渠道。

## SPEC

| ID | 规格 |
|---|---|
| `SPEC-024-DATA-001` | 同报告版本、渠道和接收方唯一投递身份；业务状态与 Outbox 同事务提交，消息重放不重复创建投递。 |
| `SPEC-024-JOB-001` | 发送结果不确定记 unknown 并停止自动重发；确认前不把超时当失败或成功，人工确认后按明确结果推进。 |
| `SPEC-024-SEC-001` | 只有 owner 可查看/确认 unknown；接收方和操作人审计可查，不在日志或客户端暴露凭据。 |
