# Plan 014：事件候选与稳定身份

## 范围与需求

`events` 领域尚未落地。[PRD 004](../prd/004-事件与热度需求.md) `FR-004-001` 要求从真实跨平台相似内容建立事件及代表内容；本卡仅负责候选、确认、稳定身份和重放幂等，为 `AC-004-001` 三平台样本提供基础。先有 M1 `AC-002-002` 真实跨平台样本；B 站仅 M2 通过后纳入。人工修订和热度分别由 Plan 015/016 承接。预计新建 `backend/app/events/` 业务模块、唯一 `schema.sql`、所属 ORM/服务、Worker 装配及 tests，开工前在 Design 确定事务所有者和跨 `content` 只读 DTO。

## SPEC

| ID | 规格 |
|---|---|
| `SPEC-014-DATA-001` | 候选内容身份、来源与时间窗可回溯；相似度或 `pg_trgm` 命中只是候选，不能自动等同事件成立。 |
| `SPEC-014-DATA-002` | 事件有稳定 ID、成员版本、标题、摘要、首次出现时间、平台分布和代表帖/评论引用；同内容重复归并不重复成员。 |
| `SPEC-014-JOB-001` | 模型确认或确定性判定的输入、版本及结果可审计；消息重放与并发候选在同一事务边界幂等。 |

## 验收与 Checklist

Given：M1 已验收的真实三平台同事件样本及不相关近似样本。When：建立候选、确认事件并重放。Then：三平台内容归一事件且不相关候选不误并，成员和证据可回查；父级 AC 还需人工修订和升温。

- [ ] `CHK-014-G0-001`：核对 046 S03、PRD/Design、M1 样本与模块边界。
- [ ] `CHK-014-G1-001`：冻结三项 SPEC、事件键、事务所有者、DDL 与跨领域 DTO。
- [ ] `CHK-014-G2-001`：先验证误并、重复消息、并发归并和来源缺失失败场景。
- [ ] `CHK-014-G3-001`：实施模块、Schema 与任务契约，不在路由直写 SQL。
- [ ] `CHK-014-G4-001`：运行 Ruff/mypy/pytest、真实 PostgreSQL/Kafka 与架构门禁。
- [ ] `CHK-014-G5-001`：真实三平台样本逐内容核对候选、事件 ID、成员与重放。
- [ ] `CHK-014-G6-001`：记录 `AC-004-001` 归并部分，待 Plan 015/016 后判完整结论。

故障时暂停事件候选任务，保留原内容和候选证据，不把热榜快照自动转为事件；DDL 仅在新库原子应用并验证恢复。
