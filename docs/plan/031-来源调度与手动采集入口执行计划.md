# Plan 031：来源调度与手动采集入口

## 交付与边界

交付可从主题页面立即运行、暂停和恢复的采集入口，以及消费版本化来源预设的独立调度器。承接 FR-002-002、NFR-001-104/106/111，贡献 AC-002-002/006。现有 `worker/scheduler.py` 已受理搜索，`POST /api/jobs` 当前以网页任务为主，不能据此认定主题搜索有完整手动入口。重试时钟属于 Plan 032；真实来源适配分别属于 007、035—038。

## 文件与实施规格

| SPEC | 路径与交付 |
|---|---|
| SPEC-031-API-001 | 修改 `backend/app/api/routers/monitor_topics.py`、`monitors/schemas.py`、`api/dependencies.py`；新增 `POST /api/topics/{topic_id}/runs`，operation_id `runMonitorTopic`。输入 `operation_id`、所选 `source_keys`；搜索窗口由服务按当前规则和回看配置固定，不接收任意 URL。200 返回同一次受理，202 返回新受理的 Job ID 列表及逐来源跳过原因；全部未受理时 409，未知主题 404、未登录 401、CSRF 403、非法参数 422。 |
| SPEC-031-JOB-001 | 修改 `monitors/services.py`、`worker/scheduler.py`；每 30 秒领取到期行，在同一事务写 Plan 033 到期事实、Job、Outbox 和 `next_run_at`。关键词间隔取 max(主题间隔, 来源最短间隔)；热榜独立间隔默认1800秒且可配置，M1窗口由008/009冻结；静默按 Asia/Shanghai 判断。关闭、风控、预算不足均保留不受理原因。 |
| SPEC-031-DATA-001 | 确定性 operation ID 包含 owner、主题、来源、能力、到期时刻和配置版本；手动请求使用客户端稳定 operation_id。连接版本在受理时固定，领取时验证执行权；后续配置更新不改旧 Job。两个调度进程竞争同一到期行最多创建一单；重启补记漏窗为缺口，不伪造已请求。 |
| SPEC-031-UI-001 | 修改 `frontend/src/app/monitors/[topicId]/components/topic-editor.tsx`，新增同目录 `topic-run-actions.tsx`；使用生成客户端展示逐来源受理/跳过、预算不足、暂停与待就绪。重复点击保持同一 operation_id，成功后可进入 `/jobs/{jobId}`。不引入新的公共组件层。 |
