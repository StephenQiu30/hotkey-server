## 1. 范围、目标与实施门禁

依据 [PRD 004](../prd/004-事件与热度需求.md)、[总需求 PRD 001](../prd/001-热点舆情监控平台需求.md)、[里程碑 Design 004](../design/004-事件与热度设计.md) 和 [总计划 Plan 001](001-热点舆情监控平台总计划.md)。范围：基于 M1 已验收真实跨平台内容做事件归并、人工修订、热度与升温。B 站只在 M2 通过后纳入。退出目标：真实三个平台同一事件归并为一项，人工合并/拆分、热度公式版本和升温可复核；热榜快照不代替事件。

046 S03 门禁已满足：旧 Acceptance 046 全局异常与响应契约验收（已删除，见 Git 历史） 为 `status: passed`，其中 `AC-046-006` 含真实本地上游验证；继续沿用 PROJECT.md 与 AGENTS.md 中的统一错误、响应及请求 ID 契约；旧 Design 046 全局异常与响应契约已删除，见 Git 历史。此项是已完成的公共前置证据，不再作为每张卡待满足依赖。每卡实施前在卡下补精确新增/修改/移动/生成文件、事务所有者、接口/任务状态与失败测试。默认先验证行为失败，再改代码；API 变更遵守运行 OpenAPI → 生成客户端，数据库 DDL 只用 schema.sql 新库原子执行。此处路径为预计范围，不提前创建空模块。

证据等级：代码/受控测试、真实运行、产品验收分别记录；以下“所需证据”是完成卡的要求，“现有证据”不推定 AC 通过。统一证据登记位置为 `docs/acceptance/004-事件与热度验收.md`（通过阶段验收后建立），每卡对应 `EV-004-NNN` 段及原始命令、库、时间窗、查询/截图链接。`CHK-004-G0-001`：开工时引用已通过的 046 验收证据，登记文件/职责、其余依赖和失败用例；`CHK-004-G4-001`：API/OpenAPI/客户端与真实依赖核对；`CHK-004-G6-001`：逐 AC 由 Claude 核对真实运行与产品结论。缺项保留未通过状态。

`TASK-004-S01-T01` 先建立事件身份、事务和候选持久契约；`TASK-004-S02-T01` 再接人工合并/拆分；`TASK-004-S03-T01` 最后以稳定的事件版本计算热度和升温。S01/S02/S03 都会改 `events/models.py`、`schemas.py`、`services.py`，实现和数据库验证按此顺序串行；S02 的 UI 状态设计可与 S01 的独立候选测试准备并行。M1 已验收的三平台真实样本是最终真实验证前置，M2 仅通过后纳入 B 站。

## 4. 退出条件、风险与回退

退出：真实三个平台同一事件归并为一项，人工合并/拆分、热度公式版本和升温可复核；热榜快照不代替事件。 每个 AC 的受控、真实、产品证据须按 PRD 原文逐项记结果；只有对应证据齐全时才写 Acceptance `passed`。Ruff、mypy、pytest、OpenAPI 漂移、前端类型/构建、真实 PostgreSQL/Redis/Kafka 与浏览器等门禁按实际变更执行并留命令结果，不以静态通过代替真实来源结果。
