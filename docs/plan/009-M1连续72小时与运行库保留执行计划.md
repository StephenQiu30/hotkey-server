# Plan 009：M1 连续 72 小时与运行库保留

## 放行顺序和验收产物

运行库恢复交付移交051，本卡只消费其同库/Schema版本通过证据。原“001—008即齐备”的表述由本卡 `depends_on` 全集替代；007/035/036/037四关键词来源、008六榜、038评论、040分析和034/039/041用户页面必须都有局部证据，才开启观察。

1. 在 `docs/acceptance/002-信息获取主链路验收.md` 写明代码SHA、库身份、Schema哈希、十来源连接/策略版本、主题版本、模型/提示词版本、热榜实际生效的 `hotlist_interval_seconds` 与配置证据、Asia/Shanghai与UTC的共同 `[T0,T1)`（T1=T0+72小时）。T0对齐当次热榜间隔；窗口内冻结该值，每榜按实际间隔计算应到期桶数及≥90%的整数阈值，逐桶记成功、明确空或失败/缺口。仅1800秒时每榜144桶、至少130桶；不能按六榜合计掩盖单榜失败。
2. 起窗前核对首周期真实帖子、四入口、HN10帖/旧帖新回复、重放与人工retry证据。读取使用004 API和006 CLI；运行期间每次重启、预算拒绝、来源停用/恢复保留事件和时间，不改配置追溯旧窗。
3. T1后至少等待最后入库样本60分钟观察成熟，保留T1内入库的完整分母；按006版本复算十来源延迟和分析有效率，样本不足、median不可判定不得写通过。HN十帖不是72小时内每帖必有新回复承诺，真实旧帖新增回复样本单独保留。
4. 验收表每一行AC-002-001—008包含受控证据、真实Job/内容/快照ID、用户操作路径、分子/分母/排除、结论与遗留。任一必需条件失败整体验收未通过；允许来源正常恢复保留缺口，只有指标失败/数据丢失/影响口径的代码配置变更需另起完整窗口，不能静默拼接。

- [ ] CHK-009-101 → 全部AC：逐项核对上述放行清单，不能仅看Plan状态。
- [ ] CHK-009-102 → AC-002-005/008：按T0冻结的实际热榜间隔手工复算逐榜应到期桶及60分钟成熟样本，记录原始ID集合；1800秒才核对144桶/至少130桶。
- [ ] CHK-009-103 → AC-002-006：真实浏览器从来源窗进入原帖/历史榜/评论/标注，再与数据库对账。

本卡不新建业务文件或测试脚本。运行前B/C/F与真实依赖门禁复用相关Issue证据，并确认对应同一待验提交；连续运行只证明本轮范围，不继承开发库约4小时计数。

逐榜分母以T0时记录的实际间隔和首个计划到期相位枚举 `[T0,T1)` 内的due_at，达标桶数为 `ceil(0.9 × 应到期桶数)`；不能只用72小时除以间隔而忽略相位。只有默认1800秒且T0对齐该榜到期点时是144桶/至少130桶。任何榜的间隔或相位在窗内变化均使窗口作废，从新T0重开。

## 范围与依赖

开发库约4小时运行不能充当 [PRD002](../prd/002-信息获取主链路需求.md) 的72小时验收。001—008、031—041的技术/局部真实证据及051同库恢复通过后，在同库同窗核对四关键词来源、六榜和Codex；M2非前置。本卡汇总AC-002-001—008及NFR-002-001，不新增业务功能。需改代码/口径或指标失败时回对应Issue修复，修复后另开完整观察窗。
