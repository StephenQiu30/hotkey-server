# Plan 009：M1 连续 72 小时与运行库保留

## 范围与依赖

开发库约 4 小时运行不能充当 [PRD 002](../prd/002-信息获取主链路需求.md) 的连续 72 小时验收。Plan 001—008 的功能、受控和逐项真实准备先完成，再在同一可保留运行库、同一观察窗核对四关键词来源、六榜和 Codex。M2 非前置。此卡承接 `AC-002-001—008` 的整体产品结论及 `NFR-002-001`；不新增业务功能，发现故障退回对应 Issue 修复后重新确定窗口。

## SPEC

| ID | 规格 |
|---|---|
| `SPEC-009-OPS-001` | 连续运行库先备份并实际验证恢复可读；若建新库，用 `psql -X --set ON_ERROR_STOP=on --single-transaction` 应用完整 Schema，再核对表行数、owner/主外键、内容身份、连接版本、Job/Outbox/offset、预算及引用。迁移不符保留旧库回退。 |
| `SPEC-009-OBS-001` | 固定开始/结束时间与库/代码/来源配置版本；四来源和六榜共用连续 72 小时窗，逐来源记录到期、尝试、真实入口、原帖、入库、预算、延迟和未确认缺口。 |
| `SPEC-009-OBS-002` | 六榜逐榜以应到期的 30 分钟桶为分母，≥90% 有成功快照或明确空榜；其余桶有失败/缺口原因，不得无记录。逐来源正常时段中位延迟 ≤5 分钟。 |
| `SPEC-009-OBS-003` | 十来源真实命中内容的 Codex 相关/不相关及理由可查；正常时段入库后 60 分钟有效结论率 ≥95%，失败、空值、积压计入分母。 |

## 验收与 Checklist

Given：Plan 001—008 的适用技术及逐项真实证据已核对，备份恢复通过。When：固定运行库与时间窗后连续运行 72 小时并逐项复算。Then：`AC-002-001—008` 的受控、真实、产品证据分别齐全，十来源入口与缺口、六榜桶、HN 十帖、预算重试和有效标注达到 PRD 原文；任一缺项只记录未通过，不改分母。

- [ ] `CHK-009-G0-001`：确认 046 S03、Plan 001—008、来源/模型预算与运行库保留门槛；记录版本与基线。
- [ ] `CHK-009-G1-001`：冻结 `SPEC-009-OPS-001` 与三项 OBS 统计口径、排除时段和证据查询。
- [ ] `CHK-009-G2-001`：先用受控故障证明空/失败、未尝试、超时、重放、预算和无效标注不会从分母消失。
- [ ] `CHK-009-G3-001`：执行备份、恢复校验和需要的新库导入对账；不能以开发库重建继承旧证据。
- [ ] `CHK-009-G4-001`：保存后端 Ruff/mypy/pytest、前端 lint/test/typecheck/build、OpenAPI、真实 PostgreSQL/Redis/Kafka 与浏览器门禁。
- [ ] `CHK-009-G5-001`：连续 72 小时采集并保存逐来源/逐榜原始 Job、快照、内容、标注、缺口、预算和运行中断记录。
- [ ] `CHK-009-G6-001`：逐条复核 `AC-002-001—008` 与 `NFR-002-001`，在同号 M1 Acceptance 写每条通过/失败、分母、证据和限制。

若来源风控、库数据丢失或指标失败，停止受影响运行并保存当前证据；修复后另起完整窗口，不拼接旧开发库结果。完成定义仅为 M1 产品 AC 全部有真实通过证据；静态检查或部分来源通过不能代替。
