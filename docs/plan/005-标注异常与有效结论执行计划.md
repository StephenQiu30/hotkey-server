# Plan 005：标注异常与有效结论

## 实施契约与具体用例

当前代码字段为 `relevant`（历史记录称related），已有 `AnnotationStatus.ANNOTATED/UNANALYZED`，不可把UNANALYZED自然允许的null当作已证实存储损坏。修改 `backend/app/analysis/services.py` 的 `resolve_annotation_results`、`persist_results_in_transaction`，`analysis/schemas.py` 与 `models.py`；在 `backend/database/schema.sql` 同步有效行约束。每条异常保存稳定error_code、ai_call_id、内容/主题/提示词版本；没有调用记录为pending、调用失败为failed、输出缺项/无效为invalid，有完整relevant+reason才valid。

`SPEC-005-JOB-001` 的事务由AnalysisService持有：唯一标注键不变，重试可将同键invalid改为valid并保存先前异常审计；旧失败不能覆盖valid，旧主题/内容版本不能写进新版本。任务调度和有限补偿归040，避免循环依赖。

- [ ] CHK-005-101 → DATA/OBS：只读定位三条记录的status/relevant/ai_call_id和输出判定；旧库不存在则记录证据缺失，使用最小脱敏复现，不声称已定位原记录根因。
- [ ] CHK-005-102 → DATA/JOB：`backend/tests/unit/test_analysis_annotations.py` 覆盖null、缺reason、字符串布尔、重复/未知content_version_id、漏返回单条、整批非法、一条失败不影响其余。
- [ ] CHK-005-103 → JOB/OBS：新增 `backend/tests/integration/test_analysis_annotations.py` 验证并发写、失败→有效、有效后重放失败、规则换版与异常计数；实际PostgreSQL约束拒绝伪有效行。

运行B门禁；结果归M1 Acceptance Plan005，真实模型样本由040联验，不能因等待040阻塞本卡技术交付。关联NFR-001-108的质量阈值由017单独验收。

## SPEC

| ID | 规格 |
|---|---|
| `SPEC-005-DATA-001` | 明确相关、明确不相关、待处理、调用失败、模型输出无效和空值状态；只有带理由的有效结论计为已判断。 |
| `SPEC-005-JOB-001` | 同一内容的分析重放和恢复幂等；失败或空结果不得覆盖已有有效结论，真实异常保留可定位原因。 |
| `SPEC-005-OBS-001` | 分别可查询待处理、失败、无效/空值、有效结论数量及版本；抽样只保存脱敏诊断，不记录敏感正文。 |
