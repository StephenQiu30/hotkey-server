# Plan 003：空榜与失败时间桶

## 范围与需求

旧 `TASK-002-S02-T01` 已有六榜快照代码和受控证据，开发库曾记录 `hotlist_36kr` 真实失败桶；尚未证明空榜和失败在连续窗口中可独立复查。本卡只负责时间桶持久事实与状态口径，覆盖查询和六榜产品核对分别由 Plan 004/008 完成。源需求为 [PRD 002](../prd/002-信息获取主链路需求.md) 的 `FR-002-006/007`、`NFR-001-102/104/111`；贡献 `AC-002-005/006`。

先行：Plan 002 的来源节奏和 operation ID 口径确定。预计核对 `backend/app/sources/adapters/rsshub_hotlist.py`、`backend/app/content/{hotlist,hotlist_execution}.py`、`backend/app/worker/scheduler.py`、`backend/app/jobs/` 覆盖聚合及测试；如需新持久字段，同步唯一 `schema.sql` 与 ORM。API 变化才生成客户端。

## SPEC

| ID | 规格 |
|---|---|
| `SPEC-003-DATA-001` | 到期时间桶以来源、能力、固定窗口和 operation ID 唯一定位；成功但空 Feed 写带 `observed_at` 的空快照，缺失排名不伪造为零。 |
| `SPEC-003-DATA-002` | 上游、解析、准入、限流和中途失败不写成功空快照；失败、部分、未尝试及预算截断保留各自原因和缺口。 |
| `SPEC-003-JOB-001` | 同桶重试归原 operation ID；跨桶恢复不覆盖旧失败桶，重复扫描/重放不重复快照或洗掉缺口。 |
| `SPEC-003-OBS-001` | 六榜每个应到期桶可按来源核对到期、尝试、快照、失败和最终状态，分母不因后续成功而缩小。 |

## 验收与 Checklist

Given：准备成功非空、成功空 Feed、上游失败、解析失败、限流、部分页和跨桶恢复样本。When：运行同桶重试及下一桶采集。Then：每桶保留独立终态及原因，成功空榜有真实观察时间，失败不会冒充空榜，旧失败可回查。六榜各自 72 小时达标率仍由 Plan 009 判定。

- [ ] `CHK-003-G0-001`：核对 PRD/Design、046 S03、Plan 002 和现有数据；列精确文件与事务职责。
- [ ] `CHK-003-G1-001`：冻结四项 SPEC 的桶键、状态迁移、快照与错误契约。
- [ ] `CHK-003-G2-001`：先保存空 Feed、失败、重试、跨桶、重复扫描及重放的失败或基线测试。
- [ ] `CHK-003-G3-001`：实现并逐项查询 `SPEC-003-DATA-001/002`、`SPEC-003-JOB-001`、`SPEC-003-OBS-001`，保留原始桶。
- [ ] `CHK-003-G4-001`：运行 `uv run ruff check .`、`uv run mypy`、`uv run pytest`；真实 PostgreSQL/Kafka 核对重放，契约变更核对 OpenAPI。
- [ ] `CHK-003-G5-001`：记录至少一个真实空榜或明确无空榜样本，以及真实失败与恢复；每类结论按实得证据填写。
- [ ] `CHK-003-G6-001`：核对 `AC-002-005/006` 本卡部分并记录未满足的六榜连续窗口条件。

失败时停用受影响榜源，保留原桶、Job、预算及快照；数据库改动仅经备份验证与新库原子应用。所有 Checklist 留命令、库、版本、时间窗和结果；本卡通过不关闭父级 AC。
