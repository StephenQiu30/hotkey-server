# Plan 015：事件人工合并拆分与审计

## 范围与需求

依赖 Plan 014 的事件身份和成员版本。本卡承接 [PRD 004](../prd/004-事件与热度需求.md) `FR-004-001` 中的人工合并/拆分，贡献 `AC-004-001` 的可复核修订；热度重算由 Plan 016 完成。预计修改 `events/` 服务与持久模型、API 资源路由、事件页面和测试；只在明确使用时建立复用组件，接口变更由运行 OpenAPI 生成客户端。

## SPEC

| ID | 规格 |
|---|---|
| `SPEC-015-API-001` | 仅 owner 可发起合并/拆分；提交携带期望版本，版本冲突与无权限返回稳定错误，成功返回新事件版本。 |
| `SPEC-015-DATA-001` | 每次修订记录操作者、时间、前后成员、原内容引用、来源事件与目标事件版本；跨领域原子写共用 Session。 |
| `SPEC-015-UI-001` | 页面可预览影响并确认操作；加载、无候选、失败、权限不足、版本冲突均可辨，旧版本仍可审计。 |

## 验收与 Checklist

Given：真实三平台事件和可分离/可合并的成员样本。When：owner 人工合并、拆分，再用旧版本重复提交和无权限访问。Then：成员与审计前后可追，冲突/权限拒绝无部分写入；升温结论仍待 Plan 016。

- [ ] `CHK-015-G0-001`：核对 046 S03、Plan 014、PRD/Design、现有前端组件和文件职责。
- [ ] `CHK-015-G1-001`：冻结 API、DATA、UI 三项 SPEC 与事务、权限和版本契约。
- [ ] `CHK-015-G2-001`：保存重复提交、版本冲突、无权限和事务回滚失败用例。
- [ ] `CHK-015-G3-001`：实现修订服务、API、页面与审计，不直接改写旧版本。
- [ ] `CHK-015-G4-001`：运行后端、OpenAPI/客户端、前端和真实 PostgreSQL/browser 门禁。
- [ ] `CHK-015-G5-001`：在真实三平台事件上核对合并、拆分和原帖/版本链接。
- [ ] `CHK-015-G6-001`：记录 `AC-004-001` 人工修订部分，待 Plan 016 后整体判定。

失败时停止新修订，保留旧事件版本及审计；不得通过删除历史成员掩盖误并。
