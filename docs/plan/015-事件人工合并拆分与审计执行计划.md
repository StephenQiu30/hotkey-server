# Plan 015：事件人工合并拆分与审计

## 确定的写入契约与用例

新增 `backend/app/events/revisions.py`，修改 `events/models.py`、`schemas.py`、`services.py`、唯一schema；新增 `event_revisions` 记录operation_id、actor、reason、before/after事件及成员版本快照，owner+operation_id唯一。014的event_members保留增删revision；人工排除成员须留决策，后续聚类不能立即加回。

新增 `backend/app/api/routers/events.py` 写端点并登记依赖/路由：POST `/api/events/merge`（mergeEvents），输入target_event_id、source_event_ids、各expected_revision、operation_id、reason；POST `/api/events/{id}/split`（splitEvent），输入selected_content_ids、expected_revision、operation_id、reason。成功200返回新revision/事件ID及受影响成员；401/403身份与CSRF、404不可访问、409版本/归属冲突、422空集合/重复成员/跨topic。合并至少两个不同同主题事件，拆分集合非空且不能取尽原事件成员。

`EventRevisionService` 在一个事务按稳定ID顺序锁全部事件，校验revision→写成员变更→保存旧事件合并去向→审计→递增revision；不在事务内调用模型。重试同operation返回同结果，载荷不同409。事件revision变化由016扫描重算热度，不链式发布另一个业务Job；前端预览和确认移交042。

- [ ] CHK-015-101 → API/DATA：新增 `backend/tests/integration/test_event_revisions.py` 验证并发合并/拆分、重复operation、跨topic/owner、旧版本409、任一步异常整体回滚、旧ID仍能查到去向。
- [ ] CHK-015-102 → DATA：扩展014聚类回归，人工拆出的成员在重放/下一批聚类中不被自动合回；审计前后集合可复算。
- [ ] CHK-015-103 → AC-004-001：真实三平台事件通过API完成合并/拆分并核对原帖和审计，用户界面联验在042汇合，不将042作为本卡实现依赖。

运行B/C门禁，证据归M3 Acceptance Plan015。原UI规格交由042实现；无前端改动时本卡不重复要求页面构建。

## 范围与需求

依赖014事件身份；本卡承接 [PRD 004](../prd/004-事件与热度需求.md) FR-004-001人工修订，交付写API和审计。热度由016、UI由042承担；本卡UI条款是对042的接口要求，完成判断按本卡API/事务用例与真实修订证据。

## SPEC

| ID | 规格 |
|---|---|
| `SPEC-015-API-001` | 仅 owner 可发起合并/拆分；提交携带期望版本，版本冲突与无权限返回稳定错误，成功返回新事件版本。 |
