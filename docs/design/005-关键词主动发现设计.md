# 关键词主动发现设计

日期：2026-09-23。本版只接受 S00 和 S01 的来源无关契约；真实来源的查询语法、原生排序、时间/语言能力、开发者凭据/费用准入及产品 AC 尚无证据。X 已由用户选定官方 API，当前先做离线适配器；没有 App/Token 与账期上限，005 不注册 X Worker 处理器。目标是让首个合法来源处理器沿已有任务、内容和窗口链路交付，而不是另造搜索系统。

## 1. 当前事实、目标与非目标

003 已有 owner 隔离的主题及不可变规则版本，规则组为 match_any、match_all、exclude；预览只做本地子串匹配，不访问来源。004 已有按来源能力分立的连接版本/准入证据，007 已有唯一作品、按 Job 保存的发现关系和不可变观察，009/031/037 已有 Job、Outbox、租约、重试、预算，010 已有显式窗口、缺口和有界游标重扫。002 的 X 官方 API 适配器仅经受控传输测试，`SearchRequest` 已有显式 UTC 时间窗但尚无语言条件；SourcePost 可保留来源返回的 language 标签，但没有实际筛选或持久结果投影。005 的受控执行器已串起多页、逐请求计量和 Job 时间窗透传；Worker 仍只注册网页采集处理器。现有 API/Web 与本机依赖运行，不等于 X 或国内平台搜索可用。

目标是在获准来源上，把手动关键词查询分别按 Latest、Top 有界执行，保存实际请求条件、独立进度、作品/通道/主题依据和明确缺口；后续在同一契约上接定时任务。非目标：全网召回承诺、把本地排序冒充原生热门、自动展开所有别名、缺乏来源证据时开放可受理但无处理器的接口、为了运行受控样本启动第二套依赖。

## 2. 依据、方案与决定

| 依据或方案 | 决定 |
|---|---|
| 现有 Job/Outbox、content_discoveries、coverage_windows | 复用。一个 Job 固定一个来源、通道和实际提交查询；同一作品在不同 Job 下保留不同发现依据，不增平行任务/结果表。 |
| 一张搜索运行表加通道子表 | 现阶段拒绝；先用同一 run_id 关联各 Job，只有真实查询与读取需求证明无法满足时再评估 DDL。 |
| [X Recent Search 官方文档](https://docs.x.com/x-api/posts/search-recent-posts) | 官方 API 支持 recency/relevancy、近 7 天时间边界与分页；2026-09-23 用户决定走此官方路径，但未取得开发者凭据与费用上限，离线适配器不证明来源可用。 |
| [X 查询构造文档](https://docs.x.com/x-api/posts/search/integrate/build-a-query) | 运算符与长度属于具体 API；通用层只保存结构化意图和实际提交值，来源适配器验证并编译，拒绝不支持的条件，不拼接未校验的用户输入。 |
| [X 分页文档](https://docs.x.com/x-api/posts/search/integrate/paginate) 与既有 010 | 游标、页/请求/时间上限分别受控；旧帖夹杂不能证明结束，实际终点须来源能力单独证明。 |

DEC-005-002：通道是执行与预算边界，不是全网排序保证。Latest 与 Top 使用各自 Job/operation_id、进度、停止原因和额度；来源只支持本地排序时明确标记 local，不写 native_top 或已确认覆盖。一次展示合并作品身份，保留两条发现关系和命中主题，不互相覆盖。run_id 仅用于关联这次显式提交，不成为第二业务事实源。

DEC-005-003：实际提交条件与规则版本分开冻结。主题查询受理时读取并锁定当前主题版本，Job 使用 configuration_ref=topic:{id} 和该版本；独立查询用 Job 内不可变输入快照与显式版本 1，不伪造主题。match_any/match_all/exclude 继续负责本地准入；没有明确选择并得到来源语法验证的别名只做本地匹配。每个真正向上游提交的查询都单独留存原文、来源、通道、提交时间、时间/语言条件是否由来源执行及消耗；不根据本地别名推算已经外采。当前 Job scope 只允许有界标量，首片可按每个实际提交查询建 Job，不塞未受约束的数组或另建查询表。查询正文只在 owner 授权的持久数据/结果中可见，不进入日志、Kafka 消息和跨 owner 响应。

DEC-005-004：覆盖证明比结果数更严格。时间/语言无法上游执行时，可保留本地过滤结果，但 010 范围不得标 confirmed；排序意图、上游实际排序和本地排序分别记录。SourcePage 的 COMPLETE/EMPTY、第一页无记录、单条过旧及 UI 的任务成功都不独自证明目标窗口终点。范围部分、取消、预算耗尽、限流和协议错误保留已提交样本及原因，未知尾段不填零。

## 3. 边界、数据与执行流程

来源适配器只负责经准入会话执行、源格式映射、实际排序/时间/语言能力、分页和类型化停止证据，不依赖 ORM/HTTP/Worker。monitors 提供版本化规则和本地匹配；connections 在每次外采前验证当前连接版本、能力、停用/认证状态；jobs 持有 owner/预算/租约/取消、run 关联、通道 Job、检查点和范围；content 在同一最外层事务中保存唯一作品、观察及按 Job 的发现。后续定时调度仍复用 009/031，不新建队列或调度服务。

首个处理器必须先实现受控来源的端到端多页链：受理前校验 owner、当前连接/来源准入、显式 UTC [start,end)、最大页数/请求数/时长与幂等 operation_id；只在 Worker 已注册处理器且来源能力可用时创建可运行 Job/Outbox。现有通用监控任务入口可受理 monitor.collect，但 Worker 尚无对应处理器；它不是 005 的可用发现入口，S01 接入时须消除这条可受理后失败的路径或提供真正处理器。Worker 每页先检查执行权与预算，再访问来源，校验响应，将内容、用量、Job checkpoint/范围页状态同事务提交；Kafka 位点只在既有持久任务状态确定后推进。重放复用 010 的同窗口有限重扫，不把游标摘要还原为原文；请求前计量，失败尝试也计数。任何无处理器、无授权会话或不支持必要查询约束的来源明确拒绝/保持未就绪，不把失败任务留给用户试错。

现有 content_discoveries 的 (owner, content, job) 唯一约束可保存同帖的两通道依据；同帖多主题只复用一个 content_records 实体，主题归属由对应配置版本 Job 的发现依据推导，读取须按 owner/当前保留权限过滤。若后续必须让单个 Job 同时归属多个主题，再以真实用例评估关系表，不在 S00 预建。

## 4. API、界面与状态

S01 的 HTTP 路由名和 DTO 在真实处理器就绪时冻结，候选为 POST /api/discovery-runs、GET /api/discovery-runs/{id} 和分页结果；它们通过 API dependencies 注入领域服务，复用 046 错误、身份/CSRF、009 幂等与生成 OpenAPI 客户端。请求包含主题版本或独立查询快照、来源、两个通道、显式范围和各通道预算；服务端只接受当前准入允许的来源，重复 operation_id 等价返回原 run，异义返回 409。成功/有效空、部分、限流、认证失效、权限拒绝、解析错误逐来源逐通道展示，响应不输出会话或原始游标。

前端归 frontend/src/app/discovery/，使用生成客户端显示实际查询、来源原生/本地排序、时间/语言实际执行位置、样本数与缺口；不显示虚假全网总数/进度百分比。桌面和窄屏覆盖加载、有效空、部分、错误、无权、取消/重试。接口尚未接入处理器时不造可点击但必失败的搜索按钮；现有主题、任务与作品页面继续可用。

## 5. S00 固定受控样本、验证与未决项

内部样本 v1 包含：Latest/Top 一条重合帖及各自独有帖；本地别名与显式上游别名；一页先旧后新、随后有限页结束；相关零互动新帖与无关高互动帖；排除词优先；同帖两个主题版本；有效空与认证/限流/解析/超时分别失败；一来源成功一来源超时；页提交后崩溃/重投、游标循环及无有界终点。断言持久实体/发现/观察、实际查询和用量、独立进度、缺口、owner/撤权/删除；所有来源响应来自受控 fixture，不能作为真实平台证据。

S01 Red/Green 先在 backend/tests/unit/test_keyword_discovery.py 与 backend/tests/integration/test_keyword_discovery.py 固定这些行为，再落首个真实可用来源处理器；复用 backend/app/{monitors,jobs,content,sources} 的既有职责，Worker 注册在 backend/app/worker/app.py。无确需持久关系变化不改 schema.sql；若有 DDL，唯一 SQL/ORM 同批并只在一次性空库验证。HTTP 变化后从运行时 /openapi.json 生成 frontend/src/api/；页面改动需浏览器桌面/窄屏实测。验证门禁为 Ruff、format、mypy、后端全量 pytest、架构测试、前端 test/lint/typecheck/format/build 和 OpenAPI 漂移；实际消息/数据库用现有本机依赖和一次性空库，不新增脚本或 .sh。

语言透传先作为独立必要子片：SourcePost.language 可空、只记录来源提供的标签，X 使用固定 SDK 已解析的 tweet.lang；没有来源值时不猜测语言，且仅透传绝不声称已上游/本地过滤。

S01 查询冻结子片的目录与职责：`backend/app/content/schemas.py` 定义内部、非 HTTP 的显式 UTC 窗口、主查询、已勾选上游别名和两个通道各自页预算；内部安全上限为窗口 30 天、最多 9 个显式别名和每通道每查询 20 页，来源/连接可进一步收紧，均非产品默认值。`backend/app/content/discovery.py` 只生成待受理的来源查询与 `JobAcceptanceInput`，不访问网络或数据库。每个查询 × 通道拥有独立 operation_id，同一 run_id 只作关联；scope 保存原样提交意图、来源、通道、窗口和预算，不将查询或游标写入 Outbox。`backend/tests/unit/test_keyword_discovery.py` 验证拒绝越界输入、未勾选别名不扩词、双通道隔离和重复运行稳定；`backend/tests/integration/test_keyword_discovery.py` 在一次性 PostgreSQL 中验证现有 Job/Outbox 幂等及查询只留在受 owner 保护的 Job scope。此子片不注册 Worker/路由，也不接受实际任务；只有处理器与来源准入均成立时才允许把生成的命令接入受理服务。此处的 scope 是**待提交快照**，不冒充已经向来源发送的实际请求；后续处理器须逐次记录提交和计量。

页数不等于实际外部请求数，因此两个通道还须分别显式提供每查询 1—100 次请求上限，并写入各自的待受理快照；后续处理器需结合 037 的当前更严格预算执行，请求初始化和失败尝试也计量。该上限不证明任何来源能完成对应页数或有界窗口。

S01 页级持久子片继续复用 `content/discovery.py`、`jobs/services.py` 的 010 游标/窗口和 `content/services.py` 的现有作品/发现事务入口，不新增表、队列或脚本。规划命令补“配置引用 + 原始查询”的 SHA-256 与配置版本到 scope，作为覆盖范围的稳定身份；同词的不同主题不得共用范围。只有完整的当前 Job/租约、连接版本、来源及保留政策均通过时，才可提交一页。来源返回的发布日期按显式 UTC `[start,end)` 做本地筛选；页内同帖只保存一次，但不同通道保留各自 Job 发现。原始游标只在当前进程继续下一页，checkpoint 仅保留摘要；作品、去重后的累计数量、checkpoint、窗口页状态同一 PostgreSQL 事务提交。来源没有可证明的上游有界时间/排序及终点证据时，即便响应 `COMPLETE/EMPTY`，窗口仍是 `partial/unverified_terminal`。本子片用受控来源页和合法测试政策验证落库、旧检查点拒绝、连接停用与整页回滚，不注册外采处理器或 API；网络请求预算、实际提交记录与真实来源准入仍须在后续多页处理器中完成。

S01 受控多页编排子片位于 `content/discovery_execution.py`，继续使用上述快照与页提交，不另建队列或表。`KeywordRequestMeter` 作为来源适配器的每次真实 HTTP 尝试前回调：核对当前 Job 租约、连接版本、来源/保留政策、组件资格和分层请求预算，预留用量并增加 Job 请求数；请求初始化与失败尝试同样计数。每页的实际 `request_count` 必须与已预留次数一致，作品、发现、checkpoint、范围和该页用量结算同事务提交；异常后保守记失败并扣费，重入恢复遗留尝试及全任务请求上限。受控执行器在重启时只按游标摘要有限重扫，来源不证明时间范围终点时仍为 `partial`。每个 Job 将 1—90 秒总时长冻结到 scope，以首次开始时间为截止基准，重入和延期不重置；请求前和页间检查截止，未请求即到期或取消也留下零页 `partial` 缺口。零成功样本的认证/拒绝/协议等停止映射为明确失败，不伪装成部分成功；429/上游暂时失败只在页数、一次重扫、请求数、重试次数和原截止均允许时沿用 Job/Outbox 延期。已发请求遇取消仍记失败用量，尚未提交内容不落库。当前仅以测试适配器验证，不在 Worker 注册、不开放 HTTP，也不提供 X 会话；真实来源的查询/排序/时间/语言能力、授权及结果读取仍是接入门禁。

适配器在未返回 `SourcePage` 前抛出传输或协议异常时，请求尝试仍按失败结算，当前窗口记录零页 `partial/upstream_error` 或 `partial/protocol_error`，不推进 checkpoint、内容和确认水位。配置/政策拒绝不冒充来源页；取消优先记录 `cancelled`。这是无页失败的显式缺口，不把请求失败伪装成已采样页面；同一 Job 后续重试仍从原范围起点执行。

S01 内部时间窗透传子片：`KeywordDiscoveryExecutor` 从不可变 Job scope 构造经 010 验证的窗口后，每页 `SearchRequest` 必须带相同的 `starts_at`/`ends_at`；无论 Latest/Top、续页或重扫都不能退化成无界查询。只修改现有执行器和受控 PostgreSQL 集成测试，不新增适配器、HTTP、Worker、表或脚本。002 的 X 适配器已支持近 7 天显式时间参数，但 005 的来源请求计量接口尚不能装配其付费授权/结算回调；此透传不表示 X 已可用于业务、窗口终点已被证明或 005 S01 产品门禁已关闭。

OPEN-005-001 仍开放：7 天及每通道 50 条仅为 PRD 建议，不作为无来源证据的默认。S01 手动运行必须显式给出有界范围和预算；首个真实来源上线及定时任务前，按获授权的关键词/新旧/Top 样本校准默认窗口、通道最低份额、来源请求上限和费用/许可。X 官方适配器仅离线开发，无 App/Token、账期硬上限及 037 付费门禁；国内平台搜索无正式适配器，均不能标记 ready 或计入 AC-005-001—006。

## 6. 安全、降级、迁移与回退

只读取公开或获授权资料，来源访问条款/预算先于业务功能；代理仅允许已核准目标，现有 HotKey 专用代理当前只放行测试域名。日志只记安全的 run/job ID、来源能力、通道、状态、请求数和停止原因；不记原始查询、URL、Cookie、Token、游标或正文。401/403 停止并要求重新授权，不轮换账号绕过；429 按既有有限延期，不无界重试。来源失败只使该来源/通道部分，不擦除已保存结果。

若无 DDL，本片无需迁移。后续增表需走 PROJECT 的备份、新空库完整 schema 与导入核对，不对现有库直接重放。回退先停关键词新受理和处理器，保留 Job、作品和缺口可读；核对在途租约/Outbox 后才切换二进制，不删除历史资料或持久卷。S00 仅设计与环境证据，不创建 Acceptance，也不宣称产品已验收。
