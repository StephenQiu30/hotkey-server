# 事件与热度设计

本 Design 是 M3 Epic，从 [总设计 001 v3.2](001-热点舆情监控平台总体设计.md) 正向拆解；总设计现为 v4.0。需求为 [PRD 004](../prd/004-事件与热度需求.md)，逐 Issue 执行计划见 [Plan 014—016、042](../plan/README.md)。本文中的“已有”仅表示代码或指定运行证据，不代表产品验收。

## 1. 范围与不包含

M3 对已验收内容做跨平台事件归并、热度快照与升温判定，支持人工合并/拆分。不把热榜命中直接当事件；M2 未通过时不纳入 B 站本人账号数据；报告区块、事件笔记与渠道送达由 M4/M5 承接。现行需求与计划分别见 [PRD 004](../prd/004-事件与热度需求.md) 和 [Plan 014—016、042](../plan/README.md)。

## 2. 当前能力与证据分层

`events` 尚无业务实现；M1 热榜与内容入库已有局部开发库记录，只能作未来输入，不能证明事件归并。当前没有受控事件状态机测试、真实三平台同事件样本或产品验收。

## 3. 架构与数据流

- 不用向量：候选分组用 `pg_trgm` 标题相似度（初值 ≥ 0.4）+ 共同命中关键词 + 72 小时时间窗；每个候选组交给 Codex 确认是否同一事件，并生成事件标题和摘要。
- 热度 = Σ log(1 + 赞 + 2×评 + 3×转 + 0.01×浏览) × 来源权重 + 帖子数加成；公式版本写入快照。新出现：首个成员落在窗口内；升温：近 3 小时热度增量 ≥ 前 24 小时平均每 3 小时增量的 3 倍。
- 人工合并/拆分优先，自动聚类不覆盖。

`content` 提供已验收内容的身份/版本、代表评论和相关性引用，`events` 拥有事件候选、成员、人工修订和热度计算；`ai` 仅对候选归并与摘要作结构化判断。独立调度扫表创建 `events.cluster` Job；`jobs` 管执行、幂等和预算，`events` 在自身事务中保存事实和快照。报告/知识库可在 M3 验收后消费事件只读 DTO，并在报告引用热度时附公式版本和计算口径，不反向写事件。

## 4. 领域、数据与状态

以下为待实现的数据设计，具体字段、约束及测试由 Plan014—016 承接：

- `events`：owner、topic、revision、标题/摘要、first_seen_at、active/merged 与 merged_into_id；`event_members` 固定内容身份/版本、来源、加入/移除修订及自动/人工来源，同一 owner/topic/content 只属于一个当前事件。
- `event_candidates`：以排序后的内容版本集合、窗口、prompt_version 生成唯一指纹；状态 pending/confirmed/rejected/failed，保留 ai_call_id 与错误。模型调用在数据库事务外，提交前锁事件并检查修订，人工变更后旧模型结果不得覆盖。
- `event_revisions`：operation_id 唯一，记录操作者、原因、操作前后成员与事件修订；合并/拆分在同一事务按稳定顺序锁行，保留人工排除约束。
- `event_heat_snapshots`：唯一(event_id,event_revision,window_end,formula_version)，固定输入观测、缺失掩码与分项。重算产生新快照，不改历史证据。

新增模型进入唯一 `backend/database/schema.sql` 和 metadata 注册；保留运行库的变更先满足 Plan051，不就地运行完整 Schema。

## 5. 接口与页面

Plan042 交付 `GET /api/events`、`/{id}`、`/{id}/members`、`/{id}/heat` 及列表/详情/修订页面；Plan015 交付 `POST /api/events/merge` 与 `/{id}/split`，输入 operation_id 和 expected_revision，成功200、冲突409、越权/不可见404，写入需CSRF。静态 merge 路由优先于动态ID。接口复用统一 DTO、游标和 ErrorView，由运行 OpenAPI 生成客户端。Web 显示正常、空、加载、错误、无权限与待归并状态，不把无事件等同来源无内容。事件完整产品验收须包含042的可操作页面。

## 6. 调度、执行与截止

`events.cluster` 每30分钟扫描，初始每候选组最多20成员、模型输入24,000字符、Job硬截止600秒；输入不足保留待归并，超过上限分批并保留剩余候选。按候选版本/窗口幂等，提交时检查人工修订。`events.heat` 每30分钟计算一次，硬截止60秒，按事件修订/窗口/公式幂等。上述为工程初始保护值，真实样本校准须更新设计与公式版本，不代表性能已通过。

公式初版固定自然对数：Σ ln(1+赞+2×评+3×转+0.01×浏览)×来源权重 + ln(1+帖子数)，来源权重初值均为1。缺失量只在分项运算中贡献0并保留缺失标记；所有互动指标未知时热度为null，不能对外显示为0。升温比较近3小时增量与此前24小时的8个3小时增量均值；基线不足、均值≤0、窗口缺口或修订不可比返回 insufficient，不能制造升温结论。当前增量必须>0且≥基线3倍。参数校准和缺失输入影响随真实三平台验收记录。

## 7. 失败语义与恢复

模型不可用或候选证据不足时保留未归并/待复核状态，不能生成确定事件。失败 Job 保留输入版本、原因和可重放位置；重试不得覆盖人工合并/拆分，按版本冲突拒绝或重新候选。来源缺口、标注异常应随事件输入审计传播；热度不可把未知量默认为零覆盖。

## 8. 安全、风控与可观测

仅处理已有授权的来源数据；人工操作需 owner 授权和审计。模型输入最小化且外部内容按不可信文本处理。记录候选数、模型确认/拒绝、人工修订、公式版本、窗口、输入缺口、重放/冲突和预算；不记录敏感正文到通用日志。

## 9. 验收设计要点

用已验收的真实三平台同事件样本核对事件成员、代表内容、来源分布、人工合并/拆分和升温；单条热榜命中、模型输出或内部样本均不能替代真实产品结论。先受控验证幂等、冲突、公式与失败，再作真实运行和人工复核。

## 10. 决策、风险与对照

沿用 DEC-001-203/207/208/212/215；DEC-001-215 已规定热榜命中先入内容再分析，事件后验。`pg_trgm` 候选阈值 0.4、72 小时窗口和热度公式来自原总设计 v3.2 §12，实施前需在真实样本校准；此处不新建 DEC-004-xxx。风险为跨平台误并、人工改动被重算覆盖及热度量纲偏差。对应原总设计 v3.2 §12、§8 事件输入及 §13 任务类型；历史来源 旧 Design 028 可追溯与可复现（已删除，见 Git 历史）。
