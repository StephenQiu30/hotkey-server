# 备份与恢复设计

日期：2026-09-21，S02 修订于 2026-09-23、2026-09-25。S01 在现有管理 CLI 中生成受控候选备份，以同一 PostgreSQL 快照导出数据库、表计数和证据对象引用，并核对 MinIO 引用是否存在；S02 在临时隔离数据库中验证恢复，并把快照引用的现存 MinIO 内容流式归档、校验后在临时对象名前缀验证回读。候选备份不等于完整已验证备份；不替换最后有效备份、不配置自动调度、不宣称独立故障域，也不通过产品 Acceptance。

## 1. 当前事实与问题

- PostgreSQL 是唯一业务事实源，当前唯一 DDL 为 `backend/database/schema.sql`；Redis 是可重建状态，Kafka 保存执行消息但不替代业务事实。
- `evidence_resources.cleanup_targets` 已登记 MinIO 对象引用，删除记录由 `evidence_deletions` 和 `evidence_cleanup_targets` 持有；备份逻辑不再建立第二份证据关系模型。
- 当前没有备份命令、清单格式、数据库一致性点或归档校验入口。仅复制文件或执行一次 `pg_dump` 无法说明表计数、证据缺失、秘密边界和恢复状态。
- 原 Plan 的独立一次性验证脚本候选路径与项目目录规范冲突，本设计删除该方案，不创建 `scripts/` 或 `.sh` 文件。

## 2. S01 目标与非目标

### 2.1 目标

1. 复用 `python -m cli` 增加仅本机维护者可执行的 `backup create-candidate` 命令；目标根目录必须显式传入，不写入仓库或隐式默认目录。
2. 使用 PostgreSQL 导出的同步快照，让 `pg_dump` custom-format 归档、19 张业务表的行数和证据对象引用基于同一数据库视图。
3. 生成严格 `manifest.json`，包含格式版本、备份 ID、一致性时刻、数据库/客户端版本、schema 和归档 SHA-256、归档字节数、逐表行数、证据对象存在性及明确覆盖边界。
4. 归档先通过 `pg_restore --list` 可读性检查；目录权限为 `0700`、文件为 `0600`。数据库和 MinIO 凭据值不进入参数、日志、清单或备份目录。
5. 输出状态固定为 `candidate`、`restore_verified=false`、`evidence_mode=inventory_only`，防止技术切片被误报为可恢复的完整备份。

### 2.2 非目标

- S01 不执行 `pg_restore`、隔离环境恢复、B0 RPO/RTO、坏备份替换保护、删除重放或恢复后调度冻结；这些属于 S02/S03。
- S01 不复制 MinIO 内容，因此候选目录不是跨 PostgreSQL 与对象存储故障域的完整备份。缺失引用必须列出，但不能因此伪造成功。
- 不备份 Redis 缓存、Kafka topic/offset、运行中 lease 或本机 `.env`；恢复凭据由备份之外的受控渠道提供。
- 不新增 HTTP、页面、后台任务、数据库表、第三方依赖、Compose 服务或第二套环境。

## 3. 一手资料与复用结论

| 依据 | 采用结论 |
|---|---|
| [PostgreSQL `pg_dump`](https://www.postgresql.org/docs/18/app-pgdump.html) | 直接复用官方 custom format；它支持 `pg_restore` 检查/恢复和 `--snapshot`，不自造 SQL 导出格式。 |
| [PostgreSQL 同步快照](https://www.postgresql.org/docs/18/functions-admin.html#FUNCTIONS-SNAPSHOT-SYNCHRONIZATION) | 导出事务保持打开时，表计数、证据引用与 `pg_dump` 导入同一 snapshot，避免分别启动事务造成视图漂移。 |
| [PostgreSQL password file](https://www.postgresql.org/docs/18/libpq-pgpass.html) | 不把数据库 URL/密码放入进程参数，也不使用官方不建议的 `PGPASSWORD`；只创建权限 `0600` 的临时 passfile，子进程结束即删除。 |
| [PostgreSQL `pg_restore`](https://www.postgresql.org/docs/18/app-pgrestore.html) | S01 用 `--list` 检查 custom archive 可解析；真正恢复、`--exit-on-error` 和目标库核对留到 S02。 |
| [MinIO Python SDK 7.2.20 API](https://github.com/minio/minio-py/blob/7.2.20/docs/API.md) | 复用锁定版本的 `stat_object`、`get_object`、`fput_object`、`remove_object`；读取按对象版本或 `If-Match` 条件约束，并按 SDK 要求关闭/释放响应；不增加 `mc` 或另一套客户端。 |

`pg_dump` 文档也明确说明常规生产备份可能需要更完整的物理/PITR 策略。HotKey 当前 B0、单数据库与“先具备最小恢复路径”的阶段采用逻辑 custom archive；该决定不承诺未来容量下仍是最终策略。

## 4. 包格式与一致性边界

每次运行只在显式目标根目录内创建一个新目录：

```text
hotkey-backup-<UTC时间>-<backup_id>/
├── database.dump
├── evidence/                 # 仅存现存且未完成删除的引用对象
│   └── <sha256-key>.blob
└── manifest.json
```

- 服务先在同一目标根目录建立唯一临时目录；只有归档、清单和校验全部成功才原子改名为最终目录。失败只删除本次创建的临时目录，不覆盖或清理任何既有备份。
- PostgreSQL 事务使用 `REPEATABLE READ READ ONLY`，先取得 `pg_export_snapshot()` 和 `transaction_timestamp()`；同一事务读取表计数和证据引用，`pg_dump --snapshot` 在事务结束前完成。
- `database.dump` 使用 custom format、`--no-owner` 和 `--no-acl`。角色、数据库级秘密及主机配置不在归档中，恢复前由目标环境重新提供。
- `schema_sha256` 对唯一 `database/schema.sql` 计算；`archive_sha256` 对实际归档计算。S01 只证明文件未在生成后静默变化及格式可读，不证明业务恢复正确。
- MinIO 对象基于数据库 snapshot 中的 `minio_object` 引用逐项核对。已完成删除的引用标记 `excluded_deleted`，其他引用标记 `present` 或 `missing`；不把 ETag 冒充内容 SHA-256。
- S02 为每个 `present` 引用将对象内容以流方式复制到候选目录，清单记录相对归档路径和独立计算的 SHA-256/字节数。归档文件名仅由稳定资源记录与对象引用摘要派生，不把不可信对象名用作本地路径。生成目录/文件权限仍为 `0700/0600`。
- 下载优先固定 `version_id`；对象无版本号时向 MinIO 发送 `If-Match` ETag 条件，避免清单读取与归档下载之间静默换版。条件不满足、内容长度不符或任何对象读取失败时，候选不发布，临时目录清理。
- `missing` 和已完成删除的引用不包含对象内容；内容归档候选须显式保留这些缺口，不能因其他对象成功而宣称完整。

## 5. 目录与职责

| 路径 | 职责 |
|---|---|
| `backend/app/backups/schemas.py` | 候选备份、数据库归档、表计数和证据对象清单 DTO；不依赖 ORM/SDK。 |
| `backend/app/backups/services.py` | 创建目录、控制快照、组合清单、校验覆盖和原子发布；不读取 HTTP 上下文。 |
| `backend/app/backups/adapters/postgres.py` | 调用系统 `pg_dump`/`pg_restore`，创建并销毁临时 passfile，返回脱敏版本/结果。 |
| `backend/app/backups/adapters/minio.py` | 将现有 MinIO `stat_object` 映射为存在/缺失元数据；对快照引用执行版本/ETag 约束的流式归档，并在临时前缀回读校验。 |
| `backend/app/evidence/schemas.py`、`services.py` | 由证据领域提供 snapshot 内的 MinIO 引用和删除状态，备份领域不直接导入证据 ORM。 |
| `backend/app/cli/commands.py` | 装配既有 Settings、Engine、MinIO SDK 和备份 Service；只输出 ID、路径和非敏感摘要。 |
| `backend/tests/unit/test_backup_restore.py` | 清单严格性、秘密隔离、临时凭据和失败不发布规则。 |
| `backend/tests/integration/test_backup_restore.py` | 复用现有隔离 PostgreSQL、MinIO 测试凭据和本机 18.4 官方工具，分别验证真实 snapshot/数据库恢复及 MinIO 内容归档/临时回读；MinIO 样本限于随机测试前缀并清理本次创建的对象版本。 |

不修改 DDL、OpenAPI、生成客户端、前端或根 Compose。新增 `backups` 是当前切片实际使用的运维领域，不创建空模块。

## 6. 安全、失败与可观察结果

- 命令行参数、清单和标准输出都不含数据库 URL、密码、MinIO access/secret key 或 `.env` 内容。临时 passfile 和最终文件使用最小权限；子进程只取得必要的 libpq 连接变量。
- 目标根目录不存在、不可写或不是目录时直接拒绝；最终目录永不复用。失败不留下可被误认的最终目录。
- `pg_dump`/`pg_restore` 超时、版本不兼容、MinIO 鉴权失败或未知对象存储错误均失败退出，只返回稳定阶段和工具退出码，不回显 stderr 中的潜在连接信息。
- MinIO 单个业务对象不存在不是命令崩溃条件，而是清单中的 `missing`；这使维护者能看到候选备份的真实缺口。无法访问 bucket 或无法判断状态则整个候选生成失败。
- CLI 是维护入口，不新增普通用户下载路径。S02/S03 在恢复资料开放前仍需验证当前权限、删除和暂停调度。

## 7. 验证与未决项

Red 先证明 `backups` 契约不存在。Green 至少覆盖：

1. 单元测试证明数据库密码只短暂进入权限 `0600` 的 passfile，未进入 argv/清单，失败后临时材料消失。
2. 真实 PostgreSQL 18.4 生成 custom archive，`pg_restore --list` 可读；清单含 19 张表、同一 snapshot 时间、schema/归档 SHA-256，目录/文件权限正确。
3. 真实 MinIO bucket 可查询；对象引用存在、缺失和已删除三态由受控样本或隔离适配器验证。
4. 全量后端、架构和静态门禁通过，测试后现有数据库与 bucket 不留样本。

`OPEN-032-001` 在 S01 不关闭：独立保存介质、加密材料恢复方式和最终保留天数需要用户提供自有资源与维护责任人。S01 的显式本地目标只用于建立候选包契约，不自动选择生产备份位置。S02 才处理损坏保护和真实恢复，S03 处理删除/撤权重放与完整业务核对，S04 执行产品 AC。032 保持 `in_progress`、产品 AC 0/6，不建立 Acceptance。

## 8. S02 设计冻结（2026-09-23、2026-09-25）

S02 的已验证数据库子片负责 PostgreSQL 候选包的损坏保护与真实隔离恢复；2026-09-25 增加 MinIO 内容子片，归档快照引用的现存对象并在临时随机前缀回读核验。两者都不把候选包晋升为“完整已验证备份”，也不替代 S03 的删除/撤权重放、独立介质和 B0 验收。

1. 复用现有 `backup` 管理 CLI，新增显式候选目录和隔离连接配置的验证入口。连接 URL 只从维护者指定的环境变量读取，不进入 argv/日志；要求隔离连接指向与业务库不同的数据库。进程只在该 PostgreSQL 服务中创建唯一随机的空临时库，恢复结束后删除；不新启 PostgreSQL、MinIO 或其他依赖。
2. 恢复前严格解析 `manifest.json`，核对受控目录名、格式、schema SHA-256、归档大小/SHA-256、普通文件和权限；使用官方 `pg_restore --list` 检查可读性。损坏或不匹配直接拒绝，既有候选目录和业务库均不变。
3. `pg_restore --dbname=<临时库名> --single-transaction --no-owner --no-acl` 在隔离库中真实执行；不使用 `--clean` 或 `--create`，避免归档中的数据库名影响目标。官方文档确认单事务模式失败即回滚，并隐含 `--exit-on-error`：[pg_restore](https://www.postgresql.org/docs/18/app-pgrestore.html)。恢复后对清单中的逐表计数进行核对，完成核心读取和事务内回滚的本地写入探针。
4. 计时从候选校验开始，到隔离库恢复、核心读/写及核对完成为止；输出耗时和结果，不将其冒充故障 RPO 或 B0 RTO。失败阶段必须可见且不泄漏连接信息；只允许删除本次生成且已确认身份的临时库，清理失败时明确报出临时库名供维护者处理。
5. Red 覆盖损坏的新候选不会改写既有候选、损坏清单/归档拒绝恢复、同库隔离拒绝；Green 使用现有 PostgreSQL 服务的隔离 QA 库与真实归档验证数据可读、行数一致、受控写入成功、临时库回收和计时。不得创建散落脚本或 `.sh`。
6. MinIO 内容沿用同一 `hotkey-backup.v1` 清单协议：老的 `inventory_only` 候选仍可读取；新候选将现存对象标记为 `content_archived` 并记载 `archive_path`、`content_sha256`。严格检查相对路径仅允许 `evidence/<64 位十六进制摘要>.blob`，归档文件必须是普通文件、权限 `0600` 且大小/摘要匹配；删除完成或对象缺失的行不得引用归档文件。
7. 使用已锁定的 MinIO Python SDK `7.2.20`，不依赖最新版 API。来源读取按已记录的 version ID 固定版本；无 version ID 时通过该版本支持的 `request_headers` 传入 `If-Match`。临时回读使用随机且不含业务对象名的前缀，验证上传后的对象大小和重新读取 SHA-256，再仅移除本次 PUT 返回的版本；非版本化对象只移除本次创建的唯一随机键。清理失败则验证失败并暴露非敏感临时前缀供维护，不碰旧对象。
8. 此对象验证复用同一 MinIO 服务和 bucket 下的隔离随机前缀，不创建 bucket/服务；仅证明对象可从候选归档回读到 MinIO，不证明独立介质、跨故障域或长期保留。没有独立介质资源、损坏对象替换/上一完整有效副本晋升、删除/撤权重放、B0 RPO/RTO 和产品 Acceptance 均仍未通过。

## 9. S03 设计准备与冻结门槛（2026-09-25；尚未接受）

本轮实现审查确认以下边界：

- `BackupRestoreService.verify()` 只在现有 PostgreSQL 服务中创建随机临时数据库，恢复并核对后删除；它不是生产恢复、晋升或开放读取的路径。
- `backend/app/evidence/services.py` 的删除请求目前只写入 PostgreSQL。恢复较早快照时，快照之后产生的删除/撤权事实不在候选数据库中；当前没有快照之外的删除日志或完整性水位。
- `monitor_topics.status` 允许 `active`，现有恢复验证命令不会暂停主题或阻止 Worker，因此不能把恢复数据库直接作为可启动的应用环境。
- S02 的 MinIO 回读只复用当前服务和 bucket 的随机前缀，不证明该对象存储与 PostgreSQL 位于独立故障域。

S03 的实现设计必须先冻结以下行为，再进入 Red：

1. 删除/撤权日志必须独立于恢复快照保存，并证明从候选快照时刻到所声明恢复截止点的覆盖完整性；日志缺失、覆盖不足或校验失败时，恢复环境保持隔离，不开放相关资料。日志只保存重放所需的最小资源身份、操作 ID、原因和时间，不包含正文。
2. 恢复顺序必须先验证候选和日志覆盖，再重放删除/撤权并核对对象关系、权限、证据及损失窗口；恢复主题保持暂停，Worker/调度不得在该屏障解除前执行。
3. 日志保存期限不得短于可恢复备份最长周期；密钥恢复路径和责任人必须可演练。036 当前的 30 天只属候选值，不能作为已冻结配置。
4. 需由维护者确认实际保存目标及其故障域、最长保留天数、加密材料恢复机制与责任角色。复用当前 MinIO 可支持技术验证，但若与数据库处于同一故障域，不满足独立灾备介质或产品验收。

以上仅为源码审查与设计准入约束，不代表 S03 设计已接受、Red/Green 已运行或产品 AC 通过。继续沿用唯一 `hotkey-server` 数据库、现有服务和用户管理介质；不创建第二套依赖、不触碰本机业务库。用户确认资源与恢复边界后，再补充具体适配器/CLI职责并更新对应 Plan。
