# 监控来源采集与证据链设计

## 现状

当前 `monitor`、`source` 与 `ingestion` 模块已经覆盖监控草稿和发布、来源连接、来源凭据、权限策略、定时与手动采集、River 任务、原始证据写入 MinIO、内容标准化和出处正文投影。已建模的来源类型包括 RSS、Hacker News、X、Bing Grounding、Bilibili、Weibo 与 Google Agent Search；并非每一种来源都必然具备可用授权或在所有部署中启用。

当前监控状态为 `draft / active / paused / archived`，来源健康状态为 `unknown / healthy / degraded / unavailable`，采集运行使用 `queued / running / succeeded / failed / cancelled`。新基线必须先保护这些现有状态和数据，再收敛用户可理解的多来源部分成功、证据可追溯和预算治理体验。

## 目标

| 需求 ID | 目标 |
|---|---|
| BR-002-001 | Monitor 必须把用户意图固定为可版本化、可审核、可重复执行的监控契约。 |
| BR-002-002 | 来源接入必须以合法授权和显式能力为前提，失败必须对用户透明。 |
| BR-002-003 | 任何进入研判的内容都必须具有可验证证据链，派生事实不得覆盖原始观察。 |
| BR-002-004 | 采集必须有界、幂等、可恢复，单来源故障不得扩大为整轮静默丢失。 |

为满足上述需求，监控支持草稿、来源级编译预览、发布、暂停、恢复与归档；每个来源独立执行并显示成功、空结果、限流、权限失败和降级原因；每个采集项保留来源、外部身份、时间、原始对象、哈希和处理版本；Connector 在调用前按 Capability→Rights/Policy→Credential 状态/引用→Budget→Rate Limit→Endpoint/SSRF Policy 的顺序完成本地门禁，只有端点通过后才解密并附加凭据发出请求。

## 非目标

- 不使用登录 Cookie、验证码绕过、设备指纹或反爬规避采集数据。
- 不把普通网页任意抓取作为默认来源能力。
- 不承诺所有已建模来源在首版都有真实授权和相同能力。
- 不在队列载荷中传输正文、原始响应或凭据。
- 不把评论会话展开混入基础发现；评论属于 003 的条件式增强。
- 不新增独立采集微服务、消息总线或第二套调度系统。

## 核心决策

### DEC-002-001：发布版本驱动采集

只有已发布的 Monitor 版本可以进入定时采集。草稿预览使用隔离运行，不更新生产 Checkpoint、不触发通知，也不改变已发布规则。预览必须生成可比较的来源级 Compiled Profile；发布版本绑定一个已就绪、不可变的 Compiled Profile 快照，保存规范化规则、来源查询、编译/Schema 版本与输入哈希，使相同版本可复现。002 拥有版本绑定和准入，003 的 `monitor.compile.v1` 只可提供受控编译建议。每次运行保存 Monitor ID、发布版本、Compiled Profile、时间窗、触发类型和输入哈希。

### DEC-002-002：Connector 能力显式化

Connector 继续位于 `source` Infrastructure，并通过 Domain Port 暴露发现、查询、指标刷新、健康检查等有限能力。调用方不得根据来源名称臆测评论、指标或历史窗口能力；不可用能力返回稳定原因。Collector 只取得授权数据并形成 Observation/指标输入，不执行 AI 研判、Event 生命周期或 Heat/Evidence 最终判断。

每次真实调用的唯一顺序为 Capability→Rights/Policy→Credential 状态/引用→Budget→Rate Limit→Endpoint/SSRF Policy→Request。前五步不得触网；端点和逐跳重定向通过后，才在请求边界解密并附加凭据，任何拒绝都不得消耗真实来源请求或泄露凭据。

### DEC-002-003：每个来源是独立采集目标

一轮扫描由多个 Target 组成。Target 独立申请预算、更新 Checkpoint 和记录结果；合法空结果是成功且计数为零的 Target，不是失败。整体 `run_outcome`（`success / partial_success / failed`）由 Application 在查询时根据已提交 Target 事实派生，不新增 `collection_runs.status` 或 Target 的持久枚举；若未来需要持久化，必须另做 Schema/兼容评审。

### DEC-002-004：先证据，后派生

来源响应先以不可变对象写入 MinIO并保存哈希、字节数、内容类型和捕获时间，再建立 Observation、Document Version 和派生结构。无法保存必要证据时，不得把该项推进到证据完整状态。

### DEC-002-005：有界持久任务

调度器只将稳定 ID、版本、时间窗和输入哈希写入 River；Worker 执行时重新读取连接、权利、凭据和监控版本，避免过期配置和大载荷。`kind + unique_key` 保证同一工作单元幂等。

### DEC-002-006：来源资源边界版本化

每个 Connector 动作使用版本化 Resource Limit Profile，分别约束连接超时、读取超时、整次墙钟、最大页数、最大条数、累计响应字节、最大重试次数和每日配额；缺项不得继承无限值。边界按 `limit-1 / limit / limit+1` 固定 Fixture 验证，越界必须在下一次拨号、翻页、重试、对象写入或下游排队前停止，已经提交的 Target/Checkpoint/Evidence 事实保持可诊断且不被回滚。

## 数据与状态

- Monitor 生命周期沿用 `draft / active / paused / archived`，状态变更通过 Application 校验并保留版本历史。
- Source Connection 记录来源类型、规范化端点、授权类型、受管凭据引用、健康状态、权利策略和软删除状态；读取 API 只返回“是否已配置”。
- Collection Run 保存整轮身份与触发信息；Target 保存来源级状态、Checkpoint、错误分类、数量与耗时；Item 保存外部身份与证据引用。
- 历史回填若在 P1 启用，使用独立触发类型和时间窗，不能伪装成实时发现或触发普通实时热点通知；是否提供单独的“回填完成”通知仍需产品批准。
- Observation 表达某次来源观察，Document/Document Version 表达标准化可阅读内容；两者不得合并成一个可覆盖记录。
- MinIO Object Key 由系统生成，数据库保存 Key 与校验元数据；业务 URL 不直接作为对象路径。
- 原始对象到期后继续保存必要证据元数据、Hash、保留策略版本和删除审计；UI 显式显示过期状态，经批准的长期保留例外必须可追溯。
- 发布时间未知时保持为空，不用发现时间伪造；发现时间与捕获时间始终保存 UTC。

## 接口与交互

- 监控页面提供草稿编辑、规则预览、发布、暂停、恢复、归档、版本历史和最近扫描。
- 来源页面提供预设、连接、凭据配置状态、能力、权利策略、健康探测和启停操作。
- 手动扫描返回运行身份；扫描详情按来源展示状态、数量、耗时和净化后的稳定错误码。
- 内容列表和详情展示来源、发布时间、发现时间、原始链接、标准化正文和证据可用状态。
- 所有业务接口使用统一 Result；分页使用当前 OpenAPI 已定义的游标或受控参数。契约变化必须同步 Swaggo、`docs/openapi/swagger.json`、生成客户端和契约测试，不引入前端手写 DTO。

## 安全与合规

- 自定义端点必须使用允许的协议；DNS 解析、重定向目标、响应大小与超时逐跳检查，拒绝私网、回环、链路本地和保留地址。
- 来源凭据由受管加密存储或批准的环境引用提供，Connector 仅在请求边界取得明文，日志和错误不得包含 Token 或上游原始敏感响应。
- 来源、凭据、预算、扫描和证据管理动作全部记录脱敏审计；普通日志不得包含 Token、Cookie、完整敏感正文或上游原始错误。
- 每个 Connector 动作在执行前读取当前权利决策；授权过期、条款变化或删除义务未满足时停止相应动作。
- 配额与成本按连接和动作记账；429、401、403、5xx、解析失败分别分类，不进行无限重试。
- 原始证据的访问继承业务对象权限和保留策略，不提供任意 MinIO Key 下载。

## 失败与降级

- 连接认证失败：Target 终止并标记稳定认证错误，不反复消耗预算；其他 Target 继续。
- 限流：记录恢复时间并延后任务，不以紧密循环重试。
- 网络或上游暂时失败：在任务最大尝试和墙钟预算内重试；耗尽后保留 Checkpoint 和失败事实。
- MinIO 不可用：停止需要原始证据的新项派生，已保存内容仍可查询。
- 标准化失败：保留原始 Observation 和错误分类，允许修复解析器后重新派生。
- 重复任务：命中唯一键或内容身份时返回既有事实，不重复写证据、内容或通知。

## 验收边界

| 验收 ID | 边界 |
|---|---|
| AC-002-001 | Monitor 草稿、来源级编译预览、发布、暂停、恢复、修改与归档均可执行；相同输入与版本得到相同 Compiled Profile 快照，每次发布绑定不可变版本/快照，旧运行仍引用旧版本，重复时间窗不产生重叠副作用。 |
| AC-002-002 | 来源缺少能力、权利、凭据、预算或安全端点条件时，请求在受控边界被拒绝并返回稳定原因；来源、凭据、预算、扫描和证据管理动作均有脱敏审计，日志不泄露 Token、Cookie、完整敏感正文或上游原始错误。 |
| AC-002-003 | 三来源扫描中一个限流、一个成功、一个合法返回空时，Target 持久事实保持各自状态，Application 派生 `run_outcome=partial_success`；成功内容继续后链路，空结果按成功零条处理，来源状态与耗时可见，数据库不新增冲突的整体状态枚举。 |
| AC-002-004 | 任一已接受 Document 在保留期内可定位 Observation、来源连接和 SHA-256 一致的 MinIO 对象；对象到期后仍可定位元数据、Hash、删除审计、UI 过期状态和经批准的保留例外，不一致时不得作为有效证据。 |
| AC-002-005 | 固定 Fixture 中的重复 URL/正文、未知发布时间和多时区经标准化后，精确重复不新建当前 Document，近重复保留分组理由，未知时间仍为空，UTC 与原时区可追溯。 |
| AC-002-006 | Worker 在分页或证据写入的关键步骤中止并恢复，或同一请求重复提交时，任务从 Checkpoint 幂等继续，不重复当前内容、对象或业务副作用。 |
| AC-002-007 | Viewer、Analyst、Editor、Admin 访问 Monitor、来源、扫描和证据时，页面与直接 API 权限一致，五态可辨识，任一角色都不能读取凭据明文或任意对象 Key；接口变更的 DTO、错误码、Swaggo、发布 OpenAPI、生成客户端和契约测试一致。 |
| AC-002-008 | 在记录硬件、Fixture、并发和网络条件后，对 50 Monitor、100 连接、日等效候选量和 20 并发扫描输出吞吐、队列、失败、P50/P95/P99 与资源报告；候选数字只有达标并批准后才能成为承诺。 |
| AC-002-009 | 对每个 P0 Connector 的连接、读取、墙钟、页数、条数、累计字节、重试和每日配额执行 `limit-1 / limit / limit+1` 矩阵；任一越界均在下一外部或持久副作用前以稳定原因停止，已提交事实保留且八类边界不存在无限缺省。 |

## 未决项

- OPEN-002-001：首版承诺的真实来源集合必须依据现有账号权限与合规证据确认，不能按代码中已有 Connector 数量推断。
- OPEN-002-002（已关闭，2026-08-27）：采用 `DEC-002-003`，整体“部分成功”是由 Target 事实派生的查询投影，不新增持久状态；未来若改变必须重新评审 Schema 与兼容性。
- OPEN-002-003：各来源默认时间窗、页数、字节数和成本上限需要真实 API 配额验证。
- OPEN-002-004：现有 legacy Content 与新 Document/Observation 投影的保留和收敛顺序需在 Plan 中逐表列出。
