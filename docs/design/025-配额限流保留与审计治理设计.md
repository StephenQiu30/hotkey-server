# 配额限流保留与审计治理设计

## 现状

来源速率、AI 预算账本、保留策略、审计日志和运行概览已有基础，但缺少面向用户的统一监控数、手动搜索数和模型用量配额。

## 目标

控制用户、监控、来源和模型成本，提供明确剩余额度、重置时间和管理员治理能力。

## 非目标

不在本条复制相邻领域的数据或服务，不以纯前端假数据宣称功能完成，也不引入第二套事实源。

## 核心决策

- 配额维度至少包含 active monitors、manual searches/day、source calls、AI tokens/cost 和通知投递；按用户/工作区和时间窗记账。
- 先在事务中 reservation，再执行外部调用，完成后 settle；失败按规则释放或记实际成本，避免并发超卖。
- 来源 429 与产品配额分开表达；响应包含稳定错误码、limit、remaining、reset_at。
- 内容、指标、会话、任务和审计采用独立保留策略；核心事件、发布报告与审计不得被普通清理静默删除。

## 数据、接口与交互

- 配额策略和用量账本
- 限流、预留、结算与超限反馈
- 数据保留和清理任务
- 管理员治理总览与审计查询

所有状态变化保存明确版本、时间和操作者；跨端字段由 Schema、后端 DTO 和生成 OpenAPI 驱动，前端不得手写重复类型。

## 安全、失败与降级

配额统计晚于调用会造成成本失控；所有昂贵动作必须先预留。

外部 AI、邮件、实时连接或归档不可用时，业务事实先可靠落库，异步重试或降级读取，不在请求链路丢失结果。

## 设计验收边界

- 并发请求不会突破硬配额
- 用户能在触发前看到剩余手动搜索/AI 额度
- 保留任务具有 dry-run、批量上限和不可删事实保护
