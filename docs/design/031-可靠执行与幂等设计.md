# 可靠执行与幂等设计

日期：2026-09-21。本文冻结 031 S00—S02 的持久受理、消息恢复、执行租约、检查点与有限调度追赶边界；有限重试、死信和 72 小时度量留给 S03。本文不把内部任务基础设施解释为 031 完整产品验收。

## 1. 范围与决策

S01 只建立后续 009 任务控制可复用的领域入口，不提前发布 HTTP 路由、生成客户端或任务页面。009 定义用户任务列表、详情、取消和重试；031 保证这些操作未来接入时，成功响应已经有可追踪的持久事实。

| 决策 | 冻结值 | 理由 |
|---|---|---|
| 受理事实 | PostgreSQL 中的 `jobs` 记录；只有事务提交后才能向调用方返回成功 | 进程内对象、Kafka 已接收或 Redis 键均不能证明任务可恢复 |
| 原子发布准备 | 同一事务写入一条 `outbox_messages` 记录，事件类型 `job.accepted.v1`，Topic `hotkey.jobs.accepted.v1` | 数据库提交与消息发送之间不建立不可恢复的双写窗口 |
| 操作标识 | 调用方为一次业务意图生成 UUID；重试必须复用，同一所有者与任务类型内唯一 | 网络响应丢失后仍可稳定找回原任务 |
| 请求等价 | 对受控 `scope` 做规范 JSON 和 SHA-256 指纹；同键同指纹返回原任务，同键异指纹返回 `idempotency_conflict` | 防止误复用标识时静默改变用户意图 |
| 状态 | S01 只创建 `queued`；数据库预留 `running`、`succeeded`、`partially_succeeded`、`failed`、`cancelled` 合法值 | 状态词来自 009/031 PRD，S01 不实现后续转换 |
| 权限 | `owner_id` 只能来自已认证服务端上下文并外键关联 owner；客户端 scope 不含 owner | 延续 035 默认私有边界，避免伪造归属 |
| 外部依赖 | Redis 不存任务事实；Kafka 不参与受理事务，发布器与消费者在 S02 接入 | Kafka 或 Redis 暂时不可用时，已提交 outbox 仍可恢复发布 |

PostgreSQL 官方文档确认多列唯一约束会强制组合唯一性并建立唯一索引；`INSERT ... ON CONFLICT` 能以原子方式处理并发冲突。SQLAlchemy 的事务上下文在正常退出时提交、异常时回滚。因此 S01 采用数据库约束与 `ON CONFLICT DO NOTHING` 竞争，不用进程锁或 Redis 锁模拟一致性。

参考：

- [PostgreSQL 18 INSERT](https://www.postgresql.org/docs/18/sql-insert.html)
- [PostgreSQL 18 Constraints](https://www.postgresql.org/docs/18/ddl-constraints.html)
- [SQLAlchemy 2.0 Session Basics](https://docs.sqlalchemy.org/en/20/orm/session_basics.html)
- [Apache Kafka 4.1 Design](https://kafka.apache.org/41/design/design/)
- [Apache Kafka 4.1 Consumer Javadoc](https://kafka.apache.org/41/javadoc/org/apache/kafka/clients/consumer/KafkaConsumer.html)

Kafka 官方资料说明，先提交 offset 可能丢失处理，先处理再提交 offset 会产生至少一次重投；外部数据库结果要获得更强语义，需要让业务结果和消费位置参与同一外部事务。S02 将据此设计消费 inbox/offset、执行权和恢复，不在 S01 的受理边界内伪称 exactly-once。

## 2. 数据契约

### 2.1 `jobs`

| 字段 | 规则 |
|---|---|
| `id` | 服务端 UUID 主键，首次受理时生成，重复请求返回同一值 |
| `owner_id` | 必填，外键到 `identity_users.id`，删除 owner 时级联删除尚未进入生命周期设计的任务 |
| `operation_id` | 调用方 UUID；与 `owner_id`、`kind` 组成唯一约束 |
| `kind` | 1—64 位小写字母、数字、点、下划线或连字符；代表稳定操作语义 |
| `scope` | 最多 32 个键的 JSON 对象，值仅允许字符串、整数、布尔或 null；只保存稳定标识/窗口，不保存秘密、正文或凭据 |
| `request_fingerprint` | 32 字节 SHA-256，用于判断重复操作是否等价 |
| `status` | S01 固定创建为 `queued` |
| `created_at` / `updated_at` | UTC 时间；S01 两者相同 |

### 2.2 `outbox_messages`

| 字段 | 规则 |
|---|---|
| `id` | UUID 消息标识，供后续发布与消费防重 |
| `aggregate_id` | 对应 `jobs.id`；同一事件类型与聚合 ID 唯一 |
| `topic` / `event_type` | 固定为 `hotkey.jobs.accepted.v1` / `job.accepted.v1` |
| `message_key` | 使用任务 ID，保证同任务后续事件可按相同分区键处理 |
| `payload` | 仅含任务 ID、owner ID、operation ID 和 kind；不复制 scope、正文或秘密 |
| `created_at` / `published_at` | 创建时间必填；S01 的 `published_at` 保持 null，发布器由 S02 实现 |

数据库唯一约束是并发正确性的最终边界。ORM 与 `database/schema.sql` 同批修改；应用启动、测试和 Worker 均不得运行 DDL。

## 3. 受理算法与失败语义

`JobService.accept` 接收服务端 owner 和验证后的 `JobAcceptanceInput`：

1. 对 kind、operation ID 和 scope 做校验并生成规范指纹；
2. 在单个 PostgreSQL 事务中执行 `INSERT ... ON CONFLICT DO NOTHING RETURNING`；
3. 插入成功时，在同一事务写入唯一 outbox；插入冲突时查询原任务并比较指纹；
4. 同键同指纹返回原任务；同键异指纹抛出已登记的 `idempotency_conflict`；
5. 事务正常提交后才返回不可变的任务视图；任意 flush、约束或提交异常均回滚任务与 outbox，不返回成功。

并发相同请求由 PostgreSQL 唯一约束串行化：一个事务创建任务和 outbox，其余事务在冲突确定后读取已提交记录。服务不捕获并伪装数据库异常；046 统一异常层在未来 HTTP 接入时负责把依赖故障转为稳定、无泄密的响应。

`OPEN-031-001` 对 S01 的结论是：受理事务不做自动业务重试，也没有执行期限；调用方可以用同一 operation ID 显式重试。各任务类型的完成期限、可重试错误、次数和退避必须在 S03 及对应业务 Plan 接入前逐类冻结，不能用本切片的默认值替代。

## 4. 切片边界

S01 不实现以下内容：

- Kafka outbox 发布循环、消费者、消费 inbox 或 offset 存储；
- 执行租约、fencing token、尝试记录、检查点和旧执行者拒绝；
- 调度窗口、追赶、死信、自动重试与 72 小时统计；
- 009 的 HTTP、OpenAPI、生成客户端、列表/详情/取消/重试页面；
- 具体作品、评论、通知等业务实体唯一约束。

Redis 和 Kafka 在当前本机既有服务中仅做可达性环境检查。它们故障不应进入受理事务；S01 通过“没有发布器仍产生可恢复 outbox”证明解耦，不为满足检查项而加入无效连接。真实消息重投、再均衡、Redis 失效及 offset 不越界在 S02 用对应实现验证。

## 5. 验证与证据边界

S01 使用以下证据闭环：

1. Red：专用测试导入不存在的 `jobs` 领域并失败，证明持久受理能力尚未存在，而非环境未启动。
2. 规则：scope 键顺序不影响指纹；不同 scope 指纹不同；输入拒绝多余字段和超限范围。
3. 真实 PostgreSQL：同一请求串行重试返回同一任务，任务和 outbox 各一条；相同标识配不同 scope 被拒绝且原事实不变。
4. 故障注入：在事务 flush 后抛出异常，任务与 outbox 都为零；并发两个数据库会话提交同一请求，返回同一任务且各表仅一条。
5. Ruff、格式、mypy、全量 pytest 与架构门禁通过；Redis PING、Kafka metadata 和 MinIO health 仅作为复用当前环境的可达性证据。

没有 HTTP 或 UI 变化，因此 OpenAPI、客户端生成、前端测试和浏览器验证在 S01 不适用；后续 009 接入公开入口时必须重新执行。上述证据不证明 AC-031-001、AC-031-003—006、Kafka 发布/消费恢复或最终业务实体防重已通过。

## 6. 本机数据与回退

本机继续复用已启动的 Homebrew PostgreSQL 18.4、Redis、Kafka 和 MinIO，不启动 Compose 或第二套依赖。旧 `hotkey`、`hotkey-server`、`hotkey_test` 数据库保持不变。当前 `hotkey_dev` 是本项目此前创建且身份表记录数为零的空业务库；因项目没有迁移框架，加入 S01 DDL 后只对该空库按完整 `schema.sql` 重建，随后让忽略提交的 `backend/.env` 继续指向它。

异常时停止新增受理并回退程序版本；已经提交的任务和 outbox 必须保留供向前修复。不得删除旧数据库、清空持久卷或通过跳过 outbox 恢复可用性。S01 尚无发布器，回退前无需处理在途 Kafka 消息。

## 7. S02 消息、执行权与恢复

### 7.1 Outbox 发布

发布器从 `outbox_messages` 按创建顺序取未发布记录，使用 PostgreSQL `FOR UPDATE SKIP LOCKED` 让多个发布者跳过已占用行。每条消息以任务 ID 为 Kafka key，并发送以下版本化 JSON：

```json
{
  "schema_version": 1,
  "message_id": "outbox UUID",
  "event_type": "job.accepted.v1",
  "job_id": "job UUID",
  "owner_id": "owner UUID",
  "operation_id": "operation UUID",
  "kind": "monitor.collect"
}
```

Producer 开启 idempotence，单次等待 broker delivery callback，默认超时 10 秒；收到成功回执后才写 `published_at`。Kafka 已接收而数据库提交失败时，记录保持未发布并可能再次发送，这是明确的至少一次边界，消费端必须防重。S02 不增加自动重试计数或死信。

PostgreSQL 官方明确 `SKIP LOCKED` 适用于多个消费者访问队列式表；SQLAlchemy 通过 `with_for_update(skip_locked=True)` 生成该语义。Kafka 官方将“先处理、后保存位置”定义为至少一次，并指出写入外部系统的 exactly-once 需要该系统协作。因此这里不以 Kafka transaction 宣称 PostgreSQL 与 Kafka 跨系统原子提交。

新增参考：

- [PostgreSQL 18 SELECT locking clause](https://www.postgresql.org/docs/18/sql-select.html#SQL-FOR-UPDATE-SHARE)
- [SQLAlchemy 2.0 with_for_update](https://docs.sqlalchemy.org/en/20/core/selectable.html#sqlalchemy.sql.expression.Select.with_for_update)
- [Apache Kafka 4.1 Consumer Configs](https://kafka.apache.org/41/configuration/consumer-configs/)
- [Confluent Kafka Python API](https://docs.confluent.io/platform/current/clients/confluent-kafka-python/html/index.html)

### 7.2 消费、inbox 与 offset

Consumer 固定 `enable.auto.commit=false`、`enable.auto.offset.store=false`、`auto.offset.reset=earliest`，默认 `max.poll.interval.ms=120000`。消息完成数据库处理后才同步提交该消息的 offset+1；处理器、数据库提交或 offset 提交任一失败，Worker 立即退出当前消费循环，不继续处理同分区更后消息，避免后续提交越过失败记录。

`processed_messages` 以 outbox message ID 为主键，并对 topic/partition/offset 建唯一约束。任务完成与 inbox 记录在同一 PostgreSQL 事务；数据库成功而 offset 尚未提交时，重平衡后的重复消息先命中 inbox，再安全提交新消费位置。无效/永久消息的隔离和有限重试属于 S03；S02 不静默跳过。

### 7.3 Lease epoch 与检查点

`jobs` 增加当前执行者、lease epoch、到期时间、检查点序号和检查点 JSON；`job_attempts` 独立记录每次取得执行权的 worker、epoch、开始/结束、到期和结果。

- 默认 lease 为 60 秒；`queued` 或 lease 已过期的 `running` 任务可取得执行权。
- 每次取得执行权均令 epoch 加一；新执行者将上一条未结束 attempt 标记为 `expired`。
- 保存检查点必须持有未过期且 worker/epoch 完全匹配的 lease；序号只能连续加一。同序号同内容可幂等返回，不同内容或跨号拒绝。
- 保存检查点同时续租 60 秒；无检查点的单次处理必须在 lease 内完成。
- 完成任务要求同一未过期 lease，并在同一事务更新 `succeeded`、完成 attempt、清除 lease、写入 inbox。
- 旧执行者即使恢复运行，也因 epoch 不匹配而不能推进检查点、完成任务或覆盖新执行者结果。

检查点只允许最多 32 个稳定标量键，不保存正文、秘密或未界定的大对象。当前 S02 只实现成功完成；失败分类、部分成功、取消与重试状态转换由 009/S03 接入。

### 7.4 有限调度追赶

调度计算以带时区的半开窗口 `[start, end)` 为单位，默认最多保留最近 3 个已到期窗口，并显式返回跳过数量。每个窗口的 operation ID 由固定 namespace 与 `owner_id + kind + schedule_key + start + end` 生成 UUIDv5；两个调度实例对同一窗口并发受理时，复用 S01 数据库唯一约束返回同一任务。

S02 不建立通用调度守护进程或新页面。009/具体业务负责提供 cadence、schedule key 和调用时机；本切片提供可验证的窗口计划及原子受理契约。被跳过的历史窗口不能写成已完成，完整补偿策略随对应业务冻结。

### 7.5 配置与边界

| 配置 | 默认值 | 约束 |
|---|---:|---|
| `HOTKEY_JOB_LEASE_SECONDS` | 60 | 5—300 秒 |
| `HOTKEY_JOB_MAX_CATCHUP_WINDOWS` | 3 | 1—100 个 |
| `HOTKEY_KAFKA_DELIVERY_TIMEOUT_SECONDS` | 10 | 1—60 秒 |
| `HOTKEY_KAFKA_MAX_POLL_INTERVAL_SECONDS` | 120 | 30—900 秒 |

Redis 仍不保存任务事实、offset 或执行权。Kafka/Redis 故障不影响已提交任务和 outbox；Redis 完全不可达时，PostgreSQL lease 与 Kafka 恢复链仍必须工作。S02 无 HTTP、OpenAPI、生成客户端或 UI 变化，浏览器与前端门禁仍为 N/A。

Worker 装配只在存在已登记的业务 kind 处理器时创建数据库/Kafka 客户端、发布 pending outbox 并订阅 topic。当前尚无完成 Design 的具体业务处理器，因此生产入口明确记录 `no_message_handlers_registered` 后安全退出；测试使用登记在用例内的最小处理器验证完整恢复链，不把测试处理器伪装成已交付业务能力。

## 8. S02 验证与证据边界

1. Red：租约、检查点、调度窗口和消息恢复测试因对应模块/契约不存在而失败，不以服务未启动冒充业务失败。
2. 真实 PostgreSQL：旧 lease 过期后新 worker 取得更高 epoch，从已保存检查点继续；旧 worker 的保存和完成均被拒绝。
3. 真实 Kafka：delivery callback 成功后注入数据库失败，outbox 重发形成相同 message ID 的两条物理消息；消费 inbox 只记录一次，业务任务只完成一次。
4. 真实 consumer group：第一消费者在保存检查点后关闭且不提交 offset；第二消费者重平衡后收到同一消息、恢复完成，再同步提交 offset。
5. 调度：超过上限的窗口只返回最近 3 个及准确跳过数；并发接受同一窗口只产生一个 job/outbox。
6. Redis：连接到明确不可达端点产生真实连接失败，同一 PostgreSQL/Kafka 恢复场景仍成功；现有 Redis 服务不停止、不清空。
7. Ruff、格式、mypy、全量 pytest 与架构门禁通过；本机只创建和删除测试专用 Kafka topic，不启动第二套依赖。

这些证据证明 S02 技术切片，不证明具体采集业务结果、009 页面、S03 有限重试/死信、72 小时运行或 AC-031-001—006 的最终产品范围已验收。

## 9. S03 前置边界：可判定毒记录与未知中断

009 已为明确的 `JobExecutionFailure` 分类实现有限重试、永久失败及同事务 inbox；`webpage.collect` 已有实际处理器。S03 不能把处理器抛出的所有 `Exception` 直接标为永久失败并确认消息：同一异常外形也可能发生在检查点已保存、Worker 随即中断的恢复路径。2026-09-23 的全量回归中，宽泛捕获使真实 Kafka 重投/再均衡用例失去未确认消息；撤回后该用例重新通过。

只有来源适配器明确判定为授权失效、禁止访问或确定的解析/协议错误，才由现有分类契约持久隔离。未知执行异常、数据库故障或失效租约仍须保持消息未确认，等待租约与重投恢复；若以后增加毒消息处置，必须先设计可验证的有限尝试、原消息/原因的脱敏持久证据和后续 offset 安全推进，不能捕获全部异常或只靠进程内计数。[Kafka 至少一次语义](https://kafka.apache.org/41/design/design/)与 [Confluent 手动提交说明](https://docs.confluent.io/platform/current/clients/confluent-kafka-python/html/index.html#confluent_kafka.Consumer.commit)是该边界的协议依据。72 小时执行率仍需实际到期单元、每类任务期限与真实观察期；本节只是 S03 设计准备，不关闭 G3/G4 或产品 AC。
