# 增量更新与历史回补设计

日期：2026-09-23。本文为 [010 PRD](../prd/010-增量更新与历史回补.md) 的执行设计；S01 来源无关的内部契约已实现，S02 时间标记子片已落地，其余仍待执行，不表示产品 AC 通过或真实平台已覆盖。先复用 [007 内容模型](007-作品资料与上下文设计.md)、[009 任务控制](009-采集任务控制设计.md)、[031 持久执行](031-可靠执行与幂等设计.md)、[036 生命周期](036-数据访问与生命周期设计.md) 与 [037 预算](037-费用与资源约束设计.md)，不另建调度器、对象库或消息队列。

## 1. 当前事实、目标与非目标

`content_records` 已按 owner/来源/对象类型/原生身份唯一；`content_versions` 与 `content_observations` 分别保存不可变正文和本轮观察，同一 source operation 的观察可幂等重放。Job 已有受 fencing 保护的检查点、租约和有限调度追赶；公开网页单页任务已有原子内容/检查点提交。S01 已新增内部跨轮次范围状态与连续确认查询，但尚无社交多页业务处理器或对用户开放的覆盖查询；内部终点 fixture 不能证明真实来源时间段或全网完整。

目标是在明确的来源、能力、目标和排序范围内重叠读取、去重并保留每轮观察；仅对有终点证据的有限窗口确认进度，预算耗尽、取消、失效游标及未知尾页留下可见缺口。旧作品的新增回复按真实发布时间与本次观察时间分别记录。非目标包括自动无限回补、推断上游全量、把旧内容触发为新事件、绕过已删除数据或缺少准入的真实来源。

## 2. 方案比较与决策

| 方案 | 结论 |
|---|---|
| 只使用 Job checkpoint | 可恢复当前任务，但任务结束后无法查询跨轮次缺口；不满足 AC-010-003。 |
| 按最大已见发布时间推进水位 | 乱序、分页截断和旧帖新回复会越过未知数据；拒绝。 |
| 一张范围状态表，加现有 Job/内容事实 | 采用。范围表只记录计划边界、状态和停止原因；页游标仍属 Job，正文仍属 content。 |

**DEC-010-002：执行位置与覆盖断言分离。** Window 使用服务端规范化的 owner、来源、能力、目标、排序、规则版本与 `[start,end)` UTC 范围定界。窗口身份不以易过期的上游游标或连接版本作键；执行 Job 固定实际连接/采集器版本，换版后重新验证并重新受理。相同窗口可重试，历史尝试留在 Job；范围状态只保存当前可证明结果。`confirmed` 仅表示指定查询范围和排序下已读到可验证终点，不表示平台所有资料均被发现。

**DEC-010-003：缺口先于确认水位。** 只有页结果与内容/证据/用量/检查点在同一事务成功提交，且适配器能证明本次查询确实受指定时间和排序约束、已到该范围的明确终点，窗口才能变为 `confirmed`。现有 `SourcePage.COMPLETE`/`EMPTY` 只说明本次分页结束，不能单独证明目标时间窗覆盖；不支持有界查询或无法验证终点的来源保持 `partial`。`partial` 保留已提交资料、停止原因和未确认尾段；未知尾段不得填成空页。查询水位取同范围连续 `confirmed` 的末端，遇 `partial`/未执行窗口停止，不另存可与范围行矛盾的第二份水位。窗口状态更新由 jobs 服务持有行锁，页内内容写入沿用 047 最外层事务与 epoch fencing。

**DEC-010-004：回填是显式业务类型，不改变来源时间。** Job scope 固定 `new_scan`、`refresh` 或 `backfill`。内容 `published_at` 只来自来源；`observed_at` 记录本次读取，回填标识属于发现/任务语义，提醒不得按“今天入库”制造新事件。相同原生 ID 不新建实体，但明确新观察、发现关系和旧根下新回复可追加；删除/保留屏障在写入和读取前仍优先。

## 3. 数据、状态与领域边界

S01 实现持久范围状态时，`backend/database/schema.sql` 与 `backend/app/jobs/models.py` 同批增加一张 owner 隔离的范围状态表；主字段为来源/能力/目标作用域摘要、排序、规则版本、UTC 起止、状态、停止原因、关联 Job 与更新时间。作用域原文留服务端已有配置，摘要不代替权限检查。约束至少禁止反向时间、非法状态，关联 Job 使用现有 `(owner_id, id)` 复合键防止跨 owner 引用；针对同一范围的并发更新由行锁串行。无需独立 `gap` 表：`partial` 行本身就是缺口；无需在 Redis 或 Kafka 保存唯一水位。

状态只允许 `pending → running → confirmed|partial`，`partial → running` 需显式新操作或恢复租约；`confirmed` 不能因一次无内容重读降为 `partial`。范围覆盖与内容存在是不同事实：有样本但无终点为部分，合法零结果必须有来源有效空页及终点证据。失败/取消时不能删已提交观察。`Job.checkpoint` 保留有界非敏感游标/页序、实际下一页和本次已见游标摘要；失效或循环游标在固定页/时间/调用预算内回到明确重叠窗口重读，同 ID 幂等，不猜测漏页已补齐。敏感 token 只能存受控引用，不能进入 Kafka、公开 API 或日志。

`jobs` 拥有范围状态、受理、预算、租约和检查点；`content` 拥有稳定对象、正文版本、观察与删除；`sources/adapters` 返回平台原生 ID、分页/终止证据和真实请求计数；`connections` 验证当前能力/版本；`evidence` 执行准入与保留。现有 `SourceRequest` 尚无有界时间查询字段，首个来源必须在对应能力契约中明确可执行的时间/排序范围及覆盖证据；若平台不支持，就只报告已观察样本和缺口。跨领域页提交复用现有同一 Session，不增加通用 repository、平行 scheduler 或新的 `scripts/` 文件。S01 可先用受控来源 fixture 验证内部状态机，不等待真实平台凭据；但无业务处理器前不增加空的 `backfill-runs` 路由或假来源可用状态。

## 4. API、任务与界面

实际来源接入后，显式 `POST /api/backfill-runs` 复用 Job/Outbox 受理语义，要求 owner、CSRF、operation ID、允许的来源/目标和有界 UTC 范围；相同操作返回原任务，冲突返回稳定错误。`GET /api/coverage-windows` 按 owner/作用域分页读取窗口状态、最早缺口及可证实水位，不回显上游游标或秘密。HTTP 具体 DTO/错误码以 FastAPI 路由和 Pydantic 为唯一事实源，随后从运行时 OpenAPI 生成 Web 客户端；无真实处理器前不创建占位 API。

Worker 每次外采前短事务检查租约、取消、当前准入/连接、预算和范围状态；网络外取一页；响应校验后同事务提交内容、观察、证据、用量、范围页进度与 Job checkpoint。Kafka offset 仅在任务持久完成/延期/失败后提交。多页执行单元必须小于租约/消费者轮询上限，崩溃重放先读持久检查点；不以 SDK 内部重试推进窗口。历史回补与追新分别用现有预算政策，追新优先，回补预算耗尽时延期并保留欠账。

Web 在现有任务页展示任务状态，在 jobs 领域页面按来源/目标/时间显示已确认范围与缺口；`partial` 保留原因和继续入口，未知进度不画虚假百分比。组件归页面专属 `frontend/src/app/jobs/components/`，只有第二个页面稳定复用时再移动到功能组件目录。桌面、窄屏、空/部分/错误/无权与取消场景需真实浏览器验证；历史结果的可读性遵守 036 当前权限与保留屏障。

## 5. 安全、可观测、迁移与回退

来源只采公开或获授权内容；范围摘要、游标与错误输出不泄漏查询原文、Cookie、令牌或敏感 URL。日志只记录安全 Job/范围 ID、状态、停止原因、页/请求计数与耗时；未知目标请求数保持 unknown。观测至少区分确认范围、最早未确认范围、预算延期、循环游标、旧资料观察与新业务通知数量。真实来源的分页和乱序程度不能由单元 fixture 代替。

唯一 DDL 只初始化新空库；存量数据迁移按 PROJECT 的备份、新库、导入核对流程，不对现有库直接重放。回退先停新任务受理/处理器，保留已确认范围及历史资料读取；在途 Job 按既有失败/延期机制收束，不能让旧二进制写入新状态。环境中没有必要来源/准入时，范围保持未验证，不能因内部模型测试勾选产品 AC。

`OPEN-010-001` 仍待逐来源真实样本校准重叠时长和旧帖刷新周期；PRD 的 10 分钟仅为建议，不作全局默认或完整性保证。没有平台样本时不冻结来源专属默认值，也不启动真实回补。S01 已在显式 UTC `[start,end)`、固定排序和规则版本的受控分页样本上验证来源无关的状态与事务；S02 的时间/游标语义仍待实现。首个真实多页处理器进入前，再以真实样本确认有界查询、终点证明、重叠与刷新策略。AC-010-001—006 均未通过，Acceptance 不创建。

### S00 冻结的内部验证范围

内部样本固定为同一 owner/来源/能力/目标/排序/规则版本下相邻窗口 A、B，A 与 B 对同一原生作品有重叠观察；A 的第一页持久成功、第二页预算耗尽，再恢复重投至来源可证明的终点。断言作品唯一、两次有效观察/发现关系按既有幂等规则保存，半批失败使 A 保持 `partial`，B 即使 `confirmed` 也不能使连续确认水位越过 A；重投只在内容与检查点同事务落盘且有有界终点证明时确认 A。另设合法空页但无边界证明的样本，必须留 `partial`。这只是内部测试数据，不充当平台覆盖证据。

S01 改动 `backend/app/jobs/{models,schemas,services}.py`、`backend/app/db/metadata.py`、`backend/database/schema.sql`、`backend/app/content/services.py` 与相应测试；新增外键后同步更新既有集成测试的清理清单及备份表清单。范围状态的权限、行锁与同一 Session 提交由 jobs 负责；内容身份与观察仍由 content 负责。S01 没有真实多页处理器，因此不建立 `/api/backfill-runs`、`/api/coverage-windows`、前端页面、来源可用标志或额外服务。内部样本以 pytest 固定输入和现有本机 PostgreSQL 的一次性空库验证；Ruff、mypy、全量后端回归和 DDL/ORM 对齐为代码门禁。API/OpenAPI/客户端、浏览器和真实来源验证本片不适用，必须在实际接口/处理器接入时补做。

### S01 已落地的内部边界

`coverage_windows` 以 owner、来源、能力、SHA-256 目标摘要、`latest|top`、规则版本和 UTC 起止唯一；只存状态、停止原因、最近 Job、检查点序号和页数，不存原始目标或游标。最近 Job 采用复合 owner 外键；Job 删除时仅清空 `last_job_id`，不删除跨轮次范围。唯一约束已提供相同作用域与起点的 B-tree 前缀，故不增加重复二级索引。[PostgreSQL 多列索引说明](https://www.postgresql.org/docs/18/indexes-multicolumn.html) 与 [复合外键按列 SET NULL 说明](https://www.postgresql.org/docs/18/ddl-constraints.html) 是本次复用依据。

`CoverageWindowService` 在现有 Job lease/epoch、owner、来源和 scope 摘要校验后锁定窗口；只有已写入 Job checkpoint 的页可推进。`MORE` 保持运行，部分/停止保留原因，`COMPLETE|EMPTY` 还需同范围、排序、有界查询与已验证终点证据才确认，否则标 `unverified_terminal` 缺口。相同页重投不重复推进；相邻已确认窗口连续推导水位。`ContentService.persist_post_in_transaction` 允许现有内容去重、观察、发现和范围/checkpoint 进入同一最外层 Session；受控测试验证回滚同时撤销范围/checkpoint。当前无真实多页调用者，故本片只证明内部规则与持久事务，不对外声称来源覆盖或用户闭环。

复用依据：[SQLAlchemy Session 事务边界](https://docs.sqlalchemy.org/en/20/orm/session_basics.html) 与 [PostgreSQL 行级锁](https://www.postgresql.org/docs/current/explicit-locking.html)；沿用项目已有 Session/`FOR UPDATE`，不引入新事务或调度组件。

### S02 时间标记先行片

有范围的 Job 在不可变 `scope` 中显式固定 `scan_kind=new_scan|refresh|backfill`；`CoverageWindowService` 在开启/提交范围前校验，缺失或非法值拒绝，不从作品入库时间猜测类型。`content_observations.published_at` 继续保留来源发布时间，`observed_at` 保留本轮读取时间，不改 DDL。`ContentJobContext` 从对应 Job 传出类型，既有作品详情的 `discoveries` 增加可空 `scan_kind`：非范围旧任务或未标记任务返回 `null`，不得默认为追新。现有详情页面专属 `ContentDetail` 在发现依据显示“追新/旧作刷新/历史回补/未标注”；只使用生成客户端字段，不据此产生通知。未来 017 的通知入口必须按服务端固定的任务类型及原始发布时间再做准入，不能信任页面标签。

实现文件限于 `jobs/{schemas,services}.py`、`content/{schemas,services}.py`、现有详情组件/展示函数、生成客户端和现有测试；不新增模块、表、脚本、回补路由或假处理器。验证旧发布时间、两次不同观察、发现依据类型与无标记旧任务的保守投影；运行时 OpenAPI 生成、前端检查和桌面/窄屏页面验证适用。游标失效/循环后的有限重扫、真实来源端点、通知抑制、实际回补/API 仍是 S02 未完成部分，因此 G3/G4 与产品 AC 不因本片勾选。
