# 容量与部署可重复性设计

日期：2026-09-21。本设计已接受 S00/S01 的运行基线决策；S02—S04 的业务容量保护、完整 B0、两环境恢复和最终 Acceptance 仍待业务能力接齐后验证，不因本设计或单次容器启动而通过。

## 1. 当前事实与本期边界

046 S03 已通过，API、Worker、CLI、Web、运行时 OpenAPI 和客户端漂移门禁可复用；001 总体 Design 已建立。开工前根目录没有 Compose，`docker compose config --quiet` 以 `no configuration file provided: not found` 退出 1；`schema.sql` 没有业务表，Worker 没有 handler。

本切片只交付一个可复现的单机开发/CI 运行基线：根 Compose、空库初始化、真实 PostgreSQL/Redis/Kafka、API/Web 健康链、Worker/CLI 入口、资源上限和部署态 OpenAPI 检查。以下不在 S01：生产高可用、存量库迁移、业务数据生成、完整 B0 压测、高水位调度、MinIO 新建、真实来源或业务页面。

## 2. 核心决策

### DEC-042-001：唯一根编排

根 `compose.yaml` 是唯一运行编排。固定 PostgreSQL `17.11-alpine3.23`、Redis `7.2.16-alpine3.21`、Apache Kafka `4.1.2`，API 与 Worker/CLI 复用同一后端镜像，Web 使用现有 standalone 镜像。开发/CI 差异通过环境变量处理，不建立第二套 Compose。

Compose 使用 `service_healthy` 等待 PostgreSQL、Redis、Kafka，再启动 API；Web 等待 API 就绪。`/api/health` 仅表示进程存活，`/api/ready` 验证当前必需数据库，Compose 同时以依赖自身 healthcheck 保证完整底座就绪。

### DEC-042-002：空库原子初始化仍由唯一 SQL 负责

`backend/database/schema.sql` 保持唯一 DDL 事实源，并自行包含 `BEGIN/COMMIT`。Compose 只读挂载该文件到 PostgreSQL 官方 `/docker-entrypoint-initdb.d/`，仅在全新空数据目录执行；不增加迁移框架、初始化 `.sh` 或另一份 DDL。

初始化失败时停止当前新环境，只允许删除并重建本次尚未承载数据的隔离卷；任何已有卷都不自动重放 `schema.sql`，更不自动删除。存量数据升级继续等待 032/036 的备份、导入和恢复设计。

### DEC-042-003：不堆验证脚本

本切片不创建 `scripts/` 工具或非必要 `.sh` 文件。运行验证直接组合 Docker Compose、`psql`、`redis-cli`、Kafka CLI、`curl`、`docker stats` 与已有 `pnpm openapi:check`；CI 与人工执行使用同一入口。容量工具在 S01 只保留标准化资源快照命令，完整采样、数据生成和报告在 S02 随真实业务模型设计，避免为尚不存在的数据结构造框架。

### DEC-042-004：单机资源预算是约束，不是容量结论

默认长期服务预算如下；Worker 为显式 profile，CLI 为一次性 profile。总上限留有宿主和临时任务空间，但单次空载快照不外推为 B0 结论。

| 服务 | CPU 上限 | 内存上限 | 数据 |
|---|---:|---:|---|
| PostgreSQL | 1.00 | 1536 MiB | named volume |
| Redis | 0.25 | 256 MiB | named volume，开启最小 RDB |
| Kafka | 1.00 | 1536 MiB | 单节点 KRaft named volume |
| API | 0.75 | 1024 MiB | 只读根文件系统，`/tmp` tmpfs |
| Web | 0.50 | 768 MiB | 只读根文件系统，缓存与 `/tmp` tmpfs |
| Worker | 0.50 | 512 MiB | 按需启动；无 handler 时退出 0 |
| CLI | 0.25 | 256 MiB | 一次性执行 |

## 3. 配置、安全与依赖边界

- 根 `.env.example` 只登记本地 Compose 必需变量，不含真实秘密；数据库密码无默认值，缺失时 Compose 配置阶段直接失败。生产秘密文件/托管方案由 034 设计，不在本切片假装完成。
- API/Web 端口默认只绑定 `127.0.0.1`；PostgreSQL、Redis、Kafka 不发布宿主端口。应用容器以现有非 root 用户运行。
- `HOTKEY_API_ORIGIN` 仅在 Web 服务端指向 `backend:8080`；浏览器仍调用同源 `/api/*`。
- MinIO 继续复用既有授权实例。当前健康与业务路径尚未使用对象存储，因此不在根 Compose 复制 MinIO，也不把未连接状态报告为已验证。
- Redis 只承载可重建状态，Kafka 的业务 topic、重试、位点和恢复由 031 设计；S01 只证明真实 broker 可用和空 Worker 不虚假消费。

## 4. 文件与运行路径

| 文件 | 职责 |
|---|---|
| `compose.yaml` | 唯一服务拓扑、健康依赖、只读边界、端口和资源上限 |
| `.env.example` | 本地运行所需非秘密配置说明 |
| `backend/database/schema.sql` | 空库事务化 DDL 唯一事实源 |
| `backend/Dockerfile` | 生产依赖安装及非 root API 入口；运行时直接使用锁定虚拟环境，不写 uv cache |
| `.github/workflows/runtime.yml` | 构建、真实依赖、健康/代理/Worker、资源快照和部署态 OpenAPI 门禁 |
| `frontend/src/app/api/[[...path]]/route.ts` | 已有同源 API 转发；本切片不新建代理实现 |

API、Worker、CLI 独立进程；FastAPI 不启动消费者。没有新 HTTP 或业务数据契约，因此本切片不新增路由、DTO、ORM 或页面，生成客户端应保持零差异。

## 5. 失败、回退与证据边界

缺失数据库密码在 Compose 配置阶段失败；依赖不健康则阻止下游创建或保持不健康；API readiness 失败返回 046 定义的安全错误。镜像回退只在 `schema.sql` 与数据兼容时进行，持久卷不随普通停止删除。

S01 成功判据：Compose 解析与镜像构建成功；五个长期服务 healthy；空库执行唯一 SQL；PostgreSQL/Redis/Kafka 探针成功；API health/readiness、Web health 和同源 `/api/health` 成功；空 Worker 记录 `no_message_handlers_registered` 后退出 0；部署中 API 的 OpenAPI 生成客户端无差异；后端与前端全量门禁通过。

该证据只关闭 042 S00/S01 和 B01，不通过 AC-042-001—006。B0、保护性延期、共同负载、第二环境、升级恢复和浏览器业务体验必须在 S02—S04 重新取证。
