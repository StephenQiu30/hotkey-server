# 监控主题管理设计

日期：2026-09-22。本版接受 003 S00—S03：主题规则、不可变版本、owner 隔离、创建—编辑—重新打开、列表、复制、启停/归档，以及不产生副作用的本地规则预览。真实上游扩词、来源、周期调度和完整产品验收属于 S04。本文不把本地预算边界、受控规则或人工准备的 job 解释为已接入平台。

## 1. 范围、事实与决策

- 042 S01、034 S01、035 S01 及 009 S01 的先行输出已交付；S01—S03 复用当前 FastAPI、SQLAlchemy、PostgreSQL、会话/CSRF、统一错误与 OpenAPI 生成链。
- 当前没有可用来证明真实平台就绪的来源目录或适配器。S01—S03 只管理主题名与本地匹配规则并提供纯计算预览；新建或复制主题固定为 `paused` 和 `pending_source_selection`，恢复时必须已由后续来源流程置为 `ready`，不显示虚构来源，也不因保存、恢复或预览直接创建采集任务。
- PRD 中“首次 7 天、周期 60 分钟”及关键词上限原为建议值。S01 仅冻结与当前输入安全直接相关的上限：名称 1–80 字符，每组最多 50 项，每项规范化后 1–100 字符。回溯、频率、来源数量和预算不在没有来源证据时臆造默认值。
- 不新增依赖、服务、通用仓储层、迁移框架、`scripts/` 目录或 `.sh` 文件。不修改 Redis、Kafka、MinIO 或 Compose。

## 2. 一手资料与复用结论

| 依据 | 采用结论 |
|---|---|
| [Python `unicodedata.normalize`](https://docs.python.org/3.12/library/unicodedata.html#unicodedata.normalize) | 使用标准库 NFKC 处理兼容字符，不引入额外文本库。 |
| [PostgreSQL Constraints](https://www.postgresql.org/docs/current/ddl-constraints.html) | 使用非空、唯一、检查和外键保护单行/跨行持久不变式；不用跨行 `CHECK` 模拟版本关系。 |
| [SQLAlchemy Versioning](https://docs.sqlalchemy.org/en/20/orm/versioning.html) | ORM 可用技术版本列检测过期行；本领域已有业务规则版本，因此不再增第二个计数器，由 Service 锁定主题行并比较 `expected_version`。 |
| [FastAPI Body Updates](https://fastapi.tiangolo.com/tutorial/body-updates/) 与现有 046 契约 | 编辑输入使用独立严格 Pydantic Schema；Router 只处理 HTTP，运行时 OpenAPI 是唯一契约源。 |
| [PostgreSQL Explicit Locking](https://www.postgresql.org/docs/17/explicit-locking.html) 与 [SQLAlchemy `with_for_update`](https://docs.sqlalchemy.org/en/20/core/selectable.html#sqlalchemy.sql.expression.Select.with_for_update) | 暂停、恢复、归档按 owner 锁定同一主题行，串行化状态判断和写入；不新增分布式锁或状态机框架。 |
| [RFC 9110 Method Semantics](https://www.rfc-editor.org/rfc/rfc9110.html#name-method-definitions) | 复制是明确创建新资源的 POST，不承诺同一业务点击的传输级幂等；Web 在请求完成前禁用重复操作，客户端不配置自动重试。暂停、恢复、归档在相同目标状态下返回同一持久结果。 |
| [FastAPI Nested Models](https://fastapi.tiangolo.com/tutorial/body-nested-models/) 与 [RFC 9110 Content](https://www.rfc-editor.org/rfc/rfc9110.html#name-content) | 预览把关键词和标题样本放入 POST 请求体，不放 URL；复用严格嵌套 Pydantic 模型和现有会话/CSRF 边界。 |
| [shadcn/ui Dialog](https://ui.shadcn.com/docs/components/aria/dialog) | 创建与编辑页复用同一领域预览组件及现有 Radix Dialog；不引入新组件库。Portal 内表单显式阻止 submit 冒泡，避免误提交外层主题表单。 |

## 3. 规则规范化与匹配语义

`MonitorTopicService` 对名称和每个关键词执行相同的基础步骤：NFKC → 去除首尾空白 → 连续 Unicode 空白折叠为一个 ASCII 空格。展示值保留规范化后的大小写；比较键在此基础上使用 `casefold()`。同组重复保留首项并稳定去重。

- `match_any`：非空时任一词命中即满足；空组不额外限制。
- `match_all`：非空时每一词都命中才满足；空组不额外限制。
- `exclude`：任一词命中都优先排除，并返回实际命中的规范化排除词作为原因。
- `match_any` 和 `match_all` 至少一组非空；两组都空时返回 422，不创造“全部命中”。
- 同一比较键不得同时出现在 `match_any`/`match_all` 或包含/排除组；冲突返回 422 `keyword_group_conflict`，不静默改写用户意图。
- S01 仅做规范化后子串匹配；不引入正则、分词、模糊匹配或自动扩词。中文别名是用户显式录入的独立关键词。

### 3.1 冻结的 12 组样本

| # | 输入/标题 | 期望 |
|---|---|---|
| 1 | `Brand` / `brand 召回` | 大小写折叠后命中 |
| 2 | `ＢＲＡＮＤ` / `brand 召回` | NFKC 后命中 |
| 3 | `  品牌\t召回  ` / `品牌 召回通知` | 空白折叠后命中 |
| 4 | any=`[华为, HUAWEI]` / `Huawei 发布会` | 显式中文别名以 OR 语义命中 |
| 5 | any=`[品牌, 厂商]` / `厂商公告` | 任一命中即通过 |
| 6 | all=`[品牌, 召回]` / `品牌新闻` | 缺一词，不命中 |
| 7 | all=`[品牌, 召回]` / `品牌召回公告` | 全部命中才通过 |
| 8 | any=`[]`，all=`[品牌]` | 只按 all 判断，不因 any 空组全量命中 |
| 9 | any=`[品牌]`，all=`[]` | 只按 any 判断 |
| 10 | any=`[]`，all=`[]` | 422，不保存空包含规则 |
| 11 | include=`[品牌, 召回]`，exclude=`[招聘]` / `品牌召回招聘` | 排除优先，原因为 `招聘` |
| 12 | `[品牌, ＢＲＡＮＤ, brand]`；或同一词跨组 | 同组稳定去重；跨组精确冲突返回 422 |

### 3.2 本地预览与扩词边界

S03 的预览输入沿用三个规则组，并接收 1—20 条、每条 1—500 字符的标题样本。Service 只复用第 3 节的规范化和匹配函数，不保存主题、不创建版本/job/Outbox、不访问来源，也不占用预算。输出只返回样本索引、是否命中和规范化后的排除原因，不回显完整标题样本；响应固定 `Cache-Control: no-store`。

扩词影响按已知与未知分开：本地别名匹配明确为 0 次外部查询、0 预算单位；上游扩词状态为 `pending_source_selection`，查询次数和预算保持 `null`/未知。没有真实来源能力、权限和预算政策时，页面只说明不能启用，不提供虚假的上游开关，也不把预览保存为规则版本。真实上游扩词在 S04 取得来源证据后另行设计和验收。

## 4. 数据、事务与并发

S01 只增加两张表，由 `backend/database/schema.sql` 一次性完整建立：

| 表 | 核心字段与约束 | 职责 |
|---|---|---|
| `monitor_topics` | UUID 主键，`owner_id` 外键，`name`，`status=paused`，`readiness_status=pending_source_selection`，`current_version >= 1`，创建/更新时间 | 稳定主题身份、当前指针和后续生命周期锚点 |
| `monitor_topic_versions` | `(topic_id, version)` 联合主键，`created_by`，三个 JSONB 字符串数组，`created_at` | 不可变规则快照；数组已在 Service/Pydantic 校验并以 PostgreSQL JSON 类型检查拒绝非数组 |

`MonitorTopicService.create_topic` 在同一事务中插入主题与版本 1。`update_topic` 按 owner 锁定主题行：不存在与跨 owner 都映射为 404；`expected_version` 不等于当前版本时返回 409 `topic_version_conflict`；名称与规则都等价时返回当前资源。仅名称变化时更新主题而不产生规则版本；三个规则组任一变化时插入 `current_version + 1` 的快照并更新主题指针。由最外层 Service 提交或回滚，Router 不直接操作 ORM。

不删除旧版本。后续创建 job 时使用稳定 `configuration_ref=topic:{topic_id}` 和显式 `configuration_version`；已运行 job 不读当前指针。S01 不创建 job、Outbox 或定时记录。

S02 的复制只读取源主题当前规则快照，创建新的主题 UUID 和独立版本 1；不复制 job、Outbox、结果或历史版本。列表按 owner 和 UUID 游标分页，默认隐藏归档项，单页 1—50 项。暂停、恢复和归档在事务内按 owner `FOR UPDATE` 锁定主题行：重复到达同一状态不刷新时间；恢复仅允许 `readiness_status=ready`，否则 409 `topic_not_ready`；归档后可读取和复制，但不能编辑、暂停或恢复，重复归档保持幂等。

暂停或归档只禁止后续调度使用该主题，不假装已经停止运行中的任务。S02 尚无主题调度器或真实主题 job；已存在的单任务 `POST /api/jobs/{job_id}/cancel` 和任务详情页仍是运行任务的实际取消入口。主题到任务的可浏览关联、周期任务不再生成及运行中任务状态联验保留到 S04。

## 5. HTTP 与错误契约

| 操作 | 契约 | 成功与边界 |
|---|---|---|
| 创建 | `POST /api/topics`，`createMonitorTopic` | 会话 + CSRF；`201 MonitorTopicView`，`Location: /api/topics/{id}`，`Cache-Control: no-store` |
| 读取 | `GET /api/topics/{topic_id}`，`getMonitorTopic` | 会话；`200 MonitorTopicView`；不存在/跨 owner 统一 404 |
| 编辑 | `PATCH /api/topics/{topic_id}`，`updateMonitorTopic` | 会话 + CSRF；必填 `expected_version`；`200 MonitorTopicView`；过期版本 409 |
| 预览 | `POST /api/topics/preview`，`previewMonitorTopic` | 会话 + CSRF；`200 MonitorTopicPreviewView`；仅本地计算，样本不入 URL/响应，不产生持久记录或外部请求 |
| 列表 | `GET /api/topics`，`listMonitorTopics` | 会话；UUID 游标，`limit` 1—50；默认隐藏归档项，可显式包含；`200 PageView` |
| 复制 | `POST /api/topics/{topic_id}/clone`，`cloneMonitorTopic` | 会话 + CSRF；`201 MonitorTopicView` 与新 `Location`；复制当前规则为独立 v1，不复制旧任务 |
| 暂停/恢复 | `POST /api/topics/{topic_id}/pause|resume` | 会话 + CSRF；`200 MonitorTopicView`；同状态幂等；来源未就绪恢复返回 409 |
| 归档 | `POST /api/topics/{topic_id}/archive`，`archiveMonitorTopic` | 会话 + CSRF；`200 MonitorTopicView`；历史保留、重复归档幂等，不删除资料或宣称任务已取消 |

`MonitorTopicInput`/`MonitorTopicUpdateInput` 只含 `name`、`match_any`、`match_all`、`exclude` 及编辑需要的 `expected_version`；owner、状态、就绪状态和版本号均不由客户端选择。输出含主题 ID、规范化名称、固定暂停/待选来源状态、当前版本、当前规则及时间，不包含 owner ID。

输入校验使用 046 统一 422；分组冲突是稳定应用错误 `keyword_group_conflict`；过期编辑是 409 `topic_version_conflict`；未登录 401，CSRF 403，隔离 404，未分类故障 500。所有操作均有中文 summary、tag、唯一 `operation_id`、显式成功状态与实际错误模型。

S03 已增加本地预览和已知/未知扩词预算说明；仍不用空来源、上游查询或调度实现占位。

## 7. 安全、日志与恢复

- owner 只来自有效 Session；写操作使用现有双提交 CSRF。同 ID 不属于当前 owner 时不泄露资源存在。
- 通用日志不写主题名、关键词数组或预览标题样本，只写 request ID、路由模板、状态、主题 ID 和版本。版本行的 `created_by`/时间提供当前最小审计事实；S02 的状态时间可核对但尚未建立独立生命周期审计表，完整操作审计留给 039/本计划后续切片。
- DDL 仅用于已确认空的开发/测试库。存量数据需要保留时，执行备份、新库完整建表和校验导入，不临时写迁移脚本。
- 回退先停止主题新增/编辑入口，保留主题和旧版本；使用向前修复恢复读取，不删表、不清理持久卷。

## 8. Red/Green 与验收边界

S01 Red 先证明以下能力缺失：12 组规则样本中的规范化/排除优先，主题端点不存在，以及过期 `expected_version` 尚不会返回 409。Green 至少验证：

1. 12 组固定规则的匹配、去重、冲突和排除原因。
2. 真实 PostgreSQL 中创建同时只产生主题和版本 1；编辑产生版本 2，版本 1 不变。
3. 两个客户端使用同一 `expected_version` 编辑时仅一个成功，另一个 409；失败事务不留半条版本。
4. 会话、CSRF、owner 404、422 和统一 500 形状正确；运行时 OpenAPI 与生成客户端无漂移。
5. 从真实 Web 创建后进入详情，编辑并刷新/重新打开仍看到新版本；版本冲突、未登录、桌面与窄屏边界可见。
6. 后端 Ruff/format/mypy/全量 pytest，前端 lint/typecheck/format/test/build 及 `pnpm openapi:check` 通过。

S02 Red 另以真实 PostgreSQL 证明 `GET /api/topics` 原为 405、`POST /api/topics/{id}/pause` 原为 404。Green 增加验证：owner 列表与游标、归档默认隐藏、复制为独立 UUID/v1/暂停且 jobs 表仍只关联原主题、来源未就绪恢复 409、ready 后恢复/暂停、重复恢复/归档不改变结果、归档后编辑拒绝、CSRF，以及桌面/390×844 的列表—复制—恢复失败—归档交互和 WCAG A/AA axe 0 violation。

S03 Red 以真实 PostgreSQL 和已认证会话证明 `POST /api/topics/preview` 原返回 405。Green 验证 NFKC/大小写/AND/OR/排除优先、会话/CSRF、响应不回显样本、topics/jobs 零写入、本地查询与预算均为 0、上游值保持未知；真实 Web 进一步发现并修复 Portal 内预览提交向外层主题表单冒泡。修复后每次操作只产生预览请求，数据库保持 0 主题/0 版本/0 job；桌面和 390×844 无横向溢出，WCAG A/AA axe 为 0 violation。

S00—S03 只能关闭 `CHK-003-G4-001/002/003`，不是 AC-003-002—006 的完整产品验收：当前没有真实来源、周期调度、真实主题任务/结果、暂停后的调度零新增联验或上游扩词预算。S03 只证明本地预览与未知边界，不满足 AC-003-006 的“启用上游扩词并保存”；S02 人工 job 也不能替代 AC-003-004/005 的产品前提。Acceptance 只能在 S04 按原始 AC 建立。
