# 可追溯与可复现设计

日期：2026-09-21。本版只冻结 028 S00—S01：以现有 job/operation 与生命周期资源建立不可变输入清单、比较参考集、方法版本和确定性指纹。本版不实现实际热度算法、模型运行记录、正文版本提示、审计 UI 或产品 Acceptance。

## 1. 当前事实与问题

- `jobs` 已保存 owner、job/operation、配置/来源上下文；`evidence_resources` 已保存受准入和保留约束的资源记录，但两者之间没有“某次计算实际使用哪些输入”的持久关系。
- 027 S00 已冻结对象身份、不可变观察和版本边界；内容域尚未实现，因此 S01 不能虚构作品快照表或复制正文。
- 当前没有评分/分析业务实现。S01 只能证明输入清单和方法身份可稳定冻结、重放同一清单得到相同指纹；真实分数一致性必须在 013 接入后复验。

## 2. 目标与非目标

### 2.1 目标

1. 每份清单属于一个 owner 和 job，自动继承 operation，并冻结 `result_kind`、方法 key/version 与受限参数。
2. 每项输入只引用当前 owner 可读的 `EvidenceResource`，角色明确为 `subject` 或 `reference`，同时保存调用方提供的不可变 `snapshot_ref`。
3. 参考集按稳定键规范排序并保存序号；相同集合不受调用方传入顺序影响，不同参考集必得不同指纹。
4. 同一 job/result kind 的等价重试返回原清单，冲突重用显式拒绝；查询继续检查 owner，不能借清单越权读取正文。

### 2.2 非目标

- 不保存正文、搜索词、模型 prompt/output、Cookie、Token 或任意调试 metadata。
- 不实现通用 provenance graph、事件溯源框架、外部观测系统或新服务。
- 不声称 RFC 8785 完整兼容；S01 只规范化已禁止浮点和嵌套对象的领域子集。
- 不提供 HTTP/UI。当前没有评分结果页面或复算入口，强建接口会形成空业务能力。

## 3. 一手资料与复用结论

| 依据 | 采用结论 |
|---|---|
| [W3C PROV Primer](https://www.w3.org/TR/prov-primer/) | 将资源快照视为 entity、job/operation 视为 activity、方法版本视为 plan；S01 保存实际使用关系，不建立一套与现有领域重复的图数据库。 |
| [RFC 8785 JSON Canonicalization Scheme](https://www.rfc-editor.org/rfc/rfc8785.html) | 哈希前需要不变表示，JSON 数组顺序不能自行改变。S01 先按领域规则规范参考集顺序，再用固定 UTF-8、键排序和紧凑分隔符编码受限标量；不接入第三方 JCS 包。 |
| [Python `decimal`](https://docs.python.org/3.12/library/decimal.html) | 后续确定性评分使用字符串构造的 Decimal、显式精度和舍入；S01 不接受 float 参数，避免二进制浮点进入历史方法身份。 |
| [PostgreSQL aggregate ordering](https://www.postgresql.org/docs/current/sql-expressions.html#SYNTAX-AGGREGATES) | 有序集合必须显式 `ORDER BY`；持久输入使用角色内序号与唯一约束，读取时按角色/序号排序，不依赖默认行序。 |

## 4. 数据契约

### 4.1 `provenance_manifests`

每行表示一次结果类型的冻结计算依据：

- `owner_id`、`job_id`、`operation_id`：与现有任务一致；服务在事务内验证 job 归属及 operation。
- `result_kind`：稳定小写标识，例如未来的 `heat_score`；S01 测试使用中性受控类型，不宣布产品算法。
- `method_key`、`method_version`：方法身份和不可变版本，均为非敏感稳定标识。
- `method_parameters`：最多 32 个稳定键，值仅允许字符串、整数、布尔或 `None`；不允许 float、数组、对象或秘密字段。
- `manifest_fingerprint`：对规范化清单做 SHA-256；它用于幂等和复核，不是访问令牌或真实性签名。
- `(owner_id, job_id, result_kind)` 唯一；同键不同指纹为冲突。

### 4.2 `provenance_manifest_inputs`

每行保存 `role`、`resource_record_id`、`snapshot_ref` 和角色内 `ordinal`：

- `resource_record_id` 以 `(owner_id, id)` 外键指向 `evidence_resources`，禁止跨 owner 引用。
- 资源元数据有清单引用时不可直接物理删除；正文和在线副本仍按 036 清理，owner 级级联删除同时移除整份清单。
- 创建时资源必须尚未到期且无删除指令；清单不会复制资源正文或 cleanup target。
- `snapshot_ref` 是调用方冻结的版本引用，只允许稳定非敏感标识；S01 不把它解释为已存在的内容版本表。
- 同一角色下 `(resource_record_id, snapshot_ref)` 不得重复；至少一个 subject 和一个 reference。

## 5. 规范化与幂等

1. 校验 job、资源归属及当前可读性。
2. 分别按 `(resource_record_id, snapshot_ref)` 排序 subject/reference，生成从 0 开始的 ordinal。
3. 构造固定 schema version、job/operation、result kind、方法、参数和有序输入列表；参数键递归排序只适用于这一层受限对象。
4. 使用 `json.dumps(..., ensure_ascii=False, allow_nan=False, sort_keys=True, separators=(",", ":"))` 编码并做 SHA-256。
5. 首次事务化写入 manifest 与 inputs；等价重放返回原记录，不同指纹拒绝。

相同参考集传入顺序不同仍得到同一指纹；改变任一资源、snapshot、方法版本或参数必须改变指纹。S01 的“确定性复算”证据只覆盖该输入身份计算，不覆盖尚不存在的产品评分值。

## 6. 目录、安全与生命周期

- 继续扩展 `evidence/models.py`、`schemas.py`、`services.py`；不创建空 `provenance/` 或 `audit/` 包。
- `database/schema.sql` 是唯一 DDL；ORM 与 SQL 同提交，使用现有空 `hotkey_dev` 完整重建验证。
- 创建清单时执行当前读取屏障；S03 再实现删除/到期后的可复算状态传播。任何阶段都不能从清单恢复已删除正文。
- 一般日志不绑定参数或 snapshot 内容。UUID/指纹只用于关联，不授予权限。

S01 不改 HTTP/OpenAPI、前端、Redis、Kafka、MinIO、依赖或服务配置；没有对应页面，客户端生成和浏览器验证 N/A。

## 7. 验证与后续边界

Red 先证明当前没有 `ProvenanceManifestInput` 契约。Green 使用真实 PostgreSQL 验证 owner/job/resource 归属、当前读取屏障、参考集规范排序、指纹差异、幂等/冲突、DDL/ORM 一致及无正文复制，再运行 architecture、Ruff、mypy 和后端全量测试。

`OPEN-028-001` 在 S01 只关闭清单随被引用资源生命周期受控；最低可复算周期不另设副本期限。S02 处理模型输出和真实内容版本，S03 处理审计与删除传播，S04 才执行产品 AC。028 保持 `in_progress`、产品 AC 0/6，不建立 Acceptance。
