# 用户角色与权限管理设计

## 现状

viewer、editor、admin 角色和管理员用户接口已经存在，账户资料页可显示角色，但缺少完整用户管理工作台。

## 目标

以最小权限控制读取、编辑和管理操作，并让管理员能够审计地调整用户状态和角色。

## 非目标

本条不跨越相邻编号实现其业务细节，也不建立第二套身份、任务、数据、API 或 UI 事实源。

## 核心决策

- 角色固定为 viewer、editor、admin；MVP 不引入自定义 RBAC 规则引擎。
- Transport 执行粗粒度角色门禁，Application 再验证资源动作；前端隐藏不是安全边界。
- 删除用户采用可恢复软删除，禁止操作者删除或降级最后一个可用管理员。
- 角色、禁用、恢复等敏感操作记录 actor、before、after、request_id 和结果。

## 数据、接口与交互

- 用户列表、筛选和分页
- 角色与状态调整
- 删除与恢复
- 权限不足状态和审计记录

所有新增跨端字段先进入 `backend/db/schema.sql` 和后端 DTO/Swaggo 注解，再生成 `docs/openapi/swagger.json` 与前端 Client。页面同时提供正常、加载、空、错误和权限不足状态。

## 安全、失败与降级

前后端权限矩阵漂移会产生误导；OpenAPI 与页面动作必须从同一角色表评审。

失败必须被分类、可观测且不破坏历史事实；可选外部依赖不可用时，核心读取链路继续工作。

## 设计验收边界

- viewer 不能调用写接口，editor 不能执行管理员动作
- 最后一个管理员保护有并发测试
- 管理员页面在移动端和键盘操作下可用
