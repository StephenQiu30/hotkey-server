# 双环境容器部署设计

## 决策

- `docker-compose.yml` 只定义一次前端、后端、PostgreSQL 16/pgvector、Redis、MinIO、数据库初始化、Bucket 初始化、依赖、健康检查与卷。
- `docker-compose-env.yml` 与 `docker-compose-prod.yml` 只保存端口、env 文件、凭据约束、运行环境和应用镜像标签差异，不复制公共服务块，也不增加启动脚本。
- 日常环境固定项目名 `hotkey-env` 与应用镜像 `hotkey-server:env` / `hotkey-web:env`；生产环境覆盖为 `hotkey-prod` 与 `hotkey-server:prod` / `hotkey-web:prod`。
- 数据库初始化只允许在空库执行完整 `db/schema.sql`；已初始化数据库只执行兼容性验证，非空但不兼容的数据库必须失败。
- PostgreSQL、MinIO 与 Vault 使用持久卷。生产环境只映射 Server HTTP 端口，不向宿主机发布数据库、Redis、MinIO 或控制台端口。
- Server 镜像使用 `golang:latest` 与 `alpine:latest` 多阶段构建、默认禁用 ONNX/CGO，并以非 root 用户运行。Compose 上游镜像使用 `latest`；pgvector 官方不提供该标签，因此保留 PostgreSQL 16 兼容边界并使用浮动 `pg16`。ONNX 镜像不属于本任务。
- `backend/.env` 与根 `.env.prod` 保存应用运行配置和密钥；示例文件不得包含可用认证密钥。容器环境分别固定 `HOTKEY_ENV=development` 与 `HOTKEY_ENV=production`。
- 日常覆盖让 Server 与 `db-init` 读取 `backend/.env`。生产覆盖仅让 Server 读取根 `.env.prod`；启动命令以 Compose 原生 `--env-file .env.prod` 将 PostgreSQL/MinIO 的三项凭据最小映射到支持服务，并由 Compose 生成内部 DSN 和 Server MinIO 凭据。
- env 示例只激活核心必填连接与认证项；程序已有默认值、Compose 已固定值和未启用的 SMTP/Provider 配置不要求填写，可选项只提供中文注释示例。

## 运行与健康边界

- `hotkey-server` 使用 `all` 角色，并等待 PostgreSQL 健康、数据库初始化成功、Redis 健康和 MinIO Bucket 初始化成功。
- 数据库初始化执行 `db verify || db init --empty-only --confirm-empty || db verify`：兼容库在第一次验证后退出，空库完成初始化，并发初始化中等待锁的一方可在最终验证后成功；非空不兼容库三步均失败且不得被修改。
- 容器健康检查使用 `/readyz`，验证 HTTP 与 PostgreSQL；Redis、MinIO、SMTP 和外部 AI Provider 的运行状态仍由各自操作与业务错误处理负责。
- 容器关闭宽限期为 30 秒，高于默认 15 秒应用关闭超时。

## 非目标

- 不修改 Schema、OpenAPI、业务模块或运行角色。
- 不在镜像或 Compose 文件中写入真实密钥。
- 不提供 TLS、反向代理、集群编排、备份恢复或 ONNX Runtime 镜像。
