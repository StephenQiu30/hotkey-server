# 双环境容器部署设计

## 决策

- 使用 `docker-compose-env.yml` 与 `docker-compose-prod.yml` 直接区分日常和生产环境，不保留通用 `docker-compose.yml`，不增加启动脚本。
- 两份 Compose 均运行同一个模块化单体镜像及 PostgreSQL 16/pgvector、Redis、MinIO、数据库初始化和 Bucket 初始化服务。
- 日常环境固定项目名和镜像标签为 `hotkey-server-env` / `hotkey-server:env`；生产环境固定为 `hotkey-server-prod` / `hotkey-server:prod`。
- 数据库初始化只允许在空库执行完整 `db/schema.sql`；已初始化数据库只执行兼容性验证，非空但不兼容的数据库必须失败。
- PostgreSQL、MinIO 与 Vault 使用持久卷。生产环境只映射 Server HTTP 端口，不向宿主机发布数据库、Redis、MinIO 或控制台端口。
- Server 镜像使用匹配 `go.mod` 的 Go 1.26 多阶段构建、默认禁用 ONNX/CGO，并以非 root 用户运行。ONNX 镜像不属于本任务。
- `.env` 与 `.env.prod` 保存运行配置和密钥；示例文件不得包含可用认证密钥。容器环境分别固定 `HOTKEY_ENV=development` 与 `HOTKEY_ENV=production`。
- 日常 Compose 的服务固定使用 `env_file: .env`，生产 Compose 的服务固定使用 `env_file: .env.prod`；生产文件不引用 `.env`，因此选择 Compose 文件即选择运行配置，不增加启动脚本、Makefile 入口或确认变量。

## 运行与健康边界

- `hotkey-server` 使用 `all` 角色，并等待 PostgreSQL 健康、数据库初始化成功、Redis 健康和 MinIO Bucket 初始化成功。
- 数据库初始化执行 `db verify || db init --empty-only --confirm-empty || db verify`：兼容库在第一次验证后退出，空库完成初始化，并发初始化中等待锁的一方可在最终验证后成功；非空不兼容库三步均失败且不得被修改。
- 容器健康检查使用 `/readyz`，验证 HTTP 与 PostgreSQL；Redis、MinIO、SMTP 和外部 AI Provider 的运行状态仍由各自操作与业务错误处理负责。
- 容器关闭宽限期为 30 秒，高于默认 15 秒应用关闭超时。

## 非目标

- 不修改 Schema、OpenAPI、业务模块或运行角色。
- 不在镜像或 Compose 文件中写入真实密钥。
- 不提供 TLS、反向代理、集群编排、备份恢复或 ONNX Runtime 镜像。
