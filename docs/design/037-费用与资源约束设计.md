# 费用与资源约束设计

日期：2026-09-21。v1.0 冻结 S00—S01 的免费组件与全尝试计量；v1.1 扩展到 S02，冻结分层窗口、原子预留、累计额度与并发槽位的结算/释放及耗尽决策。时长、存储、优先级公平、HTTP 和 UI 仍不属于本版。2026-09-23 用户允许 X 官方 API 作为唯一付费例外；离线金额账本已具备，但当前代码和数据库约束仍拒绝 `paid` 核心组件。控制台账期确认、费率快照及请求账本与金额预留的原子装配尚未完成，不能通过改 `enabled_for_core` 绕过现有门禁。

### 2026-09-23 X 离线金额账本子片

[X 官方定价](https://docs.x.com/x-api/getting-started/pricing)当前按返回的 Post 资源计费，费率会变且控制台为准。仅增加 `x_api_usd_micros` 累计预算度量，1 美元 = 1,000,000 整数单位；不使用浮点，也不内置实际费率或账期额度。`XApiPostReadCost` 接受显式正整数单价和本页最大 Post 数，计算最坏预留；完整且没有额外扩展资源的响应按实际 Post 数结算，失败或未知结果按最大数结算。Post 数上限 100，乘积必须落在 PostgreSQL BIGINT 范围内；来源上下文必须为 `x`，来源层级策略也只能指向 `x`。无有效全局政策仍由 S02 既有服务拒绝，降低额度和并发竞争复用同一持久窗口语义。

本子片限定 `jobs/schemas.py`、`jobs/models.py`、`jobs/services.py`、唯一 `database/schema.sql` 与现有预算测试；不新增表、路由、Worker、代理放行、脚本或服务。只在隔离的空 PostgreSQL 测试库按完整 Schema 验证美元单位预留、缩额、结算、来源隔离和缺政策拒绝；受控 `MockTransport` 联验仅证明适配器回调可进入持久窗口。`resource_component_policies` 及 `begin_attempt` 的 paid 拒绝保持不变；尚未有账期起止、控制台硬上限核验、费率快照与请求账本原子装配，故不能用此金额账本授权任何真实 X 请求，也不增加 037 产品 AC。测试中的 5,000 微美元单价是合成输入，不是部署默认值。

## 1. 边界与决策

| 项 | S01 决策 |
|---|---|
| 领域归属 | 执行前置约束，放入现有 `jobs` 领域；不新建空泛的 `budgets` 顶层模块。 |
| 免费语义 | `local` 和 `zero_price` 可用于免费核心路径；`free_credit`、`paid`、`unknown` 默认不可用，禁止暗中切换。 |
| 计量时点 | 每个网络请求或分析尝试在外部副作用之前写入 `started`，有结果后更新终态；过滤和空结果不撤销尝试。 |
| 重试语义 | 同一实际尝试的重放使用同一 `attempt_id`，幂等；真正的下一次重试使用新序号和新 `attempt_id`，因而另行计数。 |
| 隐私 | 账本只保存稳定组件、阶段、作业操作及结果，不保存 URL、query、body、token 或外部正文。 |

`OPEN-037-001` 在 S01 部分关闭：本切片的最小计量单位是一次实际网络/分析尝试，且核心只允许 `local`/`zero_price`。数值配额、并发、时间窗口和存储阈值由 S02—S03 在适配器实验后冻结，不在 S01 猜测默认值。

## 2. 持久化契约

### `resource_component_policies`

- 主键 `id`，所属 `owner_id`；`(owner_id, component_key)` 唯一。
- `component_key` 是稳定小写标识，`component_version` 是实际组件版本。
- `cost_class` 限定为 `local|zero_price|free_credit|paid|unknown`。
- `enabled_for_core=true` 时数据库强制 `cost_class` 只能是 `local|zero_price`。
- `terms_reference`、`reviewed_at`、`policy_version`、`created_at`、`updated_at` 支持审计和乐观版本。

### `resource_usage_attempts`

- 主键 `id`，以 `(owner_id, attempt_id)` 唯一拦截重放重复计量。
- 记录 `operation_id`、组件策略及当时 `component_version`、`usage_kind`、`stage`、`outcome`、`started_at`、`finished_at`。
- `usage_kind` 限定为 `network_request|analysis_attempt`；`outcome` 限定为 `started|succeeded|failed|filtered|empty`。
- `started` 不能有 `finished_at`；终态必须有 `finished_at` 且不早于 `started_at`。
- 复合外键 `(owner_id, component_policy_id)` 禁止跨所有者关联。

数据库以约束和唯一键守住最终不变式，写入使用 PostgreSQL `INSERT ... ON CONFLICT` 保证并发下的原子决定。参考 PostgreSQL 官方的 [INSERT/ON CONFLICT](https://www.postgresql.org/docs/18/sql-insert.html) 和 [Constraints](https://www.postgresql.org/docs/18/ddl-constraints.html)。

## 3. 服务与调用边界

`ResourceBudgetService` 仅负责三类事务：

1. `save_component_policy`：按 owner/component 插入或更新策略，变更时版本递增。
2. `begin_attempt`：锁定当前策略，只允许已启用的免费类别，在副作用前幂等写入 `started`。相同 ID 但输入不同拒绝为冲突。
3. `finish_attempt`/`usage_summary`：幂等收敛终态，并按 owner/operation 返回各结果计数；不将成功或保存条数当作总尝试数。

适配器接入时，HTTPX 在 request hook 中、Tenacity 在 `before` 回调中调用 `begin_attempt`，才能覆盖每次发送/重试。若第三方 SDK 内部重试不可观测，必须关闭内部重试或使用其公开钩子，不得从最终返回值反推。依据为 [HTTPX event hooks](https://www.python-httpx.org/advanced/event-hooks/) 与 [Tenacity callbacks](https://tenacity.readthedocs.io/en/latest/)。S01 只交付该契约和可测账本，不宣称任何尚未接入的 SDK 已覆盖。

`resource_attempt_id(operation_id, component_key, stage, sequence)` 使用固定 UUID namespace 产生确定 ID：消息重放可重用，每次真实重试必须传入递增的 `sequence`。

## 5. 启用与回退

- 只复用当前本地 PostgreSQL 和已启动服务，不新起容器或第二套配置。
- 本地数据库若已确认为空，可用完整 `schema.sql` 重建该开发库；不删除其他库、卷或现有服务。
- 新表创建后不预置“免费”组件；每个真实适配器必须以已审查的显式策略启用。
- 回退程序前先停止新尝试；保留账本作为证据，不以删表作为日常回退。

## 6. 证据边界

S01 通过只能证明：未审查或付费组件被核心路径拒绝，每个明示尝试可在结果之前持久化，重放幂等，失败/过滤/空结果均保留计数。它不能证明真实采集、SDK 内部重试、整条免费业务路径、并发配额、存储公平性或任一产品 AC 已通过。因此 037 继续 `in_progress`，不建 Acceptance。

## 7. S02 预算契约

S02 不写死业务默认值。每项预算必须显式提供正整数上限、正时间窗口与生效时间，没有当前全局政策时默认拒绝。

| 契约 | 决策 |
|---|---|
| 度量 | `network_request`、`analysis_attempt` 是窗口内累计额度；`concurrency_slot` 是结算后全量归还的并发槽位。 |
| 层级 | `global`、`source`、`connection`、`job`；每次预留选取全局政策和与调用上下文匹配的全部政策，任一层不足都不写入预留。 |
| 最严格结果 | 剩余量是全部适用窗口剩余量的最小值；耗尽时返回所有限制策略和最晚重置时刻。 |
| 幂等 | 同一 `reservation_id` 与等价输入返回原预留；重用 ID 改变 operation、度量、数量或上下文时拒绝。 |
| 结算 | 累计额度将实际使用量转入 `used_units`，未用部分释放；并发槽位结算时归还全部预留，实际占用仍记入预留记录。 |
| 持久性 | 窗口、预留和结算全在 PostgreSQL；进程重启、新任务或更换连接不会清空全局窗口。 |

预算上下文只保存稳定的 source/connection/job 标识的 SHA-256 指纹，不保存查询词、URL、凭据或正文。当前无真实业务资源表，因此 S02 由内部调用方从受信领域对象组装上下文，不得原样接受客户端 owner 或范围。

## 8. S02 持久化模型

### `resource_budget_policies`

- `(owner_id, budget_key)` 唯一，保存 metric、scope、显式上限、窗口秒数、锚点、启用状态和版本。
- `global` 的 `scope_reference` 必须为空，其余层级必须是稳定小写标识。
- 同一 key 只允许更新 `limit_units` 和 `enabled`，变更时版本递增；metric、scope、窗口和锚点为结构契约，改变时必须使用新 key，防止配置变更暗中重置额度。

### `resource_budget_windows`

- 以 `(owner_id, budget_policy_id, window_start)` 唯一，保存 `used_units` 与 `reserved_units`。
- 窗口边界以政策初始锚点和 `window_seconds` 计算，时区统一为 UTC；政策限额调低时不改写已用/预留，只使剩余量变为 0。
- 累计模式的 `used_units` 不减少；并发模式的 `used_units` 始终为 0，只使用 `reserved_units` 表示当前占用。

### `resource_budget_reservations`

- 一个逻辑 `reservation_id` 对每个适用策略保存一行；`(owner_id, reservation_id, budget_policy_id)` 唯一。
- 每行快照 policy version、window、limit、requested/actual/released units、预留后剩余量、上下文指纹与 `reserved|settled` 状态。
- 结算是幂等的；已结算预留以不同实际量重放时拒绝。

## 9. S02 事务和并发算法

`ResourceBudgetService` 增加 `save_budget_policy`、`reserve_budget`、`settle_budget_reservation`：

1. 预留事务先检查幂等重放，再按稳定顺序对全部适用 policy 执行 `SELECT ... FOR UPDATE`。
2. 在同一事务内创建/锁定当前 window，先检查所有剩余量；任意一项不足都返回 `delayed`，不更改任何计数。
3. 全部通过后才一次写入各 window 的 `reserved_units` 和预留记录。结算事务按同一顺序锁定预留与 window，然后转入实际用量并释放剩余。
4. 长时外部工作绝不在该事务中执行；行锁只覆盖短事务裁决。

PostgreSQL 官方说明 `FOR UPDATE` 会阻止其他写入者/锁定者直到事务结束，并建议多对象总以一致顺序取锁来避免死锁：[Explicit Locking](https://www.postgresql.org/docs/18/explicit-locking.html#LOCKING-ROWS)。默认 Read Committed 下，等待结束后的 `SELECT FOR UPDATE` 会锁定并返回已更新的行，与本算法的二次判定一致：[Transaction Isolation](https://www.postgresql.org/docs/18/transaction-iso.html#XACT-READ-COMMITTED)。

## 10. S02 错误、验证与边界

- 未配全局预算：`BudgetPolicyUnavailableError`，默认拒绝。
- 额度不足：正常返回 `delayed`，包含请求量、剩余量、限制 key、`next_window|capacity_release` 恢复条件及可确定的 `retry_at`；不冒充错误或成功。
- 幂等输入/结算冲突：`BudgetReservationConflictError`。
- 真实 PostgreSQL 集成测试必须覆盖：两事务竞争最后 1 单位最多一个成功；严格层级拦截；未用预留释放；并发槽结算后可重用；同窗口重启不恢复；跨窗口才获得新额度。
- S02 仍无 HTTP/OpenAPI、UI、Worker、Redis、Kafka 或 MinIO 变更；这些不用空适配器补位。

S02 通过只能证明受控预算契约在真实 PostgreSQL 下的并发、重启和跨窗口语义。它不证明真实采集已绑定预算、长时占用自动回收、优先级/存储公平性、用户界面或 AC-037-004/005 的产品端到端已通过。037 仍为 `in_progress`，不创建 Acceptance。
