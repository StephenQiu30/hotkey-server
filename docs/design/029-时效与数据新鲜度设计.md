# 时效与数据新鲜度设计

日期：2026-09-24。本版冻结 029 S00—S02：补齐计划到期事实与严格时间链，并从既有任务/尝试记录派生最后尝试、最后完整成功及当前排队原因。新增任务详情响应 DTO 和现有详情页展示，不新增表、持久字段、队列、缓存、依赖或通用 `Result<T>` 外壳。缺失时间保持未知，来源无时区或未来时间不生成误导性发现延迟。本版不实现覆盖缺口、陈旧传播、B0 P95 或产品 Acceptance。

## 1. 当前事实与问题

- `jobs` 已持久化受理、首次启动、完成和延期时间，`job_stage_attempts` 已保存 request/parse/save/analysis 的开始与结束，但定时任务没有独立的“计划到期”列。
- `sources` 契约已有可空 `published_at` 和必填 `observed_at`，`evidence_resources` 已有 `collected_at`/`created_at`；这些事实属于各自领域，029 不复制成第二套时间表。
- 当前没有统一计算契约。调用方容易把缺失当 0、把来源等待混入本地处理，或对无时区/未来发布时间算出负延迟。

## 2. S01 目标与非目标

### 2.1 目标

1. `jobs.scheduled_for_at` 保存计划任务所属窗口的到期时刻；手动任务保持 `NULL`，不以受理时间冒充计划时间。
2. 建立严格时间链 DTO：计划到期、受理、首次启动、来源请求开始、来源观察、持久化、可查询，以及可空来源发布时间/精度。
3. 只在端点齐全且顺序有效时计算非负整数微秒；缺失端点返回 `None`，不返回 0 或当前时间。
4. 来源发布时间区分 `valid`、`unknown`、`missing_timezone`、`future_skew`；后三者不计算发布到发现延迟，但保留原始输入供后续诊断。

### 2.2 非目标

- 不新增 freshness/monitoring 服务、表、队列、缓存、依赖或后台任务。
- 不在 S01 判断成功、陈旧或缺口，不冻结“两周期”建议值，不计算 P95。
- 不把阶段 DTO 当成 OpenTelemetry trace 导出，也不创建独立运维页面。
- 不推断上游发布时间；来源未提供时保持 unknown。

## 3. S02 成功时刻与延期分类

### 3.1 输出契约

在现有 `JobStatusView` 增加可空 `source_freshness` 领域 DTO；非来源任务为 `null`。来源任务返回：

- `last_attempt_at`：相同所有者、来源、能力、`configuration_ref` 与 `configuration_version` 下，`JobAttempt.started_at` 的最大值。创建但未真正取得执行权的任务不算尝试。
- `last_success_at`：同一精确作用域下状态为 `succeeded` 的 `Job.completed_at` 最大值。`partially_succeeded`、失败、取消及仅有部分页面结果均不推进该时间。
- `delay_reason`、`delay_since_at`、`delay_duration_us`：仅描述当前 `queued` 任务。延期原因采用固定枚举 `internal_queue`、`rate_limited`、`budget_exhausted`、`transient_failure`、`manual_retry`、`other`，不向用户透传任意数据库 `defer_reason`。

最后尝试/成功是来源能力配置版本的只读投影，不写回连接表或创建第二套水位。查询必须同时约束 `owner_id`、来源/能力及配置引用/版本；更换配置版本不会继承旧版本的新鲜度。任务详情、取消和重试返回同一 DTO 形状。

### 3.2 派生规则

- `queued` 且无 `defer_reason`：任务到达 `scheduled_for_at`（若没有则 `created_at`）后，归因为 `internal_queue`，`delay_since_at` 取该到期时刻。计划到期时间在未来时尚无当前延期，三个 delay 字段均为 `null`。
- 存在延期记录时，`rate_limited` 映射限流；其错误码为 `collector_budget_exhausted` 时映射 `budget_exhausted`；`transient` 映射 `transient_failure`；`manual_retry` 映射人工重试；其他内部值只映射 `other`。开始时间取该次转入队列的 `updated_at`。
- 延期时长为 `now - delay_since_at` 的非负整数微秒。若时钟/持久时间顺序异常，不输出负数，保留原因而将时间/时长标为未知。完成、失败、取消和运行中任务不报告“当前延期”。
- 没有历史尝试或完整成功时分别返回 `null`，不以 job 创建、部分成功或本次失败时间伪造成功。

### 3.3 组件与目录

| 路径 | 职责 |
|---|---|
| `backend/app/jobs/schemas.py` | 固定延期枚举和 `SourceFreshnessView`，扩展现有状态 DTO |
| `backend/app/jobs/services.py` | owner/来源能力/配置版本限定的聚合读取和只读投影；任务状态服务仍持有查询职责 |
| `backend/tests/unit/test_job_freshness.py` | 尝试/成功分离、partial 不推进、延期映射/起点/负时长防护和 SQL 过滤验证 |
| `backend/tests/integration/test_collection_jobs.py` | 复用已有隔离 PostgreSQL fixture，验证真实任务数据聚合及 owner/版本隔离；不运行破坏性 fixture 指向 `hotkey-server` |
| `frontend/src/app/jobs/[jobId]/components/job-detail.tsx` | 任务详情的最后尝试、最后完整成功和当前延期展示，沿用页面现有 `DetailItem` 与无边框样式 |
| `frontend/src/api/` | 仅通过现有运行时 OpenAPI 生成链更新类型；禁止手改生成文件 |

只增加一次面向来源任务的只读聚合查询；本切片不加 DDL/索引。它不构成 B0 查询性能证据，后续在代表性容量下验证 P95 并按测量结果决定是否需要索引。

## 4. 一手资料与复用结论

| 依据 | 采用结论 |
|---|---|
| [Python `datetime`](https://docs.python.org/3.12/library/datetime.html) | 内部时间必须是 aware datetime；比较前依赖绝对时间语义，客户端时区只负责展示。来源无时区输入作为异常事实保留，不由计算器猜测。 |
| [PostgreSQL 日期时间类型](https://www.postgresql.org/docs/current/datatype-datetime.html) | 持久字段继续使用 `TIMESTAMPTZ`；PostgreSQL 内部按 UTC 保存，输出时区不改变时间点。 |
| [RFC 3339](https://www.rfc-editor.org/rfc/rfc3339) | 跨边界时间必须携带 UTC 偏移；未知本地时间不能伪造 `Z`。 |
| [OpenTelemetry Trace API](https://opentelemetry.io/docs/specs/otel/trace/api/) | 复用显式阶段开始/结束的语义；029 计算既有业务事实，不安装 SDK 或建立第二套 span 存储。 |

## 5. 时间事实与职责

### 4.1 持久事实

- `Job.scheduled_for_at`：定时窗口的 `window.end`，代表该窗口完整后任务可到期；普通 `accept` 为 `None`。
- `Job.created_at`：受理时间；`Job.started_at`：首次取得执行权；`Job.completed_at`：任务终态时间。
- `JobStageAttempt`：来源请求、解析、保存、分析各次尝试的时间；重试继续是独立尝试。
- `SourcePage.observed_at`、内容 `published_at` 与 `EvidenceResource` 时间继续由来源/证据领域持有。

只有缺失的计划到期字段进入 DDL。其余事实通过统一计算 DTO 组合，避免复制后发生漂移。

### 4.2 计算契约

`FreshnessTimelineInput` 接收：

- `scheduled_for_at`（可空）、`accepted_at`、`started_at`（可空）；
- `request_started_at`、`source_observed_at`、`persisted_at`、`queryable_at`（均可空）；
- `source_published_at`（可空且允许 naive，以便显式标记异常）与 `source_time_precision`。

除 `source_published_at` 外，所有已提供时间必须带时区；后续阶段存在时其前置阶段必须存在，且时间不能倒退。输出统一为原事实及以下可空整数微秒：

- `schedule_wait_us`：计划到期 → 首次启动；
- `queue_wait_us`：受理 → 首次启动；
- `internal_prepare_us`：首次启动 → 来源请求开始；
- `source_wait_us`：来源请求开始 → 来源观察；
- `processing_us`：来源观察 → 持久化；
- `visibility_us`：持久化 → 可查询；
- `end_to_end_us`：计划到期 → 可查询；
- `publication_to_observation_us`：仅来源时间有效时计算。

使用整数微秒避免浮点舍入进入质量事实。S01 不聚合百分位；S03 在真实样本和 B0 冻结后再聚合。

## 6. 异常、幂等与安全

- 内部时间无时区、阶段缺前置或倒序直接拒绝；这是调用契约错误，不能保存或显示为正常指标。
- 来源发布时间缺失为 `unknown`；无时区为 `missing_timezone`；晚于观察时间为 `future_skew`。三者的发现延迟均为 `None`。
- 定时任务重试继续由既有 operation/window 幂等约束保证；同一窗口的 `scheduled_for_at` 必须一致。
- 时间 DTO 不含关键词、正文、Cookie、Token 或自由 metadata；owner/job 权限仍由现有服务边界负责。
- 新鲜度聚合是只读派生，不额外写连接/内容水位；来源任务查询的每个分组键均绑定当前已授权 job 的 owner 和精确配置版本。

## 7. 目录、迁移与验证

- S01 已修改唯一 `database/schema.sql`；S02 不改 DDL/模型或存量库，不创建 `monitors/`、`freshness/` 包。
- 新增纯规则/查询单元测试；在既有任务可靠性集成测试中验证 SQL 聚合、owner/版本隔离，不复制数据库 fixture，不把破坏性测试指向 `hotkey-server`。
- S02 增加现有任务状态 HTTP DTO 和详情页字段：运行时 `/openapi.json` 是唯一客户端输入；复用已启动 API/Web 和现有依赖，不启动第二套服务。
- 测试范围须明确隔离 PostgreSQL 是否可用。若 `HOTKEY_TEST_DATABASE_URL` 不存在，数据库集成测试跳过只可记为未验证，不能写成 PostgreSQL 通过；不得用生产/开发库清理型 fixture 代替隔离环境。

S01 Red 先证明当前缺少 `FreshnessTimelineInput`。S02 Red 先证明现有详情响应缺少成功/尝试及延期字段，再由 Green 验证全量成功聚合、失败/partial 不刷新、延期分类和来源配置隔离；浏览器需验证任务详情展示。

`OPEN-029-001` 在 S01 不关闭：各主题目标周期与陈旧阈值需要真实用户场景和来源预算。S02 处理最后尝试/成功及延期分类，S03 处理缺口、陈旧传播与 B0 聚合，S04 才执行产品 AC。029 保持 `in_progress`、产品 AC 0/6，不建立 Acceptance。
