# 时效与数据新鲜度设计

日期：2026-09-21。本版只冻结 029 S00—S01：补齐计划到期事实，并以受控时间链区分调度等待、内部准备、来源等待、处理和可见延迟；缺失时间保持未知，来源无时区或未来时间不生成误导性发现延迟。本版不实现最后成功、延期分类、覆盖缺口、陈旧传播、B0 P95、HTTP/UI 或产品 Acceptance。

## 1. 当前事实与问题

- `jobs` 已持久化受理、首次启动、完成和延期时间，`job_stage_attempts` 已保存 request/parse/save/analysis 的开始与结束，但定时任务没有独立的“计划到期”列。
- `sources` 契约已有可空 `published_at` 和必填 `observed_at`，`evidence_resources` 已有 `collected_at`/`created_at`；这些事实属于各自领域，029 不复制成第二套时间表。
- 当前没有统一计算契约。调用方容易把缺失当 0、把来源等待混入本地处理，或对无时区/未来发布时间算出负延迟。

## 2. S01 目标与非目标

### 2.1 目标

1. `jobs.scheduled_for_at` 保存计划任务所属窗口的到期时刻；手动任务保持 `NULL`，不以受理时间冒充计划时间。
2. 建立严格时间链 DTO：计划到期、受理、首次启动、来源请求开始、来源观察、持久化、可查询，以及可空来源发布时间/精度。
3. 只在端点齐全且顺序有效时计算非负整数微秒；缺失端点返回 `None`，不返回 0 或当前时间。
4. 来源发布时间区分 `valid`、`unknown`、`missing_timezone`、`future_skew`；后三者不计算发布到发现延迟，但保留原始输入供后续诊断。

### 2.2 非目标

- 不新增 freshness/monitoring 服务、表、队列、缓存、依赖或后台任务。
- 不在 S01 判断成功、陈旧或缺口，不冻结“两周期”建议值，不计算 P95。
- 不把阶段 DTO 当成 OpenTelemetry trace 导出，也不创建独立运维页面。
- 不推断上游发布时间；来源未提供时保持 unknown。

## 3. 一手资料与复用结论

| 依据 | 采用结论 |
|---|---|
| [Python `datetime`](https://docs.python.org/3.12/library/datetime.html) | 内部时间必须是 aware datetime；比较前依赖绝对时间语义，客户端时区只负责展示。来源无时区输入作为异常事实保留，不由计算器猜测。 |
| [PostgreSQL 日期时间类型](https://www.postgresql.org/docs/current/datatype-datetime.html) | 持久字段继续使用 `TIMESTAMPTZ`；PostgreSQL 内部按 UTC 保存，输出时区不改变时间点。 |
| [RFC 3339](https://www.rfc-editor.org/rfc/rfc3339) | 跨边界时间必须携带 UTC 偏移；未知本地时间不能伪造 `Z`。 |
| [OpenTelemetry Trace API](https://opentelemetry.io/docs/specs/otel/trace/api/) | 复用显式阶段开始/结束的语义；029 计算既有业务事实，不安装 SDK 或建立第二套 span 存储。 |

## 4. 时间事实与职责

### 4.1 持久事实

- `Job.scheduled_for_at`：定时窗口的 `window.end`，代表该窗口完整后任务可到期；普通 `accept` 为 `None`。
- `Job.created_at`：受理时间；`Job.started_at`：首次取得执行权；`Job.completed_at`：任务终态时间。
- `JobStageAttempt`：来源请求、解析、保存、分析各次尝试的时间；重试继续是独立尝试。
- `SourcePage.observed_at`、内容 `published_at` 与 `EvidenceResource` 时间继续由来源/证据领域持有。

只有缺失的计划到期字段进入 DDL。其余事实通过统一计算 DTO 组合，避免复制后发生漂移。

### 4.2 计算契约

`FreshnessTimelineInput` 接收：

- `scheduled_for_at`（可空）、`accepted_at`、`started_at`（可空）；
- `request_started_at`、`source_observed_at`、`persisted_at`、`queryable_at`（均可空）；
- `source_published_at`（可空且允许 naive，以便显式标记异常）与 `source_time_precision`。

除 `source_published_at` 外，所有已提供时间必须带时区；后续阶段存在时其前置阶段必须存在，且时间不能倒退。输出统一为原事实及以下可空整数微秒：

- `schedule_wait_us`：计划到期 → 首次启动；
- `queue_wait_us`：受理 → 首次启动；
- `internal_prepare_us`：首次启动 → 来源请求开始；
- `source_wait_us`：来源请求开始 → 来源观察；
- `processing_us`：来源观察 → 持久化；
- `visibility_us`：持久化 → 可查询；
- `end_to_end_us`：计划到期 → 可查询；
- `publication_to_observation_us`：仅来源时间有效时计算。

使用整数微秒避免浮点舍入进入质量事实。S01 不聚合百分位；S03 在真实样本和 B0 冻结后再聚合。

## 5. 异常、幂等与安全

- 内部时间无时区、阶段缺前置或倒序直接拒绝；这是调用契约错误，不能保存或显示为正常指标。
- 来源发布时间缺失为 `unknown`；无时区为 `missing_timezone`；晚于观察时间为 `future_skew`。三者的发现延迟均为 `None`。
- 定时任务重试继续由既有 operation/window 幂等约束保证；同一窗口的 `scheduled_for_at` 必须一致。
- 时间 DTO 不含关键词、正文、Cookie、Token 或自由 metadata；owner/job 权限仍由现有服务边界负责。

## 6. 目录、迁移与验证

- 修改 `jobs/models.py`、`schemas.py`、`services.py` 和唯一 `database/schema.sql`；不创建 `monitors/` 或 `freshness/` 包。
- 新增纯规则单元测试；在既有任务可靠性集成测试中验证计划到期持久化和幂等，不复制数据库 fixture。
- 当前 `hotkey_dev` 必须先确认 19 表且 0 行，再用完整 schema 原地重建；复用 `backend/.env`，不启动或重启服务。
- S01 无 HTTP/OpenAPI、前端、Redis、Kafka 或 MinIO 行为变化；客户端生成和浏览器验证 N/A。

Red 先证明当前缺少 `FreshnessTimelineInput`。Green 验证完整链路、缺失非零化、来源无时区/未来偏差、倒序拒绝、定时任务持久化与全量回归。

`OPEN-029-001` 在 S01 不关闭：各主题目标周期与陈旧阈值需要真实用户场景和来源预算。S02 处理最后尝试/成功及延期分类，S03 处理缺口、陈旧传播与 B0 聚合，S04 才执行产品 AC。029 保持 `in_progress`、产品 AC 0/6，不建立 Acceptance。
