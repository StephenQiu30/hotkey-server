# 采集任务控制设计

日期：2026-09-21。本版冻结 009 S00—S02 的持久受理、owner 隔离状态读取、持久进度与协作式取消；分类重试、列表/历史和真实来源执行留给 S03—S04。本文不把受控内部闭环解释为 009 产品验收。

## 1. 当前事实与切片边界

031 S01/S02 已交付 PostgreSQL `jobs`、同事务 Outbox、幂等指纹、Kafka 恢复、租约与检查点；039 S01 已补齐配置版本和来源能力上下文。009 S01 复用这些事实，不建立第二套任务表、队列或状态机。

本切片交付一个最小 HTTP 闭环：已认证 owner 提交严格任务意图，只有 `jobs` 与 Outbox 事务提交后才收到 `202 Accepted`；响应携带任务查询位置，后续独立 GET 从 PostgreSQL 读取同一条排队记录。Redis 和 Kafka 不参与受理成功判定。

监控配置、连接和真实来源处理器尚未交付，因此 S02 只发布可按任务 ID 访问的详情页，不发布任务列表，也不声称队列会完成实际采集。详情页展示持久状态、阶段、已发请求数、已保存数量、取消意图和截止时间；“已保存数量”只是结果范围，不伪造尚不存在的业务正文。

## 2. 一手资料与复用结论

| 依据 | 采用结论 |
|---|---|
| [RFC 9110 15.3.3](https://www.rfc-editor.org/rfc/rfc9110.html#section-15.3.3) | `202 Accepted` 表示请求已受理但处理未完成；响应返回当前 `queued` 状态，并用 `Location` 指向状态资源。HTTP 请求不等待外部采集。 |
| [FastAPI Response Status Code](https://fastapi.tiangolo.com/tutorial/response-status-code/) | 使用路由装饰器声明 202/200 和响应模型，由运行时 OpenAPI 生成契约，不手写 JSON/YAML。 |
| [FastAPI Dependencies](https://fastapi.tiangolo.com/tutorial/dependencies/) | Session、身份和 JobService 通过 `api/dependencies.py` 注入；Router 不导入 Service 实现或 ORM。 |
| [PostgreSQL INSERT](https://www.postgresql.org/docs/18/sql-insert.html) | 继续复用 031 已验证的唯一约束与 `ON CONFLICT`，并发重放不增加任务或 Outbox。 |
| [PostgreSQL Explicit Locking](https://www.postgresql.org/docs/current/explicit-locking.html#LOCKING-ROWS) | 取消、进度和 Worker 完成均锁定同一 job 行；`SELECT FOR UPDATE` 让并发写按事务结束顺序观察最新状态，避免取消意图被完成写覆盖。 |
| [@umijs/openapi 1.14.1](https://www.npmjs.com/package/@umijs/openapi) 与[上游源码](https://github.com/chenshuai2144/openapi2typescript) | 当前最新版生成器只从 200/201/default 选择返回模型；在既有 `afterOpenApiDataInited` hook 内仅为生成器映射 202 schema，运行时 OpenAPI 不增加虚假 200。 |

不新增依赖、框架、脚本或服务。现有 FastAPI、Pydantic、SQLAlchemy 和 PostgreSQL 已覆盖本切片。

## 3. HTTP 契约

### 3.1 提交任务

`POST /api/jobs`

- 身份：有效 `SessionCookie`；写操作还必须通过现有 `hotkey_csrf` Cookie 与 `X-HotKey-CSRF` 双提交校验。
- 输入：HTTP 边界使用可解析 JSON 枚举的 `CollectionJobInput`，当前只允许 `monitor.collect`，随后收敛为严格内部 `JobAcceptanceInput`。`operation_id` 标识同一次业务意图；kind、配置引用/版本、来源能力、计划时间和最多 32 个稳定标量 scope 共同进入既有请求指纹。输入不包含 `owner_id`。
- 输出：事务提交后返回 `202` 与 `JobAcceptedView {job_id, status: "queued"}`；`Location` 固定为 `/api/jobs/{job_id}`，`Cache-Control` 为 `no-store`。
- 幂等：同 owner、kind、operation 且指纹相同返回同一 job；指纹不同返回登记的 `409 idempotency_conflict`。S01 尚无业务处理器，公开提交记录保持 queued；任务开始执行后的重放响应形态在 S02 接入执行控制前冻结。
- 错误：无效会话 401、CSRF 失败 403、幂等冲突 409、输入失败 422、未归类内部故障 500；均使用统一 `ErrorView`。

### 3.2 读取任务

`GET /api/jobs/{job_id}`

- 身份：有效 `SessionCookie`。
- 查询：`JobService.get_status(owner_id, job_id)` 同时按 owner 与 job ID 过滤；不存在或不属于当前 owner 均返回 `404 resource_not_found`。
- 输出：`200 JobStatusView`，包含任务 ID、operation ID、kind、配置/来源观察上下文、持久状态和关键时间；不返回 `owner_id`、scope、请求指纹、租约、检查点或 Outbox 内容。`Cache-Control` 为 `no-store`。

### 3.3 进度与取消

`GET /api/jobs/{job_id}` 从 S02 起增加：

- `status` 使用公开 `JobControlStatus`；运行中且已有取消意图时返回 `cancelling`，数据库执行状态仍为 `running`。
- `progress` 固定包含 `stage`、`requests_sent`、`items_saved`、`updated_at`。未知总量不返回 total 或 percentage；初始计数为 0，阶段和时间为空。
- `cancellation` 在取消后包含 `requested_at`、运行任务的 `deadline_at` 和服务端计算的 `timed_out`。截止时间取登记取消时的当前租约到期时间；取消后的检查点不得把租约续到该时间之后。

`POST /api/jobs/{job_id}/cancel`

- 身份与 CSRF 规则同其他私有写操作；owner 过滤与详情读取一致。
- queued 任务在同一事务直接转为 cancelled；running 任务只持久化取消意图和当前租约截止时间，返回 `200 JobStatusView` 的 `cancelling`，不假报外部请求已中止。
- 重复取消 queued、running 或 cancelled 为幂等；succeeded、partially_succeeded 或 failed 返回 `409 job_not_cancellable`。
- Worker 处理器必须在每个新外部请求前调用执行上下文的 `begin_request`；该操作在同一 job 行锁内检查取消并持久递增已发请求数，只有返回 true 才允许调用来源。已在途响应可在取消截止前通过同一检查点事务保存结果范围；随后 `complete` 观察取消意图并把 job 与 attempt 结束为 cancelled。排队任务取消后若受理 Outbox 已投递，Worker 只登记 processed 并确认消息，不获取租约或调用业务处理器。超期仍未结束时详情返回 `timed_out=true`，S02 不在 GET 中改写终态。

S02 不实现集合列表、cursor、重试或来源级超时值；取消截止复用当前租约，不替代 `OPEN-009-001` 的来源超时决策。

## 4. 领域、事务与目录

| 路径 | 责任 |
|---|---|
| `backend/app/jobs/schemas.py` | 增加 HTTP `CollectionJobInput` 与只读 `JobStatusView`；继续复用既有严格内部受理输入与 `JobView`。 |
| `backend/app/jobs/services.py` | owner 隔离的单任务读取与取消事务；受理事务保持既有实现。 |
| `backend/app/jobs/execution.py`、`backend/app/worker/app.py` | 持久进度、取消检查、取消后租约上限及 Worker 终态转换；处理器在新请求边界显式检查。 |
| `backend/app/jobs/models.py`、`backend/database/schema.sql` | 同批增加取消意图/截止与进度字段和约束；Schema 仍是唯一 DDL。 |
| `backend/app/api/dependencies.py` | 从请求 Session 构造 `JobService` 的唯一 HTTP 注入入口。 |
| `backend/app/api/routers/collection_jobs.py` | 只做协议、身份/CSRF、Location 和缓存头；增加取消路由但不直接访问 ORM。 |
| `backend/app/api/router.py` | 在唯一 `/api` 命名空间注册任务路由。 |
| `backend/tests/integration/test_collection_jobs.py`、`test_job_reliability.py` | 使用真实 PostgreSQL 验证 HTTP 权限/状态和一个在途请求后的协作式取消。 |
| `frontend/openapi2ts.config.ts`、`frontend/src/api/` | 继续从同提交运行时 OpenAPI 生成任务读取与取消函数，不手写端点。 |
| `frontend/src/app/jobs/[jobId]/page.tsx`、`components/job-detail.tsx` | 页面入口与专属详情组件；数据只来自生成客户端，覆盖加载、正常、空结果、部分、错误、无权限、取消中和取消超时。 |

S02 有 DDL/ORM 变化但无依赖、消息版本或运行配置变化；只对全新项目数据库应用完整 `schema.sql`，不建立迁移脚本。Redis、Kafka、MinIO 和 Compose 均不修改。API 依赖只负责 Session 生命周期，Router 不提交事务。

## 5. 安全、恢复与可观测边界

- owner 只来自有效服务端会话，客户端无法选择归属；读取用同一 owner 过滤并用 404 隐藏资源存在性。
- scope 不出现在响应和通用日志；配置引用、来源上下文仍受 039 的非敏感格式约束。
- 接受响应丢失时，调用方必须复用 operation ID；数据库唯一约束返回原任务。更换输入但复用标识会被拒绝，不静默改变意图。
- API 不自动切换会话、账号、来源或重试写请求。无效会话和权限边界直接返回稳定错误。
- 回退时停止公开新增受理并回退 Router/客户端；已提交 job 与 Outbox 保留，详情仍可由向前修复恢复，不删除表、队列或持久数据。

## 6. Red/Green 验证与证据边界

S01 Red 必须先让专用集成测试因 `/api/jobs` 不存在而得到 404。S02 Red 必须在既有真实 PostgreSQL 上证明取消路由缺失，且既有 Worker 完成路径会忽略取消意图。Green 继续复用本机已运行服务中的项目专用隔离数据库，验证：

1. POST 返回 202、queued、Location 和 no-store；新请求按 Location 读取同一持久记录。
2. 同一输入重复三次只有一个 job 与一个 Outbox，三次得到同一 job ID。
3. 同 operation ID 更换 scope 返回 409，原记录和 Outbox 不变。
4. 缺失/伪造会话返回 401，缺失 CSRF 返回 403；不存在任务返回 owner 隔离的 404。
5. 运行时 OpenAPI 声明 SessionCookie、202/200、统一错误模型；生成客户端、后端全量测试和前端静态/构建门禁通过。
6. queued 取消立即终止；running 取消呈现 cancelling，阻止下一请求，在途结果仍把进度从 0 推进到可核对数量，最终 job/attempt 均为 cancelled。
7. 取消后检查点不延长既定截止时间；超时标记、owner/CSRF、终态冲突和重复取消可核查。
8. 同提交生成客户端驱动任务详情页；既有运行前端可用时执行桌面/窄屏浏览器验证，否则明确保留 UI 验证缺口，不用构建通过替代浏览器证据。

S02 的可控处理器只证明内部取消协议，不是 X/B站/微博/小红书/抖音真实在途请求。AC-009-001—006 全部保持待验收，不能建立 Acceptance。`OPEN-009-001` 的来源级超时和重试次数继续留给 S03 与实际来源 Design。
