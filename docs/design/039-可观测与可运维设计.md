# 可观测与可运维设计

日期：2026-09-21。本版只冻结 039 S00—S01：在现有任务、执行尝试和资源尝试之上补齐运行上下文、阶段尝试与可核对汇总。本版不实现错误动作、陈旧问题、配置审计、运维页面、Prometheus 或 OpenTelemetry 后端。

## 1. 当前事实与问题

- `jobs` 已持久化 `operation_id`、任务状态、Worker 执行尝试和资源尝试，但任务没有来源能力、配置引用和配置版本的强类型字段。
- 现有任务状态能区分成功、部分、失败和取消；延期按 046/009 既有契约仍是 `queued`，但缺少 `defer_reason` 与 `next_run_at`，不能与普通排队核对。
- `resource_usage_attempts.stage` 只覆盖需计量的网络/分析尝试，不能表达解析、保存等不产生资源计量的业务阶段。
- structlog 已在 HTTP 请求中绑定 `request_id`，Worker 尚未把任务关联字段绑定到日志上下文。

## 2. S01 目标与非目标

### 2.1 目标

1. 每个新任务必须绑定非敏感配置引用和版本；来源任务同时绑定 `source_key` 与能力，两者成对出现。
2. 以持久 `job_stage_attempts` 记录 `request`、`parse`、`save`、`analysis` 的每次开始和终态；重试是新的阶段尝试，不是新的业务任务。
3. 同一窗口的任务状态互斥汇总，并分别统计 Worker 执行尝试、阶段尝试和资源尝试；汇总可回到脱敏明细核对。
4. Kafka 消息携带相同运行上下文，Worker 日志临时绑定安全关联字段，处理结束后自动恢复上下文。

### 2.2 非目标

- 不把日志、trace 或 Prometheus 时序当作业务运行事实源。
- 不引入 OpenTelemetry SDK、Prometheus client、外部采集器或新服务。
- 不记录关键词、正文、Cookie、Token、连接串、原始异常或平台响应。
- 不实现运维 HTTP/UI；业务任务尚无公开查询入口，S01 只提供内部 Service/DTO。

## 3. 一手资料与复用结论

| 依据 | 采用结论 |
|---|---|
| [OpenTelemetry Trace API](https://opentelemetry.io/docs/specs/otel/trace/api/) | 复用“一次逻辑操作由稳定关联 ID 串联，阶段有开始/结束时间”的语义；不安装 SDK，因为 S01 要保存可对账业务事实，而非导出可采样 trace。阶段名保持低基数，不拼任务或配置 ID。 |
| [Prometheus instrumentation](https://prometheus.io/docs/practices/instrumentation/) | 不把 owner、job、operation 或配置引用作为时序标签；官方建议控制标签基数，高基数明细留在通用处理系统。S01 使用 PostgreSQL 明细，后续指标只暴露稳定低基数状态。 |
| [PostgreSQL aggregate expressions](https://www.postgresql.org/docs/current/sql-expressions.html#SYNTAX-AGGREGATES) | 尝试数按各事实表使用 `count`/`group by` 计数；任务明细每行只进入一个状态分类并校验分类和等于总数，不由日志文本推断。 |
| [structlog context variables](https://www.structlog.org/en/stable/contextvars.html) | 延用已安装的 `merge_contextvars`，Worker 使用 `bound_contextvars` 临时绑定任务安全字段并自动恢复，不建立第二套日志框架。 |

## 4. 运行上下文与状态口径

### 4.1 任务运行上下文

`JobObservationContext` 只包含：

- `configuration_ref`：不含关键词的稳定配置引用；只允许小写稳定标识。
- `configuration_version`：任务受理时冻结的正整数版本。
- `source_key` 与 `source_capability`：非来源任务二者均为 `None`；来源任务二者必须同时存在。

上下文进入任务请求指纹、`jobs` 专用列及 `job.accepted.v2` outbox payload。v2 取代不含运行上下文的 v1；当前环境无业务处理器且空库重建，不保留待消费 v1 消息。跨进程恢复读取同一持久事实；消息重放不能更换版本。

### 4.2 任务显示状态

| 运行状态 | 唯一判定 |
|---|---|
| `queued` | 数据库状态为 `queued` 且无延期字段 |
| `delayed` | 数据库状态仍为 `queued`，且 `defer_reason`、`next_run_at` 同时存在 |
| `running`、`succeeded`、`partially_succeeded`、`failed`、`cancelled` | 直接使用持久任务状态 |

延期字段必须成对出现，只能用于 `queued`；本切片只冻结存储和观察口径，实际预算/调度转换由 009/037 后续接入。

## 5. 阶段尝试

`job_stage_attempts` 由 `jobs` 领域持有，每行是一项业务任务在某阶段的一次尝试：

- 阶段固定为 `request`、`parse`、`save`、`analysis`；不把对象 ID 或平台字段拼入阶段名。
- 每个任务/阶段的 `attempt_sequence` 从 1 开始且唯一，重放同一序号必须与原开始记录完全等价。
- 终态固定为 `succeeded`、`partially_succeeded`、`failed`、`delayed`、`cancelled`；开始时为 `started`，结束时间必须不早于开始时间。
- 表不存错误正文、输入/输出正文或秘密。稳定错误类别和动作属于 S02。

`JobObservationService` 是唯一写入与汇总入口：开始和结束均事务化、幂等冲突显式拒绝；查询按 owner 和半开时间窗口隔离。

## 6. 汇总与可核对性

`OperationalSnapshot` 同时返回：

1. 脱敏任务明细：job/operation ID、kind、运行上下文、互斥状态和时间，不返回 `scope`。
2. 每个 operation 的资源尝试数，避免一个 operation 关联多个 job 时重复计数。
3. 汇总：各任务状态数、Worker 执行尝试数、阶段尝试数、资源尝试数。

任务分类之和必须等于任务总数；Worker/阶段尝试分别可由任务明细求和，资源尝试可由 operation 明细求和。空窗口返回显式 0，不伪造最后成功时间。

## 7. 目录、事务与依赖

- `jobs/models.py`、`schemas.py`、`services.py`：任务运行上下文、阶段尝试及汇总的唯一事实源和事务所有者。
- `worker/app.py`：只装配安全日志上下文，不持有观察业务规则。
- `database/schema.sql`：新增列与 `job_stage_attempts` 的唯一 DDL；ORM 同提交更新。
- `audit/` 本切片不创建；S03 的配置变更、暂停/恢复审计到实际切片再建。

S01 不改 HTTP/OpenAPI、前端、Redis、MinIO 或服务配置，不新增依赖；因运行上下文是必填消息字段，受理消息与 topic 同步升级为 v2。当前 `hotkey_dev` 已确认 16 表且 0 行；DDL 更新后按工程规则使用完整 `schema.sql` 重建同一空库，不启动第二套服务、不执行存量库就地迁移。

## 8. 安全与日志

- 一般日志只绑定 `operation_id`、`job_id`、`kind`、配置版本、来源 key 和能力；不绑定配置引用、scope、关键词或正文。
- 汇总严格按 owner 查询，其他 owner 的任务与尝试不可见。
- Pydantic 输入 `extra="forbid"`，阶段契约没有任意 metadata/details 字段，避免临时调试数据进入长期事实。
- S01 只能证明内部关联、持久尝试和汇总口径；不证明真实来源、运维页面、错误动作、新鲜度提示或完整产品验收。

## 9. 验证与后续边界

Red 先证明当前代码没有运行上下文/阶段观察契约。Green 使用真实 PostgreSQL 验证：上下文与 outbox 同事务、阶段重放/冲突、跨版本区分、七类显示状态互斥、三类尝试分别计数、owner 隔离和 Worker 上下文恢复。随后执行架构、Ruff、mypy 和后端全量测试。

`OPEN-039-001` 在 S01 只关闭任务运行事实与汇总层级。运行记录保留期沿任务级联，最终期限待 020/036；陈旧阈值、稳定错误/动作、问题去重和诊断 UI 留给 S02；配置与维护审计、暂停/恢复闭环留给 S03。039 保持 `in_progress`，不建立 Acceptance。
