# X 热点发现与持续热度观测设计

## 调研对象与结论口径

本设计基于 2026-08-12 对以下事实的逐项核验，不以项目介绍文案代替代码行为：

- 参考仓库固定版本：`liyupi/yupi-hot-monitor@cd48b0885bfa8ae9c8043cf78ef6cfd045530bdb`。
- 参考仓库定位：面向个人创作者和教学的一体化热点工具，主打关键词、8+ 来源聚合、AI 分析、筛选排序和即时通知。依据：[README](https://github.com/liyupi/yupi-hot-monitor/tree/cd48b0885bfa8ae9c8043cf78ef6cfd045530bdb)。
- 参考仓库 X 实现：使用第三方 `twitterapi.io`，同时执行 `Top` 与 `Latest` 搜索，再以点赞、转发、浏览、粉丝和蓝 V 状态做固定阈值过滤及绝对量排序。依据：[twitter.ts](https://github.com/liyupi/yupi-hot-monitor/blob/cd48b0885bfa8ae9c8043cf78ef6cfd045530bdb/server/src/services/twitter.ts)。
- 参考仓库主任务：已存在的 `(url, source)` 热点直接跳过，不刷新互动量；`getTrends` 未进入定时热点检查主链；多来源结果最终保存为单条 `Hotspot`。依据：[hotspotChecker.ts](https://github.com/liyupi/yupi-hot-monitor/blob/cd48b0885bfa8ae9c8043cf78ef6cfd045530bdb/server/src/jobs/hotspotChecker.ts)。
- 参考仓库列表：所谓“热度综合”是内容级绝对量公式，并在内存中对全部结果排序后分页，不是持续时间序列或事件级趋势。依据：[hotspots.ts](https://github.com/liyupi/yupi-hot-monitor/blob/cd48b0885bfa8ae9c8043cf78ef6cfd045530bdb/server/src/routes/hotspots.ts)。
- X 官方 Recent Search 只覆盖最近 7 天，支持 `recency` 与 `relevancy`，请求字段名为 `tweet.fields`；`relevancy` 表示搜索相关性，不等价于热度。依据：[Search recent Posts](https://docs.x.com/x-api/posts/search-recent-posts)。
- X API v2 官方运算符使用 `-is:retweet`、`-is:reply`；参考仓库使用的 `filter:retweets`、`filter:replies`、`min_faves` 属于旧搜索语法，不能直接移植到 v2。依据：[Search Operators](https://docs.x.com/x-api/posts/search/integrate/operators) 与 [迁移对照](https://docs.x.com/x-api/posts/search/migrate/overview)。
- X 官方批量 Post Lookup 可一次查询最多 100 个已知 Post，并返回 `public_metrics`，适合对已发现对象做持续指标观测。依据：[Post Lookup Quickstart](https://docs.x.com/x-api/posts/lookup/quickstart)。

参考仓库根目录未提供独立 LICENSE 文本。本项目只借鉴可观察的产品行为和问题拆分，不复制其源代码、提示词或视觉资产。

## 当前 HotKey 审计事实

HotKey 已拥有参考仓库没有的监控意图、官方 X Recent Search、不可变原始证据、内容家族、微事件、Heat v2、持久通知与稳定分页基础，因此本需求不是重建一套 `Hotspot` CRUD。

本次代码审计确认以下缺口：

1. X 连接器当前请求 `post.fields` 和 `referenced_posts`，与现行官方 Recent Search 契约的 `tweet.fields`、`referenced_tweets` 不一致；也未读取 `note_tweet` 长帖正文。
2. Recent Search checkpoint 在最后一页推进 `since_id`，适合发现新 Post，但之后不会再次返回旧 Post；因此已发现 Post 的互动指标通常只有首个快照。
3. 同一 Content 再次标准化时，`contents` 和 `content_metric_snapshots` 能更新；但指标变更触发的同步重算只覆盖 legacy `events`，当前页面使用的 `micro_events / Heat v2` 不会随之更新。这同时证明 032 定义的 legacy→v2 切换尚未收口；处置边界见 [034](034-X热点核心链路收敛与遗留系统清理设计.md)。
4. Heat v2 当前以单个微事件内部、同一来源连接的最大绝对互动量做归一化。单帖事件的互动值恒为 `1.0`，无法区分 1 次与 100 万次互动，也没有使用窗口内增量。
5. `/dashboard/events` 的微事件列表按递增 ID 返回，列表项不展示 Heat v2，也没有服务端热度排序；热点发现结果无法自然浮到前面。

## 任务边界

| 能力 | 参考仓库行为 | 033 决策 |
|---|---|---|
| X 接入 | 第三方 `twitterapi.io` | **不采用**；只使用 X 官方 API 与现有 Bearer/来源治理 |
| Top + Latest | 两次第三方搜索后静态过滤 | **吸收意图，不照搬接口**；首次用官方 `relevancy` 补齐存量相关候选，持续用 `recency` 发现，Post Lookup 负责持续观测 |
| 多来源网页抓取 | Bing/搜狗等 HTML 抓取和 UA 轮换 | **明确不做**；不扩大 RSS，也不新增未授权网页抓取 |
| 查询扩展 | AI 自动扩展后直接辅助分析 | **复用现有能力**；只有已审批扩展可进入来源查询 |
| 真假识别 | `isReal` 布尔值决定是否入库 | **明确不做**；继续区分相关性、热度和证据覆盖，不输出真假 |
| 蓝 V / 粉丝加权 | 降低固定互动阈值并加分 | **明确不做**；认证状态不代表内容真实性或事件热度 |
| 热度 | 单条内容绝对量公式 | **改为事件级持续热度**；使用指标增量、来源内滚动总体、谱系、速度、覆盖和新鲜度 |
| 已存在内容 | 直接跳过 | **必须持续观测**；按预算批量刷新已跟踪 X Post 的公开指标 |
| 列表排序 | 全量加载后内存排序 | **不采用**；服务端稳定排序与游标分页 |
| 通知、手动搜索、Agent Skill | 独立实现 | **不在 033 重建**；复用 HotKey 已有链路，仅消费新的热度结果 |
| X 全球 Trends | 有函数但未接入主链 | **本期不做**；它回答平台话题榜，不等于用户监控意图下的具体事件 |

## 目标

- 修正 X 官方请求与响应映射，让标准 Post、引用关系、公开指标和长帖正文可被可靠采集。
- 首次发布或显式重建时，用官方 Recent Search `relevancy` 做一次有界的七天相关候选补齐；日常继续用 `recency` 单调发现，并用官方批量 Post Lookup 对已跟踪 X Post 做有界、可恢复的指标刷新。
- 让指标快照真实驱动唯一生产事件事实 MicroEvent Heat v2，不再扩大 legacy Event 双写。
- 用窗口内指标增量和来源内滚动总体计算互动分，避免单帖恒为满分和跨来源绝对量不可比。
- 在事件工作台提供服务端热度排序、窗口标识和组成解释，让用户优先看到正在升温的事件。
- 允许监控只选择 X 来源；不要求 RSS 或其他来源参与才能工作。

## 非目标

- 033 本身不执行非 X 历史数据和 Connector 的破坏性删除；其默认运行面和退出计划由 034 决定。
- 不接入 `twitterapi.io`、X 网页抓取、浏览器 Cookie、代理轮换或旧版搜索语法。
- 不复制参考仓库的固定点赞/转发/粉丝阈值、蓝 V 加权、`isReal`、importance Prompt 或内容级热度公式。
- 不把 `sort_order=relevancy` 命名为“热门”，也不把 X 全局 Trends 当作用户监控事件。
- 不引入第二套 Hotspot 表、第二套事件模型、Elasticsearch、Kafka、微服务或前端本地排序。
- 不把多个转帖、多个账号或高互动解释为事实真实。

## 核心设计

### 1. 发现与持续观测分离

`Recent Search` 仍只承担候选发现，但分成两个明确场景：

- 首次发布 Monitor、首次启用 X 来源或管理员显式执行重建时，执行一次有界 `sort_order=relevancy` 七天补齐，避免高流量查询只拿到最近若干页而遗漏已经形成讨论的相关 Post。该结果只表示搜索相关，不直接标记为热门，也不推进日常 checkpoint。
- 日常轮询使用 `sort_order=recency`，保持现有首屏 `newest_id` 高水位与末页推进规则。它不为了刷新旧指标回退 checkpoint，也不周期性重扫完整七天窗口。

两条发现路径以 `(source_connection_id, external_id)` 合并，分别保留原始响应证据。首个绝对互动量只可用于刷新队列的预算优先级，不能直接写成 Heat；在第二期快照形成前，互动维度显示 `metrics_warming_up`。

新增 X 指标刷新用例读取“需要继续观测”的已知 Post ID，按官方上限每批最多 100 个调用 `GET /2/tweets`。候选必须同时满足：

- 来源连接为启用且健康的 `x`；
- Content 与 SourceObservation 未删除且在配置观测期内；
- 关联当前已发布 Monitor 的 `accepted` 或有界 `review` 候选，或已经是活跃 MicroEvent 成员；
- 距离上次成功指标快照超过配置间隔；
- 未超过来源请求预算、项目使用量和失败退避时间。

活跃 MicroEvent 成员优先于 review 候选；同一 Post 即使关联多个 Monitor，也只进入一个刷新批次。批量响应中的缺失、withheld 或不可用对象形成诊断，不推断删除。

### 2. 官方字段与不可变证据

Recent Search 与 Post Lookup 统一请求 `tweet.fields`，至少包含 `author_id,attachments,conversation_id,created_at,lang,note_tweet,possibly_sensitive,public_metrics,referenced_tweets,text,withheld`。正文优先使用非空 `note_tweet.text`，否则使用 `text`；证据定位仍绑定原始 JSON 字段。

刷新响应作为 X 官方原始证据归档，并关联既有 SourceObservation。互动变化只追加 `content_metric_snapshots` 和更新 Content 当前指标投影；不因指标变化创建新的 DocumentVersion 或内容家族成员。

### 3. Heat v2 互动语义

对每个窗口使用 `window_start` 前最近快照作 baseline、`window_end` 前最近快照作 latest。任一指标缺少 baseline/latest、发生回退或来源能力不支持时，该指标保持 unavailable，不伪造零。

可用指标沿用现有经过测试的权重与归一化原语：浏览 0.20、点赞 0.30、评论 0.25、分享 0.25；每个指标按 `(source_connection_id, content_type)` 的全体活跃 Content 窗口增量做百分位归一化，样本少于 5 时使用固定对数降级并写入 reason code。Heat v2 只消费归一化互动，不读取 credibility weight。

同一内容家族的重复发布不能重复贡献谱系；互动分按事件内可用内容聚合并限制到 `[0,1]`。没有两期快照时互动为 `null`，Heat v2 继续按现有规则重归一化其余维度。

### 4. 指标变更触发当前事件重算

Content 指标快照成功提交后，Event-owned Reader 只返回当前 MicroEvent ID。MicroEvent 按同一个分钟边界重算 1h、6h、24h 快照；相同事件、版本、窗口、profile 和输入重复执行必须得到同一收据。不得为 033 新增或恢复 legacy Event/Heat 双写。

指标重算失败不得回滚已经归档的 X 响应或指标事实；通过持久任务重试，并暴露稳定失败类型。事件成员变化仍沿用 accepted-match 投影的即时重算。

### 5. 热点工作台

MicroEvent 列表新增服务端 `sort=heat|latest`，默认 `heat`；热度排序键至少包含 `heat_score DESC, window_ended_at DESC, event.id DESC`，游标绑定排序、状态过滤和冻结时间。没有 Heat 快照的事件排在有快照事件之后，但仍可通过 `latest` 查看。

列表项展示 Heat v2 分数、窗口、加速度、独立内容起源数、最新观察时间和 `metrics_unavailable / normalization_fallback` 等原因。前端不重算热度，也不把 `relevancy`、认证状态或 AI 相关性显示为热度。

## 数据与状态

- 复用 `source_connections`、`collection_runs`、`evidence_snapshots`、`source_observations`、`contents`、`content_metric_snapshots`、`micro_event_members` 与 `micro_event_heat_snapshots`。
- 优先通过现有持久任务与最新快照时间表达刷新进度，不新增第二份指标事实表。
- 如实现阶段证明无法用现有 Job 唯一键安全表达批次游标，只允许增加 X 刷新运行状态，不允许复制 Content、Observation 或 Heat 快照。
- Post Lookup 请求只携带 Post ID；任务载荷只携带来源连接 ID、期望版本和批次游标，不携带 Bearer、正文或完整响应。

## 安全、成本与合规

- 只访问固定的 `https://api.x.com/2/tweets` 与既有 Recent Search 端点，复用公开 DNS 校验、TLS、重定向限制、响应大小限制和凭据脱敏。
- X 使用量与价格是运行时事实；每个连接配置刷新间隔、单轮最大 Post 数和每日请求预算，默认保守关闭持续刷新，管理员显式启用后运行。
- 遵守 `x-rate-limit-*` 与 `Retry-After`，429 不做紧循环；401/403 停止刷新并将连接降级。
- 不从用户认证状态、粉丝数或互动量推断可信度，不在日志、指标标签和通知中输出原始正文或 Token。

## 失败与降级

- Post Lookup 不可用：Recent Search 新内容发现继续工作，事件显示 `metrics_stale`，不沿用旧指标伪装为当前窗口增量。
- 首次观测尚无 baseline：绝对互动量只决定刷新优先级，Heat 互动为 `null` 并显示 `metrics_warming_up`。
- baseline 不足：互动为 `null` 并重归一化其他 Heat 维度。
- 滚动总体不足 5：使用固定对数降级并显示 `normalization_fallback`。
- 部分 Post 不可用：成功项正常提交，失败项形成逐项诊断；不整批回滚。
- 当前没有活跃 HeatProfile：保留指标快照，MicroEvent 重算返回可观测的 unavailable，不阻塞采集。
- X 预算耗尽：按优先级延后低优先候选，不转向 RSS、网页抓取或第三方 API。

## 验收边界

- AC-033-1：真实契约测试确认使用 `tweet.fields/referenced_tweets/note_tweet`；首次 `relevancy` 补齐不推进日常 checkpoint，`recency` 分页高水位、敏感/withheld 和凭据安全回归通过。
- AC-033-2：同一已知 X Post 至少两次官方观测只产生一个 Content/Observation/DocumentVersion，追加两期指标快照并更新当前指标。
- AC-033-3：指标变化后当前 MicroEvent 自动产生新的 1h/6h/24h Heat v2；legacy Event/Heat 不产生新写入。
- AC-033-4：单帖事件不再恒为互动 1.0；相同来源中更高窗口增量得到不低于较低增量的归一化分，缺 baseline 为 null。
- AC-033-5：事件列表默认按服务端 Heat v2 稳定排序，跨页不重不漏，列表解释窗口、加速度、谱系与降级原因。
- AC-033-6：仅启用 X 的 Monitor 能完成发现、相关性、事件、热度和通知链路；预算或 X 故障不会触发 RSS 或非授权回退。
