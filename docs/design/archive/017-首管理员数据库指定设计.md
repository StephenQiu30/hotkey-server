# 首管理员数据库指定设计

## 1. 决策

删除 `HOTKEY_BOOTSTRAP_ADMIN_EMAIL`、`HOTKEY_BOOTSTRAP_ADMIN_PASSWORD` 和 `hotkey user bootstrap-admin`。用户必须先通过正常邮箱验证完成注册并生成密码哈希，数据库操作员再以一次性事务把一个已存在、active、未删除的用户从 viewer 提升为 admin。

本设计替代 Design-013 中“环境变量凭据创建首管理员”的部分，不改变登录、会话、最后活动管理员保护和管理员 HTTP 权限。

## 2. 数据边界

- `users.role` 继续是角色事实源，现有 `admin/editor/viewer` CHECK 不变。
- 首次提升只允许在不存在 active、未删除管理员时执行；目标必须唯一、active、未删除且已经正常注册。
- 操作使用 PostgreSQL transaction advisory lock，避免两个操作员并发指定不同首管理员。
- 密码、验证码和 Token 不进入 SQL、Operations 文档或环境变量；首次提升只修改 role、version、updated_at。
- 同一事务写入不含秘密的 `audit_logs`，`actor_type=database_operator`，以数据库 `current_user` 和必填变更单号记录 viewer → admin 的初始角色变更。
- 首管理员存在后，后续角色管理继续走受限 HTTP API及应用层最后管理员保护，不使用数据库流程。

## 3. 取舍

该方式消除配置文件长期保存初始管理员密码的风险，也删除只服务首次启动的生产命令和 Repository 分支。代价是首次提升需要数据库操作权限，因此必须按 Operations-009 执行、核对返回行并限制为一次。

误指定不能依赖被提升用户登录。Operations-009 必须提供 break-glass 原子纠正：锁定流程，确认当前只有一个错误的 active admin，先提升正确 viewer，再降级错误 admin，并在同一事务写入两条共享变更单号的审计记录；任一前置条件不满足时整体回滚。
