# 采集批次与队列任务原子重试设计

## 问题与依据

现有 `POST /collection-runs/{id}/retry` 只把 `collection_runs` 与 targets 改为 `queued`。原 `collect_source` 任务已进入 `discarded` 或 `cancelled` 终态，而调度器使用 source、query signature 与窗口生成稳定唯一键；再次扫描只能命中原任务，无法产生可执行工作，批次因此永久停留在 `queued`。

River 官方把 discarded/cancelled 任务保留为可操作事实，并提供人工 retry；其 PostgreSQL 原生设计同时强调业务事实与任务应在同一事务提交。HotKey 继续使用同一原则，不新建第二条任务，也不在 HTTP 请求中执行 Connector Fetch。参考：[River 官方仓库](https://github.com/riverqueue/river)、[River 官方功能说明](https://riverqueue.com/)。

## 决策

1. 管理员只能重试 `failed` 或 `cancelled` 的采集批次。
2. 每个 `(source_connection_id, query_signature)` 使用稳定的 PostgreSQL transaction advisory claim lock。Worker 必须在该锁内重新读取 target/checkpoint 并完成 run 的 create-or-reuse 与 StartRun；Retry 也必须在同一 claim lock 内检查较新 run、恢复 checkpoint、重置 run/targets 并激活任务。锁只保护事实领取，Connector Fetch 始终在提交后、锁外执行。
3. 一次重试同时取得 `hotkey.monitor_source_configuration` 配置锁与 collection claim lock，再在同一 PostgreSQL 事务中完成三项状态变化：以 CAS 把该 run targets 的 checkpoint `next_poll_at` 恢复为原 `window_start`；把批次及 targets 重置为 `queued`；由 source、query signature 与原窗口定位的唯一 `collect_source` 任务激活为 `available`。配置生命周期和新旧窗口 Worker 都不能与重试 eligibility 检查交错提交。
4. 只允许重试同一 source connection 与 query signature 的最新窗口。事务锁定目标 run 后，只要存在任何 `window_start` 更晚的 run（不论 queued、running、succeeded、failed 或 cancelled），旧 run 重试立即冲突；管理员应处理最新终态 run，不能倒序回放。
5. checkpoint CAS 只允许 cursor、ETag、Last-Modified 仍等于该 run 的 request state，且 `last_successful_run_id` 为空或指向不晚于该失败窗口的成功 run；更新必须匹配并递增 checkpoint version。任一 target 已由更新窗口推进时，整个重试冲突回滚，禁止回放旧窗口覆盖新事实。
6. Monitor-owned Published Target Reader 必须复用调用者事务读取恢复后的 checkpoint，并继续要求 monitor active、config published、target/source enabled、source 未删除。没有完整 eligible targets 时，业务状态、checkpoint 和任务全部回滚。
7. 原任务必须处于 `discarded`、`cancelled` 或尚在自动重试等待的 `available`。不存在、kind/唯一键不匹配、`running` 或 `completed` 均使整个事务冲突回滚，不能留下孤立 queued 批次。
8. `available` 任务只提前 `scheduled_at`；`discarded/cancelled` 任务保留 attempt、`river_job_attempt` 与历史错误，并把 `max_attempts` 增加 1（最多 25）后激活。人工重试每次只授予一个新 attempt，不清零或伪造历史轮次。
9. Source Application 只依赖窄重试激活端口；Source Infrastructure 先验证 Published Target，再根据领域运行事实计算既有稳定唯一键；Platform Queue 只暴露通用的按 kind/unique key 激活能力。业务模块不得直接更新 `river_job`。
10. Operations 的按 job ID 重试是运行治理命令，保持现有“重置操作员重试周期”语义；Source 的按业务 run 重试必须保留历史并只追加一次机会。两者选择器、授权与审计边界不同，分别以回归测试固定，不能互相旁路。
11. HTTP 响应、权限、业务码、DTO 与 OpenAPI 路由保持不变。请求只提交持久状态命令，不执行 Fetch、不调用 Cron、不创建新任务。

## 一致性与失败边界

- 配置锁与 collection claim lock 后，批次行、同签名较新 runs 与 checkpoints 使用锁/CAS，并由同一事务上下文调用 Published Target Reader 与 Queue Store。若较新 Worker 先 claim，Retry 必须看到较新 run 并冲突；若 Retry 先提交，较新 Worker 必须重读到旧窗口 checkpoint 并拒绝创建较新 run。
- 任一数据库写入或队列激活失败都回滚批次、targets 与任务状态。
- Worker 仍通过 `StartRun` 的状态机领取 queued 批次；重复投递不能并发领取同一 run。
- 已被清理的终态任务不可重试，接口返回稳定冲突；运维应重新发布有效监控产生新窗口，而不是伪造任务。

## 非目标

- 不修改 Schema、OpenAPI 或采集 payload。
- 不允许重试 succeeded/running/queued 批次。
- 不绕过当前已发布监控、来源可用性与 Worker 的重新读取校验。
