# 来源凭据与个性化配置设计

## 问题与目标

来源连接参数已经由 PostgreSQL 保存并可在来源管理页创建，但第三方凭据只能填写 `env:NAME` 引用。管理员仍需编辑服务器文件并重启进程，配置事实分散在 UI、数据库和部署环境中。

本设计将当前单工作区内的来源连接升级为完整的 UI 管理事实：管理员可在登录后的来源页填写和轮换凭据；普通成员仍只看到“已配置/未配置”。部署环境只保留基础设施、身份密钥和一个来源凭据主密钥。

## 配置分层

- 部署级：数据库、Redis、MinIO、JWT/HMAC、SMTP、网络、可观测性和 `HOTKEY_SOURCE_CREDENTIAL_MASTER_KEY`，继续由环境配置管理。
- 工作区级：来源类型、端点、合规参数、配额、保留策略和来源凭据，由既有 Source 控制面与 PostgreSQL 管理。
- 用户级：时区、语言和展示偏好继续由 `user_preferences` 管理；来源是共享采集资源，不伪装成当前数据模型尚不存在的个人私有来源。

## 核心决策

1. API 接受仅写字段 `credential`；任何读取响应、审计、日志、错误和 OpenAPI 示例都不得包含其值。
2. 明文只在请求处理和连接器调用期间存在。持久化使用 AES-256-GCM，随机 96 位 nonce，并把来源 ID 与密钥版本绑定为附加认证数据。
3. `source_credentials` 一对一保存密文、nonce 和密钥版本；`source_connections.credential_ref` 只保存 `managed:v1` 或兼容的 `env:NAME` 引用。
4. 主密钥使用独立的 Base64 编码 32 字节环境变量。未配置主密钥时，既有 env 引用来源照常运行，UI 管理凭据写入返回安全的不可用错误。
5. 更新凭据必须携带来源乐观锁版本，与来源版本、密文写入和审计处于同一事务；轮换后健康状态重置为 unknown。
6. 已配置凭据永不回填表单。管理员只能替换；Viewer/Editor 仍只获得布尔事实。
7. 旧 `env:NAME` 来源无需迁移；管理员下一次从 UI 替换凭据时原子切换到托管凭据。

## 安全与失败

- 明文长度限制为 1–16384 字节，空白值和同时提交 `credential`/`credential_ref` 均拒绝。
- 密文认证失败、主密钥缺失或记录缺失统一表现为 `credential_unavailable`，不得区分可供探测的内部原因。
- 数据库备份不包含主密钥；主密钥与数据库必须分开备份。丢失主密钥时，密文不可恢复，只能由管理员重新录入。
- 回滚应用不会删除密文或历史来源；旧版本仍能运行保留 `env:NAME` 的来源，托管来源需停用或回到支持 029 的版本。

## 验收边界

- AC-029-1：管理员能在创建来源时直接填写凭据，不编辑 `.env`；请求完成后界面和 API 均不回显明文。
- AC-029-2：管理员能以乐观锁轮换凭据，健康状态重置；并发旧版本写入失败且不覆盖新密文。
- AC-029-3：数据库只出现 AES-GCM 密文、nonce 和 `managed:v1` 标记，日志与审计无明文。
- AC-029-4：现有 env 引用来源保持兼容；缺少或错误主密钥不会泄露密文，也不影响无凭据来源和历史读取。
- AC-029-5：桌面与移动端来源表单可键盘操作，Viewer/Editor 无凭据写入口。
