# 配额限流保留与审计治理设计

## 现状与问题

HotKey 已有三类可复用事实：来源连接保存 `rate_limit_per_minute`，AI 运行在调用前原子预留 `max_cost`并在终态结算，采集、AI 与投递表保存可聚合的用量事实。缺口是手动搜索没有并发安全的日配额，用户看不到统一用量，保留仓储无 dry-run 和批量保护，审计也没有管理员查询入口。

## 目标与非目标

本条用最少新代码完成可观测、可限制、可预览、可追溯的 MVP 治理闭环。不引入计费、多租户套餐、分布式令牌桶、对象存储删除编排或第二套 AI/来源/投递账本。

## 配额与用量模型

用量总览统一投影五类维度，但根据业务特性区分硬配额与观测项：

| 维度 | 事实源 | 模式 | 窗口/上限 |
|---|---|---|---|
| active monitors | `monitors.status` | 工作区硬配额 | 同时最多 50 个 |
| manual searches | `quota_usage_ledgers` | 用户硬配额 | UTC 自然日 20 次 |
| source calls | `collection_runs` + 来源速率配置 | 观测，上游 429 独立 | UTC 自然日 |
| AI tokens/cost | `ai_runs` + `ai_budget_ledgers` | token 观测，cost 依模型日预算硬限制 | UTC 自然日 |
| notification deliveries | 告警/报告投递表 | 观测 | UTC 自然日 |

监控发布和恢复复用现有工作区事务锁，在状态改为 active 前计数。手动搜索在同一事务中先插入可回滚队列任务，仅当本次确实创建任务时用原子 UPSERT 消费一次日配额；超额使整个事务回滚，五分钟内的幂等复用不重复计费。AI 外部调用继续使用已有 reservation → provider → settle 链路。

产品配额超限返回 HTTP 429 和稳定业务码 `10005`，`data` 包含 `dimension`、`limit`、`remaining`、`reset_at`。上游来源 429 仍保存为采集错误事实，AI 供应商 429 仍使用 `70003`，不伪装成产品配额。

## 保留模型

`retention_policies` 是唯一策略事实源，默认覆盖已标准化的采集临时项、内容/事件指标快照、失效会话、投递尝试、队列尝试和审计。审计策略只可见且默认禁用，普通执行接口始终拒绝删除审计。核心 `contents`、`events`、已发布 `reports` 不出现在执行白名单。

每次执行必须先 dry-run，返回截止时间、候选数、批量上限和是否仍有更多。真实执行一次最多处理 1000 个顶层记录，用有界 CTE 选定 ID 再删除，不执行无界语句。执行与 `retention.executed` 审计在同一事务提交。

## 管理员交互

新增 `/dashboard/governance` 并只对 Admin 展示导航。页面用 shadcn/ui `Card`、`Progress`、`Badge`、`Table`、`Select`、`AlertDialog` 和 `Button` 组合三个区域：五类用量、保留策略及预览/执行、可筛选的审计列表。Editor/Viewer 不获得治理 API，但 Editor 在监控页可看到当前自己的手动搜索剩余量。

## 安全、失败与边界

- 治理 API 只返回聚合数、安全审计字段和策略描述，不返回队列 args、凭据、请求正文或供应商错误。
- 保留数据类只能由服务端白名单解析，不拼接客户端 SQL 标识符。
- 上游、AI 或邮件不可用时仍以原业务事实和异步重试为准；治理总览不进入业务写链路。
- 空态、请求失败、超额、预览为零、批量截断均有明确中文反馈。

## 设计验收边界

- 并发发布/恢复和手动搜索不突破硬配额，幂等复用不多扣。
- 统一总览只读现有事实源，用户在操作前能看到手动搜索和 AI 成本额度。
- 保留必须 dry-run、有界批处理、保护核心事实并写审计。
- Admin 能在桌面和移动端完成查看、筛选、预览和二次确认执行，Editor/Viewer 无越权入口。
