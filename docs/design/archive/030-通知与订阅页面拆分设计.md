# 通知与订阅页面拆分设计

## 问题

站内通知与报告订阅原本纵向组合在 `/dashboard/notifications`。通知列表变长后，订阅入口和状态被推到页面底部，用户难以发现和持续管理，移动端问题更明显。

## 决策

- `/dashboard/notifications` 只承载站内通知、实时连接状态、手动刷新、已读同步与资源链接。
- 新增 `/dashboard/subscriptions`，只承载报告订阅列表、创建、启停、删除、私有 Feed 轮换、分页与错误重试。
- 主导航只保留“订阅”入口；通知页统一由右上角带未读提示的铃铛进入，避免同一区域出现两个等价入口。
- 两个页面复用现有 `app-page`、`PageHeader`、生成 API Client 与业务组件，不复制数据状态或引入新的后端事实。
- 报告订阅成为独立页面后使用一级标题；桌面操作位于页头右侧，移动端主操作占满可用宽度。

本设计仅局部取代 022、024、026 中“通知与订阅同页组合”的前端决策，不改变它们的通知、交付、权限、恢复或审计规则。

## 失败与兼容边界

- 两个路由必须独立挂载，通知页不得触发订阅读取，订阅页不得通过混合页面副作用修改通知已读状态。
- 订阅错误与空态继续区分，通知实时通道仍按既有 SSE/轮询策略降级。
- 不新增兼容重定向，因为 `/dashboard/notifications` 仍是有效通知终点；订阅入口迁移由导航和站内链接完成。

## 验收边界

- 桌面与移动主导航均不重复展示通知入口；铃铛进入通知页，“订阅”继续作为独立主导航入口。
- 两页分别覆盖真实数据、空态、错误态和主要交互，无页面级横向溢出。
- OpenAPI 一致性、类型检查、前端单测、生产构建、浏览器交互和视觉 QA 通过。
