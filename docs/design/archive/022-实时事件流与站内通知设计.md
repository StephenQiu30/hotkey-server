# 实时事件流与站内通知设计

## 决策结论

022 不引入 Socket.io、WebSocket、Redis Pub/Sub 或进程内广播。新增一个 PostgreSQL 事务型通知 outbox，由原业务事实的数据库触发器在同一事务内写入；API 进程以 Bearer 认证 SSE 顺序读取，普通 JSON 补拉接口提供断线恢复和轮询降级。业务详情仍从原模块正式 API 读取，通知不是第二套业务事实。

## 现有事实与差距

- `event_updates`、`alert_occurrences`、`collection_runs` 与 `reports` 已持久化关键变化，但没有统一、全局单调的通知游标。
- `/dashboard/notifications` 当前只管理报告订阅；TopNav 铃铛只查询开放告警，没有实时 Toast、通知徽标或恢复语义。
- 浏览器 access token 只保存在内存，原生 `EventSource` 不能安全携带 Bearer；不能把 JWT 放入 URL，也不能把 refresh cookie 当作 SSE 凭据。
- 全局 HTTP 请求有超时；正式 SSE 路径需要显式豁免，同时保留断连取消、心跳、连接上限和服务关闭边界。

## 持久事实与事件类型

唯一 Schema 新增 append-only `notification_events`：全局自增 `id` 是持久事件游标，保存 `event_type`、`resource_type`、`resource_id`、`audience_role`、`occurred_at`、最小 JSON payload 和唯一 `dedupe_key`。

触发器仅从已提交业务行生成安全投影，并与原写操作同事务提交：

- `event_updates` INSERT → `event.updated`，Viewer 及以上可见，资源为 Event，payload 只含 update kind/summary。
- `alert_occurrences` INSERT → `alert.triggered`，Viewer 及以上可见，资源为 AlertThread，payload 只含 severity。
- `reports` 进入 published → `report.published`，Viewer 及以上可见；进入 failed → `report.failed`，仅 Admin 可见。
- `collection_runs` 进入 succeeded → `collection.succeeded`，Editor/Admin 可见；进入 failed → `collection.failed`，仅 Admin 可见。

重复执行 Schema 或幂等业务写不会重复通知；dedupe key 由来源表、行 ID、终态和版本构成。通知 payload 不保存正文、原始证据、SQL、凭据、内部错误文本或跨模块可变详情。

## HTTP 与恢复契约

- `GET /api/v1/notifications?after_id=<id>&limit=<1..100>` 按 ID 升序补拉当前角色可见事件，返回 `next_after_id`。`after_id=0` 从最早保留事件开始。
- `GET /api/v1/notifications/stream?after_id=<id>` 使用相同授权与过滤，响应 `text/event-stream`；同时接受合法数字 `Last-Event-ID`，Header 优先于 query。
- 每个业务帧包含 SSE `id`、`event` 和由 OpenAPI DTO 序列化的 `data`；心跳只发送注释帧，不含业务数据。
- Stream 设置 `Cache-Control: no-cache, no-transform` 与 `X-Accel-Buffering: no`；客户端断开立即取消。轮询间隔、心跳间隔与单实例最大连接数由环境配置，达到上限在写入 SSE header 前返回统一 503。

前端调用生成的 stream Client，并使用 Axios 1.18 fetch adapter 获取 `ReadableStream`，不手写接口路径或 DTO。客户端按用户保存 last event ID 和 read-through ID，重复 ID 幂等忽略；连接失败指数退避，连续失败后使用生成的 JSON Client 轮询，后续自动探测并恢复 SSE。

## 页面与交互

- App 级实时控制器只在认证完成后启动；新通知进入 Zustand 有界列表，触发本地化 Toast，并更新 TopNav 通知徽标。
- 铃铛进入“站内通知”，页面按新到旧展示类型、摘要、时间、传输状态与原资源链接；进入页面即把当前游标标记已读。
- 现有报告订阅保留在同页独立区域，不与通知事实混用。
- 正常、连接中、轮询降级、空态与局部错误态使用现有 shadcn/ui Alert、Badge、Button、Card、Empty 与 ScrollArea；390px 不出现横向滚动。

## 权限、安全与容量

- Repository 只根据认证中间件写入的数据库-backed Role 过滤；客户端角色、query 或 payload 不能扩大 audience。
- Viewer 只能读取 audience=viewer；Editor 可读 viewer/editor；Admin 可读全部。匿名请求在 Repository 前被拒绝。
- 列表和每次流补拉最多 100 条，使用 `(audience_role,id)`/`id` 索引；慢客户端只按游标重新读取，不在内存积压无限队列。
- 多实例、重启和短时网络中断均从 PostgreSQL 游标恢复；outbox 保留策略留给 025，不在本条物理删除历史。

## 非目标

- 不做双向实时命令、在线状态、跨用户聊天、浏览器推送、邮件推送替代或通知偏好中心。
- 不把 Content/Alert/Report 详情复制进 outbox，不为每个用户复制同一通知，也不在本条实现长期保留清理。

## 设计验收边界

- 业务事实与通知同事务成功或同事务回滚；重放与重复写不生成重复 dedupe key。
- 断线后携带 Last-Event-ID 可补齐全部可见事件且顺序稳定，客户端容忍重复；SSE 不可用时 JSON 轮询继续更新页面。
- Viewer 永远收不到 collection/report failure 等 Admin 诊断；匿名、伪造角色与超连接上限被服务端拒绝。
- Admin/Viewer、桌面/390px、正常/空/降级/错误、键盘焦点和 axe 全部通过。
