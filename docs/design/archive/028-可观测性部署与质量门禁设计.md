# 可观测性部署与质量门禁设计

## 现状

项目已有 health/readiness/metrics、结构化日志、OpenTelemetry 基础、运行概览、单二进制角色、双环境 Compose、后端 CI 和前端构建测试入口。

## 目标

让 MVP 在本地和生产可重复部署、诊断、升级和回滚，并以端到端质量门禁约束所有 001–027 实现。

## 非目标

不在本条复制相邻领域的数据或服务，不以纯前端假数据宣称功能完成，也不引入第二套事实源。

## 核心决策

- 保持 all/api/worker 三种角色和 PostgreSQL、Redis、MinIO 基础设施；开发与生产只通过根 Compose 覆盖环境差异。
- HTTP 请求继续使用路由模板、方法和状态码作为低基数标签；Operations 基础设施从现有事实表生成来源采集、持久任务、配额与 AI 成本的 Prometheus 投影，不新增时序数据库。
- 来源标签只允许固定 `source_type`；任务标签只允许固定 `kind`、`state`、`outcome`；不记录查询文本、URL、账号、凭据、资源 ID 或上游错误文本。
- 队列失败历史只持久 `retryable`、`permanent`、`cancelled` 等稳定原因码；管理员通过任务 ID、类型、状态、安全资源 ID 和来源采集运行的分类错误定位失败，不读取 River 任务原始参数。
- CI 顺序包含架构门禁、Schema 验证、OpenAPI/生成 Client 漂移、后端测试、前端类型/单测/构建、生产依赖漏洞审计、Compose 配置与真实容器浏览器烟测。
- 备份恢复、密钥轮换、来源授权和故障处置在对应功能验收后形成 Operations；发布使用向前兼容和能力开关。

## 数据、接口与交互

- 健康、指标、日志、追踪和运行总览
- 开发/生产容器部署
- CI、契约、浏览器和安全门禁
- 备份恢复、发布回滚和容量基线

所有状态变化保存明确版本、时间和操作者；跨端字段由 Schema、后端 DTO 和生成 OpenAPI 驱动，前端不得手写重复类型。

## 安全、失败与降级

只有指标没有告警阈值和恢复流程仍不可运营。MVP 只定义可从现有指标直接计算的队列滞后、失败率、依赖可用性和配额/成本阈值，并绑定故障处置手册；不内置 Prometheus 服务器、可视化平台或通用告警规则引擎。

外部 AI、邮件、实时连接或归档不可用时，业务事实先可靠落库，异步重试或降级读取，不在请求链路丢失结果。

## 设计验收边界

- 全新环境按 README 可启动并通过 readiness
- 任一流水线失败能通过低基数指标、任务安全投影和采集运行定位，不泄露业务内容或上游原始错误
- 本地与 CI 均能阻止 Schema、OpenAPI、生成客户端、Compose 和生产依赖安全门禁漂移
- 备份/恢复、升级/回滚、密钥轮换与容量判断均有可重复执行且不包含真实凭据的 Operations 手册
