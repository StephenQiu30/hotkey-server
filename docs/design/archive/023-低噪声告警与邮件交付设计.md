# 低噪声告警与邮件交付设计

## 现状与问题

项目已基于不可变 `EventUpdate` 评估 Alert Thread，并具备 Occurrence、确认、解决、抑制、重开、稳定分页和审计。现有策略只判断监控的综合事件阈值；它无法区分高热度但低动量、单一来源或低重要性的变化。SMTP 已用于身份邮件和报告交付，但告警邮件没有持久事实、事务性任务规划、重试诊断或前端详情。

## 目标

对每个已发布 Monitor，以同一份不可变 EventUpdate 同时判断热度、动量、来源宽度和重要性；仅当全部门槛通过时创建或更新 Alert Thread。新 Occurrence 与可选邮件 Delivery 必须原子落库，SMTP 在后台可靠投递，失败不改变告警事实。

## 非目标

- 不实现短信、Webhook、移动推送、邮件营销或自定义 HTML 模板编辑器。
- 不按每个用户复制告警事实；MVP 每个 Monitor + Event 只有一条 Thread。
- 不把收件地址写入 Monitor 配置或公开 API；收件人取 Monitor 创建者当前有效账户邮箱并冻结在 Delivery 中。
- 不重新实现实时通知、报告 Delivery 或基础表单控件。

## 策略模型

已发布的 Monitor 配置新增以下字段，并纳入配置哈希与版本快照：

| 字段 | 范围 / 默认值 | 含义 |
| --- | --- | --- |
| `alert_min_heat` | 0–100 / 70 | EventUpdate 的热度下限 |
| `alert_min_momentum` | 0–100 / 55 | 将趋势分 `[-100,100]` 归一化后的动量下限 |
| `alert_min_breadth` | 0–100 / 25 | `min(source_count × 25, 100)` 的来源宽度下限 |
| `event_threshold` | 0–100 / 70 | Monitor-Event 综合重要性下限，沿用现有字段 |
| `alert_warning_threshold` | 0–100 / 75 | warning 严重级别分界 |
| `alert_critical_threshold` | 0–100 / 90 | critical 严重级别分界，必须不低于 warning |
| `alert_cooldown_minutes` | 5–1440 / 60 | 相似变化的打扰冷却期 |
| `alert_email_enabled` | false / false | 是否规划告警邮件 |
| `alert_email_min_severity` | warning 或 critical / critical | 最低邮件严重级别 |

系统只使用已发布且处于 active 状态的配置。草稿修改不会改变运行中告警。动量和来源宽度必须从 EventUpdate 的 `after_state` 计算，不读取随后变化的 Event 当前态。四项门槛全部满足才告警；最终综合分低于 warning 为 info，达到 warning 为 warning，达到 critical 为 critical。

策略语义升级为 `alert-policy-v2`。Thread 和 Occurrence 冻结配置版本、配置哈希、所有门槛、各维度得分、原因和严重级别，使历史结论可解释，不随新配置改写。

## 线程、冷却与状态

- 唯一身份为 `Monitor + Event + policy version`；每个实质 EventUpdate 以稳定 fingerprint 幂等创建一个 Occurrence。
- 同一变化并发评估依赖数据库唯一约束与行锁，只允许一个创建者继续规划邮件。
- 冷却期内相似变化只追加 Occurrence、更新 Thread，不产生新的实时打扰或邮件；不同 EventUpdate 仍保留事实。
- open 可确认、解决或抑制，acknowledged 可解决或抑制；resolved/acknowledged 在冷却期外遇到新实质变化可重开，suppressed 不自动重开。
- 状态命令继续使用乐观锁、最小角色授权与不可变审计。

## 邮件交付模型

新增 `alert_email_deliveries` 和 `alert_email_attempts`：

- 每个 Occurrence 最多一个 Delivery；`occurrence_id` 和 `idempotency_key` 均唯一。
- Delivery 冻结收件人、主题、正文、严重级别与状态；收件地址不通过告警 API 返回。
- 状态为 queued、claimed、retrying、succeeded、failed；每次尝试追加 Attempt。
- 仅当邮件开关开启且 severity 达到策略下限时规划 Delivery。
- Occurrence、Delivery 和 River Job 在同一数据库事务内创建。任一持久化失败全部回滚；重复评估不会重复发信。
- SMTP 仅由 `deliver_alert_email` 后台任务执行，临时或永久错误均记录通用诊断并按既有退避策略最多尝试 5 次。SMTP 失败只改变 Delivery，不回滚或删除 Thread/Occurrence。

## 接口与前端

- Monitor 创建/草稿接口读写完整告警策略，发布后由后台评估器消费。
- 告警列表保留筛选、稳定分页和状态操作。
- 告警详情返回 Thread、Occurrence、审计和安全的邮件投递投影：状态、严重级别、尝试次数、下次重试时间、成功时间及通用错误；不返回收件地址、SMTP 响应或凭据。
- 前端使用生成的 OpenAPI Client 和 shadcn/ui Dialog、Select、Input、Checkbox、Badge、Table 等组件。监控表单提供保守默认值、字段范围和邮件最低严重级别；告警详情覆盖触发依据、历史、审计与交付诊断。

## 安全、可观测性与降级

- Monitor 可见性继续作为告警读取边界；抑制仅 Editor/Admin，其他既有状态权限不放宽。
- 邮箱、SMTP 凭据和上游原始错误不得进入 API、日志、审计或浏览器。
- 邮件未配置或暂时不可用时，告警仍可创建；已规划 Delivery 保留并可安全重试，前端显示通用状态。
- 任务处理记录成功、重试、最终失败计数，数据库事实用于运营恢复。

## 设计验收边界

- 同一变化并发评估只产生一个 Occurrence、一个 Delivery 和一个后台任务。
- 任一维度未达门槛时不创建告警；严重级别和冷却行为严格使用已发布快照。
- SMTP 故障不回滚告警事实，重试不会重复 Delivery，达到上限后可诊断。
- 用户能在桌面与移动端完成策略配置、告警筛选、详情阅读和授权状态操作，键盘与辅助技术可用。
