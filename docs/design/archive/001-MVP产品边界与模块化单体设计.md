# MVP产品边界与模块化单体设计

## 现状

Go 模块化单体、PostgreSQL、River、Next.js 工作台已经形成主链路，但现有能力与“鱼皮热点监控完整 MVP”的对标范围尚未由一套新文档统一约束。

## 目标

在不推翻现有可靠底座的前提下，形成一个可自托管、可审计、以事件为中心的热点监控 MVP，并明确当前事实与目标能力的边界。

## 非目标

本条不跨越相邻编号实现其业务细节，也不建立第二套身份、任务、数据、API 或 UI 事实源。

## 核心决策

- 保持单仓库、Go 单二进制模块化单体和 Next.js App Router，不引入微服务、Kafka 或第二套 Schema。
- PostgreSQL 保存业务事实，MinIO 保存原始证据，River 执行持久任务；Redis 仅用于短期状态。
- 功能链路固定为来源→采集→标准化→相关性→事件→热度→告警→报告；任何新来源只能通过 Source 端口接入。
- MVP 对标功能按 001–028 独立交付，目标设计不得伪装成当前实现。

## 数据、接口与交互

- 统一能力地图与依赖顺序
- 模块所有权和调用边界
- 当前/目标差距标注
- 跨端契约和事实源规则

所有新增跨端字段先进入 `backend/db/schema.sql` 和后端 DTO/Swaggo 注解，再生成 `docs/openapi/swagger.json` 与前端 Client。页面同时提供正常、加载、空、错误和权限不足状态。

## 安全、失败与降级

最大的风险是一次性复制参考项目的实现细节，破坏现有事件模型；执行时只对齐用户能力，不复制其技术债务。

失败必须被分类、可观测且不破坏历史事实；可选外部依赖不可用时，核心读取链路继续工作。

## 设计验收边界

- 所有交付项均有同编号 Design、PRD、Plan
- 架构依赖继续满足 transport→application→domain
- 代码、Schema、OpenAPI 和文档只有一套事实源
