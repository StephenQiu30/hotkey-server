# 全局异常与响应契约设计

日期：2026-09-21。本文统一 API、Web、Worker 与 App 的边界协议，承接 031、033—035、038—040、042 的既有质量需求，不新增产品功能或验收分母。2026-09-21 已按当前实现指令完成设计复核并接受本文决策；运行验收结果仍以同编号 Acceptance 为准。总体 001 Design 和各领域 Design 仍需建立，不由本文替代。

## 1. 前置地位与现状

**DEC-046-001：先统一设计，再完成 046 修复与验收，最后开始其他计划的实现切片。** 001/002/003—045 可继续范围、研究和设计准备；042 虽已有部分实现，也必须先满足本门禁才能继续底座实施。046 只依赖已存在的应用骨架与本文冻结的公共契约，不依赖 042 S01、业务表、真实来源或 Flutter 初始化，避免循环依赖。设计复核按现有项目流程记录，不额外创建每个技术细节都需用户确认的流程。

2026-09-21 对当前代码及隔离 ASGI 探针的核对：

| 现有位置 | 已有能力 | 必须先修复的缺口 |
|---|---|---|
| `backend/app/api/exception_handlers.py` | 应用、HTTP、校验、未知异常处理器 | 自定义 HTTP 500 的 detail 可直接返回，500 映射为 http_error；校验运行响应与自动 OpenAPI 422 不一致 |
| `backend/app/api/middleware.py` | 请求 UUID、响应头、结构化访问日志 | 未知异常经过外层错误处理器时 contextvars 已清理，探针返回 request_id=unknown |
| `backend/app/core/errors.py` | ApplicationError、依赖不可用错误 | 应用异常携带 HTTP status_code，协议映射与业务分类耦合 |
| `backend/app/core/schemas.py` | ErrorView、HealthView、输入/输出基类 | 公共响应家族与注册规则尚未完整定义 |
| `frontend/src/request.ts` | 单一 Axios 入口与 ApiRequestError | 读取 detail 而服务端返回 details；缺少 body request_id 回退、非 JSON 与网络分类 |
| Worker / App | Worker 骨架 / App 尚未初始化 | HTTP handler 不覆盖消息失败；App 需按同契约独立验证 |

既有 HTTP 测试 7 项通过，但未知异常测试仅比较 body/header 相等，未排除两者同为 unknown；这不是本设计的通过证据。

## 2. 分层责任与全局状态

**DEC-046-002：HTTP 状态、错误原因、业务资源状态、页面状态分别建模。** 不增加一个包揽所有状态的全局枚举，也不以 HTTP 200 携带失败码代替错误状态。

| 层 | 输入与输出 | 责任 |
|---|---|---|
| Service / Adapter | 类型化结果或 ApplicationError | 应用错误只携带登记的 code 与安全结构化上下文，不携带 HTTP 状态、Response、任意可公开的异常字符串；驱动/上游异常在此归类 |
| HTTP 边界 | DTO 或 ErrorView | `api/exception_handlers.py` 集中维护 code → HTTP 状态、安全文案、必要响应头；Router 不逐个 try/except 重写协议 |
| Worker 边界 | 任务持久状态及安全原因 | 根据错误分类、尝试次数、预算、授权决定延期/失败；不生成 HTTP Response，不用捕获后继续循环代替恢复 |
| Web / App 传输层 | 生成 DTO 或本地请求错误 | 统一解码、超时、网络中断、取消、协议异常；公共类型来自生成客户端 |
| 页面 / 功能层 | 加载、空、数据、失败、无权限、过期数据 | 决定字段提示、页面恢复与操作反馈；不解析服务端 message 来判断分支 |

任务状态沿用 009：`queued → running → succeeded / partial / failed / cancelled`。延期仍为 queued，带安全原因及 next_run；取消请求与最终 cancelled 区分，不能在接受取消时伪造终态。具体转换、并发取消、结果保留、尝试记录由 009/031 Design 细化。查询 failed 任务成功是 HTTP 200，body 的业务状态为 failed；合法空查询是 200 和空 items；未受理请求按 HTTP 错误处理。`/health` 的存活、`/ready` 的依赖就绪、任务进度和页面加载状态互不代用。

## 3. 统一返回结构

**DEC-046-003：统一类型化响应家族，保留现有资源 DTO，不引入全接口 Result<T> 外壳。** 单资源直接返回声明的 DTO，分页和异步受理使用公共模型，失败统一 ErrorView。禁止中间件改写 JSON body；禁止再嵌套 success/code/data/message 与真实 HTTP 状态重复表达成功。新增公共模型必须有真实使用者或契约测试，不铺业务空模块。

| 场景 | HTTP / 媒体 | 结构与规则 |
|---|---|---|
| 读取、同步修改 | 200 application/json | 显式资源 `response_model`；健康接口继续 HealthView |
| 同步创建 | 201 application/json | 创建的资源 DTO；可寻址时返回 Location |
| 分页集合 | 200 application/json | `PageView[T] = {items: T[], next_cursor: string \| null}`；字段必需，末页 null；默认不执行总数查询，不混用 total/page/offset 外壳 |
| 异步受理 | 202 application/json | `JobAcceptedView = {job_id: UUID, status: "queued"}`；Location 指向任务查询；任务与 Outbox 持久提交后才能返回；幂等重放返回原任务当前 DTO，状态码及模型在具体端点明确声明 |
| 删除等无内容操作 | 204 | 无 body；不包装 null 或空对象 |
| 失败 | 实际 4xx/5xx application/json | 下述 ErrorView；错误不返回半成功业务 data |
| 文件、重定向、条件缓存、流 | 对应媒体与 3xx/304 等 | 在具体端点声明；204/304 无 body；文件和流不进入 JSON 包装 |

分页 cursor 不透明、校验格式，绑定查询/排序和访问范围；必须有稳定的最终排序键。具体限额和排序由端点设计给出，不能把 cursor 当作授权凭据。046 验证公共模型与代表性测试路由；真实集合/任务端点在所属计划接入，不能把测试路由发布为产品接口。

ErrorView 保留当前字段名称，作为项目自有 JSON 契约，不宣称实现 RFC 9457：

```json
{
  "code": "validation_error",
  "message": "请求参数不合法",
  "request_id": "4ec781a4-a51a-47da-bbf3-8e5d94b728b9",
  "details": [{"location": ["query", "limit"], "message": "请输入有效整数", "type": "int_parsing"}]
}
```

`code/message/request_id` 必需，`details` 仅字段校验错误使用，其余省略；字段项只允许 location/message/type，不返回原始 input、ctx、请求体或异常对象。校验 message 从受控映射生成，未知校验类型返回通用文案，不透传自定义 validator 消息；路径只含契约字段与索引，任意用户字典键需遮蔽。前端可按 type 显示字段文案，但不依赖 message 文本。成功响应 request_id 在 `X-Request-ID`，无需重复塞入所有 DTO。

## 4. 错误注册与 HTTP 映射

**DEC-046-004：一个稳定错误码只能有一个公共含义和默认 HTTP 映射。** 应用 code 使用小写 snake_case，公开后不更名或复用。`core/errors.py` 登记代码与应用分类；HTTP 映射放在 API 层，测试检查完整性。新增领域错误在所属切片追加登记、映射、schema 和验证，不先建数百个空错误码。不在领域错误中存 HTTP status_code，不允许 Router 任意传状态覆写。

| HTTP | 基础 code | 含义与客户端动作 |
|---|---|---|
| 400 | bad_request | 无法处理的请求语义；修正输入 |
| 401 | unauthorized | 当前请求未认证；登录端点就地提示，受保护接口由会话层单次协调失效处理 |
| 403 | forbidden | 已认证但无权限；不循环刷新或重试 |
| 404 | not_found | 资源或路由不存在；按权限设计避免泄露资源是否存在 |
| 405 | method_not_allowed | 方法不允许；保留 Allow |
| 409 | conflict | 状态/版本/幂等键冲突；读取最新状态或修正操作 |
| 413 | payload_too_large | 请求过大；缩小输入 |
| 415 | unsupported_media_type | 不支持的媒体类型；修正上传格式 |
| 422 | validation_error | 字段校验失败；显示安全 details |
| 429 | rate_limited | 当前请求被限流；仅有可靠时间时发送 Retry-After |
| 500 | internal_error | 未预期错误或响应模型校验失败；通用文案与请求标识 |
| 502 | upstream_error | 同步调用上游的无效响应；不泄露上游 body |
| 503 | dependency_unavailable | 必需依赖暂不可用；不能将所有数据库错误一律算此类 |
| 504 | upstream_timeout | 同步等待上游超时；写入结果可能未知，不自动重发 |

现有已使用的具体依赖错误码在 S00 逐一登记并保留含义，不为表格统一擅自改名。预期唯一约束冲突可归类 conflict，其他数据库编程/完整性错误若未识别仍归 internal_error。非表内 HTTPException：保持有效错误状态，安全通用 code=http_error；所有 5xx 的 detail 均禁止原样返回。公开文案来自登记表，第三方或临时 HTTPException 的 detail 不构成安全文案来源。

保留框架/认证协议必要的 Allow、WWW-Authenticate 和经校验的 Retry-After；不盲目复制任意异常 header，尤其不能覆盖请求标识、设置 Cookie 或返回外部 Location。未知异常使用内部错误的安全响应，不向用户暴露异常类或堆栈。取消与客户端断连按传输生命周期处理，不捕获 BaseException 改写为业务失败。

## 5. Request ID、日志与进程边界

**DEC-046-005：请求标识必须跨越错误处理器生命周期。** API 为每次 HTTP 请求产生 UUID，写入 request scope/state；异常处理从该持久请求上下文读取，contextvars 只用于日志绑定，不能是唯一来源。正常、404、422、应用异常、未捕获异常的 body/header/访问日志同一 ID，禁止 unknown。外部提供的 X-Request-ID 不直接信任或替换本次 ID；有合法链路追踪时另记受控关联信息。

访问日志只记录 request_id、method、路由模板、status、duration；未知路由使用固定占位，禁止记录原始路径/查询参数。内部错误日志保存异常类型及脱敏后的堆栈位置，不能直接序列化含 SQL、参数、URL 或秘密的异常链。中间件顺序和日志清理必须通过未捕获异常实测，不依靠“使用了日志框架”推断安全。并发请求验证上下文不串号。

| 边界 | 失败处置 |
|---|---|
| FastAPI 尚未发送响应 | 统一 ErrorView，正确状态与请求 ID |
| 同源代理未连接到 API | 属于代理可控的 HTTP 失败使用相同 ErrorView/502 或 504，并产生代理本次请求 ID；不伪造后端 trace；已有 API 响应保留其状态、头与 body |
| 不可控网关、离线、连接断开 | 客户端允许非 JSON、无 status、无 request_id，归传输或协议错误，不把 HTML 展示给用户 |
| 文件/流已发送响应头 | 不能再写 ErrorView 或修改 HTTP 状态；终止传输并记录 ID；若未来定义流内错误事件，须在该端点 Design/OpenAPI 单独声明 |
| Worker / 进程外任务 | 关联 job_id、attempt_id 与原始受理 request_id；重试产生独立尝试标识。记录原因并持久化处置后才允许推进连续完成位点；未知错误不得静默丢弃 |
| 启动/后台异常 | 启动失败使进程退出或不就绪；已发送响应的后台失败独立记录，不宣称能改写此前成功响应；可靠业务任务必须进入持久队列 |

046 只冻结 Worker 策略并验证错误分类可复用；真实 PostgreSQL/Outbox/Kafka 的提交、恢复和位点证明属于 031，不以 046 的单元测试替代。

## 6. Web 与 App 消费规则

**DEC-046-006：传输层统一解析，功能层决定反馈。** Web 的 `src/request.ts` 是唯一入口，使用生成的 ErrorView/分页/受理类型；不能手写另一套服务端 DTO。未知 body 先做结构检查，不直接强制断言类型。ApiRequestError 至少区分 `http/network/timeout/cancelled/protocol`，保留可选 status/code/details/requestId，requestId 优先取有效响应头，再取合法 body；都缺失则为空，不伪造服务端 ID。网络错误不伪装 HTTP 500；取消不弹失败提示。非 JSON 错误使用安全本地文案，绝不透传原始 HTML 或 Axios 消息里的 URL。

成功 JSON 直接返回 DTO；204 不解析 JSON；文件按端点 responseType 消费。HTTP 成功但不满足声明的必要格式时归协议错误，不能显示成功。传输层不自动弹 Toast、重定向或重试写请求。可重试读取由调用策略设置次数上限；写请求只有所属端点已定义幂等键和结果查询协议才可重试。超时不等于服务端未执行。

页面使用局部字段错误、持久页面失败与重试入口、短时操作反馈各自承担的职责；保留旧数据时明确其过期与刷新失败，空列表不等于加载失败。401 的会话失效处理避免多请求重复导航，403 不触发登录循环，429 尊重有效等待时间。所有客户端按 code/status 分支，不能按中文 message 匹配。

Flutter 复用服务端运行时 OpenAPI 和上述状态语义，HTTP 库、生成器及设备行为在 App 初始化后实现；服务端 046 门禁不等待未确定的 Flutter 工程，App 的业务接入则必须同时满足 046 与 APP-02 的独立契约验证。

## 7. OpenAPI 与防回退门禁

**DEC-046-007：运行返回、运行时 OpenAPI、生成客户端必须一致。** 所有 API 操作显式定义 operation_id、成功 status/response_model 和实际可达的错误响应。可通过 API 层统一注册帮助函数消除重复，但不得维护手写第二份 OpenAPI，也不能给每个路由虚假声明所有状态。

带请求校验的路由显式以 ErrorView 声明 422，架构测试阻止自动 HTTPValidationError 泄漏成公共错误契约；401/403/409/429/503 按实际依赖声明，未知内部失败的 500 为公共兜底。路由级 404/405 与代理错误单独验证，不把它们冒充每个操作的业务分支。成功泛型须得到具体 schema，不能输出无约束 object。

验证使用已存在健康/就绪接口与仅测试环境注册的代表路由，覆盖参数校验、应用错误、HTTPException、自定义 5xx、响应校验、未捕获异常、分页、202/204、文件和并发上下文。前端覆盖 details、body ID 回退、无响应、非 JSON、取消及 401 协调。代理不可用路径须通过真实代理请求验证，不能仅凭 Next rewrite 配置推断已有统一错误返回。

从同提交启动的 API 生成 Web 客户端、类型检查及生产构建；CI 对生成差异与契约矩阵失败阻断。046 建立这条最小契约检查链，042 在其上扩展 Compose 和真实依赖验证，不能各建一套生成器。

## 8. 交付、兼容与参考

实施与证据见 [046 前置计划](../plans/046-全局异常与响应契约前置计划.md)。迁移先登记现有 code 和消费者，再修复 handler/context/schema/客户端，最后完成真实代理与生成链验证；保持 HealthView、ErrorView 已有字段和现有合法错误码兼容。若必须破坏公开契约，先同步版本策略及消费者，不能悄悄增加统一外壳。

046 通过意味着公共协议可作为下一计划的基础，不代表认证、可靠任务、所有领域异常、Flutter 或产品验收完成。新端点必须持续运行同一门禁；缺少某领域映射时在其切片补齐，不能自行绕过。

框架机制参考：[FastAPI 错误处理](https://fastapi.tiangolo.com/tutorial/handling-errors/)、[额外响应声明](https://fastapi.tiangolo.com/advanced/additional-responses/)、[响应状态码](https://fastapi.tiangolo.com/tutorial/response-status-code/)、[Starlette 异常边界](https://starlette.dev/exceptions/)、[RFC 9457](https://www.rfc-editor.org/rfc/rfc9457.html)。项目选择以上明确决策，不因引用 RFC 而自动更换为另一种错误媒体类型。
