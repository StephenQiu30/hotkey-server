# 可观测性部署与质量门禁设计

## 现状

项目已有 health/readiness/metrics、结构化日志、OpenTelemetry 基础、运行概览、单二进制角色、双环境 Compose、后端 CI 和前端构建测试入口。

## 目标

让 MVP 在本地和生产可重复部署、诊断、升级和回滚，并以端到端质量门禁约束所有 001–027 实现。

## 非目标

不在本条复制相邻领域的数据或服务，不以纯前端假数据宣称功能完成，也不引入第二套事实源。

## 核心决策

- 保持 all/api/worker 三种角色和 PostgreSQL、Redis、MinIO 基础设施；开发与生产只通过根 Compose 覆盖环境差异。
- 每个外部来源、任务种类和 API 暴露 latency、success/failure、retry、queue lag、quota 和 cost 指标，标签不得含用户内容或高基数字段。
- CI 顺序包含架构门禁、Schema 验证、OpenAPI 漂移、后端测试、前端类型/单测/构建和 Compose 配置。
- 备份恢复、密钥轮换、来源授权和故障处置在对应功能验收后形成 Operations；发布使用向前兼容和能力开关。

## 数据、接口与交互

- 健康、指标、日志、追踪和运行总览
- 开发/生产容器部署
- CI、契约、浏览器和安全门禁
- 备份恢复、发布回滚和容量基线

所有状态变化保存明确版本、时间和操作者；跨端字段由 Schema、后端 DTO 和生成 OpenAPI 驱动，前端不得手写重复类型。

## 安全、失败与降级

只有指标没有告警阈值和恢复流程仍不可运营；每个关键 SLO 必须绑定可执行手册。

外部 AI、邮件、实时连接或归档不可用时，业务事实先可靠落库，异步重试或降级读取，不在请求链路丢失结果。

## 设计验收边界

- 全新环境按 README 可启动并通过 readiness
- 任一流水线失败能定位到来源、运行和任务而不泄露内容
- main 分支不能合入 Schema/OpenAPI/生成客户端漂移
