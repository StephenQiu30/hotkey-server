# 数据访问与生命周期设计

日期：2026-09-21。本文只冻结 036 S00—S01 的来源访问条件、组件许可记录和入库前字段最小化门禁。保留期限、删除传播、在线副本清理、备份重放和清理证明留给 S02—S04；本文不把内部政策服务解释为具体来源已获授权或 036 产品验收通过。

## 1. 范围与核心决策

来源是否公开、组件是否开源、平台是否允许当前用途是三个独立判断。S01 建立一个由 PostgreSQL 持有的当前政策事实：未来来源适配器只有在“来源能力已核对、组件版本与许可已登记、处理目的和字段用途已冻结、政策仍有效且显式启用”时，才能把白名单字段交给业务领域。

| 决策 | 冻结值 | 理由 |
|---|---|---|
| 领域归属 | `evidence` 持有跨来源的数据使用政策；`sources` 以后只实现无 ORM 的能力契约和适配器 | 总体 Design 已把生命周期归给 evidence，避免来源 SDK 自行决定可保存范围 |
| 事实存储 | PostgreSQL `source_access_policies` | Redis、配置文件和日志不能成为授权与字段范围的唯一事实 |
| 政策身份 | `owner_id + source_key + capability` 唯一 | 搜索、作者作品、评论和回复分别准入；一个能力通过不能放行其他能力 |
| 状态 | `pending / approved / blocked`；另有显式 `enabled` | “已核对”和“当前启用”分离；未知、阻止、过期或停用均拒绝数据进入业务层 |
| 访问依据 | `official_api / authorized_feed / written_permission / manual_import` | 只登记可审计依据，不把第三方组件技术可用性当作平台授权 |
| 字段规则 | 每项政策保存 `field_purposes` 对象，最多 64 个稳定顶层字段 | 以明确用途白名单投影，未知字段在内存中丢弃，不建立通用原始响应仓库 |
| 版本 | 每次保存同一政策都原子增加 `policy_version` | 下游数据未来可绑定实际采用的政策版本，不依赖可变“最新配置”解释历史 |
| 当前入口 | 内部 Service/DTO，无 HTTP、OpenAPI 或 UI | 004/020 尚未进入实现；S01 只提供可复用门禁，不提前建设管理页面 |

NIST Privacy Framework 将处理授权的建立/撤销/维护、数据生命周期以及数据最小化列为可实施的管理能力；欧盟 GDPR Article 25 对“默认只处理特定目的所必需数据”的表述用于支持工程默认值。两者都不替代 HotKey 实际适用法、平台条款或书面授权判断。PostgreSQL 的行内 `CHECK`/唯一约束负责不变量，`INSERT ... ON CONFLICT DO UPDATE` 负责并发下单条政策的原子新增或换版。

- [NIST Privacy Framework 1.0](https://www.nist.gov/privacy-framework/privacy-framework)
- [NIST Privacy Framework Core](https://www.nist.gov/document/nist-privacy-framework-v10webinardeck-29jan2020-002pdf)
- [EUR-Lex GDPR Article 25](https://eur-lex.europa.eu/eli/reg/2016/679)
- [PostgreSQL 18 Constraints](https://www.postgresql.org/docs/18/ddl-constraints.html)

## 2. 政策数据契约

### 2.1 `source_access_policies`

| 字段 | 规则 |
|---|---|
| `id` | 服务端 UUID 主键 |
| `owner_id` | 必填，关联当前单 owner；与 source/capability 组成唯一范围 |
| `source_key` | 1—64 位稳定小写标识，不保存 URL、Token 或账号正文 |
| `capability` | `search / author_posts / comments / replies` |
| `status` / `enabled` | 只有 `approved` 可设为 enabled；门禁仍实时检查是否过期 |
| `access_basis` | approved 时必填，取四种已登记依据之一 |
| `terms_reference` | approved 时必填；保存公开条款 URL 或受控内部授权引用，不保存授权正文/凭据 |
| `processing_purpose` | 必填，1—256 字符；说明当前能力为何处理数据 |
| `component_name/version/license` | approved 时全部必填；记录实际适配组件或内部适配器版本和许可标识 |
| `field_purposes` | JSON object；应用输入边界限制最多 64 个稳定顶层字段，数据库约束对象类型；值为 1—256 字符用途说明 |
| `reviewed_at` / `review_expires_at` | approved 时 reviewed_at 必填；可选失效时间必须晚于核对时间 |
| `policy_version` | 从 1 开始，同一身份每次保存递增 |
| `created_at` / `updated_at` | UTC；更新时间不得早于创建时间 |

字段名只允许小写稳定顶层标识；`authorization`、`cookie`、`password`、`secret`、`token`、API key 及常见 access/refresh/session 变体禁止登记。可放行的字段值只限 JSON 标量或标量列表；适配器先把复杂上游结构规范为经过评审的扁平 DTO。S01 不用正则判断个人敏感信息是否合法；任何身份、正文或指标字段都必须由对应来源 Design 给出具体用途后显式列入。

### 2.2 服务输入与输出

`SourceAccessPolicyInput` 是严格输入，拒绝多余字段。approved 政策缺少访问依据、条款引用、核对时间、组件版本/许可或字段用途时不能保存；pending/blocked 不得 enabled。失效时间不在 Pydantic 中依赖系统时钟，而由 Service 在保存和每次 admission 时按注入时钟判断。

`SourceAccessPolicyView` 只返回政策元数据与字段用途，不含来源响应、凭据或授权正文。`AdmittedSourcePayload` 返回：

- 政策 ID 与实际版本；
- owner/source/capability；
- 只含白名单顶层字段的内存对象。

未来 content/evidence 写入必须显式携带政策 ID/版本；本切片尚无内容表，因此不提前增加无使用方的外键。

## 3. 保存与入库门禁

### 3.1 政策保存

`SourceAccessPolicyService.save` 由已认证 owner 调用：

1. Pydantic 冻结标识、枚举、字段数量、秘密字段和 approved 完整性；
2. Service 拒绝把已过期 review 保存为 enabled；
3. 单个 PostgreSQL statement 按唯一身份执行 UPSERT；新建 version=1，更新 version+1；
4. 整条政策原子替换，不把新字段白名单与旧许可依据拼接；
5. 事务提交后返回不可变 View。

S01 不建立通用审计事件表。版本、时间和 owner 是当前最小追踪；039/audit 接入后记录操作者事件，但不得复制条款正文或来源 payload。

### 3.2 Payload admission

`SourceAccessPolicyService.admit_payload` 在每次业务持久化前查询当前政策：

1. 按 owner/source/capability 精确读取；缺失与其他 owner 的政策同样视为不可用；
2. 要求 status=approved、enabled=true、字段集合非空且 review 未过期；
3. 只复制 `field_purposes` 中列出的顶层标量或标量列表；额外字段、复杂未规范结构和常见秘密字段不进入返回对象；
4. 返回实际政策 ID/version，供未来业务表绑定；
5. 任一条件不满足抛出领域级 `SourceAccessUnavailableError`，不自动降级、放宽或切换来源。

Service 不保存传入 payload、不记录字段值、不外发网络请求。适配器仍应尽量只请求必要字段；入库门禁是第二道保护，不是扩大抓取范围的理由。

## 4. 状态转换与并发

允许由维护用例显式保存任意下一状态，但不隐式启用：

```text
pending ──核对通过──> approved + disabled ──显式启用──> approved + enabled
   │                         │                         │
   └────条件不满足────> blocked <────条款变化/撤权────┘
```

- 核对过期后数据库记录可以保留 approved/enabled 历史值，但实时 admission 必须立即拒绝；后续维护用例再回写 pending/blocked。
- UPSERT 在唯一约束上串行化同一政策并递增版本；不同来源/能力互不阻塞。
- S01 没有缓存。未来若加入 Redis，只能缓存可重建 View；每次写入和撤权必须失效，删除屏障仍以 PostgreSQL 为准。

## 5. 文件、事务与依赖方向

| 路径 | 职责 |
|---|---|
| `backend/app/evidence/models.py` | `SourceAccessPolicy` ORM 映射 |
| `backend/app/evidence/schemas.py` | 严格政策输入、枚举、View 与字段规则 |
| `backend/app/evidence/services.py` | 原子换版、当前政策读取及 payload admission |
| `backend/app/db/metadata.py` | 登记 evidence Model；不建表 |
| `backend/database/schema.sql` | 唯一 DDL，完整新库初始化 |
| `backend/tests/unit/test_data_lifecycle.py` | 输入、秘密字段和字段投影规则 |
| `backend/tests/integration/test_data_lifecycle.py` | 真实 PostgreSQL 的换版、未知/过期拒绝、owner 隔离与最小化 |

不修改 jobs、API、前端、Compose 或本机 `.env`。`evidence` 不导入 identity Model；数据库外键只存在于 DDL/ORM 字符串引用，Service 的 owner_id 来自上层已认证上下文。最外层 Service 拥有事务，Session 不跨线程共享。

## 6. S01 验证与证据边界

1. Red：专用测试因 `evidence` 领域不存在而收集失败，证明当前门禁缺失，不以环境未启动冒充失败。
2. 单元：pending/blocked 不能 enabled；approved 缺核对依据或字段用途被拒绝；秘密字段不能进入白名单；投影只留下允许字段。
3. 真实 PostgreSQL：pending 政策拒绝 admission；approved+enabled 政策只返回白名单字段和政策版本；过期政策立即拒绝。
4. 版本与隔离：同一 owner/source/capability 保存递增版本且整条替换；另一 owner 不能读取或使用该政策。
5. DDL/ORM 同批更新，在本项目空 `hotkey_dev` 重建验证；旧数据库、卷和现有服务不修改或重启。
6. Ruff、格式、mypy、全量 pytest 与架构门禁通过。

这些证据只证明受控内部政策与字段最小化机制。未核对任何真实平台的新授权，未保存真实来源资料，未证明删除传播、MinIO/缓存/索引清理、备份重放、UI 或 AC-036-001—006 的产品范围通过。

## 7. 启用、迁移与回退

- 本机继续复用已启动的 PostgreSQL/Redis/Kafka/MinIO；只对记录为空的 `hotkey_dev` 应用完整 `schema.sql`，旧数据库保持不变。
- 当前没有来源适配器调用该门禁，因此部署 S01 不会开始采集或改变用户页面。
- 回退程序时保留 `source_access_policies`；旧程序不读取该表。若向前修复，政策版本和禁用状态继续有效。
- 不通过删除表、清空卷或放宽 pending/expired 策略恢复可用性。

## 8. 后续边界

S02 冻结结构化/原始/媒体保留规则、逻辑删除屏障、派生引用和在线清理任务；S03 接入备份删除重放、自动回补阻止、来源不可达/明确删除区分及最小清理凭证。具体平台 Design 必须引用实际 policy ID/version 和字段清单后才能执行真实探针。
