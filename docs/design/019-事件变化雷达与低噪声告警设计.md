# 事件变化雷达与低噪声告警设计

## 1. 问题与产品边界

HotKey 的核心对象是现实事件，不是文章。现有采集、相关性、事件聚类、热度和证据摘要已经能够形成事件事实，但公开读取仍按事件 ID 升序，无法回答“最近发生了什么实质变化”；事件热度重算只覆盖当前投影，没有不可变变化记录；系统也没有告警收件箱、去重、冷却或确认状态。因此当前链路在生成摘要后结束，尚未形成“发现变化—提醒—处理”的监测闭环。

本设计固定以下原则：

1. **变化优先**：告警消费 EventUpdate，而不是每一条 Content。
2. **维度优先**：Radar 分别返回 attention、momentum、breadth、confirmation、data confidence 和 Watch relevance，不用一个黑箱 AI 分数替代依据。
3. **证据优先**：变化记录冻结 heat/evidence hash、来源数量和原因码；AI 只负责把原因翻译成人话，不参与确定性触发。
4. **低噪声**：同一 Watch、Event、触发类型和策略版本聚合为一个线程；重复执行只追加一次 occurrence，不创建重复线程。
5. **降级可用**：没有任何 AI Provider 时，采集、聚类、热度、EventUpdate、Radar、Watch 匹配和告警仍然工作。
6. **当前部署边界**：P0 保持现有单工作区自托管权限模型；多租户 Workspace、配额和租户级数据隔离必须在对外 SaaS 化前单独设计，不能在本任务中隐式实现。

Obsidian、复杂报告模板、更多 Provider 和新来源连接器继续保留，但不进入本闭环的关键路径。

## 2. EventUpdate：事件的不可变变化事实

`event_updates` 是事件时间线的事实源，与操作审计和当前 Event 投影分开。每次 24 小时热度重算后，系统读取上一份同窗口快照，并以确定性规则判断是否存在实质变化。

字段：

- `id`、`version`、`event_id`、`sequence_no`
- `kind`：`event_created`、`rising`、`cooling`、`reactivated`、`source_expansion`、`metric_changed`
- `summary`：确定性短句；不得包含无证据的模型结论
- `observed_at`、`reason_codes`
- `before_state`、`after_state`：固定 Schema 的最小指标快照
- `evidence_set_hash`、`idempotency_key`
- `created_at`

约束：

- `UNIQUE(event_id, sequence_no)`；同一事件序列单调递增。
- `UNIQUE(event_id, idempotency_key)`；相同输入重试不重复。
- UPDATE/DELETE 由数据库触发器拒绝。
- 记录时锁定 Event 行，在同一事务中分配序号并写入；并发重算最多产生一条同输入变化。
- `before_state` 可为空对象表示首次有效 24h 快照；`after_state` 必须含 heat、trend、trend status、source/content count、window end、heat/evidence version。

### 2.1 实质变化规则 v1

规则按优先级只选择一个 `kind`，同时保留全部 reason code：

1. 没有上一份 24h 快照：`event_created`。
2. 上一状态为 dormant/falling，当前为 emerging/rising：`reactivated`。
3. 当前首次进入 rising/emerging：`rising`。
4. 当前首次进入 falling/dormant：`cooling`。
5. 独立来源数至少新增 2，或在非零基线上达到 2 倍：`source_expansion`。
6. 绝对 heat 变化至少 10 分：`metric_changed`。
7. 其余重算只更新当前指标，不写 EventUpdate。

输入摘要使用 `metric-update-v1`。`idempotency_key` 为下列有序 UTF-8 字段以换行连接后的 SHA-256 小写十六进制：算法版本、event ID、UTC RFC3339Nano captured at、window hours、heat version、evidence set hash、capability profile set hash、固定两位小数的 heat/trend、trend status、source count、content count。算法升级必须产生新版本输入，不能改写历史。

写入在单事务中先锁定 Event 行，再查询最大 sequence、插入候选；`ON CONFLICT(event_id,idempotency_key) DO NOTHING` 后返回既有记录。只有本次插入成功才占用新 sequence；相同输入并发只能看到同一 EventUpdate。

## 3. Radar：可解释事件读模型

新增 `GET /api/v1/radar/events`，只读现有 Event、最新 Event Metric、Claim 验证状态和可选 MonitorEvent 投影。它不保存第二套业务事实。

### 3.1 查询能力

- 时间窗口：`1h`、`6h`、`24h`、`7d`，按 Event `last_seen_at` 过滤。
- 可选 `monitor_id`。
- lifecycle、trend、verification 过滤。
- 排序：`momentum`、`attention`、`breadth`、`latest`、`relevance`；没有 monitor 时拒绝 relevance 排序。
- 最低 heat、最多 100 条、绑定查询形状的稳定游标。

### 3.2 返回维度

- `attention`：当前 heat。
- `momentum`：将确定性 trend 从 `[-100,100]` 映射为 `[0,100]`，并同时返回原始值。
- `breadth`：最新快照中的独立来源数量及其 0–100 归一结果。
- `confirmation`：基于 Claim 状态派生；corroborated、single source、disputed、unverified 和 insufficient 分开。
- `data_confidence`：来源数量与指标新鲜度的版本化确定性组合。
- `watch_relevance`、`watch_final_score`：只在指定 monitor 时返回。
- `ranking_score`：只用于当前排序的透明组合值；所有组成维度和 `reason_codes` 必须同时返回。

v1 公式固定如下，所有结果保留两位小数并裁剪到 0–100：

- `attention = heat_score`。
- `momentum = (trend_score + 100) / 2`。
- `breadth = min(100, independent_source_count * 25)`。
- `freshness = 100 * exp(-ln(2) * age_hours / 24)`，其中 `age_hours = max(0, as_of - last_seen_at)`。
- `data_confidence = breadth * 0.7 + freshness * 0.3`。
- momentum、attention、breadth、latest、relevance 排序的 `ranking_score` 分别等于 momentum、attention、breadth、freshness、`monitor_events.final_score`；所有排序再以 `last_seen_at DESC, event_id DESC` 打破平局。

核验状态只统计非 retracted Claim，优先级为 disputed、corroborated、single_source、unverified；没有非 retracted Claim 时为 insufficient。前三者与 unverified 的可选分数分别为 20、100、60、30；insufficient 的分数为 `null`，不能伪装为零可信。

首屏以同一个 `as_of` 完成过滤、维度计算与排序，并冻结最多 100 个有序位置。位置至少包含 event ID、ranking score、last seen 和稳定 tie-break；首屏返回当前 `limit` 对应的位置，游标携带尚未消费的有序位置集合。后续页只能从该集合按原顺序切片，不因 Event、Metric、MonitorEvent 或 Claim 当前投影变化而重新选取、插入或重排成员。所有参与冻结的不可变事实读取均约束 `created_at <= as_of`，避免首屏之后补写的历史事实穿透快照。修改 window、monitor、lifecycle、trend、verification、min heat 或 sort 后复用旧游标必须返回参数错误；limit 不属于语义形状，可在 1–100 内调整。

Radar 游标采用版本化 base64url payload 与 HMAC-SHA256 MAC，payload 包含 `as_of`、查询形状哈希、剩余有序位置和 15 分钟绝对过期时间。签名密钥不得直接复用基础认证 secret，而应以 `HMAC-SHA256(base_secret, "radar-cursor-v1")` 做用途隔离后再签名；验证使用常量时间比较。签名错误、payload 非法、位置非法、查询形状不匹配或过期统一返回参数错误，不能接受无签名 base64 JSON。

全局默认排序为 momentum。Radar 不调用 LLM，不读取完整正文，不返回 Provider payload 或敏感来源配置。

## 4. Alert：线程、触发与状态

告警由独立 `alert` 模块拥有。P0 使用现有 Monitor 作为 Watch 的物理映射，使用 published config 的 `event_threshold` 与当前 `monitor_events.final_score` 判定 eligibility。

### 4.1 Alert Thread

`alert_threads` 表示用户收件箱中的一条持续告警：

- `monitor_id`、`event_id`、`trigger_type`、`policy_version`
- `monitor_config_version_id`、`monitor_revision`、`monitor_config_hash`、`event_threshold_snapshot`
- `state`：`open`、`acknowledged`、`resolved`、`suppressed`
- `severity`：`info`、`warning`、`critical`
- 冻结 `title_snapshot`、`reason_snapshot`
- `first_triggered_at`、`last_triggered_at`、`occurrence_count`、`cooldown_until`
- 确认/解决/抑制时间和操作人
- 乐观锁 `version`

唯一身份为 `(monitor_config_version_id,event_id,trigger_type,policy_version)`。P0 固定 `alert-policy-v1` 与 60 分钟冷却；每次评估冻结当时 active Monitor 的 published config ID/revision/hash/threshold。发布新 revision 后可形成新线程，不能让新阈值静默改变旧线程语义。

### 4.2 Alert Occurrence

`alert_occurrences` 是 append-only 触发事实，引用 `event_update_id`，冻结 severity、`monitor_events.final_score`、threshold、原因和 fingerprint。fingerprint 为 `alert-occurrence-v1`、monitor config version ID、event update ID、trigger type、policy version以换行连接后的 SHA-256 小写十六进制。`UNIQUE(fingerprint)` 与 `UNIQUE(alert_thread_id,event_update_id)` 保证任务重试和并发 Worker 只产生一次 occurrence。

触发映射：

- `event_created` → `new_event`
- `rising` → `rising`
- `reactivated` → `reactivated`
- `source_expansion`、`metric_changed` → `threshold_crossed`
- `cooling` 只进入时间线，不产生 P0 告警

线程在冷却期内只累加 occurrence 和更新时间，不产生第二条收件箱记录；acknowledged/resolved 线程只有在冷却期后出现新实质变化时重新打开；suppressed 为人工终态。

v1 severity 只由满足阈值后的 `monitor_events.final_score` 决定：`>= 90` 为 critical，`>= 75` 为 warning，其余为 info。`RecordOccurrence` 在进入 Repository 前必须拒绝 NaN/Inf 等非有限 `final_score` 或 threshold、`final_score < threshold`，以及与上述确定性映射不一致的 severity，不能信任 Worker 传入的派生值。

每个新 occurrence 都参与事实计数，但线程当前快照由 `(triggered_at,event_update_id)` 的全序决定。只有严格晚于线程当前最新位置的 occurrence 才推进 `last_triggered_at`、severity、title/reason snapshot、`cooldown_until = triggered_at + 60 分钟`，并可能在冷却期满足时重新打开 acknowledged/resolved；乱序但唯一的新 occurrence 只增加 `occurrence_count` 与 `version`，不得覆盖快照、缩短或后移冷却、改变状态或触发 reopen audit。线程 `updated_at` 采用本次事实写入时刻并与既有值取最大，任何乱序输入都不能使其倒退。重复 fingerprint 不更新时间、计数、版本或冷却期。

Alert Repository 的单事务顺序固定为：按唯一身份插入或取得 Thread；锁定 Thread；以 fingerprint 插入 Occurrence；若冲突则原样返回且不改变 Thread；只有插入新 Occurrence 后才增加 count/version，再按上述全序决定是否推进最新快照、冷却和必要 reopen，并仅在有效自动 reopen 时追加 system state audit。Occurrence 成功而 Thread 更新/audit 失败必须整笔回滚。

### 4.3 状态与审计

允许：

```text
open -> acknowledged | resolved | suppressed
acknowledged -> resolved | suppressed
acknowledged|resolved -> open 仅由冷却期后的新 occurrence 触发
suppressed -> 终态
```

`alert_state_audits` 追加记录 actor type（user/system）、可选 user ID、from/to、expected version 和 reason code。旧版本写入返回冲突，失败不产生部分状态或审计。`event_updates`、`alert_occurrences`、`alert_state_audits` 均由数据库拒绝 UPDATE/DELETE；`alert_threads` 是唯一按 version 受控修改的告警记录。

## 5. 任务链与一致性

自动链路调整为确定性 fan-out：

```text
cluster_content
  -> recompute_event_heat
  -> record/reuse EventUpdate
     |-> actionable Update: evaluate_event_alerts
     `-> always: generate_event_summary
```

- Heat 重算与 EventUpdate 是可重试的两步；Heat 已提交而 Update 失败时，原 job 重试并按 idempotency key 补齐。
- Heat Handler 以稳定唯一键先入队可选 Alert evaluation、再入队必需 Summary；任一步入队失败均重试 Heat，已入队项由 Queue 唯一键复用。Alert evaluator 运行失败不会阻塞或重复 Summary。
- `evaluate_event_alerts` payload 只包含 EventUpdate ID/version/hash，不携带业务正文。
- Alert evaluator 通过 Event 的只读 WatchMatch 端口和 Monitor 的只读 published policy 端口读取候选，不从 Alert Repository 直接查询其他模块拥有的表。
- 事务失败、队列入队失败或 Worker 重启后重复处理，EventUpdate、Occurrence 和 Thread 数量保持幂等。

## 6. HTTP 与权限

新增：

```text
GET  /api/v1/radar/events
GET  /api/v1/events/:id/updates
GET  /api/v1/alerts
GET  /api/v1/alerts/:id
POST /api/v1/alerts/:id/acknowledge
POST /api/v1/alerts/:id/resolve
POST /api/v1/alerts/:id/suppress
```

- 所有接口要求 BearerAuth。
- 当前单工作区模型下 viewer/editor/admin 均可读取 Radar、EventUpdate 和 Alert；状态操作记录真实 actor。
- viewer/editor/admin 均可 acknowledge 与 resolve；suppress 是全局终态，只允许 editor/admin。
- 状态操作必须提交 `expected_version` 与稳定 `reason_code`。
- Result 继续只返回 `code`、`message`、`data`；错误不得泄露 SQL、队列 payload、Provider 错误或凭据。

Alert 列表支持 state、severity、monitor、limit 与绑定查询形状的 `(last_triggered_at,id)` 降序游标。Alert 游标同样采用版本化 base64url payload 与 HMAC-SHA256 MAC，包含查询形状、位置和 15 分钟绝对过期时间；签名密钥以 `HMAC-SHA256(base_secret, "alert-cursor-v1")` 做独立用途派生。篡改、跨查询复用、非法位置和过期统一返回参数错误，不接受无签名游标。

Alert 详情在一个只读 `REPEATABLE READ` 事务中读取线程、按 triggered time 降序的最近 50 条 occurrence 和完整状态审计，保证三个结果来自同一数据库快照；不返回 Event 正文、Monitor 配置或队列 payload。

## 7. 降级、非目标与后续依赖

P0 降级：

- AI 不可用：Radar、EventUpdate 与 Alert 完整工作；事件 summary 保持现有 degraded 语义。
- Provider 已配置但 unavailable、transient failure 或 timeout：前三项不调用 LLM 且已经提交；summary 在重试边界内仍失败时生成带安全 reason code 的证据化 fallback，不暴露 Provider 原始错误。
- 无 Claim：verification=`insufficient`，不得伪装为 0% 可信。
- 无指标快照：事件不进入 Radar，API 不制造零值热点。
- 没有 active Monitor：仍有全局 Radar，但不产生 Monitor 告警。

非目标：

- 不在本任务实现多租户 Workspace、SSE/WebSocket、Webhook/Email 告警投递、自然语言 Watch 编译、Signal Snapshot 重建、深度 Analysis 或新数据源。
- 不把现有 knowledge/report 能力移除；只是不让它们阻塞核心链路。
- 不让 AI 决定 Alert eligibility、severity、cooldown 或 confirmed 状态。

后续优先任务：不可变 Signal Snapshot 与 Evidence 引用、自动 Claim 抽取、Analysis 产物、告警外部投递和运行健康监督。
