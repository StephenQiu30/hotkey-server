# 故障隔离与降级设计

日期：2026-09-23；2026-09-24 补充 S01 资源公平派发的技术门槛。本版仍只接受 S00 与 S01 的内部状态分项子片，不接受资源公平、熔断、恢复、用户展示或产品验收。

## 1. 当前事实与问题

031 已有持久 Job、Outbox、租约及 Kafka 重投防重；037 已有分层预算；039 的 `OperationalSnapshot` 有逐任务来源/能力与总状态，但只有全局汇总。只看总数会掩盖“X 搜索成功、X 评论失败”的差别。当前 Worker 在一个同步消费循环中逐条执行 handler；预期正式 topic 在本机 Kafka 尚不存在，不能据此声称跨来源并行或隔离吞吐。X 官方 API 与国内平台的真实业务处理器仍未就绪。

## 2. 目标、非目标与复用依据

本子片在同一个 owner、同一个半开观察窗口内，按 `(source_key, source_capability)` 汇总已有任务的互斥状态。无来源的内部任务只进入总汇总，不冒充某来源；无任务的能力不显示“健康”。分项总数必须能与逐任务记录核对，且不含 scope、正文或凭据。

复用 039 的 Job 运行事实、`JobObservationService.snapshot` 和 `OperationalTaskStatus`，不增加表、消息、HTTP、UI、依赖或脚本。[Apache Kafka Consumer 配置](https://kafka.apache.org/41/generated/consumer_config.html)说明处理过久不再调用 poll 会触发消费组再均衡；[Confluent Python Consumer API](https://docs.confluent.io/platform/current/clients/confluent-kafka-python/html/index.html)说明同步提交的是消息 offset 后继位置。因此本子片不通过吞掉未知异常并提交 offset 伪造隔离，也不把增加消费者数量等同于公平调度。

## 3. 状态契约与领域边界

`OperationalSnapshot.capabilities` 是按来源 key、能力稳定排序的分项；每项保存任务数和 `queued/delayed/running/succeeded/partially_succeeded/failed/cancelled` 七态计数。每项计数之和等于该项任务数；所有分项任务数之和等于窗口内带合法来源/能力对的任务数，不要求等于含内部任务的全局总数。分项仅用于观察，不能作为连接 ready、内容完整、来源最后成功或自动恢复许可。

此读取仍由 `jobs/schemas.py` 定义 DTO、`jobs/services.py` 组装；不读取别的领域 ORM。分项只使用已加载的 owner 任务，不增加跨 owner 查询。测试归 `backend/tests/integration/test_operational_observability.py`，用隔离 PostgreSQL 构造同来源不同能力、不同来源、内部任务和失败/成功/延期，先证实缺分项，再实现。

## 4. 后续 S01—S03 门禁

S01 的资源公平尚需解决单循环串行 handler 及 Kafka 分区/执行容量问题，并用真实 Kafka、超时来源与正常来源并行负载证明；仅增加分项 DTO 不勾 `CHK-033-G3/G4-001`。S02 才将明确的局部状态和历史缺口接入实际页面；S03 再依据获授权的逐来源样本冻结失败阈值、探测间隔与预算。`OPEN-033-001` 保持开放，不把 PRD 候选“三次失败”当默认值。

### S01 资源公平派发技术门槛（未接受）

2026-09-24 对现有实现的核对显示：`worker.messaging.run_consumer_loop` 在同一 poll 线程中同步执行 handler，再按消息提交 offset；`Outbox` 以 Job UUID 为 key，解码器要求 key 与 Job ID 一致；连接目录当前仅登记 `x`、`douyin`、`web`，Worker 当前仅注册 `webpage.collect`。只读检查本机 Kafka 也确认 `hotkey.jobs.accepted.v2` topic 不存在。因此目前既没有第二个真实可执行来源，也没有可验证的正式 topic 分区拓扑。

Kafka 官方文档说明，超过 `max.poll.interval.ms` 未调用 `poll` 会触发消费组重新分配；并行处理仍须在业务完成后提交正确的连续 offset。Confluent Python `Consumer` 本身支持多线程调用；本项目后续仍选择由单一 poll 控制线程串行管理 `poll`、分区 pause/resume、offset commit 与关闭，handler 线程只执行 Job 并回传结果，以减少共享 offset/重平衡状态，不把此选择误述为客户端线程安全限制。`pause`/`resume` 只控制已分配分区；据此推得，它们本身不能消除同一分区内的来源队头阻塞。[Kafka consumer 配置](https://kafka.apache.org/41/generated/consumer_config.html)、[Kafka Consumer API](https://kafka.apache.org/41/javadoc/org/apache/kafka/clients/consumer/KafkaConsumer.html)、[Confluent Python Consumer API 与线程安全说明](https://github.com/confluentinc/confluent-kafka-python#thread-safety)

后续实现只能复用既有 PostgreSQL Job/Outbox 与同一 Kafka broker，不增加消息中间件或第二套队列。实现设计必须同时满足：

- Consumer API 始终由 poll 线程调用；handler 使用有界并发，不允许一个失败来源占满全部执行槽。
- Kafka 分区/路由须让各个启用来源具有稳定、无碰撞的隔离 lane；只按 Job UUID 默认散列不能证明来源公平。来源目录与 topic 分区数不匹配时，必须拒绝启用/启动，不得在运行时静默重分区或自动扩容。
- 每个分区保持有序完成边界；未知异常、数据库/Kafka 故障不确认消息。只有业务结果或分类失败已在 PostgreSQL 持久化后才能提交对应连续 offset；重投继续由 031 的 inbox、租约与 fencing 处理。
- 先以既有 Kafka 上可清理的多分区测试 topic 验证一个受控超时 handler 与一个正常 handler 的持久结果、offset 恢复和有界资源占用；该验证仅关闭技术门禁，不等于真实来源产品验收。

当前不接受具体 lane 数、并发上限或 topic 自动建表策略：这些值须由已登记的真实来源集合和部署 topic 配置共同确定，并在 G2 记录。禁止为满足测试先注册假来源，或修改共享 Kafka 的 broker 默认分区数。

未知异常、数据库中断、Kafka offset 未确认仍遵循 031 恢复语义；只有已分类且持久处理完成的业务失败可在后续设计中讨论局部隔离。凭据失效不得自动重登、换账号或切付费来源。没有实际处理器、页面和 72 小时负载证据前，AC-033-001—006 均未通过。

## 5. 兼容、验证与回退

分项是内部 DTO 新增字段，没有 DDL、HTTP/OpenAPI、前端、运行配置或服务重启。失败优先的真实 PostgreSQL 用例和全量后端回归验证状态核对、owner 隔离及空窗口；Ruff、格式和 mypy 同跑。若需回退，只回退此内部读模型，不改持久任务、offset 或历史资料。正式资源隔离设计必须在代码前补入本文件并单独验收。
