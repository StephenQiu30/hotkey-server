# 推送设计

本 Design 是 M5 Epic，从 [总设计 001 v3.2](001-热点舆情监控平台总体设计.md) 正向拆解；总设计现为 v4.0。需求为 [PRD 006](../prd/006-推送需求.md)，逐 Issue 执行计划见 [Plan 024—026](../plan/README.md)。本文中的“已有”仅表示代码或指定运行证据，不代表产品验收。

## 1. 范围与不包含

M5 单独验收报告定稿后的渠道投递与状态恢复。飞书自定义机器人已有代码但用户决定暂缓；SMTP 邮件尚待实现和启用条件。推送不作为 M1 信息获取、M4 报告生成或 Obsidian 导出的完成条件。现行需求与计划分别见 [PRD 006](../prd/006-推送需求.md) 和 [Plan 024—026](../plan/README.md)。

## 2. 当前能力与证据分层

`notifications/`、`notification.send` 飞书代码与受控测试已有；连续真实送达及 `unknown` 人工确认未证实。SMTP 未见实现，凭据/启用条件待用户决定。当前 M5 暂缓，不把代码存在或机器人请求成功解释为产品验收。

## 3. 架构与数据流

### 3.1 渠道与秘密

- 飞书自定义机器人（Webhook + 可选签名密钥）已有代码；SMTP 邮件尚未见实现，作为后续单独切片。当前推送暂缓，不参与信息获取、日报生成或知识库写入的验收门禁。
- 秘密只从环境变量读取（`HOTKEY_FEISHU_WEBHOOK_URL`、`HOTKEY_FEISHU_SECRET`、`HOTKEY_SMTP_HOST/PORT/USER/PASSWORD/FROM`）；`notification_targets` 表只存目标名、类型、收件人和所用环境变量名。
- 飞书设计为摘要卡片：概览 + Top 3 + Web 报告链接 + 已存在时的 Obsidian 链接；邮件未来从同一 Markdown 渲染完整 HTML。不存在的笔记不写入链接。

### 3.2 投递状态（问题 #26）

- `notification_deliveries` 唯一键 `(report_id, report_version, target_id)`；状态 `pending → sending → succeeded | failed | unknown`。
- 发送前先把状态提交为 `sending`；请求前就失败（连接不上、4xx 参数错）记 `failed`，可自动重试 3 次；请求已发出但超时或进程中断，记 `unknown`，**不自动重发**，在 Web 上提示人工确认。

`reports` 只提供已定稿报告及版本，`notifications` 拥有目标、投递和渠道适配器；独立调度在启用渠道时扫“已定稿且无相同版本投递”创建 `notification.send`。`jobs` 负责持久执行/预算，渠道密钥只从进程环境读取。渠道结果不反向更改报告。

## 4. 领域、数据与状态

`notification_targets` 只保存目标名、类型、收件人和环境变量名，禁止秘密明文；`notification_deliveries` 唯一键 `(report_id, report_version, target_id)`。投递状态 `pending → sending → succeeded | failed | unknown`，每次尝试与外部响应分类可追溯。新渠道和人工确认审计字段由实施切片定义，不能凭目标表存在称 SMTP 已实现。

## 5. 接口与页面

Web 后续显示每个报告版本/目标的状态、失败原因、`unknown` 的人工确认入口与权限限制；渠道配置不展示秘密。具体读/写端点与 DTO 在实施切片定义，经运行 OpenAPI 生成客户端，遵守 PROJECT.md 与 AGENTS.md 的现行错误/响应契约（旧 Design 046 已删除，见 Git 历史）。

## 6. 调度、执行与截止

仅已启用渠道且报告定稿时创建确定性 `notification.send` Job；硬截止 60 秒，外部请求也受更短读/连接超时。日报目标为设定生成时间后 15 分钟内送达（默认 09:15 前），周报目标为每周一 09:15 前送达；按渠道和接收方核对实际收到的时间，M4 的 600 秒生成硬截止不能当作送达时限已满足。发送前先提交 `sending`，同一 `(report_id, report_version, target_id)` 不重复受理；Kafka 重投不得无条件重发。每个渠道的启用条件与收件人由后续计划落实，飞书暂缓期间不触发。

## 7. 失败语义与恢复

请求前明确失败可记 `failed` 并在上限内有限重试；请求可能已发送后超时或进程中断记 `unknown`，禁止自动重发，等待人工确认/处置。明确成功需核对渠道响应与持久记录；只拿到 HTTP 200、健康检查或任务完成均不足以证明目标已收到。人工确认动作须审计，不能回写为未有证据的成功。

## 8. 安全、风控与可观测

飞书 Webhook/签名密钥与 SMTP 凭据只来自 `HOTKEY_` 环境变量，不入数据库、Git、日志或错误体；报告链接只指真实可访问位置和已存在笔记。按目标/报告版本记录受理、尝试、成功、失败、未知与人工处置数量，日志脱敏；授权用户才可查看目标和确认未知状态。

## 9. 验收设计要点

受控验证唯一键、发送前/后失败分界、超时 unknown 不自动重发及人工确认；启用后分别用真实飞书/SMTP 目标核对送达时间、内容、版本和失败恢复，包含周一 09:15 前收到周报及连续 3 个自然日日报均在设定时间后 15 分钟内收到。来源/Codex 故障生成的缺口或模板版报告、vault 只读时的已定稿报告仍须按获准渠道独立核对送达。每个渠道分别验收，飞书暂缓期间只保留历史代码和受控证据；SMTP 启用前需用户提供凭据和发信目标。

## 10. 决策、风险与对照

沿用 DEC-001-210/212 与 PRD DEC-001-110。DEC-001-212 替代旧 P1 必须先完成飞书的顺序口径；DEC-001-210 固定秘密环境读取与未知投递不自动重发。本次不新建 DEC-006-xxx。风险为重复推送、未知结果误重发、秘密泄露和渠道不可达；M4 可等分析水位至 09:10 且生成硬截止 600 秒，故 09:15 送达不能凭任务启动或硬截止配置推定通过，必须按接收方时间实测。对应原总设计 v3.2 §10、§13 和 §15—16；历史约束为旧 Design 037 费用与资源约束、旧 Design 046 全局异常与响应契约（均已删除，见 Git 历史）。
