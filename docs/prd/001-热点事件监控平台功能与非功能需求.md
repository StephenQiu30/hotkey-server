# 热点事件监控平台功能与非功能需求

日期：2026-09-21。本文是产品需求草案，覆盖整个 HotKey；不是 X 采集器说明，也不是已实现清单。当前阶段重点是确定用户问题、功能边界、质量要求及验收依据，暂不新增业务实现。

[002 X 专项设计](../design/002-X免费采集与热点监控设计.md)作为来源可行性研究输入；它的评分权重、刷新频率和候选库不是本 PRD 强制的最终实现。[平台总体 Design](../design/001-热点事件监控平台总体设计.md) 已建立为 proposed，[平台总计划](../plans/001-热点事件监控平台总计划.md)、逐项 Plan 与 [BACKLOG](../../BACKLOG.md) 已建立；首批国内来源、授权样本和实际资源仍待评审，不能据此进入真实外采。

同编号功能调研见 [001 鱼皮项目对照研究](../research/001-热点事件监控平台调研.md)，编号与文档关系见 [文档台账](../README.md)。Research 与本 PRD 共同属于平台总体需求交付项。

本文件的 27 项功能需求与 16 项非功能需求已逐项展开为独立 PRD，阅读入口为 [逐项 PRD 索引](README.md)。003—026 对应 FR-001-001—FR-001-024，027—042 对应 NFR-001-001—NFR-001-016；043—045 对应新增 FR-001-025—FR-001-027。原始需求 ID、优先级及父级验收保持不变；详细文件通过 parent / source_requirement 记录来源，补充各自规则和验收。全部仍为待评审草案。

## 1. 需求结论

产品要让用户完成：

**设置关注主题或账号 → 持续发现相关作品 → 判断哪些内容正在变热 → 归并为具体事件 → 查看评论与上下文 → 分析讨论变化 → 获得提醒并留存证据。**

功能需求规定用户能完成什么；非功能需求规定这些能力在正确性、时效、可靠性、费用、安全和可维护性上必须达到什么条件。两者共同构成首版验收，不用“页面已经做完”替代产品完成。

### 1.1 已确认与建议的区分

| 类型 | 内容 |
|---|---|
| 用户已确认 | 热点事件监控；按关键词获取相关热门内容；采集事件评论并分析；关注指定平台用户及其作品；必须包含 X；采用免费开源方案，不接受付费订阅 |
| 持续约束 | 不以按量收费接口规避免费要求；优先复用已有开源能力；公开或获授权的数据访问；不能拿全站热榜过滤冒充关键词检索 |
| 本文建议，待评审 | 18 项 P0 功能、16 项 P0 质量要求；先验证 X 与一个国内来源的完整流程，再分批覆盖目标平台；以下规模与数值验收目标 |
| 尚未确认 | 实际主题/账号样本、首批国内平台排序、刷新时效目标、使用人数、硬件容量、保留期、外部通知渠道 |

“P0”是建议的首版必要范围，“P1”是后续重要增强，“P2”是有额外价值证据后再做的扩展。优先级用于安排交付顺序，不代表从产品目标中删除低优先级需求。

### 1.2 当前角色与使用场景

首要用户是进行热点跟踪、评论研究和账号观察的信息研究者，初始可由项目所有者本人承担；这是一项使用角色假设，尚未进行用户访谈。

| 故事 | 用户要解决的问题 | 完成的表现 |
|---|---|---|
| U1 主题监控 | 我不想反复去多个平台搜索同一组关键词 | 设置一次后能持续看到相关新增、热门与升温内容 |
| U2 账号观察 | 我想知道某个指定用户发布了什么 | 新作品按账号归集，不会因未命中主题词漏掉 |
| U3 事件研究 | 我需要知道发生了什么、大家在讨论什么 | 一个事件包含代表作品、发展时间线、回复上下文和观点证据 |
| U4 结论留存 | 我要把研究结果导出并能再次核查 | 报告可追溯至原作品和评论，范围与版本明确 |
| U5 监控维护 | 我需要知道系统是否还在正常获取数据 | 来源失效、预算耗尽、延迟和部分采集清晰可见且能处理 |

## 2. 功能调研依据与差距

本轮是公开资料与现有项目调研，不是用户访谈、竞品实测或需求批准。项目 README 的能力描述属于项目方声明，不视为本项目已经可用。

| 依据 | 调研观察 | 转化的需求 |
|---|---|---|
| R0 [鱼皮 AI 热点监控源码](https://github.com/liyupi/yupi-hot-monitor/tree/cd48b0885bfa8ae9c8043cf78ef6cfd045530bdb)，本轮固定提交核查 | 有关键词、定时发现、筛选、AI 相关性、通知和技能报告；微博入口为热搜过滤，评论为数量字段，账号能力为局部路径，X 使用收费第三方接口 | 吸收发现与通知流程；事件、评论正文/回复树、独立作者追踪、持续快照和免费来源必须补齐；逐项证据见 001 Research |
| R1 [TrendRadar README](https://github.com/sansan0/TrendRadar/blob/master/README.md)，本轮读取 | 描述关键词筛选、增量内容、分组、报告与通知；同时存在 AI 服务配置 | 监控规则、变化提醒、报告、通知降噪值得保留；免费基础能力必须可独立运行，不照搬付费依赖 |
| R2 [BettaFish README](https://github.com/666ghj/BettaFish/blob/main/README.md)，本轮读取 | 展示评论洞察、分析流程和报告产出，配置涉及模型与搜索服务 | 不能只做采集和词云；需要讨论焦点、证据及分析结果，但不因此采用其全部 Agent 架构或假定零运行成本 |
| R3 [twscrape API](https://github.com/vladkens/twscrape/blob/v0.20.1/twscrape/api.py)，前轮源码核查 | 关键词、作者作品、直接回复与会话是不同入口 | 将三条采集路径作为独立功能；回复上下文和采样范围必须可见 |
| R4 [MediaCrawler 配置](https://github.com/NanmiCoder/MediaCrawler/blob/main/config/base_config.py)，前轮源码核查 | 评论数量、回复开关与平台采集参数存在独立限制 | 采集预算、逐项能力状态、部分完成和评论层级进入需求 |
| R5 [YouTube 评论线程文档](https://developers.google.com/youtube/v3/docs/commentThreads)，前轮官方资料核查 | 评论线程返回内容不必然包括全部回复 | 不把一次接口成功或返回数量等同于评论完整；必须记录缺口与来源边界 |

进一步资料位于项目父级 research/2026-09-17-hotspot-monitoring 与 research/2026-09-17-x-free-monitoring。本 PRD 中没有将上述项目宣传的覆盖率、全天候可用性或智能分析效果作为承诺。

目前最重要的产品差距是：热榜工具解决线索发现，爬虫库解决部分获取，报告工具解决表达；HotKey 还需要统一事件身份、持续追踪、数据质量状态、评论上下文与可核查的分析。这一判断是基于资料的产品推导。

鱼皮对照研究进一步明确以下验收边界，补充已有需求而不新增重复条目：

1. **FR-001-001/003：**别名本地匹配和扩大上游搜索是不同能力；真正扩展检索时记录扩展词、查询范围与请求预算，不静默扩大采集。
2. **FR-001-002：**手动搜索、定时监控与其他调用入口分别声明来源覆盖，不因后台存在一个函数就认为前台已有完整功能。
3. **FR-001-004：**关注账号由用户明确选择并确认稳定身份，不仅依据名字相似或粉丝量自动认定。
4. **FR-001-008/011：**去重不能阻止已有作品的指标与新回复更新；页面分数和排序分数使用同一口径，确需不同指标时分别命名、解释和记录版本。
5. **FR-001-013/014、NFR-001-015：**模型判断或默认 isReal 值不是事实核验；未知保持未知，分析失败不应让可复核的原始资料静默丢失。
6. **NFR-001-011：**保存条数上限不等于资源预算，被过滤结果产生的请求和分析调用同样计入。

## 3. 业务需求与产品边界

| ID | 业务需求 | 成功判断 |
|---|---|---|
| BR-001-001 | 持续发现与主题相关的新内容及热门内容 | 监控规则可解释，能发现并回看相关内容，不只匹配已上榜标题 |
| BR-001-002 | 稳定跟踪指定用户作品 | 账号身份明确，新作品可识别且不重复，关键词过滤可选 |
| BR-001-003 | 以事件组织作品和讨论 | 同主体不同事件能区分，同事件跨平台资料可关联，人工可纠错 |
| BR-001-004 | 从评论形成有依据的分析和成果 | 焦点、代表观点、变化与报告有样本范围及可追溯证据 |
| BR-001-005 | 在免费自建约束下持续运行 | 不依赖付费核心服务；任务、预算、故障、数据与凭据可控 |
| BR-001-006 | 保留 X 与多平台产品目标，诚实表达实际能力 | X 未验证不声称首版完成；每个平台按实际已验收能力发布 |

### 3.1 目标平台与交付范围

| 来源 | 产品范围 | 首批要求与边界 |
|---|---|---|
| X | 用户明确必需 | 验证关键词发现、作品、账号追踪及事件回复路径；不会通过换成其他海外平台满足此项 |
| 微博、小红书、抖音、B站 | 国内主流目标来源 | 建议首批至少一个来源形成完整路径，其余分批；顺序尚未确认，不能写成已取消需求或都已支持 |
| YouTube、知乎、快手、贴吧等 | 按研究对象补充的候选 | 根据用户需求与逐能力验证决定，不为了平台数量堆接入 |
| 热榜、新闻网页、RSS | 补充线索 | 不替代上述关键词、账号和评论路径；可后续加入 |

每个平台分别登记：关键词搜索与排序、作品详情、作者作品、评论、嵌套回复、互动快照、所需会话、已知限制、验证时间。声明“支持某平台”必须附可用能力范围。

例如：B站弹幕与评论为不同对象；首版评论能力不自动包含弹幕。视频标题与描述可采集也不表示理解了视频正文；需要额外上下文时应提示而非推断。

### 3.2 核心对象

| 对象 | 定义与关系 |
|---|---|
| 监控主题 | 用户长期关注的一组规则，如某品牌或某行业 |
| 事件 | 一个具体发生事项，如该品牌的产品召回；一个主题可以关联多个事件 |
| 作品 | 帖子、视频、笔记、文章等来源内容；同一作品可以被多个主题发现 |
| 评论/回复 | 依附作品或会话的讨论，保留父子关系；不要求每条都包含主题关键词 |
| 关注账号 | 被观察的公开平台用户，以稳定平台 ID 区分，不能只靠昵称 |
| 指标快照 | 某一时点观察到的互动值；不是永不变化的作品属性 |
| 分析与报告 | 针对明确样本、时间窗与方法产生的结果，能回到证据 |
| 变化提醒 | 对新作品、新事件、显著升温或运行故障产生的可解释通知记录 |

### 3.3 首版不承担

全平台全量历史归档、保证抓到全部评论、毫秒级实时监控、自动社交互动、私信采集、账号画像推断、默认下载全部媒体、企业销售/工单系统，以及未经校准的舆情真实性或全网民意判断。

### 3.4 发布层次与首版体验范围

首版验收对象为 server 内的 Web 工作台与服务端闭环；Flutter App 单独冻结平台及设备验收，继续复用本 PRD，不把 Web 证据记为 App 通过。18 项 P0 功能和 16 项 P0 质量均保留，其中身份、安全、任务、预算、删除屏障与追踪从 M1 建设；M5 对完整业务范围统一验收。首批国内平台选择不等于取消其他目标来源，扩面队列见 [BACKLOG](../../BACKLOG.md)。

首版交互围绕监控、事件、资料检索、通知、报告和设置组织。作品、回复、证据、热度解释及人工修订优先从主题或事件上下文进入，不要求为每个需求编号建立独立一级页面。高级采样、回补和模型配置按需展开，首屏先回答发生了什么、资料是否新鲜、依据在哪里以及下一步能做什么。

首次部署必须有可执行的首个使用者初始化与凭据恢复说明，随后能登录、创建首个主题/账号并查看任务；初始化失败不开放工作台，禁止内置通用默认密码。这属于 020/034/035 的身份范围，不要求开放公众注册、团队邀请或复杂组织体系。部署初始化/恢复采用何种管理入口在身份 Design 中明确。

P0 基础分析提供样本统计、趋势、人工焦点/诉求和代表评论引用；情绪和立场允许人工标注与未知状态。P1 才承接经独立评估的自动分类/摘要；关闭所有模型时，P0 的研究和导出仍可完成。P0 的规则相关性与事件归并仍须执行 041 的相应效果验证，不能以“人工兜底”免除已实现自动能力的验收。

## 4. 功能需求

每行描述产品行为和必要性，不绑定具体 SDK、数据库表或界面组件。

| ID | 优先级 | 功能 | 必须具备的行为 | 来源或必要性 |
|---|---|---|---|---|
| FR-001-001 | P0 | 监控主题管理 | 创建、编辑、复制、暂停和归档主题；设置关键词/别名、任意命中/全部包含/排除、平台、语言、时间窗、频率与预算；保留规则版本。 | U1；主题是持续监控的基本单位。 |
| FR-001-002 | P0 | 平台与连接管理 | X 必须纳入；按关键词、作者作品、评论、回复分别显示已验证/待验证/受限/不可用，以及最近验证和成功时间；管理连接与失效提示。 | U1/U2；平台已连接不能代替逐项能力成立。 |
| FR-001-003 | P0 | 关键词主动发现 | 在已接入平台执行关键词检索；同时支持最新与热门发现意图，保留原生排序与本地排序区别；支持时间/语言过滤、手动检索和定时检索。 | U1；榜单标题过滤不能替代检索。 |
| FR-001-004 | P0 | 指定用户作品追踪 | 通过主页链接或账号标识添加关注用户，以稳定平台 ID 标识；提供初始回溯范围、更新频率、作品类型、可选关键词过滤和评论采集开关。 | U2；关注作者的作品不必包含关键词。 |
| FR-001-005 | P0 | 作品资料与上下文 | 保存原生 ID、链接、作者、标题/正文、作品类型、发布与观测时间、可用互动指标；缺失项明确；区分原创、转载、引用、回复及删除/不可见状态。 | U1/U3；分析必须知道在分析什么。 |
| FR-001-006 | P0 | 评论与回复采集 | 按事件和代表作品采集评论、回复及可访问上下文；支持采样数量/时间/层级预算，保留父子关系；显示来源排序、样本范围和停止原因。 | U3；评论脱离父帖会产生错误解读。 |
| FR-001-007 | P0 | 采集任务控制 | 提供定时/手动运行、暂停、取消、按原因重试、进度、历史记录；区分零结果、部分完成、等待预算、限流、需登录、无权限与解析失败。 | U1/U5；用户必须知道是否真的在监控。 |
| FR-001-008 | P0 | 增量更新与历史回补 | 作品、评论和指标分别增量更新；新回复可落在旧帖下；重叠回看去重，记录漏采时窗；历史回填独立限额，不用补采时间制造新事件。 | U1/U2/U3；持续监控不能每轮当首次抓取。 |
| FR-001-009 | P0 | 事件识别与归并 | 主题、事件、作品分层；按主体、发生事项和时间形成事件候选；支持跨平台归并、人工合并/拆分/移出及修改记录。 | U3；同一品牌可能同时发生不同事件。 |
| FR-001-010 | P0 | 事件详情与发展时间线 | 展示事件标题、涉及主题、代表作品、平台分布、首次发现和最近实质更新；时间线区分发生/发布/采集时间，支持关注和归档。 | U3；用户需要理解事件经过。 |
| FR-001-011 | P0 | 相关性与热度排序 | 先判断与主题相关性，再提供最新、热门、升温、相关性排序；作品分数与事件分数分开；展示指标、比较范围、算法版本和低置信状态。 | U1/U3；用户需要找到值得关注的内容。 |

### 4.1 首版基础分析必须回答的问题

- **发生了什么：**相关事件及其关键进展，区分原文事实、用户观点和分析推断。
- **讨论什么：**主要焦点、问题、诉求以及有代表性的不同意见，每项有评论依据。
- **怎么变化：**已采集作品、评论与互动在同口径时间窗内的变化；采样策略变更、断采和补采单独标记。
- **数据有多充分：**包含哪些平台/作品、多少样本、什么时间、何种选择方式，哪些来源缺失。

数量统计、词频和趋势是基础；有证据的讨论焦点与观点整理也是 P0。自动大模型生成不是必要前提：可先通过可解释规则、局部文本处理与人工整理完成，仍须验收其用户价值。自动化程度不能代替质量。

情绪（如愤怒/担忧）和立场（支持或反对谁/什么）不是同一个指标。不能由“负面情绪多”直接推断“反对该品牌”，也不能从方便采到的评论推断全体用户占比。

### 4.2 首版提醒的边界

站内提醒属于 P0；外部通知暂列 P1。若用户的必要场景是“离开网页后也要及时收到消息”，应将至少一种免费或自建渠道升级为 P0，不能声称站内通知已经满足离线提醒。

本轮只定义功能，未配置通知账号、发送任何消息或创建自动化。

### 5.1 性能与恢复测试基线 B0

数值仅用于提出可评审目标，实际硬件或规模不同应先更新基线再测，不能挑选更轻负载宣称达标：

- 单个主要使用者，模拟 5 个并发读取会话；10 个主题、20 个关注账号的配置规模。配置数量不是每日全部来源都能按频率执行的保证。
- 100,000 条作品、500,000 条评论/回复、1,000,000 条指标快照；来源分布、正文长度与事件大小记录在测试清单。
- 自建环境初步按 4 vCPU、8 GiB RAM、SSD 的总服务预算估算；UI 测量补记浏览器、设备和网络。若实际可用资源不足，先报告差距。
- API 热缓存测试先预热，再持续 15 分钟并至少采集 1,000 个有效读请求；冷缓存/重启后请求单独统计；请求失败与超时纳入报告。
- 外部来源使用可控数据验证系统性能；真实平台另做低频观察，不能压测真实社交平台。模型推理等重任务单独测，不能占用核心接口并发而隐藏在排除项中。
- 备份恢复在隔离环境使用 B0 数据；RTO 从开始恢复到核心读写可用计时，RPO 按最后可恢复数据时间计算。
- 72 小时试运行只证明短期观察结果，不能外推全年可用性；完整报告同时列出上游失败、部分完成、预算延期与内部执行失败。

### 5.2 分析质量基线 Q0

初步建议冻结不少于 200 条作品、300 条评论、10 个事件与 20 组检索结果，覆盖至少 X 和一个国内来源，包含：

- 有关/无关、同主体不同事件、跨平台转载、作者引用他人观点；
- 直接回复与嵌套回复、缺失上下文、反讽、否定、混合情绪及未知立场；
- 新事件、旧事重提、低样本、增长快照不足、采样策略改变。

记录原始样本、许可范围、人工标签和分歧处理；标签集与调参样本分开，避免在训练/调参样本上自评。比较平台返回排序、发布时间/互动量基线与 HotKey 排序。没有总体真值时，不报告“全网召回率”。

Top-10 相关率的分母是被评估的前十条；不足十条的查询单独标记，不补假样本。自动事件归并精确率以判定为同事件的作品对为口径，同时报告错拆与漏归并；不能通过拒绝所有归并获得虚假高分。自动分析还应报告弃判率，不能只展示有把握样本的准确率。

| OPEN-001-002 | 首批国内平台及后续覆盖顺序 | 建议 X 加至少一个国内完整来源，但此建议尚未得到用户确认 |
| OPEN-001-003 | 需要多及时发现新内容，是否必须离线收到提醒 | 决定轮询和通知优先级；不能只从爬虫默认配置推导 |
| OPEN-001-004 | 实际使用人数、硬件、数据规模与保留期 | 决定 B0、容量、权限和恢复目标是否需要调整 |
| OPEN-001-005 | 基础分析的主要业务问题与允许人工处理程度 | 决定主题/情绪/立场/观点对比的优先级与自动化水平 |
| OPEN-001-006 | 访问条件与开源用途是否符合项目使用范围 | 实际接入前核实；本轮文档不构成已取得授权或商业许可 |
