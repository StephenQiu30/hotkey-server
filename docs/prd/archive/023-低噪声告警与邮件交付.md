# 低噪声告警与邮件交付

## 用户问题

用户目前能看到告警，但不能用多维门槛控制噪声，也看不到一次告警为何触发及邮件是否送达。单一综合分会让单来源、低动量变化造成打扰；同步或无事实记录的 SMTP 又会造成重复、丢失和不可恢复。

## 产品目标

让用户按保守默认策略获得少而可信的告警，能够解释、处理并追踪每次变化；warning/critical 告警可通过持久后台任务发送邮件，任何重试都不重复业务事实。

## 用户故事

- 作为编辑者，我能为监控配置热度、动量、来源宽度、重要性、严重级别、冷却期和邮件策略。
- 作为阅读者，我能从列表进入详情，看到触发依据、Occurrence 历史、当前状态与邮件交付状态。
- 作为处理者，我能确认、解决告警；作为 Editor/Admin，我能抑制噪声线程。
- 作为管理员，我能通过通用错误和尝试次数定位失败，而不会暴露收件人或 SMTP 秘密。

## 功能要求

- FR-023-1：仅使用 active Monitor 的已发布配置和 EventUpdate 不可变快照评估热度、动量、来源宽度与综合重要性，四项全部达标才创建告警。
- FR-023-2：配置必须版本化并校验严重级别边界、5–1440 分钟冷却期、邮件开关和最低邮件严重级别；默认策略为 70/55/25/70、warning 75、critical 90、60 分钟、邮件关闭、最低 critical。
- FR-023-3：Monitor + Event + policy version 形成 Thread，每个变化形成幂等 Occurrence；并发评估、冷却、重开和 suppressed 终态遵循 Design 状态规则。
- FR-023-4：符合邮件条件的新 Occurrence 与唯一 Delivery、唯一 River Job 同事务创建；SMTP 后台最多尝试 5 次，失败不改变告警事实。
- FR-023-5：告警详情展示冻结阈值、维度分、Occurrence、审计和脱敏投递诊断；不得返回收件地址、SMTP 原始响应或凭据。
- FR-023-6：列表、详情、确认、解决和抑制使用真实 API、生成类型和现有 RBAC；无权限操作不可见且服务端拒绝越权。

## 非功能要求

- 写路径使用数据库唯一约束、事务、乐观锁与审计；列表保持稳定游标分页。
- OpenAPI 是跨端唯一契约，生成结果无漂移；前端复用 shadcn/ui 与 Radix 组件。
- 单元、集成、契约、前端组件和浏览器端到端测试覆盖正常、空、错、并发、重试、角色、响应式和可访问性场景。
- 所有 API 错误使用统一业务码；日志和响应不得泄漏邮箱或基础设施细节。

## 非目标

短信、Webhook、移动推送、按用户订阅、富文本模板编辑、自定义重试策略和历史数据回填不属于 MVP。

## 验收标准

- AC-023-1：四项维度均达标时创建一次告警；任一未达标不创建，且严重级别由已发布 warning/critical 快照确定。
- AC-023-2：同一 EventUpdate 并发评估只产生一个 Occurrence；符合邮件条件时也只有一个 Delivery 和一个任务。
- AC-023-3：冷却期内不重复邮件或实时打扰；acknowledged/resolved 在冷却期外可因新变化重开，suppressed 不自动重开。
- AC-023-4：SMTP 失败不回滚 Thread/Occurrence，任务按退避安全重试并在第 5 次进入最终失败；详情仅展示脱敏诊断。
- AC-023-5：用户可配置并发布完整策略，在告警列表进入详情、查看依据/历史/审计/投递状态并完成获授权状态操作；匿名和越权请求失败。
- AC-023-6：后端 CI、前端 OpenAPI/类型/单测/构建、Compose 检查、差异检查和 agent-browser 桌面/移动/键盘/axe 验收全部通过。
