# 配额限流保留与审计治理

## 用户问题

Editor 不知道手动搜索和 AI 还剩多少，并发操作可能在业务层超额。Admin 不能在一个界面查看采集、AI、投递用量，也无法安全预览并批量执行保留策略或查询审计。

## 产品目标

在 025 单项交付内，对两个硬配额做到并发不超卖，以五个现有事实源维度提供统一用量，以最大 1000 条的 dry-run → 确认 → 执行闭环保护数据，并让 Admin 可筛选审计事实。

## 角色与范围

- Viewer：无治理入口，无治理 API 权限。
- Editor：可触发手动搜索，能在监控页看自己的当日已用、剩余和重置时间。
- Admin：拥有 Editor 能力，并可查看全部用量、保留策略和审计，可预览并二次确认执行保留批次。

## 功能要求

- FR-025-1：监控从非 active 发布/恢复为 active 前检查工作区 50 个硬上限；已 active 的幂等请求不重复占用。
- FR-025-2：每个用户每 UTC 日最多创建 20 次手动搜索；队列写入与配额消费同事务，并发只允许限额内请求成功，同冷却桶复用不消费。
- FR-025-3：产品超额返回 429/`10005` 及 `dimension`、`limit`、`remaining`、`reset_at`；来源和 AI 供应商限速继续使用独立错误分类。
- FR-025-4：Admin 总览展示 active monitors、manual searches/day、source calls/day、AI tokens/cost/day、notification deliveries/day；数字只聚合已有事实表和手动搜索账本。
- FR-025-5：系统提供标准化采集临时项、内容/事件指标、失效会话、投递尝试、队列尝试和审计策略列表；每次预览/执行批量为 1–1000。
- FR-025-6：审计、核心内容、事件和已发布报告不能被普通保留执行删除；真实保留执行与其审计同事务。
- FR-025-7：Admin 可按 action、resource type 和 result 筛选审计，并使用稳定 ID 游标翻页；响应不暴露 before/after 原始数据、IP hash 或队列载荷。
- FR-025-8：治理页面使用已安装 shadcn/ui 官方组件组合，覆盖加载、空态、失败重试、零候选、批量截断、键盘焦点和 390px 响应式。

## 非功能要求

- 所有列表有界；配额与业务写入共享事务；保留 SQL 只从服务端白名单产生。
- OpenAPI 由 Swaggo 注解生成，前端只调用生成 Client，不手写重复 DTO。
- 新增逻辑覆盖领域/应用/仓储/HTTP/前端单元测试与真实浏览器主故事。

## 非目标

不提供套餐购买、余额加购、按组织自定义配额、实时流式账单、核心业务事实硬删除或对象存储文件物理删除。

## 验收标准

- AC-025-1：并发请求下 active monitors 不超过 50，单用户当日新建手动搜索不超过 20；超额时队列和监控状态均不变。
- AC-025-2：五个用量维度与底层事实数一致，AI 成本显示 reserved/settled，手动搜索显示 limit/remaining/reset_at，上游 429 不映射为 `10005`。
- AC-025-3：保留 dry-run 不修改数据，真实执行不超过请求批量，重复执行收敛为零；审计/核心事实请求被拒绝。
- AC-025-4：每次真实保留批次只产生一条安全审计；Admin 筛选和游标翻页无重复/漏项，Editor/Viewer 均获得 403。
- AC-025-5：Admin 在 1440×900 和 390×844 下完成用量查看、审计筛选、保留预览和二次确认执行；错误可重试，无横向溢出，键盘和 WCAG 2 A/AA 自动检查通过。
- AC-025-6：后端 CI、OpenAPI 零漂移、前端类型/全量单测/生产构建、开发/生产 Compose、`git diff --check` 和 `$agent-browser` 全部通过。
