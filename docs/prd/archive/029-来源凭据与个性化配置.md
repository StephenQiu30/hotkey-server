# 来源凭据与个性化配置

## 用户问题

管理员创建 X、Bilibili、微博、Google 或 Foundry 来源时，必须先修改服务器 `.env`，再把变量名复制到 UI。这个流程要求部署权限、容易填错，并让来源配置存在两个事实源。

## 产品目标

管理员在登录后的来源管理页完成连接参数、凭据和后续轮换；系统安全持久化且永不回显明文。基础设施和系统主密钥仍由部署环境管理。

## 用户故事

- 作为管理员，我能直接粘贴 API Key、Token 或 OAuth 凭据包并创建来源，不需要登录服务器。
- 作为管理员，我能在不读取旧值的前提下轮换来源凭据，并立即重新执行健康探测。
- 作为成员，我只能知道凭据是否已配置，不能读取、复制或修改它。
- 作为运维人员，我能继续使用既有 env 引用，并能独立备份数据库和主密钥。

## 功能与非功能要求

- 创建与更新契约增加仅写 `credential`，保留 `credential_ref` 作为兼容入口。
- 管理页使用密码输入、明确的“不回显/可替换”说明和提交状态；响应不得返回明文或引用。
- 托管凭据使用认证加密、随机 nonce、版本化主密钥标识、事务和乐观锁。
- 无凭据来源、env 引用来源、Viewer/Editor 读取和历史采集事实保持兼容。
- 不在本条引入多租户、个人私有来源、外部 Secret Manager 或第二套来源配置表单。

## 验收标准

验收标准使用 Design 中 AC-029-1 至 AC-029-5；后端领域/应用/仓储/Transport、前端单测、OpenAPI 漂移、构建和真实浏览器主故事必须通过。
