# HotKey 产品需求分析与总体架构

关联文档：[Design](../design/001-HotKey产品需求分析与总体架构设计.md) · [Plan](../plans/001-HotKey产品需求分析与总体架构计划.md)

## 当前事实与用户问题

HotKey 已有 Go 模块化单体、PostgreSQL 单一 Schema、River 持久任务、MinIO、Redis、自建 JWT/RBAC、Next.js 工作台、统一 `code/message/data` Result 和生成式 OpenAPI 契约。代码中也存在多 Provider、ONNX、Embedding 与 pgvector 路径；这些是迁移现状，不表示已经清理，也不构成新知识检索的目标架构。

需要持续关注产品、公司、人物、政策、作品或技术主题的用户仍面临以下问题：

- 信息分散，人工巡检与复制整理成本高；
- 关键词噪声、转载和跨平台重复内容会掩盖真实事件；
- 绝对互动量无法表达近期升温趋势；
- AI 结论容易脱离原始出处，难以复核；
- 报告、长期知识与运行记录缺少一致的审计和恢复闭环；
- 当前权限只有 `viewer`、`editor`、`admin`，尚无独立 `analyst`，与目标产品角色存在差距。

## 用户角色

| 产品角色 | 目标职责 | 当前权限模型差距 |
|---|---|---|
| Viewer | 查看事件、内容、证据、报告、知识和全文检索 | 已有 `viewer`，仍需逐接口验证只读边界 |
| Analyst | 创建自己的 Monitor、手动扫描、反馈相关性、提出治理建议 | 当前无 `analyst`；实施前必须完成 Schema、Domain、OpenAPI、客户端和回归的兼容演进 |
| Editor | 审核规则、事件成员、Claim/Evidence、报告和知识发布 | 已有 `editor`，需收敛审核权限与 Analyst 写权限的边界 |
| Admin | 管理用户、来源授权、策略、运行、保留、审计和恢复 | 已有 `admin`，不得因此暴露密钥或原始任务 Payload |

在 Analyst 正式落地前，不得仅在前端伪造该角色，也不得把 Editor 的全部权限静默等同于 Analyst。

## 产品目标与 KPI

产品目标是形成一套本地优先、自托管、面向授权公开来源、以事件和证据为中心的热点监控闭环：

```text
Monitor → 多来源采集 → 原始证据 → 标准化/去重
→ 智能研判 → Event/Heat/Evidence → 通知/日报
→ Obsidian 人类知识投影 → 非向量全文检索
```

| KPI | 目标 | 口径状态 |
|---|---|---|
| 首个 Monitor 建立时间 | 10 分钟内 | 候选，需定义起止点、账号与来源授权前提 |
| P0 正式来源 | 至少 3 个真实授权来源完成闭环 | 候选，需定义成功样本量和观察窗口 |
| 报告事实性 Claim 证据覆盖率 | 100% 具有 Evidence ID | P0 硬门禁 |
| 人工知识保护 | 自动发布导致的人工内容丢失为 0 | P0 硬门禁 |
| 业务事实可靠性 | 来源、Codex 或检索故障不造成已提交事实丢失 | P0 硬门禁 |
| 活跃 Monitor | 50 | 候选，需基线校准 |
| 每日候选/标准化正文 | 50,000 / 30,000 | 候选，需基线校准 |
| 核心 API 月可用性 | 99.5% | 候选，需定义环境、窗口和排除条件 |

## 范围

### P0：24 周承诺范围

- 现有认证、任务、存储、Result 和 OpenAPI 契约内的模块化单体演进；
- Viewer、Analyst、Editor、Admin 产品权限目标及当前三角色的兼容迁移；
- Monitor 版本生命周期、授权来源、定时/手动扫描和多来源部分成功；
- 原始证据、内容标准化、去重、事件、Heat 和 Evidence 分离；
- 受控 Codex CLI 分析及不可用降级；
- 站内通知、日报、Obsidian 发布、非向量全文检索；
- 审计、幂等、任务恢复、备份恢复和 P0 质量门禁。

### P1：P0 验收后排期

- 评论会话采集与评论洞察；
- 周报、邮件通知和更多获得授权的来源；
- 更完整的 Vault 双向冲突处理和多 Vault；
- 生产高可用、横向扩展和更复杂的协作流程。

### P2：候选方向

- 隔离式浏览器采集，但只处理明确授权页面；
- 自定义报告模板、外部 Webhook、离线分析仓库和多地域采集；
- 团队批注、任务协作和高级成本优化。

## 用户故事

- 作为 Viewer，我可以理解一个热点为何被发现、当前热度和证据状态，并回到原始出处。
- 作为 Analyst，我可以在权限范围内创建 Monitor、发起扫描并反馈误报，而不接触来源凭据。
- 作为 Editor，我可以审核智能建议、修正事件和批准日报，且每次更改均可追溯。
- 作为 Admin，我可以治理授权、失败任务、保留和恢复，而不直接篡改业务事实。
- 作为研究人员，我可以在 Obsidian 中长期维护人工笔记，并通过关键词和过滤条件找到历史知识。
- 作为运维人员，我可以在单个应用运行面定位 API、任务、来源、Codex、存储和投影故障。

## 业务需求

- `BR-001-001`：系统必须把分散的授权公开信息转化为可追溯、可治理的热点事件，而不是不可解释的内容列表。
- `BR-001-002`：AI 只能提供结构化建议；业务事实、权限和最终状态必须由 Go 应用规则与人工治理决定。
- `BR-001-003`：日报和长期知识必须同时支持自动生成效率、证据审计和人工持续维护。
- `BR-001-004`：P0 必须可在本地或单机自托管环境运行，不以新增分布式基础设施为前提。

## 功能要求

- `FR-001-001`：系统必须提供从 Monitor 创建到通知、日报、Obsidian 和全文检索的 P0 垂直闭环。
- `FR-001-002`：业务能力必须保持在现有 Go 模块化单体内，跨模块通过 Application 接口或只读端口协作。
- `FR-001-003`：PostgreSQL 必须是业务事实源，MinIO 保存原始证据，River 承载持久任务，Redis 只保存短期状态。
- `FR-001-004`：所有 Web 功能必须通过现有 HTTP API 和生成客户端访问，不得绕过 OpenAPI 直接访问数据库、任务或对象存储。
- `FR-001-005`：所有 JSON API 必须保持 `code`、`message`、`data` Result，成功业务码为 `0`，无数据使用 `data: null`。
- `FR-001-006`：系统必须表达 Viewer、Analyst、Editor、Admin 四类产品职责，并对当前缺少 Analyst 的迁移状态给出真实反馈。
- `FR-001-007`：每个智能结论、报告 Claim 和知识投影必须保留来源、Evidence ID、生成/审核版本与审计关联。
- `FR-001-008`：单一来源或 Codex 失败时，已完成的采集与确定性处理必须保留，运行状态必须显式显示部分成功或待分析。
- `FR-001-009`：新知识检索必须使用可审计的词法全文检索、过滤、聚合和高亮，不得依赖向量、Embedding 或 RAG。
- `FR-001-010`：24 周发布范围只能由 P0 需求和同编号 Plan 的门禁推进，P1/P2 不得作为 P0 完成条件。

## 非功能要求

- `NFR-001-001`：关键写操作必须认证、服务端授权、校验、幂等或乐观锁保护，并产生不可静默覆盖的审计事实。
- `NFR-001-002`：桌面和移动工作台必须支持键盘操作、可见焦点、语义化标签、合理对比度和减弱动效。
- `NFR-001-003`：列表必须使用稳定分页；错误不得泄露 SQL、堆栈、Token、凭据、Provider 原始响应或任务 Payload。
- `NFR-001-004`：候选性能目标为普通 API P95 300 ms、热点列表 P95 500 ms、全文检索 P95 800 ms；批准前必须补齐数据规模、并发、硬件、缓存冷热、统计窗口和排除条件。
- `NFR-001-005`：候选恢复目标为 RPO 15 分钟、RTO 2 小时；批准前必须通过 PostgreSQL、MinIO、Vault 和任务状态的联合演练验证。
- `NFR-001-006`：所有目标能力必须标注“当前、部分具备、待实现或已验收”，PRD/Design/Plan 不得替代 Acceptance 宣称完成。

## 权限矩阵

| 能力 | Viewer | Analyst | Editor | Admin |
|---|---:|---:|---:|---:|
| 查看已发布事件、证据、报告、知识 | 允许 | 允许 | 允许 | 允许 |
| 创建自己的 Monitor、手动扫描、反馈 | 禁止 | 允许 | 允许 | 允许 |
| 审核事件、证据、报告和知识发布 | 禁止 | 提交建议 | 允许 | 允许 |
| 管理来源授权、策略、用户和运行 | 禁止 | 禁止 | 禁止 | 允许 |
| 查看密钥明文、原始任务 Payload | 禁止 | 禁止 | 禁止 | 禁止 |

当前实现仍只有 Viewer/Editor/Admin；在 Analyst 迁移完成前，服务端必须按真实角色拒绝请求，界面不得显示虚假成功状态。

## 界面与交互状态

| 状态 | 产品要求 |
|---|---|
| 正常 | 展示数据更新时间、状态、证据入口、允许动作和下一步 |
| 空 | 区分尚未创建、暂无匹配、过滤后为空和尚未分析，并提供合法主动作 |
| 加载 | 保持布局稳定，长任务显示可离开页面的持久运行状态 |
| 错误 | 显示稳定错误码、可重试性和已保留成果，不展示敏感详情 |
| 权限不足 | 服务端返回明确业务码；前端隐藏危险动作并说明所需角色，不以空状态替代 403 |

## 非目标

- 不把 Kafka、Temporal、Python FastAPI 微服务、Elasticsearch、Keycloak、增量迁移目录或分布式事件总线作为 V1 前置条件。
- 不实现未经授权的 Cookie 抓取、验证码/指纹绕过、私密账号采集、自动对外发布或普通用户跨平台画像。
- 不实现向量数据库、Embedding 新链路、RAG、知识问答、重排器或 AI 真伪概率。
- 不在本 PRD 中宣称现有 Provider、Embedding 或 pgvector 已删除；替换和清理由专项兼容验收决定。
- 不承诺 P1 评论、周报、更多来源、邮件或高可用在 24 周 P0 内完成。

## 依赖、风险与待决策

| ID | 项目 | 处理要求 |
|---|---|---|
| `RSK-001-001` | 当前权限没有 Analyst | 在单一 Schema 中做兼容演进，同时更新 Domain、API、OpenAPI、客户端和测试 |
| `RSK-001-002` | 现有智能路径与目标 Codex 路径并存 | 先建立等价评估、回滚和迁移门禁，不做无证据清理 |
| `RSK-001-003` | 单人研发面对过大范围 | 24 周只承诺 P0，以垂直切片和删减规则控制范围 |
| `RSK-001-004` | 候选指标无测量口径 | PRD 批准前补齐负载模型和基线报告 |
| `RSK-001-005` | 原始证据保留期与长期可追溯目标冲突 | 在 002/005 中定义元数据长期保留、原始对象期限和例外策略 |

待决策项包括 Analyst 的兼容迁移方式、P0 三个正式来源的授权就绪条件、Codex 不可用时的补算 SLA、知识投影的单写者策略和候选性能基线。

## 验收标准

| ID | Given | When | Then |
|---|---|---|---|
| `AC-001-001` | 一个已授权用户和至少一个可用来源 | 用户创建并发布 Monitor，完成扫描、研判、事件、通知、日报、知识发布和检索 | 每个步骤状态可见，最终对象可追溯到 Monitor、运行和 Evidence；日报每个事实性 Claim 均引用允许的 Evidence ID，自动知识更新不覆盖人工区域，且没有绕过模块化单体契约 |
| `AC-001-002` | Viewer、Editor、Admin 当前角色及 Analyst 目标角色 | 分别访问读、写、审核和管理动作 | 服务端按真实权限允许或拒绝；Analyst 未迁移时明确拒绝，不由前端伪造角色 |
| `AC-001-003` | P0 实施分支及其 Design、PRD、Plan、代码、Schema、OpenAPI 与 Acceptance | 核对目标、当前实现和验收证据 | 未新增 Kafka、Temporal、Python 业务微服务、Elasticsearch、Keycloak 或 migrations 目录作为 P0 依赖；代码/契约只描述当前事实，Design/PRD/Plan 只描述目标与执行状态，只有 Acceptance 声明已验证完成 |
| `AC-001-004` | 任一核心页面 | 返回正常、空、慢请求、可恢复错误和权限不足响应，并以键盘、减弱动效和可访问性工具操作 | 桌面与移动端分别呈现可辨识的五态，全部关键操作可键盘完成，焦点可见，语义化标签、对比度和 `prefers-reduced-motion` 行为符合仓库规范 |
| `AC-001-005` | 一个需要新增或修改的 API | 完成后端契约变更 | Result、错误码、DTO、Swaggo、`docs/openapi/swagger.json`、生成客户端和契约测试保持一致，Schema 仍只有 `backend/db/schema.sql` 一套 |
| `AC-001-006` | 已记录负载模型、基线环境及可用的 PostgreSQL、MinIO、Vault 与持久任务备份 | 执行候选容量/性能基线和隔离环境联合恢复演练 | 报告明确数据规模、并发、硬件、缓存状态、统计窗口、P50/P95/P99、排除条件及真实 RPO/RTO；事实、证据、人工区域和任务状态完成对账，未达标时不得把候选数字改写为已承诺 SLA |
| `AC-001-007` | 正在运行的多来源扫描及一个产生结构化建议的 Codex 任务 | 一个来源失败、Codex 不可用或 Codex 返回可解析建议 | 已采集事实和确定性计算不丢失，运行显示部分成功/待分析，恢复后幂等补算；AI/Codex 输出只作为建议，经 Application/Domain 校验和授权人工治理后方可影响当前视图，不能直写业务事实、权限或最终状态 |
| `AC-001-008` | 已发布的报告、含人工区域的 Obsidian 知识及可丢弃检索投影 | 用户执行关键词、标签、实体、时间和状态检索，并重建自动知识区域与检索投影 | 可返回权限内的高亮结果，链路不调用向量、Embedding 或 RAG；自动区域和索引从 PostgreSQL 重建，人工区域仅从受保护 Vault、Knowledge Revision 或备份恢复且逐字保留 |
| `AC-001-009` | 一个需要认证、授权和资源版本保护的关键写操作，以及固定幂等键、旧版本和并发请求 Fixture | 首次提交、重复提交、重放同一幂等键并以过期版本并发修改 | 服务端在副作用前完成认证、授权和输入/版本校验；重复请求不产生重复事实，过期写入返回稳定冲突，成功、拒绝与冲突均追加不可覆盖且不含秘密的审计事实 |
| `AC-001-010` | 一个含并列排序值的列表、固定页大小和并发新增 Fixture | 使用游标连续遍历，并提交无效、过期、越权游标与超限页大小 | 排序由不可变字段和唯一 ID 确定，已越过区间不回流，同一连续遍历无重复或漏项；非法参数返回稳定脱敏错误且不泄露资源存在性 |
