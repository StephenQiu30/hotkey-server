# 通知报告知识投影与检索

关联文档：[Design](../design/004-通知报告知识投影与检索设计.md) · [Plan](../plans/004-通知报告知识投影与检索计划.md)

## 用户问题与当前事实

发现热点只有在及时、低噪声地送达用户，并沉淀为可审核日报和可长期维护的知识时才产生价值。用户需要离线后补拉通知、核查报告引用、保留 Obsidian 人工笔记，并通过关键词、实体、时间和状态找到历史内容，而不是得到无出处的模型答案。

当前仓库已落地追加式 Notification Outbox、User Notification、服务端 Notification Read Receipt、Delivery Attempt、短期 Delivery Claim、WebSocket 与邮件派发；已读状态以服务端单调游标收敛，lost-ack 以 Fencing、Provider 幂等/回执能力和持久 `unknown` 停止语义治理。报告 Revision/内容安全、知识 Vault 确定性投影/原子更新/受保护恢复，以及认证后的 PostgreSQL 词法检索 API 与默认前端读路径也已实现；全文检索已有固定 3,000 条三类语料的 warm-cache 候选容量报告，但仍保持 `approval=required`。通知与投递尝试事实及稳定游标不能像检索索引一样清空重建。PostgreSQL、MinIO 和本地 Vault 是当前批准边界。M4 仍需完成通知→报告→Vault→检索统一容量与日志哨兵、端到端浏览器验收和完整重建对账；在此之前不将候选时延或局部功能写成已批准用户闭环。

## 目标与 KPI

| KPI | 目标 | 口径状态 |
|---|---|---|
| 日报事实性 Claim 的 Evidence ID 覆盖率 | 100% | P0 硬门禁 |
| 已批准 Revision 被重新生成覆盖 | 0 | P0 硬门禁 |
| 自动发布造成的人工 Vault 内容丢失 | 0 | P0 硬门禁 |
| 站内新通知页面可见 | 2 秒内 | 候选，需定义连接、并发和统计窗口 |
| Obsidian 发布 | 审批后 30 秒内 | 候选，需定义文件系统与任务条件 |
| 全文检索 P95 | 800 ms | 候选，需定义语料量、查询集和缓存冷热 |
| 投影后可检索 | 10 秒内 | 候选，使用 PostgreSQL/River 投影口径校准 |
| 投影故障造成核心事实丢失 | 0 | P0 硬门禁 |

## 范围

### P0

- 低噪声站内通知事实、服务端 Notification Read Receipt/未读状态、事件深链、WebSocket 实时提示与断线补拉；
- 日报时间窗冻结、来源覆盖、事件选择、Evidence 清单、草稿、校验、审批和不可变 Revision；
- 批准后的事件与日报投影为 Obsidian Markdown；
- 稳定 ID、Frontmatter、系统自动区域、人工区域、原子写入和基本冲突保护；
- PostgreSQL 全文检索、关键词、类型、Monitor、来源、实体、时间、状态过滤和安全高亮；
- Delivery Claim/租约、WebSocket 会话和客户端缓存等临时状态的恢复，以及外部交付、Vault 自动区域和检索投影的 River 重试、幂等、对账、重建和删除/撤权同步；Notification Outbox、User Notification、上线后的 Notification Read Receipt、Delivery Attempt 和人工区域不得被当作可丢弃投影；
- 所有交付通过现有 Result、OpenAPI 和生成客户端。

### P1

- 周报、邮件通知、评论洞察进入报告；
- 更完整的 Vault Watcher、人工提案、双向冲突处理和 Git 审阅模式；
- 多 Vault、团队协作和自定义报告模板。

### P2

- 外部 Webhook、更多订阅通道和高级报告分发；
- 更复杂的知识关系导航、离线分析和多工作区知识策略。

## 用户故事

- 作为 Viewer，我在线时收到站内实时提示，离线回来后也不会漏掉已提交通知。
- 作为 Analyst，我可以查看日报草稿和证据覆盖警告，但不能批准或修改冻结版本。
- 作为 Editor，我可以审核日报的每条事实性 Claim、批准 Revision 并发布到 Obsidian。
- 作为研究人员，我可以在自动区域之外维护人工笔记，后续自动发布不会覆盖它们。
- 作为 Viewer，我可以用关键词和过滤器搜索权限内的内容、事件和知识，并看到安全高亮和原始出处。
- 作为 Admin，我可以重试失败投影、查看冲突、执行对账和撤权同步，而不直接修改事实表或 Vault 文件。

## 业务需求

- `BR-004-001`：热点提醒必须及时、可补拉、低噪声，交付通道失败不得丢失通知事实。
- `BR-004-002`：日报必须冻结输入和 Evidence，经过人工审批后形成不可变、可复核版本。
- `BR-004-003`：Obsidian 必须是人类可维护、可重建的知识投影，自动内容不得破坏人工内容。
- `BR-004-004`：用户必须能通过非向量全文检索找到权限内知识，而不会得到未经引用的生成式回答。

## 功能要求

- `FR-004-001`：触发规则必须把 Monitor、Event、规则版本、触发窗口和去重键保存为通知事实，WebSocket 和未来邮件只是交付通道。
- `FR-004-002`：通知中心必须支持稳定列表、事件深链、`after_id` 或等价游标补拉和断线重连，不以 WebSocket 作为事实源；服务端必须以追加式 Notification Read Receipt 保存每个用户单调前进的 `read_through_id`，校验该 ID 属于用户可见范围并以服务端最新回执派生未读/已读。前端 `localStorage` 只作缓存，不能覆盖或倒退服务端状态。
- `FR-004-003`：通知规则必须支持最小间隔、重复抑制和用户偏好；站内通知失败重试不得回滚 Event 或 Heat 事实。
- `FR-004-004`：日报任务必须先冻结日期/时区、Monitor、来源覆盖、Event/Claim/Evidence 版本和输入哈希，再生成草稿。
- `FR-004-005`：每个事实性报告句必须引用冻结的 ClaimEvidence 白名单；Event 级 Evidence State 不能替代逐句引用校验，无引用、伪造、已撤权或完整性失败的引用必须阻止审批。
- `FR-004-006`：Editor 批准后必须形成不可变 Report Revision；重新生成创建新草稿，不覆盖已批准 Revision。
- `FR-004-007`：Vault 文件必须使用稳定业务 ID 和受控相对路径；标题或文件名变化不得改变知识身份。
- `FR-004-008`：系统只能替换明确标记且可由 PostgreSQL 重建的自动区域，人工区域必须原样保留；人工区域只能从现存 Vault、Knowledge Revision 或备份恢复，不能由系统生成。缺失标记、ID 冲突、Revision 倒退或重复 Stable ID 必须停止覆盖并显示冲突。
- `FR-004-009`：Vault 写入必须使用临时文件、同步与同文件系统原子替换；成功后记录投影哈希、Revision 和运行身份。
- `FR-004-010`：P0 检索必须使用 PostgreSQL 词法全文、规范化字段和必要索引，支持关键词、类型、Monitor、来源、实体、时间、状态、排序和高亮。
- `FR-004-011`：搜索 Application 必须在查询时执行服务端权限与撤权过滤，返回业务对象身份和安全高亮，不把索引字段作为第二业务事实。
- `FR-004-012`：通知恢复必须从持久 Notification Outbox/User Notification/Notification Read Receipt/Delivery Attempt 按原稳定 ID、派发键和游标顺序执行；只可清理 Delivery Claim/租约、WebSocket 会话和客户端缓存，禁止清空上述事实。外部交付恢复必须保留既有 Attempt，并遵守 Claim Fencing、Provider 幂等/回执和 `unknown` 停止规则；Vault 自动区域和检索投影必须具备幂等重建与对账，人工区域只从受保护来源恢复。投影失败不回滚核心事实。
- `FR-004-013`：删除、撤权、更正和归档必须同步改变通知深链可见性、Vault 投影和检索结果，并保留审计。
- `FR-004-014`：每个外部通道 Claim 必须包含不可猜测 Token、租约截止和递增 Fencing Generation，完成 Attempt 时用数据库时间验证当前 Claim；租约过期可被抢占，旧 Worker 的迟到完成必须失败停止。通道适配器必须声明 Provider 幂等键与回执查询能力：能力存在时复用稳定派发键并先对账；请求可能已被 Provider 接收但本地无法确认时，追加 `unknown` Attempt 或等价不可变事实并阻止盲目自动重发，不对缺少该能力的通道承诺 exactly-once。

## 非功能要求

- `NFR-004-001`：候选目标为通知 2 秒、Vault 发布 30 秒、投影检索 10 秒、搜索 P95 800 ms；批准前必须补齐语料、查询集、并发、硬件、文件系统、缓存状态和统计窗口。
- `NFR-004-002`：重复通知投影、报告构建、Vault 发布和全量重建不得创建重复用户通知、文件、当前 Revision 或搜索结果。
- `NFR-004-003`：Markdown、报告正文和搜索高亮必须防 XSS、脚本 URL、路径穿越、符号链接逃逸和不可信 HTML。
- `NFR-004-004`：Vault 根路径必须由部署配置控制；任何 API 均不得接受任意绝对路径或返回宿主机路径。
- `NFR-004-005`：检索结果不得跨角色或对象权限泄露；删除/撤权后的投影同步延迟必须被监控并可人工修复。
- `NFR-004-006`：报告、通知和投影日志必须关联安全的运行、Event、Report、Knowledge ID，但不记录完整敏感正文、邮件地址列表或来源凭据。
- `NFR-004-007`：Claim 过期抢占、旧 Token 迟到完成和 Provider lost-ack 必须使用固定竞态/故障 Fixture 可重复验证；系统只能声称可证明的 Provider 交付语义，不得把本地唯一键等同于外部 exactly-once。
- `NFR-004-008`：通知、日报、知识和检索页面必须覆盖正常、空、加载、错误和权限不足状态，并与 Viewer/Analyst/Editor/Admin 的服务端权限一致；Analyst 不得获得报告批准或知识发布权限。

## 界面状态

| 状态 | 产品要求 |
|---|---|
| 正常 | 通知展示时间、原因和深链；报告展示引用与状态；知识展示投影状态；搜索展示高亮与过滤 |
| 空 | 区分暂无通知、该日无入选事件、尚未发布知识、查询无结果和过滤后为空 |
| 加载 | 实时连接与普通 API 状态分离；构建、审批、发布、重建显示持久运行身份 |
| 错误 | 区分连接、报告校验、Evidence、Vault 冲突、投影和查询错误，并保留可用历史结果 |
| 权限不足 | 直接 API 与页面一致拒绝；不以空结果掩盖越权，也不泄露对象是否存在 |

## 非目标

- 不自动向社交平台或外部网站发布内容。
- 不把 WebSocket、邮件、Vault 文件或检索投影作为业务事实源。
- 不在 P0 承诺周报、邮件、评论洞察、多 Vault 或团队文档协作。
- 不引入 Kafka、Logstash、Elasticsearch 或外部全文检索集群。
- 不实现向量知识问答、RAG、语义向量检索或基于搜索结果自动回答。
- 不宣称现有 Embedding/pgvector 已清理；新知识检索只是不依赖它们。

## 依赖、风险与待决策

| ID | 项目 | 处理要求 |
|---|---|---|
| `RSK-004-001` | WebSocket 连接不可靠 | 普通 API 补拉为恢复路径，连接状态独立展示 |
| `RSK-004-002` | 日报等待审批可能无限挂起 | 定义截止、提醒、取消和次日处理规则 |
| `RSK-004-003` | Vault 人工编辑与自动发布冲突 | 单写者、自动/人工区域、版本/hash 和冲突副本门禁 |
| `RSK-004-004` | PostgreSQL 全文检索质量和容量未知 | 用多语言语料和真实查询集校准；不以引入 Elasticsearch 规避基线工作 |
| `RSK-004-005` | 原始 Evidence 到期影响历史报告 | 报告冻结引用、元数据长期保留和例外归档依赖 002/005 策略 |
| `RSK-004-006` | Provider 已接收但本地 Attempt 未提交，自动重试可能重复外部交付 | 稳定派发键、Claim Fencing、Provider 回执对账；无法确认时进入 `unknown` 并停止自动重发 |

待决策项包括日报时区和审批截止、通知低噪声阈值、Vault 单写者与 Git 是否为 P1、P0 支持语言及分词配置、搜索排名 Profile、删除同步 SLA，以及 P0 邮件/外部 Provider 的幂等键和回执查询能力。

| ID | Given | When | Then |
|---|---|---|---|
| `AC-004-001` | 已提交的站内通知、含最小间隔/重复抑制的规则、用户当前通道偏好、两个设备和在线/离线客户端 | 同一触发窗口重复投影，偏好变更后交付，执行 WebSocket 推送、断线、重连和最后位置补拉；设备 A 标记已读后清空设备 B 的本地缓存并重新登录 | 最小间隔和重复抑制生效，Dispatcher 使用交付时偏好，通知只展示一次且顺序稳定；离线不丢失，连接故障不影响普通列表与通知事实；设备 B 从服务端 Read Receipt 收敛，已读游标不倒退且不能越权推进 |

| `AC-004-003` | 一个已批准 Report Revision | 用户重新生成或修改同一日期报告 | 原批准版本保持不可变，新内容形成可追溯草稿/Revision，版本和操作者可查询 |
| `AC-004-004` | 包含自动区域、人工笔记、冲突变体、绝对/穿越/符号链接逃逸路径及恶意 Markdown/不可信 HTML 的 Vault Fixture | 重复发布、改标题、标记丢失、Revision 倒退或提交恶意 Fixture | 正常重复发布不产生重复文件且人工内容逐字保留；非法路径和恶意内容在写入/发布前被拒绝并形成不泄露宿主路径的审计，危险冲突停止覆盖并产生可治理记录 |

| `AC-004-006` | 可丢弃的 Delivery Claim/租约、WebSocket 会话、客户端缓存、知识自动区域或检索投影，以及 Claim 过期、Worker A 迟到、Worker B 抢占、Provider 成功后本地提交失败的 Fixture；Notification Outbox/User Notification/Notification Read Receipt/Delivery Attempt 和 Vault 人工区域保持存在 | 从 PostgreSQL 与受保护 Vault 恢复、对账和重建，并分别在 Provider 支持和不支持幂等/回执时执行 lost-ack 故障注入 | 新 Claim 使用更高 Fencing Generation，Worker A 的旧 Token 不能提交或删除 B 的 Claim；既有 Attempt 保留，支持 Provider 能力时稳定派发键/回执避免重复派发，不可确认时形成可见 `unknown` 且不盲目重发，不虚构 exactly-once；自动知识与检索投影幂等恢复，持久事实和人工区域未清空，差异有报告 |

| `AC-004-008` | 已固定语料、查询集、并发、硬件、文件系统、缓存状态及带正文/邮件列表/宿主路径/凭据哨兵的 Fixture | 执行通知、日报发布、Vault 与全文检索基线并扫描结构化日志 | 输出 P50/P95/P99、错误率、投影积压和资源报告；链路以安全运行 ID 关联且日志不含正文、邮件地址列表、宿主路径或凭据，候选时延只有达标并批准后转为承诺 |
