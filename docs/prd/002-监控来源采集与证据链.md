# 监控来源采集与证据链

关联文档：[Design](../design/002-监控来源采集与证据链设计.md) · [Plan](../plans/002-监控来源采集与证据链计划.md)

## 用户问题与当前事实

用户需要把一个持续关注意图转化为可运行、可暂停、可追溯的 Monitor，并在多个来源能力和授权不同的情况下理解每轮扫描实际发生了什么。来源限流、凭据过期、空结果或单点失败不能抹掉其他来源的成功结果；标准化内容必须能回到不可变原始证据。

当前仓库已有 `monitor`、`source`、`ingestion` 模块、PostgreSQL/River 持久任务、MinIO 证据和来源权利治理相关 Schema/API。源码或表存在不等于所有来源都已取得真实授权或完成用户闭环，本 PRD 只定义待验收范围。

## 目标与 KPI

| KPI | 目标 | 口径状态 |
|---|---|---|
| 首个 Monitor 创建并发布 | 10 分钟内 | 候选，需定义账号、授权、网络与起止点 |
| P0 正式来源 | RSS/Atom、Hacker News、X 三类真实授权来源闭环 | 候选，实施前逐来源确认 API、配额和许可 |
| 多来源隔离 | 单来源失败时其他成功结果继续处理 | P0 硬门禁 |
| 证据覆盖 | 被接受 Document 具有 Observation、来源和可校验原始 Evidence | P0 硬门禁 |
| 活跃 Monitor / 来源连接 | 50 / 100 | 候选，需基线校准 |
| 每日候选 / 标准化正文 | 50,000 / 30,000 | 候选，需基线校准 |
| 手动扫描入队 | 1 秒内 | 候选，需定义负载和统计窗口 |
| 同时扫描任务 | 20 | 候选，需基线校准 |

## 范围

### P0

- Monitor 草稿、来源级编译预览、不可变 Compiled Profile、发布版本、暂停、恢复、归档和历史追溯；
- 定时与手动扫描、时区/时间窗、重复提交防护和运行详情；
- RSS/Atom、Hacker News、X 的真实授权闭环，未就绪来源不得伪装可用；
- Capability、Rights、Credential、Budget、Rate Limit、Endpoint Policy 调用前门禁；
- 来源级独立执行与整轮 `partial_success` 产品语义；
- 原始响应先写 MinIO，再生成 Observation、Document 和指标事实；
- 标准化、URL 规范化、精确/近似去重、发布时间治理、Checkpoint 和幂等恢复；
- 原始对象保留状态、哈希校验、权限下载与审计。

### P1

- YouTube 及更多获得授权的平台来源；
- 评论会话采集、指标深度刷新和历史回填；回填使用独立触发语义，不伪装实时发现或触发普通实时热点通知；
- 更细粒度的来源预算、动态配额和授权到期工作流。

### P2

- 新增经批准的官方 API、RSS、Atom 或明确授权 Feed Connector；
- 多地域采集节点和大规模离线回填；
- 面向外部系统的受控采集 Webhook。

## 用户故事

- 作为 Analyst，我可以创建 Monitor 草稿、预览查询影响并在确认后发布，不改变旧版本的运行历史。
- 作为 Analyst，我可以手动扫描并看到每个来源的成功、空、限流、权限失败或临时失败。
- 作为 Viewer，我可以从一篇标准化内容回到来源链接、Observation 和仍在保留期内的原始 Evidence。
- 作为 Editor，我可以审核 Monitor 规则和相关性反馈，但不能查看来源凭据明文。
- 作为 Admin，我可以配置来源授权、预算、健康和保留策略，并审计所有管理动作。
- 作为运维人员，我可以在 Worker 中断后恢复同一工作单元，而不会创建重复事实。

## 业务需求

- `BR-002-001`：Monitor 必须把用户意图固定为可版本化、可审核、可重复执行的监控契约。
- `BR-002-002`：来源接入必须以合法授权和显式能力为前提，失败必须对用户透明。
- `BR-002-003`：任何进入研判的内容都必须具有可验证证据链，派生事实不得覆盖原始观察。
- `BR-002-004`：采集必须有界、幂等、可恢复，单来源故障不得扩大为整轮静默丢失。

## 功能要求

- `FR-002-001`：Monitor 必须支持草稿、预览、发布、暂停、恢复和归档；发布后修改必须创建新版本，历史运行绑定原版本。
- `FR-002-002`：Monitor 必须显式保存主题、包含/排除规则、实体、语言、来源选择、时间窗、时区、调度、告警和预算引用；预览必须展示来源级编译结果与差异，发布版本必须绑定同输入可复现、不可变且带编译/Schema 版本和输入哈希的 Compiled Profile。
- `FR-002-003`：定时和手动扫描必须生成稳定运行身份，并以 Monitor 版本、时间窗和触发类型形成幂等工作单元。
- `FR-002-004`：每个 Connector 动作必须按 Capability→Rights/Policy→Credential 状态/引用→Budget→Rate Limit→Endpoint/SSRF Policy→Request 的顺序执行；端点通过前不得解密或附加凭据，也不得发出真实来源请求。
- `FR-002-005`：凭据读取接口只能返回配置状态和脱敏标识；包括 Admin 在内均不得通过普通 API 读取明文。
- `FR-002-006`：一轮多来源扫描必须保存来源 Target 的状态、数量、耗时、Checkpoint 和稳定错误码，并由 Application 派生 `success / partial_success / failed` 的 `run_outcome` 查询视图；合法空结果是成功零条，不新增与现有 Schema 冲突的整体持久状态。
- `FR-002-007`：来源响应必须先以不可变对象保存到 MinIO，并记录 Object Key、SHA-256、内容类型、字节数、捕获时间和保留期限。
- `FR-002-008`：Observation 必须记录来源连接、外部身份、采集时间、原始证据和处理版本；Document 必须记录标准化正文及其版本，二者不得合并成可覆盖记录。
- `FR-002-009`：去重顺序必须优先使用来源外部身份、规范 URL 和正文哈希，再使用有版本的近似指纹；智能建议不得替代精确去重。
- `FR-002-010`：未知发布时间必须保持为空；发现时间、捕获时间和原始时区必须分别保存，不得用发现时间伪造发布时间。
- `FR-002-011`：重试、分页恢复和重复发现必须复用幂等键与 Checkpoint，只追加新 Observation、版本或指标，不创建重复当前 Document。
- `FR-002-012`：原始对象过期后必须保留必要证据元数据、哈希和删除审计，并在界面明确显示“原始对象已过保留期”；长期保留例外由策略批准。
- `FR-002-013`：Monitor、来源、扫描、内容和证据接口必须通过 Swaggo/OpenAPI 发布，并由前端生成客户端消费。
- `FR-002-014`（P1）：历史回填必须保存独立触发类型、原时间窗和回填身份，不得改写发布时间或触发普通实时热点通知；是否发送独立回填完成通知需另行批准。

## 非功能要求

- `NFR-002-001`：来源请求必须设置连接、读取、墙钟、页数、条数、字节、重试和每日配额上限；401、403、429、5xx 与解析失败分别处理。
- `NFR-002-002`：自定义端点必须逐跳防 SSRF，拒绝回环、私网、链路本地、保留地址、URL userinfo 和未经批准的重定向。
- `NFR-002-003`：证据对象写入成功且哈希可验证前，不得把内容标记为证据完整或送入事实性 Claim。
- `NFR-002-004`：候选容量为 50 个活跃 Monitor、100 个连接、每日 50,000 候选、30,000 正文、20 个并发扫描；本轮以当前本机开发环境和固定 CI Runner 上的真实 Fixture 结果校准，不要求额外目标硬件。
- `NFR-002-005`：候选手动扫描入队 P95 为 1 秒、运行状态更新 P95 为 5 秒；需记录并发、队列深度、统计窗口和排除条件。
- `NFR-002-006`：来源、凭据、预算、扫描和证据管理动作必须审计；日志不得包含 Token、Cookie、完整敏感正文或上游原始错误。

## 权限矩阵

| 能力 | Viewer | Analyst | Editor | Admin |
|---|---:|---:|---:|---:|
| 查看已发布 Monitor、运行、内容和允许的证据 | 允许 | 允许 | 允许 | 允许 |
| 创建自己的 Monitor、手动扫描和反馈 | 禁止 | 允许 | 允许 | 允许 |
| 审核 Monitor 规则 | 禁止 | 提交 | 允许 | 允许 |
| 管理来源连接、权利、凭据、预算和保留 | 禁止 | 禁止 | 禁止 | 允许 |
| 下载明文凭据或任意 MinIO Key | 禁止 | 禁止 | 禁止 | 禁止 |

005 已完成 Analyst 的兼容角色基线：Analyst 仅能创建、修改、发布和扫描自有 Monitor；Editor 可管理全部 Monitor 并审核规则；Admin 额外管理来源、用户和运行。最终门禁仍需重跑本 PRD 的四角色正负向 UAT，不以角色枚举存在代替完整验收。

## 界面状态

| 状态 | Monitor/来源/扫描要求 |
|---|---|
| 正常 | 展示版本、调度、来源能力、最近运行、证据状态和可执行动作 |
| 空 | 区分无 Monitor、无已授权来源、合法空结果和过滤后为空 |
| 加载 | 创建/扫描请求只提交一次；长任务展示运行 ID、来源进度和可离开提示 |
| 错误 | 区分限流、授权、预算、解析、网络、证据写入和系统失败，显示已保留成果 |
| 权限不足 | 返回稳定业务码；凭据配置与管理动作不降级为只读敏感详情 |

## 非目标

- 不绕过登录、验证码、反爬、设备指纹或平台访问限制。
- 不以普通网页任意抓取替代缺失的正式来源授权。
- 不把评论会话、周报或更多平台作为 24 周 P0 完成条件。
- 不在 River Payload、URL、日志或前端状态中携带原始正文和凭据。
- 不新增采集微服务、Kafka、Temporal、独立调度系统或第二套 Schema。
- Connector/Collector 不执行 AI 研判，不计算或提交权威 Event 生命周期、Heat 或 Evidence State。
- 不保证已经建模的来源默认可用；真实授权和能力是上线门禁。

## 依赖、风险与待决策

| ID | 项目 | 处理要求 |
|---|---|---|
| `RSK-002-001` | 三个 P0 来源的授权、成本或配额可能变化 | G2 前保存来源审批、额度和降级证据，不能用 Mock 代替上线门禁 |
| `RSK-002-002` | 某些来源无稳定发布时间或外部 ID | 保持空值，并建立来源专用规范化和 Fixture |
| `RSK-002-003` | 原始响应 30 天候选保留与长期追溯冲突 | 原始对象期限、元数据长期保留、报告证据例外和删除告知必须共同批准 |
| `RSK-002-004` | 重试和 Checkpoint 错误会造成漏采或重复 | 用时间窗、版本、Target 与页游标的组合幂等，并做故障注入 |
| `RSK-002-005` | Analyst 所有权过滤或前后端权限发生漂移 | 以应用层所有权授权、路由负向测试、生成客户端和四角色 UAT 防回归 |

待决策项包括默认扫描窗口与时区、每类来源预算、P0 原始证据保留期限、历史回填是否提供独立完成通知，以及 P0 三来源的正式验收环境。历史回填不触发普通实时热点通知已由 `FR-002-014` 固定。

## 验收标准

| ID | Given | When | Then |
|---|---|---|---|
| `AC-002-001` | 一个有创建权限的用户和含来源差异的 Monitor Intent | 创建草稿、生成来源级编译预览、发布、暂停、恢复、修改并归档 | 相同输入与版本产生相同 Compiled Profile 快照；每次发布绑定不可变版本/快照，旧运行仍引用旧版本，重复时间窗不产生重叠副作用 |
| `AC-002-002` | 来源缺少能力、权利、凭据、预算或安全端点条件之一，且存在来源、凭据、预算、扫描和证据管理动作 | 用户测试连接、系统准备采集或授权用户执行管理动作 | 不合规请求在受控边界被拒绝并返回稳定原因；全部管理动作有脱敏审计，日志不包含 Token、Cookie、完整敏感正文或上游原始错误 |
| `AC-002-003` | 一轮包含三个正式来源的扫描 | 一个来源限流、一个成功、一个合法返回空 | Target 事实分别保存，Application 派生 `run_outcome=partial_success`；成功内容继续进入后续链路，空结果按成功零条处理，各来源状态和耗时可见，数据库未新增冲突的整体状态枚举 |
| `AC-002-004` | 任一已接受 Document，以及保留期内、已过期和经批准长期保留的 Evidence Fixture | 用户查看证据、执行完整性检查或保留任务 | 保留期内可定位 Observation、来源连接和 SHA-256 一致的 MinIO 对象；到期后仍保留元数据、Hash、删除审计并显示 UI 过期态；批准例外保留对象与批准依据，不一致时不得作为有效证据 |
| `AC-002-005` | 含重复 URL、重复正文、未知发布时间和多时区的固定 Fixture | 执行标准化与去重 | 精确重复不创建新当前 Document，近重复保留分组理由，未知发布时间仍为空，UTC 与原始时区可追溯 |
| `AC-002-006` | 采集任务正在分页或写入证据 | Worker 在每个关键步骤被终止并恢复，或同一请求重复提交 | 任务从 Checkpoint 幂等继续，不重复当前内容、对象或业务副作用，历史尝试仍可诊断 |
| `AC-002-007` | Viewer、Analyst、Editor、Admin 访问 Monitor、来源、扫描和证据页面，且相关接口发生契约变更 | 分别触发正常、空、加载、错误和越权场景并重新生成契约 | 页面与直接 API 权限一致，五种状态可辨识，任一角色都不能读取凭据明文或任意对象 Key；DTO、错误码、Swaggo、发布 OpenAPI `docs/openapi/swagger.json`、生成客户端和契约测试无漂移 |
| `AC-002-008` | 已记录当前本机或固定 CI 环境、数据 Fixture、并发和网络条件 | 执行 50 Monitor、100 连接、日等效候选量和 20 并发扫描基线 | 输出吞吐、队列、失败、P50/P95/P99 和资源报告；报告只代表所记录环境，不因缺少另一套硬件阻断本轮交付 |
| `AC-002-009` | RSS/HN/X 的版本化 Resource Limit Profile，以及连接、读取、墙钟、页数、条数、累计字节、重试和每日配额八类边界 Fixture | 分别执行 `limit-1 / limit / limit+1`，并在分页、重试和配额跨日边界恢复 | 八类限制均有显式有限值；越界在下一次拨号、翻页、重试、对象写入或下游排队前返回稳定原因，已提交 Target/Checkpoint/Evidence 不回滚且不新增越界副作用 |
