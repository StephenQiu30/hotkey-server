# 集中测试资产与目录边界优化

## 1. 背景与目标

当前仓库已采用 `cmd/hotkey`、`internal/bootstrap`、`internal/platform`、`internal/shared` 和按业务域划分的 `internal/modules`。本任务不评价或调整这些生产包的内部实现，只处理已确认的测试资产位置问题：五个业务包下的 `testdata` 只被测试读取，却位于 `internal/modules` 生产树，与本仓库“测试源码、fixture 和运行器集中到 `test/`”的约束不一致。

目标是在不改变业务包、Go import path、API、Schema 和运行时行为的前提下，将纯测试 fixture 迁入 `test/_suite` 的镜像包路径，由 runner 在 `go test` 期间临时物化包内 `testdata`。

## 2. 边界

- 迁移 event、ingestion、intelligence、source/rss 和 source/hackernews 的 10 个纯测试 fixture 文件。
- `test/runner` 同时发现 `_test.go` 文件与 `testdata` 目录，按 `test/_suite` 相对路径物化，并在正常成功、Go 子进程非零退出或物化冲突时清理。
- 架构测试禁止 `test/` 外的 `testdata` 目录；运行时需要的 JSON Schema 继续位于 `internal/modules/intelligence/schemas`，不得误移。
- 同步 AGENTS 和中英文 README 的目录契约。

## 3. 非目标

- 不改动 `cmd/internal/modules/platform/shared` 的生产分层，不新增 `pkg` 或微服务目录。
- 不迁移运行时 JSON Schema、OpenAPI、数据库 Schema 或业务实现。
- 不增加 shell 启动脚本，不改变 GoLand 单入口。
- 不为并发执行多个 runner 引入跨平台锁或新依赖；本任务只保证单个 runner 内的原子失败清理。
- 不在本任务迁移 `internal/shared/repository` 中的 GORM/pgx 实现；该生产边界问题作为独立后续 PRD/Plan 处理。

## 4. 验收条件

1. `find internal -type d -name testdata` 无输出，10 个 fixture 全部位于对应 `test/_suite/.../testdata` 镜像路径。
2. runner 测试证明它只收集 `_test.go` 和整个 `testdata` 目录，冲突或中途失败不留残留链接。
3. 原有 fixture 读取路径不改，10 个 fixture 的全部实际消费用例定向通过；相关六包全量测试在隔离 PostgreSQL 可用时执行，否则明确记录为 blocked。
4. 架构门禁能拒绝任何 `test/` 外新增的 `testdata`。
5. 构建、lint、仓库验证、Schema/OpenAPI 差异检查通过，未留下测试符号链接或根目录产物。
6. `internal/modules/intelligence/schemas` 零差异，SchemaRegistry 相关测试通过。

## 5. 依据

- Go 官方 `go test` 文档明确 `testdata` 是测试辅助数据目录，Go 工具会忽略它。
- Go 官方仓库 `cmd/go/testdata` 将测试脚本与支持文件共同管理。
- Ardan Labs Service 和 ThreeDotsLabs Wild Workouts 验证了按业务能力保持生产包边界的做法；本项目不照搬其目录名称。
