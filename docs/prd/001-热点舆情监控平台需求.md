# 热点舆情监控平台需求

日期：2026-09-25。本文是 HotKey 唯一的产品需求事实源。产品目标收敛为三个交付物：**日报、周报、Obsidian 知识库**；采集、分析、调度都为这三者服务。

v2.1 在 v2.0 基础上吸收了用户 2026-09-25 的决策（采集栈、Codex 模型、飞书+邮件、Obsidian 知识库）、实测结果和 Codex 设计评审。v1.7 旧需求见 Git 提交 `3a72611a`，对应关系见第 10 节。

## 1. 需求结论

HotKey 按关键词持续收集各平台的相关帖子和评论，每天、每周自动生成舆情报告推送到飞书和邮箱，并把报告、事件和精选内容沉淀到本地 Obsidian 知识库，供浏览、检索和提问。

三条原则：

1. **先让日报可信地按时到达**，其余能力按它反推；日报在模型不可用时也必须送达（降级为模板版）。
2. **数字由程序算，模型只做判断和写作**；报告里的每个数字、每条观点都能点回原帖。
3. **来源逐个接、逐个验收**；一个来源接通不代表其他来源可用，缺失的来源在报告里写明。

## 2. 用户与场景

使用性质：**个人/非商业研究**（DEC-001-108）。部署在本机，沿用现有单 owner 登录。

| 角色 | 说明 |
|---|---|
| 研究者（主要用户） | 配置关注的品牌/产品/话题，读日报周报，在 Obsidian 里浏览和提问 |
| 报告订阅者 | 只接收飞书/邮件推送的人，不需要登录 |

核心场景：

1. **早读**：09:00 飞书收到昨日日报，3 分钟内知道发生了什么、热度多高、大家怎么看、有没有风险。
2. **周会**：周一收到周报，看到本周趋势、主要事件和与上周对比。
3. **追查**：在 Obsidian 里从日报点进事件、帖子和主题笔记；或向 HotKey 提问，答案连同出处写回 Obsidian。
4. **突发**：负面讨论短时间激增时立即收到告警（P4）。

## 3. 业务需求

| ID | 业务需求 | 成功判断 |
|---|---|---|
| BR-001-101 | 持续、及时地收集关键词相关的帖子和评论 | 每个主题按频率自动采集；每个来源的覆盖情况和缺口可见 |
| BR-001-102 | 把分散的内容整理成观点和事件 | 每条相关内容有情感和摘要；P2 起跨平台归并为事件 |
| BR-001-103 | 按时交付可直接阅读、可追溯的报告 | 日报/周报按时推送；数字和观点都能定位到原帖 |
| BR-001-104 | 沉淀可浏览、可提问的本地知识库 | 报告、事件、主题、精选帖子写入 Obsidian；提问得到带出处的回答 |
| BR-001-105 | 长期稳定、低成本运行 | 只用本地自建服务和本机 Codex 额度；限流时延后而不是失败或超支 |

## 4. 来源范围

每个来源分别验收 **搜索 / 帖子 / 评论 / 热榜** 中它支持的能力。

| 档位 | 来源 | 接入方式 | 能力 | 阶段 |
|---|---|---|---|---|
| A | Hacker News | Algolia 公开 API | 搜索、帖子、评论、楼中楼 | P1（首个竖切） |
| A | Google News | 搜索 RSS | 搜索、帖子 | P1 |
| A | 新闻网页搜索 | 本地 SearXNG（DuckDuckGo News 引擎，唯一带发布时间的引擎） | 搜索、帖子 | P1 |
| A | 行业媒体/博客 | 指定 RSS/Atom 或 RSSHub 路由 | 帖子 | P1 |
| B | B 站、微博 | MediaCrawler（扫码登录态，服务端保存） | 搜索、帖子、评论、楼中楼 | P2 |
| B | 微博热搜、知乎热榜、B 站排行 | RSSHub | 热榜 | P2 |
| B | 知乎 | MediaCrawler 或 RSSHub（P2 实测后定） | 搜索、帖子、评论 | P2 |
| C | Reddit | 官方 OAuth API（匿名 RSS 实测易 429，不计为 Reddit 能力） | 搜索、帖子、评论 | P4 |
| C | 小红书、抖音 | MediaCrawler | 搜索、帖子、评论 | P4 |
| C | 微信公众号 | RSSHub 路由 | 帖子 | P4 |
| C | X | 官方 API（OPEN-001-104） | 搜索、帖子、回复 | P4 |

约束：只采集公开或获授权的数据；遵守平台频率限制；登录态与凭据只存服务端；RSS/搜索地址只允许预设或白名单中的主机。

## 5. 功能需求

阶段：P1 = 第 1—2 周，P2 = 第 3—4 周，P3 = 第 5—6 周，P4 = 之后逐项。

| ID | 阶段 | 功能 | 要求 |
|---|---|---|---|
| FR-001-101 | P1 | 监控主题 | 关键词规则（任一/全部/排除）、来源选择、采集频率、报告时间、推送对象。复用现有主题管理并补齐后四项 |
| FR-001-102 | P1 | 定时采集 | 每个主题 × 来源按频率（默认 30 分钟，最短 10 分钟）自动采集；可手动立即运行、暂停；失败有限重试 |
| FR-001-103 | P1 | 帖子采集 | 保存平台、原生 ID、链接、标题、正文、作者 ID 与昵称、发布时间、互动指标；重复采集只追加指标观察。**来源没有发布时间时，以首次发现时间入库并标注"时间依据=发现时间"**，不丢弃、不伪造发布时间 |
| FR-001-104 | P1 | 评论采集 | 对命中且热度靠前的帖子采集评论和楼中楼，保留父子关系；每帖默认最多 200 条一级评论、每条 20 条回复 |
| FR-001-105 | P1 | 相关性判断 | 关键词规则初筛 → 模型判断是否真正相关（排除同名歧义）并给出理由 |
| FR-001-106 | P1 | 摘要与情感 | 每条相关帖子一句话摘要和情感（正/中/负）；评论按帖子批量判断情感并提取主要观点 |
| FR-001-107 | P1 | 日报生成 | 每天设定时间（默认 09:00 Asia/Shanghai）生成前一自然日日报，内容见 6.1。模型不可用时生成模板版日报，照常推送 |
| FR-001-108 | P1 | 报告推送 | 飞书群机器人与 SMTP 邮件，P1 结束前两者都可用（先飞书）；记录每次发送状态；**同一报告对同一接收方不重复推送**，发送结果不确定时不自动重发、标记待人工确认 |
| FR-001-109 | P1 | 报告存档 | 报告存数据库并写入 Obsidian（见 FR-001-114）；Web 工作台可按主题和日期查看 |
| FR-001-110 | P2 | 事件归并 | 相似帖子跨平台聚合为事件：标题、摘要、首次出现、平台分布、热度、情感分布、代表帖子与评论；支持人工合并/拆分 |
| FR-001-111 | P2 | 热度与升温 | 事件热度综合互动量、帖子数、来源权重；识别"新出现"和"快速升温"；口径写入报告附注 |
| FR-001-112 | P2 | 热榜发现 | 采集微博/知乎/B 站热榜，命中主题关键词的条目进入事件；热榜条目以观察时间计 |
| FR-001-113 | P3 | 周报生成 | 每周一 09:00 生成上周周报，内容见 6.2 |
| FR-001-114 | P1—P3 | Obsidian 知识库 | 写入现有 vault `~/Desktop/Markdown/Obsidian` 的 `HotKey/` 子目录：P1 日报；P2 事件与精选帖子（被报告或事件引用的）；P3 周报与主题笔记。笔记间用双链相连、带 frontmatter；**用户在笔记"我的笔记"区块写的内容永不被覆盖** |
| FR-001-115 | P3 | 知识库问答 | 向 HotKey 提问（Web 或 CLI），HotKey 检索已采集资料后由 Codex 回答，逐句标注出处并说明资料时间范围；资料不足时明确说不足；问答结果写入 Obsidian `HotKey/问答/` |
| FR-001-116 | P3 | 导出 | 报告导出 Markdown/PDF；原始数据导出 CSV/JSON |
| FR-001-117 | P4 | 突发告警 | 负面内容或事件热度 1 小时内超阈值即时推送，带冷却时间 |
| FR-001-118 | P4 | 指定账号追踪 | 关注指定作者，其新帖全部收录，不受关键词限制 |
| FR-001-119 | P4 | C 档来源 | Reddit、小红书、抖音、公众号、X 逐个接入，逐个验收 |

## 6. 报告内容

### 6.1 日报

| 区块 | 阶段 | 内容 |
|---|---|---|
| 今日概览 | P1 | 相关帖子数、评论数、平台分布、情感分布，与前一日对比 |
| 重点内容 Top 10 | P1 | 按互动量排序的相关帖子：标题、一句话摘要、情感、平台、链接、1—2 条代表评论 |
| 风险提示 | P1 | 负面且高互动的内容及理由 |
| 值得关注的声音 | P1 | 高互动的观点性帖子或评论（原文摘录 + 链接） |
| 重点事件 / 新出现事件 | P2 | 事件归并上线后替换"重点内容"：事件标题、摘要、热度、情感、平台、代表帖子与评论 |
| 数据覆盖说明 | P1 | 各来源本时间窗的采集成功情况、缺口时段、按发现时间计入的条数；注明"样本观察，不代表全网" |

时间口径：以发布时间落在时间窗内为准；没有发布时间的内容以首次发现时间计，并在覆盖说明中单列条数。

### 6.2 周报

本周概览与上周对比、每日趋势（帖子量与情感）、本周 Top 事件及时间线、持续发酵与已平息的事件、主要观点变化、下周建议关注项、数据覆盖说明。

## 7. 非功能需求

| ID | 要求 | 验收口径 |
|---|---|---|
| NFR-001-101 | 可追溯 | 报告中每个数字、观点都能定位到具体帖子/评论、采集时间和分析版本；同一报告可按冻结的输入重新生成 |
| NFR-001-102 | 数据正确 | 同平台同 ID 唯一；评论父子关系正确；缺失值与 0 区分；时间存 UTC、按 Asia/Shanghai 展示；发布时间与发现时间分开记录 |
| NFR-001-103 | 时效 | 有发布时间的内容从发布到入库中位延迟 ≤ 采集频率 + 10 分钟；日报在设定时间后 15 分钟内送达 |
| NFR-001-104 | 可靠执行 | 重复调度、重试、进程重启不产生重复数据、重复推送或静默丢任务 |
| NFR-001-105 | 故障隔离 | 单个来源或模型故障不阻断其他来源和报告；报告注明缺失 |
| NFR-001-106 | 资源控制 | 模型调用有并发和频次上限；账号限流时任务延后重试，不改用付费接口；每次调用有记录 |
| NFR-001-107 | 安全 | 凭据不进前端、日志、代码库和模型输入；模型进程只拿到最小环境变量；外部正文按不可信内容处理（提示注入防护）；RSS/搜索只访问白名单主机 |
| NFR-001-108 | 分析质量 | 相关性准确率 ≥ 90%、情感准确率 ≥ 80%（每主题人工抽检 100 条） |
| NFR-001-109 | 知识库安全写入 | Obsidian 写入原子化；只写 `HotKey/` 子目录；不覆盖用户区块；vault 不可写时报告照常推送 |
