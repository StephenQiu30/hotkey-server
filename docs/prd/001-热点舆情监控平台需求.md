# 热点舆情监控平台需求

日期：2026-09-25。本文是 HotKey 唯一的产品需求事实源，取代 v1.7《热点事件监控平台功能与非功能需求》及 003—045 逐项 PRD。v2.0 把产品目标收敛为三个交付物：**日报、周报、知识库**；采集、分析和调度都为这三者服务。

旧版需求的完整文本见 Git 提交 `3a72611a`；旧需求与本文的对应关系见第 9 节。

## 1. 需求结论

HotKey 按用户配置的关键词，持续收集各主流平台的相关帖子和评论，整理成可检索的知识库，每天和每周自动生成舆情报告并推送给用户，让用户不看原平台也能及时掌握最新消息和舆情变化。

v1.7 的问题：P0 功能 18 项、质量要求 16 项，共 34 项必须验收，但没有把"日报/周报"列为需求，知识问答排在 P2；5 个月过去，验收仍为 0/34。v2.0 的调整：

1. 以"每天早上收到一份可信的日报"作为第一验收目标，其余能力按它反推。
2. 质量要求只保留影响日报可信度和系统能否持续运行的部分，其余降为后续改进。
3. 来源按接入难度分档，先用能立即取得数据的来源跑通全链路，难接入平台逐个补充。

## 2. 用户与场景

| 角色 | 说明 |
|---|---|
| 舆情负责人（主要用户） | 产品经理、市场、公关；配置关注的品牌/产品/话题，阅读日报周报，按需检索历史 |
| 报告订阅者 | 团队成员；只接收日报/周报推送，偶尔打开原文链接 |
| 管理员 | 部署、配置来源凭据和模型/推送渠道，处理采集故障 |

首版按单个团队自建部署；账号体系沿用现有单 owner 登录，订阅者通过推送渠道接收报告，不要求登录。

核心场景：

1. **早读**：09:00 收到昨日日报，3 分钟内知道"发生了什么、热度多高、大家怎么看、有没有风险"。
2. **周会**：周一收到周报，看到本周趋势、主要事件时间线和与上周对比。
3. **追查**：看到某个事件，在知识库里检索相关帖子和评论，或直接提问"用户对 X 功能的主要抱怨是什么"，得到带出处的回答。
4. **突发**：负面讨论短时间激增时，不等日报，立即收到告警（P2 阶段）。

## 3. 业务需求

| ID | 业务需求 | 成功判断 |
|---|---|---|
| BR-001-101 | 持续、及时地收集关键词相关的帖子和评论 | 每个主题按设定频率自动采集；日报时间窗内的数据覆盖情况可见 |
| BR-001-102 | 把分散的内容整理成事件和观点 | 同一事件跨平台、跨帖子合并；每个事件有摘要、热度、情感和代表评论 |
| BR-001-103 | 定期交付可直接阅读的舆情报告 | 日报/周报按时生成并推送；内容全部可追溯到原帖 |
| BR-001-104 | 沉淀可检索、可问答的知识库 | 历史帖子、评论、事件、报告可按关键词和语义检索；问答附出处 |
| BR-001-105 | 在可控成本内长期运行 | 付费来源和模型调用有月度上限；超限停止并提醒，不静默超支 |

## 4. 来源范围

来源按接入难度分三档，逐档交付。每个来源分别验收"关键词搜索 / 帖子 / 评论 / 热榜"四项能力，不以某个来源接通代表其他来源可用。

| 档位 | 来源 | 接入方式 | 需要评论 | 交付阶段 |
|---|---|---|---|---|
| A 公开可用 | RSS/Atom（行业媒体、官方博客、新闻站）、Hacker News、Reddit、Google News | 公开 API / RSS；Reddit 需官方 OAuth 应用 | HN、Reddit 需要 | P1 |
| B 公开页面/接口 | B 站、微博、知乎 | 公开 Web 接口 + 现有 Playwright 浏览器服务 | 需要 | P2 |
| C 需登录或付费 | X（官方 API）、小红书、抖音、微信公众号 | 付费 API、登录态浏览器或第三方数据服务 | X、小红书、抖音需要 | P4 |

约束：只采集公开或获授权的数据；遵守平台频率限制；登录态和凭据只存服务端。C 档的接入方式见 OPEN-001-103。

## 5. 功能需求

优先级按交付阶段标注：P1 = 第 1—2 周，P2 = 第 3—4 周，P3 = 第 5—6 周，P4 = 之后逐项交付。

| ID | 阶段 | 功能 | 要求 |
|---|---|---|---|
| FR-001-101 | P1 | 监控主题 | 主题包含关键词规则（任一命中/全部包含/排除）、来源选择、采集频率、报告时间和接收人。复用现有主题管理 |
| FR-001-102 | P1 | 定时采集 | 每个主题 × 来源按频率（默认 30 分钟，最短 10 分钟）自动生成采集任务；支持手动立即运行、暂停；任务失败自动有限重试 |
| FR-001-103 | P1 | 帖子采集 | 保存平台、原生 ID、链接、标题、正文、作者（ID 与昵称）、发布时间、互动指标（赞/评/转/浏览/播放）；同一帖子重复采集只更新指标，保留指标历史 |
| FR-001-104 | P1 | 评论采集 | 对命中且热度达到阈值的帖子采集评论和楼中楼，保存父子关系；每帖默认最多 200 条（按热门排序），可配置 |
| FR-001-105 | P1 | 相关性过滤 | 先用关键词规则过滤，再由模型判断是否真正相关（去除同名歧义）；保留"为什么相关"的依据 |
| FR-001-106 | P1 | 内容摘要与情感 | 对每条相关帖子生成一句话摘要和情感（正/中/负）；评论按帖子批量判断情感并提取主要观点 |
| FR-001-107 | P1 | 日报生成 | 每天按主题在设定时间（默认 09:00，Asia/Shanghai）生成前一自然日的日报，内容见 5.1 |
| FR-001-108 | P1 | 报告推送 | 支持邮件（SMTP）与飞书、企业微信群机器人 Webhook，至少一种可用；记录发送状态，失败重试 3 次 |
| FR-001-109 | P1 | 报告存档与查看 | Web 工作台可按主题、日期查看历史报告，报告中每条引用可点回原帖 |
| FR-001-110 | P2 | 事件归并 | 把相似帖子（跨平台）聚合为事件：事件标题、摘要、首次出现时间、平台分布、热度、情感分布、代表帖子与代表评论；支持人工合并/拆分 |
| FR-001-111 | P2 | 热度与升温 | 事件热度综合互动量、帖子数、来源权重；识别"新出现"和"快速升温"事件；计算口径写入报告附注 |
| FR-001-112 | P2 | 热榜发现 | 采集 B 站、微博、知乎热榜，命中主题关键词的热榜条目进入事件 |
| FR-001-113 | P3 | 周报生成 | 每周一生成上周周报，内容见 5.2 |
| FR-001-114 | P3 | 知识库检索 | 对帖子、评论、事件、报告做全文 + 语义检索；按主题、平台、时间、情感、事件筛选 |
| FR-001-115 | P3 | 知识库问答 | 用自然语言提问，回答基于已采集资料，逐句标注出处，并说明资料的时间范围；资料不足时明确说"不足" |
| FR-001-116 | P3 | 数据导出 | 报告导出 Markdown/PDF；原始数据导出 CSV/JSON |
| FR-001-117 | P4 | 突发告警 | 负面帖子或某事件热度在 1 小时内超过阈值时即时推送，带冷却时间，避免刷屏 |
| FR-001-118 | P4 | 指定账号追踪 | 关注指定作者（如竞品官方号、KOL），其新帖全部收录，不受关键词限制 |
| FR-001-119 | P4 | C 档来源接入 | X、小红书、抖音、公众号逐个接入，每个平台单独验收 |

### 5.1 日报内容

| 区块 | 内容 |
|---|---|
| 今日概览 | 相关帖子数、评论数、平台分布、情感分布，以及与前一日的变化 |
| 重点事件 Top 5—10 | 事件标题、2—3 句摘要、热度、情感、涉及平台、2—3 条代表帖子链接、1—2 条代表评论 |
| 新出现事件 | 首次出现于本时间窗的事件 |
| 风险提示 | 负面占比高或负面快速增长的事件，以及理由 |
| 值得关注的声音 | 高互动的观点性帖子或评论（原文摘录 + 链接） |
| 数据覆盖说明 | 各来源本时间窗内的采集成功率、失败或缺口时段；样本不代表全网 |

报告正文由模型根据结构化数据撰写，所有数字直接取自数据库，不由模型编造；每条事件和观点都附原帖链接。

### 5.2 周报内容

本周概览及与上周对比、每日趋势图（帖子量与情感）、本周 Top 事件及其时间线、持续发酵的事件、已平息的事件、主要观点变化、下周建议关注项、数据覆盖说明。

## 6. 非功能需求

v1.7 的 16 项质量要求保留以下 8 项作为当期要求，其余降级为改进项（见第 9 节）。

| ID | 要求 | 当期验收口径 |
|---|---|---|
| NFR-001-101 | 可追溯 | 报告中每个事件、观点、数字都能定位到具体帖子/评论和采集时间 |
| NFR-001-102 | 数据正确 | 同平台同 ID 唯一；评论父子关系正确；缺失值与 0 区分；时间统一存 UTC、按 Asia/Shanghai 展示 |
| NFR-001-103 | 时效 | 从帖子发布到入库的中位延迟 ≤ 采集频率 + 10 分钟；日报在设定时间后 15 分钟内送达 |
| NFR-001-104 | 可靠执行 | 重复调度、重试、进程重启不造成重复数据或任务静默丢失（复用现有任务底座） |
| NFR-001-105 | 故障隔离 | 单个来源或模型故障不阻断其他来源和报告生成；报告注明缺失的来源 |
| NFR-001-106 | 成本控制 | 付费来源与模型调用各有月度上限；达到 80% 提醒，100% 停止付费调用，免费来源不受影响 |
| NFR-001-107 | 安全 | 凭据、Cookie、Token 不出现在前端、日志和代码库；外部正文按不可信内容处理（含提示注入防护） |
| NFR-001-108 | 分析质量 | 相关性判断准确率 ≥ 90%、情感判断准确率 ≥ 80%（每主题人工抽检 100 条）；报告明确"样本观察，不代表全网民意" |

## 7. 验收标准

| ID | 对应 | 验收场景 |
|---|---|---|
| AC-001-101 | FR-101/102/103 | 新建主题后 1 个采集周期内，A 档来源出现真实帖子；连续运行 72 小时无人工干预 |
| AC-001-102 | FR-104 | 选 10 条高热帖子，评论条数、楼中楼父子关系与原平台抽样一致 |
| AC-001-103 | FR-105/106、NFR-108 | 人工抽检 100 条，相关性与情感准确率达标 |
| AC-001-104 | FR-107/108/109、NFR-101/103 | 连续 3 天在 09:15 前收到日报；随机点 10 条引用均能打开原帖 |
| AC-001-105 | FR-110/111/112 | 同一新闻在 3 个平台的帖子合并为 1 个事件；新事件、升温事件标注正确 |
| AC-001-106 | FR-113 | 周一 09:15 前收到周报，数字与当周日报合计一致 |
| AC-001-107 | FR-114/115 | 10 个测试问题中，≥ 8 个回答正确且出处可点开；资料外问题回答"不足" |
| AC-001-108 | NFR-105/106 | 人为停掉一个来源或模型，日报仍生成并注明缺失；模拟费用达上限后付费调用停止 |
| AC-001-109 | FR-117/118/119 | 每个 P4 能力和每个 C 档平台单独验收 |
