# X 热点发现与持续热度观测

## 用户问题

用户希望以 X 为主要信息源，持续获取与自己监控意图相关、正在升温的具体事件，而不是依赖大量 RSS 或通用网页聚合。当前 HotKey 能从 X Recent Search 发现新 Post，但发现后通常不再刷新互动指标，当前 MicroEvent Heat v2 也不会被指标变化驱动，导致“热点”更接近首次发现列表，而不是持续变化的事件热度。

参考项目证明了 Top+Latest、低噪筛选、热度排序和即时通知对个人热点工作流有直接价值；但它使用第三方 X API、旧搜索语法、固定绝对量阈值、蓝 V 加权和真假布尔值，并跳过已入库内容。这些实现不符合 HotKey 的官方来源、持续观测和证据语义，不能原样移植。

## 产品目标

- X 可以作为 Monitor 的唯一来源完成发现、事件化、热度计算与通知。
- 首次由官方 Recent Search `relevancy` 有界补齐近七天相关候选，日常由 `recency` 发现新 Post；已知且仍相关的 Post 由官方 Post Lookup 持续刷新公开指标。
- 热度以具体 MicroEvent 为单位，反映窗口内传播增量、谱系、报道速度、覆盖和新鲜度。
- 用户能按服务端 Heat v2 排序查看正在升温的事件，并理解分数窗口与降级原因。
- 全链路不依赖 RSS 回退，不输出真假结论，不使用认证状态作为热度或可信度加权。

## 范围

### P0：X 契约正确性

- 修正 X Recent Search 当前官方参数与字段映射。
- 支持 `note_tweet` 长帖正文和 `referenced_tweets` 关系。
- 首次发布/启用或显式重建时执行一次有界 `relevancy` 补齐；它只扩大相关候选召回，不作为热度结论。
- 保持分页 checkpoint、原始证据、敏感/withheld、安全与错误分类不回退。

### P1：持续指标与 Heat v2

- 对符合资格的已知 X Post 执行有界官方批量 Lookup。
- 更新 Content 当前指标并追加指标快照，不制造新正文版本。
- 指标提交后只重算当前 MicroEvent 1h/6h/24h Heat，不扩大 legacy Event 双写。
- Heat v2 互动改为窗口增量和来源内滚动总体归一化；缺失保持 null。

### P1：热点排序与解释

- MicroEvent 服务端支持 `heat/latest` 稳定排序与绑定条件的游标。
- 事件列表展示 Heat、窗口、加速度、独立内容起源与指标降级原因。

## 用户故事

- 作为用户，我只选择 X 来源也能看到与监控目标相关的事件，并优先看到正在升温的事件。
- 作为分析人员，我能区分“首次就有高绝对互动”和“最近一小时互动快速增长”，而不是把单条 Post 永远视为满分。
- 作为内容核查人员，我能从热点事件回到 X 原始 Post、归档证据和具体指标窗口。
- 作为管理员，我能限制 X 刷新频率和预算，并在限流、认证失败或指标过期时看到明确状态。

## 功能要求

- FR-033-1：X 连接器必须使用官方 Recent Search/Lookup、Bearer 凭据和当前 `tweet.fields` 契约，不调用第三方 X 数据服务或网页回退。
- FR-033-2：长帖优先使用 `note_tweet.text`；引用/回复关系使用 `referenced_tweets`；缺失与显式零指标保持不同。
- FR-033-3：首次发布/启用或显式重建可执行一次有界 `relevancy` 七天补齐且不得推进日常 checkpoint；日常 `recency` 继续单调发现新 Post，不能为了刷新指标回退 checkpoint 或周期性重扫完整七天窗口。
- FR-033-4：系统按来源预算批量刷新仍在观察期、关联当前 Monitor 或 MicroEvent 的已知 X Post；同一 Post 跨 Monitor 只刷新一次。
- FR-033-5：重复观测必须复用 SourceObservation、Content 和 DocumentVersion，只追加原始响应关联与指标快照。
- FR-033-6：Content 指标变化必须触发当前 MicroEvent Heat 重算且不得新增 legacy Event/Heat 写入；失败可重试且不回滚指标事实。
- FR-033-7：Heat v2 互动使用窗口 baseline/latest 增量，并按来源连接与内容类型的滚动总体归一化；不得使用事件内绝对最大值。
- FR-033-8：没有完整两期指标、能力不支持或计数回退时互动为 null；首次绝对量只能决定刷新预算优先级并显示 `metrics_warming_up`，小总体降级必须带 reason code。
- FR-033-9：MicroEvent 列表支持服务端 Heat/最新排序和稳定游标；默认按 Heat，缺快照事件排后。
- FR-033-10：事件列表与详情显示 Heat 窗口、加速度、谱系、最新观测和降级原因，前端不计算热度。
- FR-033-11：管理员可配置 X 持续刷新开关、间隔、单轮最大 Post 数和每日请求预算；默认保守关闭。
- FR-033-12：仅配置 X 的 Monitor 不得因 RSS 缺失而失败；X 故障时不自动转向 RSS、网页抓取或第三方 API。

## 非功能要求

- X 请求严格遵守固定官方端点、TLS、DNS/SSRF、重定向、响应大小、限流和凭据脱敏边界。
- 批量 Lookup 每次不超过官方 100 ID 上限；部分失败不阻塞成功项，429/401/403 有稳定退避或停用行为。
- 指标刷新与 Heat 重算具备持久任务、幂等键、可观测状态和重放测试。
- 热度列表游标绑定排序、过滤和冻结时间；静态数据跨页不重不漏。
- Schema、OpenAPI、生成 Client、后端和前端测试同步；不创建第二套 Hotspot 或指标事实源。

## 非目标

- 不扩展 RSS 数量，不删除既有授权来源，也不做全网爬虫。
- 不实现 X 全球 Trends、全量社交图谱、情感分析或用户画像。
- 不使用 `isReal`、真假概率、蓝 V、粉丝数或来源信誉分决定入库、热度或告警。
- 不移植参考项目的固定阈值、绝对热度公式、旧搜索运算符和内存全量分页。
- 不改变 032 的相关性、事件、热度、证据覆盖与正文完整度相互独立原则。
- 033 不单独执行 legacy 和非 X 数据删除；单 ID、停止双写、运行面退出和删除门槛由 [034](034-X热点核心链路收敛与遗留系统清理.md) 负责。

## 验收标准

- AC-033-1：X 官方请求契约、长帖、引用关系、分页、原始证据和安全回归全部通过。
- AC-033-2：同一 Post 两次指标观测形成一份内容事实和至少两期快照，第二期能反映公开指标变化。
- AC-033-3：新的指标快照驱动 MicroEvent 1/6/24h Heat v2，互动分使用增量且不再单帖恒满分。
- AC-033-4：缺 baseline、指标回退、小总体和 X 限流均显示明确降级，不伪造零或当前值。
- AC-033-5：事件列表按 Heat 稳定排序，窗口和组成可解释，前端没有本地热度公式。
- AC-033-6：X-only Monitor 的发现到通知链路通过；关闭持续刷新可无损回退到现有 Recent Search 行为。
