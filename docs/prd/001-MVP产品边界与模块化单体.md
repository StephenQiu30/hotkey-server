# MVP产品边界与模块化单体

## 用户问题

Go 模块化单体、PostgreSQL、River、Next.js 工作台已经形成主链路，但现有能力与“鱼皮热点监控完整 MVP”的对标范围尚未由一套新文档统一约束。

## 产品目标

在不推翻现有可靠底座的前提下，形成一个可自托管、可审计、以事件为中心的热点监控 MVP，并明确当前事实与目标能力的边界。

## 范围

- 统一能力地图与依赖顺序
- 模块所有权和调用边界
- 当前/目标差距标注
- 跨端契约和事实源规则

## 用户故事

- 作为普通用户，我能够看懂当前状态、结果来源和下一步动作。
- 作为编辑者，我能够在权限范围内完成配置或处理任务，并获得明确反馈。
- 作为管理员，我能够治理配置、失败、成本与审计，而不直接修改数据库事实。

## 功能要求

- FR-001-1：保持单仓库、Go 单二进制模块化单体和 Next.js App Router，不引入微服务、Kafka 或第二套 Schema。
- FR-001-2：PostgreSQL 保存业务事实，MinIO 保存原始证据，River 执行持久任务；Redis 仅用于短期状态。
- FR-001-3：功能链路固定为来源→采集→标准化→相关性→事件→热度→告警→报告；任何新来源只能通过 Source 端口接入。
- FR-001-4：MVP 对标功能按 001–028 独立交付，目标设计不得伪装成当前实现。

## 非功能要求

- 所有写操作具备认证、授权、输入校验、幂等或乐观锁保护和审计。
- 列表支持稳定分页；第三方调用具备超时、配额、重试和降级。
- Web 覆盖桌面与移动端，并满足键盘操作、可见焦点和减弱动效。

## 非目标

不使用未授权抓取补齐来源能力，不为本条引入与仓库规范冲突的新基础设施。

## 验收标准

- AC-001-1：所有交付项均有同编号 Design、PRD、Plan
- AC-001-2：架构依赖继续满足 transport→application→domain
- AC-001-3：代码、Schema、OpenAPI 和文档只有一套事实源
