# 智能研判事件热度与人工治理

关联文档：[Design](../design/003-智能研判事件热度与人工治理设计.md) · [Plan](../plans/003-智能研判事件热度与人工治理计划.md)

## 用户问题与当前事实

关键词命中不等于与 Monitor 相关，单篇内容不等于现实事件，绝对互动量也不等于正在升温。研究人员需要看到智能建议的依据、不确定性和证据，并能纠正错误聚类、证据和摘要，而不是接受不可复核的“AI 真伪”结论。

当前仓库已经存在 `intelligence`、`ingestion`、`event` 模块，以及多 Provider、ONNX、Embedding、pgvector、AI Run、Go Codex CLI Adapter、相关性、内容家族、MicroEvent、Heat、Claim/Evidence 和人工反馈等实现事实。新写链路的产品 `Event` 对应 `micro_events` v2；legacy `events/topics` 只保留历史读取与回滚兼容，不得与新链路无标记双写。获批目标运行时是根目录 `agent/` 的 Python 数据分析服务，由 Go Worker 通过内部契约调用；在迁移验收前，现有路径不得被描述为已移除，也不得做无备份物理清理。

## 目标与 KPI

| KPI | 目标 | 口径状态 |
|---|---|---|
| Evidence 白名单违规落库 | 0 | P0 硬门禁 |
| Python Agent 故障污染业务事实 | 0 | P0 硬门禁 |
| 重试产生重复有效决定 | 0 | P0 硬门禁 |
| Relevance Precision/Recall | 待基线后批准 | 候选，需建立人工标注 Golden Dataset |
| Event 聚类 Precision/Recall 或人工修正率 | 待基线后批准 | 候选，需建立跨来源和转载 Fixture |
| 同时 Agent 分析任务 | 单机 2、候选扩展至 4 | 候选，需按 CPU、内存、模型和任务大小校准 |
| Heat 排序稳定性 | 相同输入/Profile 得到相同结果 | P0 硬门禁 |
| 人工治理可追溯 | 100% 记录操作者、理由和基准版本 | P0 硬门禁 |

## 范围

### P0

- 确定性关键词、实体、时间、链接、来源关系和指纹先生成候选；
- Go Worker 通过内部认证调用根目录 `agent/` Python 数据分析服务，输入有界、结果结构化、失败可恢复；
- `monitor.compile.v1`、`content.relevance.v1`、`event.cluster.v1`、`claim.extract.v1`、`event.brief.v1` 的 P0 产品契约；
- JSON Schema、Evidence ID 白名单、枚举/长度、安全检查和 Go Domain 二次校验；
- Observation、Document、Content Family、Event 分层及重复成员防护；
- Relevance、Heat、Evidence State 分离；
- Heat 的独立谱系根宽度、速度、加速度、来源覆盖、可选归一化互动、时效、可用权重、warming-up 和 Profile/Golden Vector；
- 相关性反馈、成员修正、Claim/Evidence 修正、事件合并/拆分建议、争议/更正/归档和审计。

### P1

- 有界评论会话、抽样、立场、争议、用户需求和纠错线索；
- 自动合并/拆分建议的更高置信度辅助；
- 更丰富的跨语言聚类与人工评估工具。

### P2

- 团队级标注集、主动学习和离线质量实验；
- 可插拔但仍受同一验证链约束的额外智能运行时；
- 面向研究的高级传播网络分析。

## 用户故事

- 作为 Analyst，我可以看到内容为何被接受、拒绝或标记待分析，并提交相关性反馈。
- 作为 Viewer，我可以区分一个事件“很热”“与我的 Monitor 相关”和“证据充分”，不会把三者混为一谈。
- 作为 Editor，我可以审核事件成员、Claim 和 Evidence，纠正错误并保留历史。
- 作为 Admin，我可以查看净化后的 Agent 运行、超时、Schema 失败和资源使用，但不能读取来源或模型凭据。
- 作为运维人员，我可以在 Agent 不可用时继续采集和确定性处理，并在恢复后幂等补算。

## 业务需求

- `BR-003-001`：智能能力必须提升筛选和整理效率，但不能成为事实、权限或来源权利的拥有者。
- `BR-003-002`：系统必须把相关内容聚合为可持续更新的事件，同时抑制重复转载对热度和来源广度的放大。
- `BR-003-003`：Relevance、Heat 和 Evidence State 必须独立解释和治理。
- `BR-003-004`：任何自动决定都必须允许授权用户反馈、复核和追加式纠正。

## 功能要求

- `FR-003-001`：智能任务必须由 Go Application/Worker 创建稳定 Job/Run，输入只引用目标 ID、版本、时间窗、输入哈希和允许的 Evidence 清单。
- `FR-003-002`：Python Agent 必须通过内部认证、版本化 HTTP 契约接收有界请求；不得获得业务存储凭据、直接写业务表/Vault、使用 Shell 拼接或自行扩展证据范围。
- `FR-003-003`：每个 Skill 必须具有稳定 Skill ID、版本、输入 Schema、输出 Schema、允许枚举、字段上限和错误码。
- `FR-003-004`：Agent 输出必须依次通过 HTTP 状态、结构解析、Pydantic/JSON Schema、Evidence 白名单、枚举/长度、安全检查和 Go Domain Policy；任一失败都不得形成有效业务决定。
- `FR-003-005`：相同 Workspace、Skill/Prompt/Input Schema/Output Schema/运行时版本、目标版本、输入哈希和 Evidence Set Hash 必须使用同一复用键；只可复用在途或成功运行，失败、取消、非法输出或越权结果不得复用，修复输出形成新 Attempt。
- `FR-003-006`：Agent 不可用时，内容必须进入明确的 `pending_analysis` 或等价现有状态；采集、证据、精确去重、指标和历史查询继续，恢复后可幂等补算。
- `FR-003-007`：系统必须区分 Observation、Document Version、Content Family 和 Product Event（`micro_events` v2）；同一转载家族不得重复增加事件成员或独立来源数，legacy `events/topics` 不得接收同输入的新写。
- `FR-003-008`：Event 成员判断必须保存确定性信号、智能建议、最终规则决定、Profile 版本和人工覆盖，重复输入不得创建重复有效成员。
- `FR-003-009`：`relevance_score` 必须表达与 Monitor 的匹配；`heat_score` 必须表达传播升温；ClaimEvidence 必须表达单条 Claim 的可引用关系；Event `evidence_state` 必须表达当前 ClaimEvidence 集合的聚合状态，四者不得互相推导替代。
- `FR-003-010`：P0 Heat 必须由版本化时间窗中的独立谱系根宽度、速度、加速度、来源覆盖、可选归一化互动和时效六类分量确定性组合，并保存可用权重。Mention Volume、Novelty、Monitor Relevance 与 Spam Penalty 不得在未评审 Profile/Schema 时暗中加入。
- `FR-003-011`：归一化互动不可用时必须保持 unknown，并按 `available_weight` 重归一化而不是按零惩罚；时间基线不足时显示 warming-up，不得用当前绝对值伪造增量；每个 Snapshot 保存分量、窗口和 Profile 版本。
- `FR-003-012`：Event Evidence State 至少能表达无可引用正文、单一出处、多个独立出处、争议、发布者更正和发布者撤回，并由 ClaimEvidence Version 集合计算；报告审批必须逐句验证 ClaimEvidence，不能只凭 Event 聚合状态。任何新增枚举必须与当前 Schema/OpenAPI 兼容评审。
- `FR-003-013`：人工相关性覆盖、成员修正、合并、拆分、证据纠正、争议、更正、归档和摘要重生成必须追加治理事实，不静默覆盖自动运行历史。
- `FR-003-014`：P1 评论任务必须满足根内容资格、来源权利和数量/页数/深度/字节/时长/配额边界；评论数量不得增加独立事实来源计数。
- `FR-003-015`：Product Event 必须由有界 River Refresh 任务持续吸收新成员和指标、重算 Heat/Evidence、产生版本化 Event Update 并评估告警；同一事件版本、时间窗和 Profile 重放不得产生重复成员、Snapshot 或通知。

## 非功能要求

- `NFR-003-001`：Agent 运行不得获得数据库 DSN、Redis URL、来源 Token、MinIO/Vault 凭据、仓库源码或未授权网络目标；来源文本始终按不可信输入处理。
- `NFR-003-002`：单任务必须有请求体/输出大小、墙钟超时、并发、有限重试和取消限制；River 重试与 Agent 客户端重试必须共享总预算。
- `NFR-003-003`：候选并发为单机 2、容量目标 2–4；批准前必须按任务类型、Context 大小、CPU、内存和执行时长校准。
- `NFR-003-004`：结构、幂等、Evidence、安全和确定性规则必须由 Fake Agent、Python/Go 契约测试和 Golden Test 覆盖；真实模型 Live Test 只在受信 Runner 执行。
- `NFR-003-005`：日志只保留 Job/Run、版本、耗时、退出类别和净化错误，不记录完整 Prompt、正文、认证文件或不受控模型输出。
- `NFR-003-006`：现有 Provider/Embedding 迁移必须先完成调用方盘点、质量对比、数据处置、回滚和读兼容验收，不能成为 P0 主链的隐性依赖。

## 界面状态

| 状态 | 产品要求 |
|---|---|
| 正常 | 同时展示相关性、Heat、Evidence、版本、解释、引用和允许的治理动作 |
| 空 | 区分暂无候选、暂无事件、暂无证据、尚未建立 Heat 基线和筛选后为空 |
| 加载 | 智能任务显示持久 Run 状态，可离开页面；不得反复提交同一动作 |
| 错误 | 区分超时、未认证、Schema、Evidence、安全、预算和领域拒绝，并显示是否可补算 |
| 权限不足 | Viewer 只读，Analyst 只提交反馈，Editor/Admin 的采纳动作由服务端校验 |

## 非目标

- 不让 Python Agent、现有 Provider、Codex Adapter 或 Embedding 结果直接写最终事实或决定权限。
- 不实现 AI 真伪概率，不把评论情绪、热度或相关性当作证据充分性。
- 不在已批准的根目录 `agent/` 之外新增其他 Python/业务微服务、独立向量库、RAG、重排器或通用规则引擎。
- 不全量抓取评论，不在 P0 承诺评论洞察。
- 不在本 PRD 中删除 Provider、Embedding、pgvector、历史 AI Run 或现有数据。
- 不允许智能任务自行联网搜索或扩展 Evidence 白名单。

## 依赖、风险与待决策

| ID | 项目 | 处理要求 |
|---|---|---|
| `RSK-003-001` | Agent/模型 Provider 接口、认证或输出可能变化 | 锁定内部契约和生产依赖，做启动能力探测、Fake Agent、双端契约测试和稳定错误码 |
| `RSK-003-002` | Prompt Injection 或伪造 Evidence | 最小权限 Sandbox、无秘密、白名单和 Domain 二次校验 |
| `RSK-003-003` | Heat/聚类只有概念公式 | 批准前确定 Profile、窗口、归一化、阈值和 Golden Vector |
| `RSK-003-004` | 新旧智能路径双写产生歧义 | 每个决定保存 origin/runtime/version，切换需质量与回滚门禁 |
| `RSK-003-005` | 跨语言聚类质量未知 | 先以 P0 来源样本建标注集，质量不足时进入人工审核而非自动合并 |

待决策项包括 P0 分析契约/模型版本、`pending_analysis` 与现有状态的映射、Heat Profile、独立出处判定规则、现有 Provider/Codex 停止新写条件和模型质量阈值。

## 验收标准

| ID | Given | When | Then |
|---|---|---|---|
| `AC-003-001` | 一个包含不可信正文和允许 Evidence 清单的智能任务，以及按任务类型和 Context 分层的容量样本 | Go Worker 调用内部 Python Agent，并分别执行并发 2、3、4 校准 | Agent 无业务存储/来源/Vault/源码秘密和公网入口，结果只能经 Go Application/Domain 提交；校准实际记录任务类型、Context 字节数或 Token 数、CPU、内存峰值、时长、成功率和候选并发 |
| `AC-003-002` | Agent 分别超时、未认证、契约/Schema 版本不符、输出非法 JSON、枚举/长度越界、错误码未知或伪造 Evidence ID | Worker 处理结果并重复提交同复用键 | 每种情况返回允许集合内的稳定失败码，不写有效决定或 Claim，失败结果不进入可复用结果；重试/修复形成新 Attempt 并保留净化运行事实 |
| `AC-003-003` | Agent 暂时不可用且已有来源采集，或准备从旧 Provider/Codex/Embedding 切流 | 执行扫描、恢复补算和迁移验收 | 证据、精确去重和指标继续保存，内容显式待分析，补算不重复；调用方盘点、质量比较、数据处置、旧记录读兼容、分阶段灰度和实际切回全部有证据后才可停止旧路径新流量 |
| `AC-003-004` | 跨来源相关内容、转载、重复观察和晚到指标 Fixture | 重复执行聚类与 Event Refresh | 相关独立内容形成一个 `micro_events` v2 Product Event，转载家族不重复放大成员和来源广度；相同事件版本/窗口/Profile 幂等，legacy `events/topics` 无新双写 |
| `AC-003-005` | 同一 Event 同时具有高热、低 Claim 引用覆盖或低相关样本 | 查询 API、界面并请求报告审批 | Relevance、Heat、ClaimEvidence 和 Event Evidence State 独立展示，改变任一项不会隐式改写其他项；报告逐句校验 ClaimEvidence，不能仅凭 Event 汇总状态批准 |
| `AC-003-006` | 固定 Heat 输入、Profile、互动可用/不可用和有/无时间基线 Fixture | 多次计算并切换能力与基线场景 | 相同输入输出一致且六类分量可解释；互动缺失保持 unknown 并按可用权重重算，无时间基线显示 warming-up，不以绝对值制造速度或加速度 |
| `AC-003-007` | Editor 对成员、证据、争议或合并/拆分提交治理动作 | 动作成功、冲突或重放 | 成功时追加操作者、理由、基准版本和审计；版本冲突被拒绝；重放不重复产生当前副作用 |
| `AC-003-008` | 四产品角色及智能任务的正常、空、加载、错误场景 | 访问研判和治理页面或直接 API | 五态清晰；Viewer 只读、Analyst 提交建议、Editor 采纳、Admin 配置运行，未实现 Analyst 时按真实角色拒绝 |
