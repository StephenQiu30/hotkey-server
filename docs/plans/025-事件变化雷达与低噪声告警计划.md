## 3. RED/GREEN

1. RED：领域测试要求首次、rising、reactivated、source expansion、heat delta 与非实质变化得到确定 Update kind/reason/idempotency 输入；当前没有 EventUpdate。
2. RED：Radar application/repository 测试要求过滤、维度、排序和绑定查询形状的游标；当前 `/events` 仅按 ID 升序。
3. RED：Schema/Repository 测试要求 EventUpdate append-only、并发 sequence/idempotency，以及 Alert Thread/Occurrence 唯一性；当前表不存在。
4. RED：Alert application 测试要求 eligibility、trigger mapping、severity、cooldown、reopen/suppress 和 optimistic state mutation；当前没有 Alert 模块。
5. RED：Worker 测试要求 Heat 处理后只为 actionable Update 入队稳定 `evaluate_event_alerts`，重复 job 不重复业务事实；当前队列直接进入 summary。
6. RED：HTTP/OpenAPI 测试固定 Radar、EventUpdate、Alert 读取和动作接口、错误码、BearerAuth 与安全 DTO。
7. 实现复审 RED：篡改 Radar/Alert 游标必须失败；Radar 首屏后修改 Event/Metric/MonitorEvent/Claim 或补写 `created_at > as_of` 事实，后续页仍保持首屏冻结的最多 100 个位置；15 分钟后游标失效。
8. 实现复审 RED：以更旧和同时间不同 EventUpdate 的 occurrence 乱序写入，断言只增加 count/version，只有 `(triggered_at,event_update_id)` 严格更新者推进快照、冷却与 reopen，`updated_at` 不倒退；非有限值、未达阈值和错误 severity 被拒绝；详情三组读取来自同一 REPEATABLE READ 快照。

### 3.1 唯一实现语义

- Update application 从已提交的当前 24h snapshot 与严格更早的上一份 24h snapshot 构造候选；Repository 锁定 Event 行、分配 sequence，并依靠 `(event_id,idempotency_key)` 关闭同输入竞争。不同窗口/证据输入产生不同 key，非实质变化不入表。
- Update key 严格采用 Design-019 v1.2 的 `metric-update-v1` 有序字段/SHA-256；同一事务先锁 Event，再分配 sequence，冲突时返回既有 Update 而不占第二个序号。
- Heat Handler 在成功重算后 record/reuse Update，以稳定唯一键先入队可选的 `evaluate_event_alerts`，再无条件入队一个 summary。任一步入队失败均重试 Heat，已成功项由 Queue 去重复用；cooling/无 Update 只入队 summary，Alert evaluator 的运行失败不阻塞或重复 summary。
- Radar 公式与 confirmation 优先级采用 Design-019；Repository 在首屏 `as_of` 计算并冻结最多 100 个排序位置，把剩余有序集合、查询形状和 15 分钟过期时间放入 HMAC-SHA256 签名游标。后续页消费冻结集合而不重排；不可变事实读取增加 `created_at <= as_of`。Radar 与 Alert 分别从基础 secret 以固定 purpose 派生签名密钥，拒绝无签名、篡改、过期和跨形状游标。
- Alert evaluator 分别调用 Event candidate port 与 Monitor policy port，再把冻结 config/revision/hash/threshold/final score 的触发命令交给 Alert Repository。fingerprint 采用 Design-019 v1.2 的有序字段/SHA-256；Application/Domain 先校验 score 与 threshold 有限、达到阈值且 severity 符合 90/75 绝对边界。Repository 先插入 occurrence，只有插入成功才增加已锁 Thread 的 count/version；再以 `(triggered_at,event_update_id)` 全序决定是否推进最新快照、冷却与 system reopen audit。乱序输入不得推进这些快照字段，`updated_at` 使用实际事实写入时刻与既有值的最大值。
- Alert action 在单事务内锁定 Thread、校验 expected version/状态、更新线程并追加 audit；任一步失败整笔回滚。viewer/editor/admin 可 acknowledge/resolve，只有 editor/admin 可 suppress。
- Alert detail 在一个只读 REPEATABLE READ 事务中读取 Thread、最近 50 条 occurrence 与完整 audit，避免跨提交拼接不一致响应。

## 4. 事务、并发与失败验证

- 两个 goroutine 对同一 Event/输入记录 Update，断言 sequence 唯一且只有一个 idempotency key。
- Queue 入队失败后重试 Heat，断言 Update 可复用且 Alert job 最终可入队。
- 两个 Worker 对同一 Update evaluate，断言一个 occurrence、一个 thread、正确 occurrence count。
- Alert 状态 CAS 冲突、非法状态和审计写失败均整笔回滚。
- 注入 occurrence 插入后/thread 更新前故障、thread 更新失败和 system reopen audit 失败，断言 occurrence/thread/count/cooldown 全部回滚。
- Radar 在首屏冻结最多 100 个有序位置；首屏后修改可变投影、插入新事件或补写 `created_at > as_of` 的不可变事实，跨页仍按冻结集合返回且没有重复/插入/重排。逐字段篡改、跨查询复用、非法位置、无签名或超过 15 分钟的 cursor 返回稳定 invalid input。
- Alert list 的 `(last_triggered_at,id)` HMAC-SHA256 游标绑定 state/severity/monitor 形状并在 15 分钟后过期；详情只返回最近 50 条 occurrence、完整 audit 和安全快照，且并发写入期间三组读取仍来自同一 REPEATABLE READ 快照。
- 先写较新的 occurrence，再写较旧及同一 `triggered_at` 下更小/更大的 `event_update_id`，验证全序、count/version、snapshot/cooldown/reopen audit 与 `updated_at` 单调性；验证非有限 score/threshold、未达 threshold 和不匹配 severity 均无部分写入。
- AI Registry 为空，以及 Provider unavailable、transient failure、timeout 时运行 deterministic Fixture，断言 Radar/Update/Alert 从不调用 LLM 且正常提交；summary 返回证据化 fallback 和安全 reason code。无 Update、cooling、任一 fan-out 入队失败、evaluator 重试/终态失败分支均恰好保留一个可执行 summary job。
- Radar cursor 改变 filter/sort 后返回参数错误；目标索引查询不得出现无界全表扫描。
- HTTP 错误固定复用现有稳定业务码：非法参数/游标 `10000/400`、未找到 `10003/404`、版本或状态冲突 `10002/409`、viewer suppress `20001/403`、依赖不可用 `90001/503`；不新增并行错误目录。
- 定向契约阶段运行 `make openapi-check`，覆盖 `TestOpenAPIContract` 与 `TestGeneratedOpenAPIRegistryMatchesCommittedArtifact`，并验证所有新路径 BearerAuth、请求 required/范围和安全响应字段。
- 集成测试只接受 `HOTKEY_TEST_DSN`/`HOTKEY_TEST_REDIS_URL`；空值、与 `HOTKEY_DATABASE_URL`/`HOTKEY_REDIS_URL` 规范化后相同均立即失败。每个 PostgreSQL 测试使用唯一可丢弃数据库并由 cleanup 删除；验收核对无残留 `hotkey_it_*`。

## 5. 提交与回滚

- 测试 RED、实现 GREEN、生成契约与文档分开形成职责清晰的提交；提交仅包含 hotkey-server。
- 只允许兼容性应用回滚：先关闭 Heat 的新任务入队，停止 Worker，核对并处理完或安全保留 available/running `evaluate_event_alerts`，再回退 Alert/Radar 路由和业务启用点；不能留下可入队但无 handler 的任务。
- `db/schema.sql`、四张新增表/约束、必要记录模型和历史读取能力在回滚版本中保留，恢复采用前滚；本 Plan 不执行物理表降级或历史删除，因而不制造唯一 Schema 事实源漂移。

## 6. 残余风险

- P0 仍使用单工作区与现有 Monitor 物理模型，不宣称具备多租户 SaaS 隔离。
- P0 告警只提供站内状态，不提供外部投递；Email/Webhook 需独立 Plan。
- Claim 仍引用当前 Content 而非不可变 Signal Snapshot；Radar verification 只能表达当前证据投影，此风险由后续 Snapshot/Evidence Plan 关闭。
- 本机开发库没有 active Source/Monitor/AI Profile；完整业务链以隔离 Fixture 验证，不修改现有开发数据。
