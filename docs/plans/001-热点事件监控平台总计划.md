# 热点事件监控平台总执行计划

日期：2026-09-17。依据 [001 需求总纲](../prd/001-热点事件监控平台功能与非功能需求.md)，统筹 [40 份逐项计划及 X 专项](README.md)。当前 planned，应用实现已清理，文档完成不计为功能完成。总体进度的唯一入口是根目录 [BACKLOG](../../BACKLOG.md)。

## 1. 目标与交付层次

首版按既定建议范围交付 18 项 P0 功能和 16 项 P0 质量要求，共 34 项。核心链路是关键词/账号设置、发现作品、形成事件、采集评论、理解讨论、查看依据、收到变化记录并导出。

首批完整来源建议为 X 加一个国内平台，国内来源顺序待范围确认；多平台目标保留。X 的免费自动路径必须实际验证，不能以替换平台或合法导入样本声称首版完成。P1 的 4 项增强与 P2 的 2 项扩展分别后续交付，不因计划齐全扩大首版。

本计划负责里程碑、共享职责、全局门禁和集成验收；子 Plan 负责具体实现与局部 AC。BACKLOG 只维护排期、状态、阻塞和证据入口，不复制子计划的所有任务。

## 2. 已知缺口和开工门禁

当前仅有规范、研究、PRD 和 proposed 的 X 设计；不存在已重新实现的 backend/frontend、依赖锁、迁移、测试、Compose 或可运行来源。S01 补总体设计，各子 Plan S00 补同编号设计；填写实际路径后才进入代码切片。

| 门禁 | 必须产出 | 不满足时允许的工作 |

| G1 依赖与环境 | 所需先行切片、隔离 PostgreSQL/RabbitMQ/MinIO、明确来源条件 | 与缺失条件无关的受控逻辑验证 |
| G2 契约与目录 | 领域职责、SPEC、数据/状态/权限、拟改文件和命令 | 补契约与失败用例设计，不先铺空模块 |

## 3. 实现约束与共享主责

沿用 Python 3.12 / FastAPI / SQLAlchemy 2 / Alembic / Celery / RabbitMQ / PostgreSQL、既有 MinIO 和 Next.js/TypeScript。使用唯一 backend、frontend、Compose 与 FastAPI OpenAPI 生成链。来源适配器复用成熟免费组件，业务数据保持一个事实来源；不恢复旧实现。

## 4. 总体 SPEC 与变更顺序

| ID | 执行约束 |
|---|---|
| SPEC-001-API-001 | FastAPI/Pydantic 为唯一 HTTP 契约；路由经依赖注入业务服务；运行时 OpenAPI、快照及生成前端客户端一致。 |
| SPEC-001-DATA-001 | SQLAlchemy 2 + Alembic；新迁移随切片交付，业务事务归服务。来源 ID、所有权、版本、父链及删除约束先明确。 |
| SPEC-001-JOB-001 | 业务状态和 outbox 同事务；RabbitMQ 至少一次交付，进度、幂等和旧执行权保护在数据库；不使用任务结果缓存作为业务事实。 |
| SPEC-001-UI-001 | 先构建核心监控→事件→证据流程；正常空、部分、失败、无权限与陈旧状态真实可见；同源 API 和生成客户端。 |
| SPEC-001-SEC-001 | 秘密不回读、不入日志/代码；当前权限、停用、删除和预算优先于历史配置；外部数据不执行指令。 |
| SPEC-001-OBS-001 | 从任务到结果保留关联 ID、配置与输入版本、阶段时间和停止原因；聚合能回到明细，敏感查询不进通用日志。 |
| SPEC-001-OPS-001 | 单一 Compose，隔离测试依赖，不删除持久卷；先验证回退/恢复，再声明相应环境可运行。 |

各业务切片按数据及状态→领域服务/Worker→路由契约→OpenAPI/客户端→交互→运行验证推进；无变更的层明确不适用。不能先做所有页面再一次补后台和质量。

## 6. 验证、停止条件和进度口径

具体命令由子计划列出；042 建立依赖锁、架构门禁、OpenAPI 与前端脚本。已有规范要求的 Ruff/mypy/pytest、真实 PostgreSQL/RabbitMQ、生成客户端、类型/构建和浏览器验证不得省略，但不能执行尚不存在的脚本后把环境错误当业务红测。

真实平台只做有界、合法且显式的采样验证；限流/挑战/拒绝分支通过受控故障验证。B0 性能、备份及容量在隔离数据上验证，Q0 人工参考集与调参集分离；纯技术绿测不代替来源、体验或恢复证据。

当来源拒绝、预算耗尽、权限失效或持久化失败时，先停止相关新增工作并保存状态；不绕过访问限制，不切付费兜底，不清空数据。版本回退必须先确认数据兼容；不兼容使用已演练的向前修复或隔离恢复。

BACKLOG 的首版进度为“已通过全部必要验收的 P0 需求数 / 34”。001 总计划与 002 专项是统筹/来源门禁，不再作为独立产品需求加入分母。P1 按 4 项、P2 按 2 项分别统计。

首版发布不意味着本总计划包含的 P1/P2 全部完成。001 保持 in_progress，直到已批准的全部阶段交付；若后续范围取消，须先明确更新需求状态与分母并保留变更记录，不能静默删除未完成项。
