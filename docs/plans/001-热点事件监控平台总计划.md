## 1. 目标与交付层次

首版按既定建议范围交付 18 项 P0 功能和 16 项 P0 质量要求，共 34 项。核心链路是关键词/账号设置、发现作品、形成事件、采集评论、理解讨论、查看依据、收到变化记录并导出。

搜索/账号发现建议先验证 X 加一个国内平台，国内发现次序待准备度确定；2026-09-22 用户已确认 B站、小红书、抖音、微博评论均必需，按 008/047 从已知作品 URL 开始分别交付，不能只完成其中一个。X 的免费自动路径必须实际验证，不能以替换平台或合法导入样本声称首版完成。P1 的 7 项增强与 P2 的 2 项扩展分别后续交付。

本计划负责里程碑、共享职责、全局门禁和集成验收；子 Plan 负责具体实现与局部 AC。BACKLOG 维护可交付内容、跨计划工作批次、排期、状态、阻塞和证据入口；子 Plan 保留 TASK/CHK/EV 的详细执行事实。

## 4. 总体 SPEC 与变更顺序

| ID | 执行约束 |
|---|---|
| SPEC-001-API-001 | FastAPI/Pydantic 为唯一 HTTP 契约；路由经依赖注入业务服务；运行时 OpenAPI 与生成前端客户端一致；如需归档，由 CI 导出产物，不建立第二份契约源。 |
| SPEC-001-DATA-001 | SQLAlchemy 2 负责运行时映射，backend/database/schema.sql 是唯一 DDL 事实源；两者随切片同批交付，业务事务归服务。来源 ID、所有权、版本、父链及删除约束先明确。 |
| SPEC-001-JOB-001 | 业务状态和 outbox 同事务；Kafka 按至少一次处理设计，业务事务提交后提交连续完成位置的 offset，进度、幂等和旧执行权保护在数据库；不使用任务结果缓存作为业务事实。 |
| SPEC-001-UI-001 | 先构建核心监控→事件→证据流程；正常空、部分、失败、无权限与陈旧状态真实可见；同源 API 和生成客户端。 |
| SPEC-001-SEC-001 | 秘密不回读、不入日志/代码；当前权限、停用、删除和预算优先于历史配置；外部数据不执行指令。 |
| SPEC-001-OBS-001 | 从任务到结果保留关联 ID、配置与输入版本、阶段时间和停止原因；聚合能回到明细，敏感查询不进通用日志。 |
| SPEC-001-OPS-001 | 单一 Compose，隔离测试依赖，不删除持久卷；先验证回退/恢复，再声明相应环境可运行。 |

各业务切片按数据及状态→领域服务/Worker→路由契约→OpenAPI/客户端→交互→运行验证推进；无变更的层明确不适用。不能先做所有页面再一次补后台和质量。

## 6. 验证、停止条件和进度口径

具体命令由子计划列出；046 先完成统一契约、最小生成链与阻断检查，042 复用并扩展运行环境、真实依赖和底座验证。已有规范要求的 Ruff/mypy/pytest、真实 PostgreSQL/Redis/Kafka、生成客户端、类型/构建和浏览器验证不得省略，但不能执行尚不存在的脚本后把环境错误当业务红测。

真实平台只做有界、合法且显式的采样验证；限流/挑战/拒绝分支通过受控故障验证。B0 性能、备份及容量在隔离数据上验证，Q0 人工参考集与调参集分离；纯技术绿测不代替来源、体验或恢复证据。

当来源拒绝、预算耗尽、权限失效或持久化失败时，先停止相关新增工作并保存状态；不绕过访问限制，不切付费兜底，不清空数据。版本回退必须先确认数据兼容；不兼容使用已演练的向前修复或隔离恢复。

BACKLOG 的首版进度为“已通过全部必要验收的 P0 需求数 / 34”。001 总计划与 002 专项是统筹/来源门禁，不再作为独立产品需求加入分母。P1 按 7 项、P2 按 2 项分别统计。

首版发布不意味着本总计划包含的 P1/P2 全部完成。001 保持 in_progress，直到已批准的全部阶段交付；若后续范围取消，须先明确更新需求状态与分母并保留变更记录，不能静默删除未完成项。
