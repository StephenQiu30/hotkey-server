# 监控来源采集与证据链计划

## 当前实现与差距

### 当前实现

- `monitor` 模块已包含 Monitor、规则、Intent 草稿/版本/发布、预览和读取能力；
- `source` 模块已有来源连接、凭据、Rights、Capability、采集控制、RSS、Hacker News、X 等 Connector，以及 River 采集、手动搜索、重试和指标刷新 Job；
- `source_observations`、`evidence_snapshots`、关联表、MinIO 原始对象和校验字段已构成证据基础；
- `ingestion` 模块已有正文抽取、标准化、去重、文档版本、引用、来源正文和匹配投影；
- 未知发布时间已从 Source Observation 贯通至 Ingestion、PostgreSQL、OpenAPI 和前端并保持 `null`；原始 UTC 偏移独立保留，未知时间内容不会进入实时 Event 聚类；
- `backend/db/schema.sql` 已保存 Monitor、来源、采集运行、Checkpoint、Observation、Evidence、Document 和内容血缘结构；
- 前端已有来源页面、连接/凭据对话框、Monitor Intent 预览和内容页面。

### 主要差距

- 需要把现有广泛来源能力收敛为 24 周 P0 的 RSS、Hacker News、X 三个真实授权来源，不把其他来源和评论正文带入承诺；
- `Monitor → RSS → Evidence → Event → UI` 薄切片必须先在 W3–W6 可复测，不能等所有来源完成后才做端到端联调；
- Monitor Intent 已有预览和 `monitor_compiled_profiles` 事实，但来源级编译差异、发布版本绑定及相同输入可复现仍需由测试固化；
- Capability、Rights/Policy、Credential、Quota/Budget、Rate Limit、SSRF、Checkpoint 的调用前顺序需要由测试固化；
- 多来源运行必须显式表达每个 Target 的成功、空结果、限流和失败；`partial_success` 只能是 Application 派生的 `run_outcome`，不能扩张现有持久状态枚举，单来源失败不能回滚已提交事实；
- 原始对象 Hash、Observation、Evidence Selection、Document Version 与 Event 成员之间需完成可追踪对账；
- 候选容量和时延需在固定夹具与真实授权冒烟中分别测量。

## 前置门禁

1. 001 已通过 G0–G3，架构和 P0 范围冻结；
2. 002 Design=`accepted`、PRD=`approved`；
3. RSS 测试 Feed、Hacker News 官方 API 与 X 官方 API 的权限、配额、保留和删除义务有可审计负责人；
4. MinIO 测试桶、可丢弃 PostgreSQL/Redis 测试实例和来源 Fixture 可用；
5. `backend/db/schema.sql`、River 和 OpenAPI 仍是唯一数据、任务和 HTTP 契约入口；
6. 未获授权的来源默认禁用，禁止 Cookie 抓取、登录绕过、验证码绕过或隐式 HTML 回退。

## 测试先行任务

### S01：Monitor 与 RSS 薄切片

1. `TASK-002-S01-T01`：先写 Monitor 草稿、来源级编译预览、相同输入/版本得到相同 Compiled Profile、发布绑定不可变快照、暂停、恢复、归档和并发资源版本冲突测试，再补最小领域/Application 行为。映射 `AC-002-001`。
2. `TASK-002-S01-T02`：先写“未发布 Monitor 或未就绪 Compiled Profile 不排队、同窗口同发布版本只产生一个 River Job、Job 仅携带稳定 ID”的失败测试，再接入 Monitor 调度。映射 `AC-002-001`、`AC-002-006`。
3. `TASK-002-S01-T03`：用固定 RSS/Atom Fixture 覆盖分页/条件请求、空 Feed、格式错误、超时、超大响应、重复条目和发布时间缺失；再实现或收敛 Connector。映射 `AC-002-002`、`AC-002-003`、`AC-002-005`。
4. `TASK-002-S01-T04`：先写 MinIO 写入失败、Hash 不一致、重复写入、数据库事务失败，以及保留期内/过期/批准例外 Evidence 测试；再建立 Raw Object→Evidence Snapshot→Observation 的提交顺序和到期后的元数据、Hash、删除审计与 UI 过期态。映射 `AC-002-004`、`AC-002-006`。
5. `TASK-002-S01-T05`：先用重复 URL、相同 External ID、正文近重复和无发布时间夹具证明 Document/Version 去重与时间语义，再把 Accepted Match 投影到 Event 与 UI。映射 `AC-002-005`。
6. `TASK-002-S01-T06`：作为 S01 首个实现门禁，在任何真实 RSS 请求前为 RSS 冻结并实现版本化 Resource Limit Profile，逐项对连接、读取、墙钟、页数、条数、累计字节、重试和每日配额运行 `limit-1 / limit / limit+1` 与跨页/跨日 Fixture；断言越界在下一拨号、翻页、重试、对象写入或下游排队前停止，已提交 Target/Checkpoint/Evidence 保留且无额外副作用。HN/X 在 S02 复用同一契约并各自校准有限值。映射 `AC-002-009`。

### S02：Hacker News 与 X

1. `TASK-002-S02-T01`：用 HN 官方 Item/Search Fixture 覆盖空结果、deleted/dead、分页、429/5xx、Checkpoint 和重复页；再接入现有 Go Connector。映射 `AC-002-002`、`AC-002-003`、`AC-002-006`。
2. `TASK-002-S02-T02`：用 X 官方 API Fixture 覆盖认证失效、限流窗口、Lookup、指标缺失、分页 Token、配额耗尽和永久权限失败；再实现有界采集。映射 `AC-002-002`、`AC-002-003`、`AC-002-006`。
3. `TASK-002-S02-T03`：先写 Capability→Rights/Policy→Credential 状态/引用→Budget→Rate Limit→Endpoint/SSRF Policy→Request 的顺序断言；端点通过前不得触网、解密或附加凭据，逐跳重定向必须重新校验。同步覆盖来源、凭据、预算、扫描和证据管理动作的审计完整性及日志脱敏。映射 `AC-002-002`。
4. `TASK-002-S02-T04`：在受信任环境执行三来源真实授权冒烟，输出只保存状态、计数、延迟和脱敏错误，不保存 Token 或私密响应。映射 `AC-002-002`、`AC-002-008`。

### S03：多来源运行与恢复

1. `TASK-002-S03-T01`：先构造 RSS 成功、HN 成功零条、X 限流的运行，断言 Target 事实分别持久化、Application 派生 `run_outcome=partial_success`、RSS 继续后链路且现有数据库状态枚举不变。映射 `AC-002-003`。
2. `TASK-002-S03-T02`：先覆盖 Worker 在领取后、MinIO 写后、Observation 提交后和 Document 投影中途退出；再补租约回收、幂等重试和 Checkpoint 恢复。映射 `AC-002-004`、`AC-002-006`。
3. `TASK-002-S03-T03`：先验证 401/403、429、5xx、解析失败、Rights 拒绝和预算耗尽的重试类别，禁止全部重试或无限快速重试。映射 `AC-002-002`、`AC-002-006`。

### S04：UI、权限与基准

1. `TASK-002-S04-T01`：先覆盖 Viewer/Editor/Admin 当前角色及 Analyst 目标角色对 Monitor、凭据、来源健康和采集动作的服务端负向权限，再同步前端五态；001 批准角色决策、005 实施 Analyst，实施前必须真实拒绝，实施后重跑四角色矩阵。契约变化必须先更新错误码/DTO/Swaggo，生成发布 OpenAPI 与前端客户端并通过漂移检查。映射 `AC-002-007`。
2. `TASK-002-S04-T02`：为 50 个活跃 Monitor、100 个连接、候选内容量和 20 个并发采集任务建立可缩放夹具，记录队列等待、采集时长、写入吞吐和 API P95。映射 `AC-002-008`。
3. `TASK-002-S04-T03`：建立 PostgreSQL、MinIO、Observation、Evidence、Document 和 Event 的抽样对账，覆盖保留期内对象、到期删除、元数据/Hash/删除审计、UI 过期状态与批准例外；Hash 或授权不一致时不得标记有效证据。映射 `AC-002-004`。

## 数据与契约顺序

1. 先保存 Monitor、Connector、Evidence、去重和恢复的失败测试；
2. 必要数据结构只在 `backend/db/schema.sql` 做向前兼容修改，并同步 Model、Schema 检查和非空库兼容验证；
3. 先实现/验证 Compiled Profile 与 Domain/Application/Repository，再注册只消费已发布快照的 River Handler；
4. 先完成 MinIO 对象写入和 Hash 验证，再在数据库事务中提交 Evidence/Observation；不得留下“有效证据”指向不存在对象；
5. Transport 变化后生成 OpenAPI，随后生成前端客户端，再修改页面；
6. 先灰度 RSS，稳定后启用 HN，最后启用 X；每个来源分别验收授权、配额和回滚。

## 灰度、迁移与回滚

- 使用来源连接状态、Capability 和调度准入逐来源灰度，不创建第二套 Connector Registry；
- 新字段或表采用只增不删、先写后读、对账后切流；不创建数据库迁移文件；
- 新 Evidence 链先影子写入并抽样对账，未达一致性阈值前不替代现有读取；
- 某来源异常时先禁用其连接和新 Job，保留其他来源与已提交事实；
- Worker 回滚到旧代码前确认新旧 Job 参数兼容，不能让旧 Worker 读取未知载荷；
- MinIO 或 Schema 回滚不删除原始对象、Observation、Evidence 或历史 Checkpoint；需要清理时另立保留/删除任务；
- 其他已实现来源保持关闭或 P1，不因 P0 收敛而直接删除代码和历史数据。
