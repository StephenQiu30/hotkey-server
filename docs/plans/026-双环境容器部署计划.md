# 双环境容器部署计划

## 目标

仓库只增加 `docker-compose-env.yml` 和 `docker-compose-prod.yml` 两个启动入口。日常服务固定读取 `.env`，生产服务固定读取 `.env.prod`；不增加通用 Compose、启动脚本、Makefile 目标或额外部署抽象。

前置 PLAN-002、PLAN-020 已完成；Design-020 与 PRD-026 已 accepted。只有本计划经非主要编写者复核为 `accepted/approved/ready` 后才创建测试或实现文件。

## 必要实现

1. `Dockerfile` 使用 Go 1.26 多阶段构建、`CGO_ENABLED=0`、Alpine Runtime、非 root 用户，并安装 CA、时区和 wget。
2. 两份 Compose 均提供 Server、PostgreSQL/pgvector、Redis、MinIO、`db-init` 和 `minio-init`；PostgreSQL、MinIO、Vault 使用卷。
3. `db-init` 执行 `db verify || db init --empty-only --confirm-empty || db verify`：兼容库只验证、空库初始化、并发竞争最终验证、非空不兼容库失败。
4. `minio-init` 使用 `mc mb --ignore-existing`；Server 等待两个初始化服务成功，并以 `/readyz` 健康检查。
5. 日常项目名/镜像为 `hotkey-server-env` / `hotkey-server:env`，可发布依赖端口；生产为 `hotkey-server-prod` / `hotkey-server:prod`，只发布 Server HTTP，关闭宽限均为 30 秒。
6. `docker-compose-env.yml` 仅引用 `.env`，`docker-compose-prod.yml` 仅引用 `.env.prod`。生产示例中的真实密钥项保持为空。

## RED / GREEN

1. 创建 `test/architecture/docker_test.go`，包含 `TestDockerDeploymentContract` 和 `TestDockerProductionIsolation`。
2. RED：

   ```bash
   go test ./test/architecture -run '^TestDocker(DeploymentContract|ProductionIsolation)$' -count=1
   ```

   预期因 Dockerfile、两份 Compose 和生产模板缺失而失败。
3. 实现最小文件集后重复命令；通过标准为两个测试均成功，且静态覆盖镜像、初始化、健康检查、卷、30 秒关闭、env 文件绑定和生产零基础设施端口。
4. 直接使用 Docker Compose 验证，不新增封装命令：

   ```bash
   docker compose -f docker-compose-env.yml config --quiet
   docker compose -f docker-compose-prod.yml config --quiet
   docker compose -f docker-compose-env.yml up --build -d
   docker compose -f docker-compose-prod.yml up --build -d
   ```

   生产 `.env.prod` 缺失时第二条命令须失败；从 `.env.prod.example` 创建并填写测试密钥后，两个环境均须启动并由 `/readyz` 返回 200。重复执行 `db-init` 和 `minio-init` 须成功；在非空不兼容测试库上 `db-init` 须失败且保留原对象。
5. 使用仓库现有质量门禁运行 `make lint`、带隔离 DSN/Redis 的 `make test`、`make build`、`make validate`、`make schema-verify`、`make openapi-check` 和 `make clean`；不修改 Makefile。全部返回 0，Schema/OpenAPI 无差异且无构建产物残留。
