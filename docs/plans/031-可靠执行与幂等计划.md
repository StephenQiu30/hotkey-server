## 4. 实施规格 SPEC

这些是可评审的执行规格；路径/接口名称为候选，G2 冻结后才是实施契约。若调整需同步测试、客户端与本文件，不私自改变 PRD 的用户语义。

| SPEC ID | 规格 |
|---|---|
| SPEC-031-API-001 | 为 009 提供持久受理与重试幂等契约；响应丢失后同一操作标识返回原任务，数据库提交失败不得确认。 |
| SPEC-031-DATA-001 | 任务、业务结果和 outbox 同事务；幂等键、尝试、执行租约及进度字段独立，消息结果不替代事实存储。 |
| SPEC-031-JOB-001 | 使用 Kafka 消费者；业务事务提交后提交连续完成位置的 offset，以数据库消息 ID 去重；验证重投、再均衡、中断和旧执行者提交。Redis 用于缓存/限流，不承担执行权事实。重试、死信与定时调度在本项 Design 定义，补偿窗口有界。 |
| SPEC-031-UI-001 | 改进本质量要求影响的实际业务页面、状态或运维记录，不默认新建一个独立质量功能页面；无界面变化时以书面理由说明该 UI 分支不适用，不能跳过实际受影响界面。 |
| SPEC-031-SEC-001 | 先检查当前身份及资源权限；配置版本不能绕过撤权、删除、停用和更严格预算。秘密不可回读，正文与外部输入只作数据。关键变更留操作者、对象、时间与版本。 |
| SPEC-031-OBS-001 | 构建故障注入与72小时试运行统计，执行率候选≥99%，内部失败计入；恢复路径与通知防重逐类核对。 |
| SPEC-031-OPS-001 | 在隔离依赖验证后渐进启用本能力；保持历史资料可读。配置缺失或外部条件不满足时明确拒绝/延期。变更前评估数据兼容与回退，停止新增操作优先于破坏性迁移。 |

数据/接口/前端执行顺序：先冻结字段、状态与权限 → 同步更新 schema.sql 与 ORM → 领域服务和 Worker → FastAPI/Pydantic 运行契约 → 导出并核对 OpenAPI → 生成客户端 → 页面接入 → 配置/镜像与完整验收。无 API 或数据变更的质量项在 G2 记录不适用，不强建空接口或无效 DDL。
