# 智能研判、事件热度与人工治理计划

## 当前实现与差距

### 当前实现

- `intelligence` 模块已有模型 Profile、运行、预算、Schema Registry、OpenAI/DeepSeek/Ollama/ONNX Provider 和 Embedding 服务；
- `monitor` 与 `ingestion` 已包含查询扩展、召回、相关性研判、反馈、校准、Embedding 与混合召回路径；
- `event` 已包含聚类、Micro Event、Storyline、实体、Claim/Evidence、Heat、生命周期、摘要和人工治理；
- PostgreSQL 已保存 AI Run、预算、Embedding、决策、Heat Snapshot、Evidence State、反馈和审计事实；
- 新写 Product Event 已由 `micro_events` v2、成员、Heat Snapshot 和 ClaimEvidence 事实承载；legacy `events/topics` 仍用于历史读取/回滚兼容；
- River Job 已承载查询扩展、相关性、摘要、Claim/Evidence 等异步任务；
- 前端已有事件列表、热点卡片、内容详情、版本工作台和治理页面。

### 主要差距

- 目标智能运行时应收敛为 Go Worker 内受控 Codex CLI Adapter，不新增 Python/FastAPI 服务，也不允许 Codex 直接写核心表；
- CLI 进程的 argv、stdin、环境变量、临时工作区、超时、进程组终止、JSONL、最终结果和 Evidence 白名单需要独立契约；
- 仅检查退出码不足以保证结果可信，Schema 错误、伪造 Evidence ID、Prompt Injection 回显和超长输出必须拒绝；`ai_runs` 的 queued/running/validating/retry_wait/终态与复用规则必须保持一致；
- Codex 不可用时，采集、Evidence、精确去重、确定性 Heat 和人工治理必须继续，AI 字段应显式处于未分析/待补算状态；
- 相关性、Heat、ClaimEvidence 和 Event Evidence State 必须分离，模型不能直接决定 Heat、事实真假或最终生命周期；
- Product Event 的首次聚类和后续 Refresh 必须统一使用 `micro_events` v2；legacy `events/topics` 不得无标记双写；
- 当前多 Provider、Embedding、向量和混合召回路径不能直接删除。必须先用 Fake/Golden/Shadow/Live 完成等价或更优替换验收，保留可操作回滚，再另立清理步骤；
- 人工合并、拆分、移除成员、纠正、争议、归档和重算需要不可变审计与并发保护。

## 前置门禁

1. 001 已冻结 Codex、无向量/RAG 和模块化单体边界；
2. 002 已提供稳定的 Document、Match、Evidence Reference、Event Candidate 和来源权利事实；
3. 003 Design=`accepted`、PRD=`approved`；
4. Codex CLI 目标版本、非交互参数、认证保存方式、许可、网络出口和资源上限已完成安全评审；
5. 每个 Skill 的输入、输出 JSON Schema、Evidence ID 白名单和确定性 Go 二次校验规则已批准；
6. Fake Runtime、Golden Dataset 和受信任 Live Runner 可用；普通 CI 不依赖真实 Codex 登录；
7. 旧 Provider/Embedding 路径、数据表、配置、消费者和前端读法已完成引用清单，回滚负责人明确。

## 测试先行任务

### S01：受控 Codex CLI Adapter

1. `TASK-003-S01-T01`：先用 Fake 可执行文件断言 Adapter 使用参数数组和 stdin，不使用 `shell=true`、`os/exec` 的 Shell 包装或字符串拼接；再实现最小进程端口。映射 `AC-003-001`、`AC-003-002`。
2. `TASK-003-S01-T02`：先覆盖独立任务目录、只读输入、输出大小、墙钟超时、取消、进程组终止、清理和并发上限，再实现 Workspace/Runner。映射 `AC-003-001`。
3. `TASK-003-S01-T03`：先证明传给子进程的环境变量白名单不含数据库 DSN、来源 Token、JWT Secret、MinIO Secret 或用户 Cookie，再实现显式环境构造。映射 `AC-003-001`、`AC-003-002`。
4. `TASK-003-S01-T04`：先覆盖退出码 0 但无结果、JSONL 错误事件、破损 JSON、Skill/Schema 版本不符、未知字段、枚举/长度越界、未知错误码和伪造 Evidence ID；断言失败/取消/非法结果不进入可复用结果，修复输出形成新 Attempt，再实现完整校验链。映射 `AC-003-002`。
5. `TASK-003-S01-T05`：使用至少两类 P0 Skill 与小/中/大 Context，在固定环境分别执行并发 2、3、4；实际记录任务类型、Context 字节数或 Token 数、CPU 使用、内存峰值、执行时长、成功率和失败类别，再批准默认并发。映射 `AC-003-001`。

### S02：Skill 与降级/补算

1. `TASK-003-S02-T01`：为 Monitor Compile、Relevance、Event Cluster、Claim/Evidence 和 Event Summary 建立版本化 Schema Golden；先验证 Go 生成输入和解析输出兼容。映射 `AC-003-001`、`AC-003-002`。
2. `TASK-003-S02-T02`：先写 Codex 未安装、未认证、超时、取消、Schema 错误和预算耗尽测试，断言采集/去重/Heat 继续且 AI 状态为未分析或待补算。映射 `AC-003-003`。
3. `TASK-003-S02-T03`：先写包含 Workspace、Skill/Prompt/Input/Output Schema、Runtime、目标版本、输入 Hash 和 Evidence Set Hash 的复用键测试，断言只复用在途/成功 Run；再实现有限重试、失败码和管理员补算入口，Job 参数只传运行 ID。映射 `AC-003-002`、`AC-003-003`。
4. `TASK-003-S02-T04`：使用不可信来源文本构造 Prompt Injection 夹具，断言其命令、Evidence ID 和输出格式指令不能改变系统契约。映射 `AC-003-002`。

### S03：事件、Heat 与 Evidence

1. `TASK-003-S03-T01`：先用跨来源、转载、同源评论、近重复、晚到和重复候选夹具验证聚类幂等与成员唯一性，再实现最小聚类策略。映射 `AC-003-004`。
2. `TASK-003-S03-T02`：先写同一内容的 `relevance_score`、`heat_score`、ClaimEvidence 和 Event `evidence_state` 相互独立的领域测试，禁止模型字段或 Event 汇总状态覆盖 Claim 级引用与确定性分数。映射 `AC-003-005`。
3. `TASK-003-S03-T03`：先建立 Heat Profile 与 Golden 数据集，覆盖独立谱系根、速度、加速度、来源覆盖、按来源能力/类型归一化的可选互动、时效、`available_weight`、无互动 unknown、无时间 Baseline=`warming_up`、重算幂等和 Profile 版本。映射 `AC-003-006`。
4. `TASK-003-S03-T04`：先验证单一 origin 下多条评论/转载不能提升独立来源；ClaimEvidence 必须绑定可引用 Document Version/selector，Event Evidence State 只能从当前 ClaimEvidence 集合聚合，报告不能仅凭汇总状态批准。映射 `AC-003-005`、`AC-003-006`。
5. `TASK-003-S03-T05`：为 Product Event Refresh 建立 River 幂等测试，覆盖新成员、晚到指标、Heat/Evidence 重算、Event Update 与告警评估；同一事件版本、时间窗和 Profile 重放不重复写成员、Snapshot 或通知，legacy `events/topics` 无新写。映射 `AC-003-004`、`AC-003-006`。

### S04：人工治理

1. `TASK-003-S04-T01`：先写合并、拆分、移除成员、纠正、争议、归档和恢复的权限、资源版本冲突和不可变审计测试。映射 `AC-003-007`、`AC-003-008`。
2. `TASK-003-S04-T02`：先证明治理变更只追加 Revision/Audit 并重建读模型，不覆盖原始 Document、Observation 或 Evidence。映射 `AC-003-007`。
3. `TASK-003-S04-T03`：先覆盖治理页面正常、空、加载、错误、权限不足和并发冲突状态，再接入生成客户端。映射 `AC-003-008`。

### S05：双轨替换

1. `TASK-003-S05-T01`：盘点每个 Provider Profile、Embedding 写入/读取、召回、River Handler、API、页面、报表和运维调用方；为历史与新增数据逐项标明保留、停止新写、归档或待批准删除，并定义旧记录读兼容。映射 `AC-003-003`。
2. `TASK-003-S05-T02`：用固定 Golden 输入并行执行现有 Provider 路径和 Codex 路径，记录结构有效率、Evidence 精确率、人工接受率、延迟、成本和失败类别，并形成可批准的质量比较。映射 `AC-003-001`、`AC-003-003`。

## 数据与契约顺序

1. 先版本化 Skill 输入/输出 Schema 与 Golden，并保存失败测试；
2. 若需新增 Run、Profile 或 Snapshot 字段，只修改 canonical `schema.sql`，同步 Model、Repository、Schema 检查和非空库兼容验证；
3. 先完成 Go Infrastructure Adapter 与 Fake Runtime，再接 River Handler；
4. 先完成 JSON/Schema/Evidence/领域二次校验，再允许事务持久化；
5. Event/Heat/Evidence Domain 稳定后再暴露 API；生成 OpenAPI 和前端客户端后更新 UI；
6. Codex 先 Shadow 不写最终决定，再小流量写入可回滚 Revision，最后才切换默认 Profile；
7. 旧 Provider/Embedding 停流与删除分开；本计划不执行不可逆删除。

## 灰度、迁移与回滚

- Codex Adapter 通过现有 Model Profile 或等价配置按 Skill、Monitor 和环境灰度；
- Shadow 阶段保存脱敏比较指标，不覆盖现有最终决定；
- 切流阶段新旧结果写不同 Run/Revision，最终选择有明确 Profile 版本和审计；
- Codex 连续失败、质量低于门槛、延迟/成本超限或安全校验失败时，关闭 Codex 新 Job，切回已验证旧 Profile，并保留待补算队列；
- 旧 Provider 代码、配置解析、Embedding 表、向量扩展和历史数据在回滚窗口内保留；不得在同一发布中同时切流和删除；
- 只有 Replacement Acceptance 证明所有 P0 Skill、降级、质量、成本、数据兼容和回滚通过后，才能另立清理任务；
- Event/Heat 算法回滚按 Profile 版本切回，不删除新 Snapshot；人工治理事实永不回滚删除，只追加纠正 Revision。
