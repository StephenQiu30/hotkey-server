# 智能研判、事件热度与人工治理计划

## 当前实现与差距

### 当前实现

- `intelligence` 模块已有模型 Profile、运行、预算、Schema Registry、OpenAI/DeepSeek/Ollama/ONNX Provider 和 Embedding 服务；
- `monitor` 与 `ingestion` 已包含查询扩展、召回、相关性研判、反馈、校准、Embedding 与混合召回路径；
- `event` 已包含聚类、Micro Event、Storyline、实体、Claim/Evidence、Heat、生命周期、摘要和人工治理；
- PostgreSQL 已保存 AI Run、预算、Embedding、决策、Heat Snapshot、Evidence State、反馈和审计事实；
- 新写 Product Event 已由 `micro_events` v2、成员、Heat Snapshot 和 ClaimEvidence 事实承载；legacy `events/topics` 仍用于历史读取/回滚兼容；
- River Job 已承载查询扩展、相关性、摘要、Claim/Evidence 等异步任务；
- 前端已有事件列表、热点卡片、内容详情、版本工作台和治理页面。

### 主要差距

- 目标智能运行时应收敛为根目录 `agent/` 的 Python 数据分析服务，由 Go Worker 通过内部认证和版本化 HTTP 契约调用，不允许 Agent 直接读写核心存储；
- Agent 请求/响应版本、服务认证、请求体/输出限制、超时、并发、稳定错误码、Pydantic/JSON Schema 和 Evidence 白名单需要独立契约；
- 仅检查退出码不足以保证结果可信，Schema 错误、伪造 Evidence ID、Prompt Injection 回显和超长输出必须拒绝；`ai_runs` 的 queued/running/validating/retry_wait/终态与复用规则必须保持一致；
- Agent 不可用时，采集、Evidence、精确去重、确定性 Heat 和人工治理必须继续，AI 字段应显式处于未分析/待补算状态；
- 相关性、Heat、ClaimEvidence 和 Event Evidence State 必须分离，模型不能直接决定 Heat、事实真假或最终生命周期；
- Product Event 的首次聚类和后续 Refresh 必须统一使用 `micro_events` v2；legacy `events/topics` 不得无标记双写；
- 当前多 Provider、Embedding、向量和混合召回路径不能直接删除。必须先用 Fake/Golden/Shadow/Live 完成等价或更优替换验收，保留可操作回滚，再另立清理步骤；
- 人工合并、拆分、移除成员、纠正、争议、归档和重算需要不可变审计与并发保护。

## 测试先行任务

### S01：受控 Python Agent 服务

1. `TASK-003-S01-T01`：先以 Python 测试定义 `/healthz`、`/readyz` 和内部 `/v1/analyze` 契约，断言未认证、超大请求、未知契约/任务类型和不可信正文不能改变系统策略；再实现最小 FastAPI 服务。映射 `AC-003-001`、`AC-003-002`。
2. `TASK-003-S01-T02`：先以 Go 契约测试定义 Agent Client 的版本头、服务认证、超时、取消、请求/响应上限和稳定错误映射，再实现 Infrastructure Client；River Job 仍只携带 Run ID，Activity 重读有界 Context。映射 `AC-003-001`、`AC-003-003`。
3. `TASK-003-S01-T03`：在 CI 中加入 Python 格式、静态检查、类型检查、单元测试、依赖审计和 Agent 镜像构建；Compose 只在内部网络暴露 Agent，并让 Go readiness 区分 Agent 可选降级。映射 `AC-003-001`、`AC-003-003`。
4. `TASK-003-S01-T04`：先覆盖 Agent 返回空响应、破损 JSON、契约/Schema 版本不符、未知字段、枚举/长度越界、未知错误码和伪造 Evidence ID；断言失败/取消/非法结果不进入可复用结果，修复输出形成新 Attempt，再实现完整双端校验链。映射 `AC-003-002`。
5. `TASK-003-S01-T05`：使用至少两类 P0 分析任务与小/中/大 Context，在固定环境分别执行并发 2、3、4；实际记录任务类型、Context 字节数或 Token 数、CPU 使用、内存峰值、执行时长、成功率和失败类别，再批准默认并发。映射 `AC-003-001`。

## 数据与契约顺序

1. 先版本化 Skill 输入/输出 Schema 与 Golden，并保存失败测试；
2. 若需新增 Run、Profile 或 Snapshot 字段，只修改 canonical `schema.sql`，同步 Model、Repository、Schema 检查和非空库兼容验证；
3. 先完成 Python Agent 双端契约、Fake Agent 与 Go Infrastructure Client，再接 River Handler；
4. 先完成 JSON/Schema/Evidence/领域二次校验，再允许事务持久化；
5. Event/Heat/Evidence Domain 稳定后再暴露 API；生成 OpenAPI 和前端客户端后更新 UI；
6. Agent 先 Shadow 不写最终决定，再小流量写入可回滚 Revision，最后才切换默认 Profile；
7. 旧 Provider/Embedding 停流与删除分开；本计划不执行不可逆删除。

## 灰度、迁移与回滚

- Python Agent 通过现有 Model Profile 或等价配置按 Skill、Monitor 和环境灰度；
- Shadow 阶段保存脱敏比较指标，不覆盖现有最终决定；
- 切流阶段新旧结果写不同 Run/Revision，最终选择有明确 Profile 版本和审计；
- Agent 连续失败、质量低于门槛、延迟/成本超限或安全校验失败时，关闭 Agent 新 Job，切回已验证旧 Profile，并保留待补算队列；
- 旧 Provider 代码、配置解析、Embedding 表、向量扩展和历史数据在回滚窗口内保留；不得在同一发布中同时切流和删除；
- 只有 Replacement Acceptance 证明所有 P0 Skill、降级、质量、成本、数据兼容和回滚通过后，才能另立清理任务；
- Event/Heat 算法回滚按 Profile 版本切回，不删除新 Snapshot；人工治理事实永不回滚删除，只追加纠正 Revision。
