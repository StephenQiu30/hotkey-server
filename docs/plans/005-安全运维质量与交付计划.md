# 安全、运维、质量与交付计划

## 当前实现与差距

### 当前实现

- `identity` 模块已有注册、登录、密码、JWT、会话、Refresh Token、邮件验证、服务端中间件和审计；
- `operations` 模块已有运行概览、River Job 管理、Retention、治理、证据血缘维护、决策质量和审计入口；
- 来源层已有凭据加密、Rights、SSRF Resolver、配额与失败分类；智能层已有 Schema 和运行审计基础；
- 平台层已有 JSON 日志、Prometheus Metrics、OpenTelemetry Trace、健康/就绪检查、PostgreSQL、Redis、MinIO 和 River Worker；
- 根 `docker-compose.yml`、`docker-compose-prod.yml`、应用 Dockerfile 与环境示例构成当前部署入口；
- GitHub Actions 已覆盖后端、前端、OpenAPI、Schema、架构、漏洞、Compose 和新容器浏览器冒烟。
- 新鲜容器浏览器门禁已运行时生成并遮蔽 JWT/HMAC、数据库、MinIO、来源、Agent/模型、SMTP、Cookie 与用户密码合成凭据，扫描错误、日志、Metric、Job、审计、前端 Bundle、Vault、OpenAPI、文档和验收附件；Trace 与 Codex 子进程环境由独立负向测试覆盖。
- 平台日志已使用固定消息/字段白名单，错误只保留稳定失败码、堆栈只保留稳定摘要；HTTP、依赖和业务 Metric 已归并到有限标签集合，Access Log 保留批准的 Request/Trace 关联 ID。

### 主要差距

- Viewer、Analyst、Editor、Admin 兼容迁移、资源所有权与会话生命周期自动化矩阵已落地；仍需完整四角色 UAT，前端隐藏不能替代服务端鉴权或人工验收；
- 合成 Secret 跨外发表面零泄露门禁已落地；JWT/HMAC、来源主密钥、数据库/MinIO/Identity SMTP/Delivery SMTP/Codex 的完整合成轮换已由固定提交的远端矩阵与同轮敏感面扫描闭合，真实生产凭据仍须由目标供应商正式发行、撤销并复演；
- 日志/Metric 高基数负向门禁已落地；P0 告警目录、固定策略、Dashboard 和五步 Runbook 已由数据库/外部 readiness/前端恢复往返及远端全量门禁闭合；后续主线转入 Retention/删除与撤权对账；
- Retention/删除需要按 Rights、数据类型和证据系谱执行，禁止把删除投影误当作删除事实或留下无权可读副本；
- River Worker 在领取、执行、提交和重试各阶段的崩溃恢复需要故障注入证据；
- PostgreSQL、MinIO、Vault 和配置的备份恢复尚需在隔离环境验证候选 RPO/RTO，Redis 不作为业务恢复事实；
- W22 RC、W23 UAT/缓冲和 W24 发布观察必须有明确阻断门禁，不能把未执行命令预写为通过；
- 根治理文件要求的 `make openapi`/`make ci` 当前没有 Makefile；G3 前必须统一到真实 runner/脚本入口或补齐包装，不能在验收中引用不存在的命令；
- Kubernetes HA、多地域、Kafka/Temporal/Elasticsearch 和 P1 功能不进入本轮发布承诺。

## 启动条件与阶段门禁

1. S01 的威胁盘点、合成 Fixture 和门禁设计自 W1 与 001 的 S01–S02 同步启动，允许相关 Design=`proposed`、PRD=`draft`；这些只读/测试设计工作不得借机改变未批准行为；
2. 每条 M1/M3/M4 主链进入实现或启用前，其对应 001–004 Design/PRD 和 005 中适用的安全条款必须批准；进入 W19 的 S02 集中收敛前，001–005 Design 必须为 `accepted`、PRD 必须为 `approved`，范围不得越过 P0；
3. 安全测试使用合成账号、假密钥、隔离 Vault/MinIO 和可丢弃 PostgreSQL/Redis，不接触真实生产数据；
4. 恢复演练使用独立 Compose Project、明确的新卷和非生产端口，禁止覆盖现有卷；
5. 每条候选 SLO/RPO/RTO 都定义环境、负载、起止点、统计方法、责任人和失败处理；
6. 发布负责人、回滚负责人、安全/来源权利审批人、UAT 签字人和观察窗口值班人明确；
7. P1 能力和禁用基础设施不作为 G5/G6 的隐式验收条件。

- W19：执行跨域负向回归、Secret/依赖/镜像扫描和豁免收敛，而不是首次补安全边界。

## 数据与契约顺序

1. 先保存权限、安全、Retention、River、恢复和发布故事的失败测试；
2. 数据治理结构只通过 canonical `schema.sql` 向前兼容演进，先验证空库与非空库；
3. 先上线新的角色读取兼容和审计，再更新前端，最后收紧旧角色；
4. 先建立读取阻断和 Dry Run，再执行投影/对象删除；
5. 运维 API 先完成 Domain/Application 权限与审计，再生成 OpenAPI/客户端和 UI；
6. 恢复演练成功、对账闭合后才能批准 RC；
7. 发布采用代码/配置/Schema 向后兼容顺序，清理旧字段、Provider 或历史数据不与切流同版。

## 灰度、迁移与回滚

- 角色迁移采用兼容读、双轨授权观察、前端切换、服务端收紧四步；出现越权或误拒绝立即恢复旧映射；
- Retention 先按少量合成数据 Dry Run/执行，再按数据类型灰度；任何未解释差异停止后续批次；
- 新告警先静默评估误报，再启用通知；误报不通过放宽数据正确性断言解决；
- 发布前保存 PostgreSQL、MinIO、Vault 和配置备份及校验和；
- 灰度从内部账号/少量 Monitor 开始，达到错误、延迟、队列、来源失败或对账阈值即回滚应用与配置；
- 代码回滚必须与当前 Schema 向后兼容；不通过回滚删除新表、新列、审计、Evidence 或批准 Revision；
- Codex 回滚沿用 003 的旧 Provider/Profile，全文检索回滚沿用 004 的旧读路径；二者旧实现未过回滚窗口不得删除；
- 若恢复演练、来源授权、P0 主故事或安全门禁失败，W24 发布取消，不以缩短观察或吸收 P1 的方式追赶日期。
