# 评论会话采集与采集运行时边界计划

## 执行前置条件

本 Plan 只记录后续的测试先行实现顺序，当前状态为 `planned`，不得开始生产实现。开始前必须同时满足：

1. 036 Design 由 `proposed` 评审为 `accepted`。
2. 036 PRD 由 `draft` 评审为 `approved`。
3. 首批来源的账号权限、配额、可处理数据和保留/删除义务已保存为可审计证据。
4. 035 首版的当前实现工作不会因此扩大范围或延后主链收敛。

## Slice 0：准入与合规证据

1. 先为每个候选来源写 Rights/Capability 失败测试，覆盖未授权、权限不足、不支持、超配额和删除义务。
2. 将 X/HN 官方能力、微博权限探测结果和 Bilibili 书面授权状态固化为来源级契约，不以口头判断启用采集。
3. 浏览器、HTML 和用户 Cookie 不出现在第一批启动图。

## Slice 1：会话关系事实

1. 先增加 Schema/Domain/Application 架构失败测试，证明 `comment`、parent、root、relation 和 Evidence Reference 能从 Source 进入 Ingestion 且不被改写。
2. 用追加型关系表保存外部父项与根项，父 Observation 晚到时追加解析绑定，不更新历史 Observation。
3. 删除 Hacker News `comment -> post` 兼容归一化，同时保证现有 article/post/video 路径无回归。
4. 生成数据库契约并执行集中测试。

## Slice 2：按需任务与预算

1. 先写任务准入、幂等、重试、租约、断点续传、配额和全部上限的失败测试。
2. 只从 Accepted Match/热 MicroEvent 派生 Conversation Enrichment Job，建立独立消费者，不改变 Collection/Document/MicroEvent 主任务事务。
3. 保存 root ID、页游标、窗口、深度、数量和配额消耗，硬上限到达时正常收敛而非无限重试。

## Slice 3：X 与 Hacker News 官方会话

1. 用伪造官方 API 响应先覆盖 X 直接回复/多级回复/分页/窗口边界，再实现 `conversation_id` 检索适配器。
2. 用伪造 HN item 树先覆盖 story/comment、`parent`/`kids`、deleted/dead、深度和数量上限，再实现有界遍历。
3. 对两类来源执行双次采集幂等、上游删除/更正、证据系谱与单来源失败隔离集成测试。

## Slice 4：分析与产品验证

1. 先写评论不提升 independent origin/EvidenceState 的领域测试。
2. 将评论只接入热度、立场、情绪与纠正候选的独立派生任务，任何 AI 失败不回滚会话事实。
3. 在决定前端评论树前，先用真实 X/HN 样本评估召回价值、噪声、配额成本、保留成本和用户价值，并在 Acceptance 保存结论。

## Slice 5：非 Go Worker 的独立决策（默认不执行）

1. 只在某来源通过 036 Design 的全部准入门槛后，新建独立编号的 Design/PRD/Plan。
2. 优先选择 TypeScript/Playwright 作为隔离浏览器 Worker，仅实现有界 ConversationFetcher 远程契约。
3. 仅当受授权静态 Spider 规模证明 Scrapy 生态能显著降低成本时，才评估 Python/Scrapy；不与 Playwright 同时默认引入。

## 回滚

- Conversation Enrichment 消费者可独立停用，已有 035 多源发现、Document、MicroEvent、WebSocket 和邮件不受影响。
- 新关系事实是追加型，回滚读模型或分析消费者不删除原始 Observation/Evidence。
- 来源授权撤销或条款变化时先在 Rights Gate 禁用新请求，再按保留/删除契约处理已有正文。
