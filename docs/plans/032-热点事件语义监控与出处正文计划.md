# 热点事件语义监控与出处正文计划

## 计划边界

本计划把 032 的功能设计落实到当前 `hotkey-server`，不更换技术栈、仓库结构或部署形态：

- 后端继续使用 Go、Gin、Fx、PostgreSQL/pgvector、MinIO 原始证据、本地 Vault 人类可读投影和现有持久任务体系。
- 前端继续使用 Next.js App Router、React、TypeScript、Tailwind、现有 Radix/组合组件和生成式 OpenAPI Client。
- 数据库结构只修改 `backend/db/schema.sql`，不新增 migration 目录或第二套 Schema。
- API 只由 Swaggo 注解生成 `backend/openapi/docs.go` 与 `docs/openapi/swagger.json`。
- Design 与 PRD 已完成实现前独立审核；本 Plan 自 v1.1 起进入 `in_progress`。v1.2 增补语义命名和 POJO 式分层门禁，v1.3 开始记录已验证的纵向切片，v1.4 同步 Source 证据读取、DerivedArtifact saga 与 exact DocumentVersion API 的实际进度，v1.5 记录 exact locator 事务 producer、Rights 管理写路径和 legacy 正文双写关闭，v1.6 记录 Monitor Intent 规范化存储/API、真实 AI 扩词编排、正文→词法索引生产链、Hybrid Recall/RRF 基础和最小前端闭环，并把未接线的 compiler/preview/embedding 明确保持为未完成；后续行为变更严格按本计划保存红—绿—重构证据。

P0、P1 和 P2 可分别作为发布里程碑验收，但 032 Plan 只有在三个阶段全部完成后才能标记为 `completed` 并归档。任一阶段的延后都必须通过 PRD/Plan 正式变更，不能在 Acceptance 中直接豁免。

## 计划变更范围

### 命名与 POJO 式分层门禁

- 计划编号只保留在文档编号、验收关联和 `db upgrade --target 032` 这类受控运维参数中；业务代码、SQL function/constraint、测试函数和文件一律采用语义命名，禁止 `plan032_*`、`Plan032*`。
- Domain 以 Entity/Aggregate/Value Object 的纯 Go `struct` 表达不变量；Application 以 `Command`、`Query`、`Result`、跨模块只读 `DTO` 表达用例；Infrastructure 以 `Row`/`Record`/`Manifest` 表达持久化；Transport 以 `RequestDTO`/`ResponseDTO` 表达 OpenAPI。
- 每层必须显式映射，不得复用数据库 Row 作为 Domain Entity，不得把 Transport DTO 传入 Repository，也不得让一个万能结构同时服务 HTTP、队列、数据库与领域逻辑。
- 架构测试和 review 必须检查文件/符号语义命名、跨层 import、DTO 中的正文/raw bytes 边界，以及 Repository Record 不泄漏到 Transport。

## 数据与状态设计步骤

### 0. 冻结 legacy→v2 处置和写入开关

- 为 Design 矩阵中每个现有实体保存架构测试，证明 reuse/alter 不产生同义表，supersede 表只有 legacy Repository 可读。
- 引入 `legacy`、`shadow`、`allowlist`、`default`、`rollback_expired` 切换状态；状态变化写审计，不能由环境变量静默改变。
- 先保存 legacy 读写路径和 v2 目标路径的契约测试，再建立 `migration_runs/items`，记录源身份、目标身份、输入哈希、批次游标和 reason code。
- 明确禁止项：新正文进入 `collection_run_items.captured_item`/`contents.excerpt`、新 Markdown 写 MinIO、v2 读取 legacy credibility/claim confidence、旧 embedding 参与 v2 ANN、角色广播充当用户通知。
- 为 `api/worker` 角色增加 Vault 共享卷/单 writer readiness 契约测试。

### 1. 先建立数据库约束测试

- 为所有新枚举、唯一键、外键、不可变版本和历史关系保存失败测试。
- 证明来源观察的唯一键不依赖 canonical URL。
- 证明 EvidenceSnapshot 与 SourceObservation 多对多、selector/selected hash 完整，且 raw 状态只能按允许的状态机转换。
- 证明 RightsPolicy/Decision 不可变、作用域和 action 完整、冲突/unknown fail closed，旧 `allow_body_storage` 不能生成 v2 allow。
- 证明 DocumentVersion 不可原地覆盖，正文更新产生新版本。
- 证明内容家族不会删除观察记录，事件成员只引用家族或明确代表版本。
- 证明证据覆盖按独立 lineage root 计算，而不是按 URL、文档或来源连接数量计算。
- 证明 v2 表不包含 `is_real`、`truth_score`、`credibility_probability` 等禁用字段，并证明 legacy credibility/claim confidence 字段只能被 legacy Repository 读取。

### 2. 收敛修改单一 canonical Schema

- 只在 `backend/db/schema.sql` 中增加或收敛表、约束、索引和版本字段；不得创建 migration 文件、文档 SQL 或代码内第二份 DDL。
- pgvector 继续使用 `halfvec(1024)` 和对应 HNSW 索引；模型 profile/manifest 必须声明 1024 维，P0-0 不实现任意维度。未来维度变化必须另行评审 Design/Schema，不得仅换 profile 写入当前列。
- PostgreSQL FTS 与 `pg_trgm` 索引覆盖标题、规范正文和批准查询词；不引入第二套检索事实源。
- Source-owned MinIO raw 引用、observation selector 以及 Vault 投影路径、SHA-256、MIME、长度、转换器版本、RightsDecision、保留期限和状态统一保存在 PostgreSQL。
- 扩展 `cmd/hotkey db upgrade --target 032`：命令只读取编译进二进制的 canonical Schema；`--dry-run` 输出 catalog/preflight 摘要，非空 apply 必须同时提供 `--apply-schema --confirm-non-empty`。命令不得包含复制的结构 SQL。
- 运行空库初始化、legacy 非空恢复库升级、运行态指纹、重复 apply 和失败事务测试，再进入 Application 实现。

## 数据迁移与上线顺序

1. **恢复库预演**：按 Operations 002 创建一致备份并恢复到独立 Compose 项目；记录旧 catalog fingerprint、行数、MinIO/Vault 清单哈希和 active producer。
2. **Canonical Schema dry-run**：执行 `db upgrade --target 032 --dry-run`，确认命令只读取 embedded `backend/db/schema.sql`，输出加法/收敛摘要、锁风险、预计索引空间和阻断项，不执行 DDL。
3. **停止相关 producer**：停用采集、正文、匹配、事件和通知 v1 producer，等待 running job 归零；旧读路径保持服务。
4. **显式非空 apply**：仅在预演通过后执行 `--apply-schema --confirm-non-empty`；失败事务不得留下 partial catalog，随后运行 Schema fingerprint 和重复 apply 验证。
5. **分阶段保守回填**：maintenance backfill 按 `source → evidence metadata → document → match → family/event/evidence state` phase、批次和 migration run ID 执行；支持 dry-run、断点 resume、同输入幂等和单 phase 停止。
6. **历史证据边界**：旧 MinIO `text/markdown` 只能回填为 `legacy_derived`，永不标成 raw EvidenceSnapshot。无法证明正文类型的历史内容标为 `unknown/metadata_only`；无法区分双 URL、主体、权利或 lineage 时保留原值并待核查，不猜测。
7. **历史重算**：只从仍在保留期、RightsDecision 允许且确有 raw snapshot 的资产重建 Markdown、embedding、内容家族和事件；不得从旧 Markdown、AI 摘要或 excerpt 反推 raw evidence。
8. **三存储对账**：按 run ID 比较 PostgreSQL 清单、MinIO HEAD/哈希和 Vault 文件/哈希；缺失、孤儿、摘要不符和到期资产进入稳定状态，先 dry-run 再经显式 apply 修复。
9. **影子计算**：v2 匹配、去重、聚类、Heat/EvidenceState 和通知只写决策日志/对比指标，不触发用户告警。
10. **小流量切换**：按 Monitor 白名单启用 v2 读和允许的 active profile，验证 P0 UI、误报、降级、事件碎片、通知权限和成本；每次扩容白名单保存审计。
11. **默认切换**：达到对应阶段 Acceptance 指标后 v2 成为默认，停止对应 legacy 新写；回滚窗口内保留隔离旧读，不继续双写事实。
12. **清理评审**：只有回滚窗口结束且审计确认后，才单独提出删除旧字段/路径的 Design、PRD 和 Plan；032 不执行破坏性清理。

上述命令、参数、dry-run 输出、批次/重入和对账口径详见 [Operations 005](../operations/005-032非空库升级与证据对账.md)。在对应命令实现并通过恢复库演练前，该手册保持 `planned`，不得用于生产。

## 回滚

- 停止新 032 任务入队和用户告警，保留来源观察、正文版本、模型运行和决策日志作为审计记录。
- 将读取流量切回切换前稳定路径；加法 Schema 保留，不执行逆向删除。
- 已发布 MonitorVersion、DocumentVersion 和事件决策不可覆盖；通过新状态撤销错误关系。
- MinIO 新对象按原保留策略继续管理，回滚不得孤立或批量删除证据。
- 若模型或阈值回归，只回滚 profile/version 并重放受影响决策，不修改历史输入。
- 若三存储状态异常，先把受影响 DocumentVersion 切为不可读并停止相应 producer；对象和文件只按对账宽限期处理，不用回滚作为批量删除理由。
